## Principle 2: Engineer Spatial Features via Clustering, Not Raw Coordinates

*Consensus: 4/5 regression solutions (NYC Taxi, PKDD-15, Geotab, Restaurant)*

Cluster geographic coordinates (pickup/dropoff locations, intersections) using k-means and derive distances to cluster centers. Avoid raw latitude/longitude as direct features to prevent overfitting to specific coordinate values that won't generalize.

**Why this matters:** Raw coordinates cause models to memorize specific locations rather than learning transferable patterns. Clustering captures regional structure (downtown, airport, residential zones) in a way that generalizes to unseen intersections or times. Distance-to-center features encode 'how central' or 'which zone' without overfitting.

**When to use:** When your data includes geographic points (coordinates, addresses, intersections) and you need location-aware features. Especially critical when the test set includes locations not seen in training (new intersections, unseen coordinate pairs).

**When NOT to use:** Skip if all locations in test are present in training and you can one-hot encode them (small, fixed location set). Skip if location doesn't matter (purely temporal problem). In routing optimization, use raw coordinates for distance calculations, not clustering.

**How to reason about it:**
Start with k=1 (distance to city center). Increase k to 6-10 to capture neighborhoods. Experiment with clustering by population density, average congestion, or other outcome-relevant metrics instead of pure geography. Check if using zip code centroids as cluster seeds helps. Always validate that clusters are interpretable and stable.

```python
from sklearn.cluster import KMeans

# Cluster intersections/locations
coords = data[['latitude', 'longitude']].values
kmeans = KMeans(n_clusters=8, random_state=42).fit(coords)

# Distance to each cluster center as features
for i in range(8):
    data[f'dist_to_cluster_{i}'] = haversine_distance(
        coords, kmeans.cluster_centers_[i]
    )
```
