## Principle 6: Model Network Topology Explicitly for Congestion Problems

*Consensus: 1/1 congestion competition (Geotab #2 solution)*

For intersection congestion, construct features describing network structure: how many paths/turns at this intersection, which intersections are upstream/downstream, link distance to next intersection, turn types (left turn penalties), betweenness centrality in the road graph. Avoid raw IntersectionId—use topology that generalizes.

**Why this matters:** Congestion depends on network position and flow structure, not just location. A high-betweenness intersection (many shortest paths pass through it) will be more congested than a dead-end. Link distance affects stopping patterns. Left turns create longer delays. Topology features let the model predict congestion at unseen intersections based on their structural role.

**When to use:** When the problem involves a transportation network (roads, transit lines) and you must predict flow or congestion at nodes/edges. Use if test data includes new intersections not in training. Essential when you need to generalize spatially within a network.

**When NOT to use:** Skip if intersection IDs are fixed and all test intersections appear in training—then you can one-hot encode them. Do not invest in graph construction if simple spatial features (coordinates, clusters) suffice. Avoid if you lack network connectivity data (only have point locations, not edges).

**How to reason about it:**
Build the network graph: nodes are intersections, edges connect intersections when a path goes from one to the next. Compute per-intersection: number of entry/exit directions, number of paths (turns), betweenness centrality. Compute per-path: link distance to next intersection, turn type (left/right/straight), whether entry and exit have the same street name (indicator of through traffic). Use external road network data (TIGER) to match competition data to real roads and extract road class (highway, arterial, local).
