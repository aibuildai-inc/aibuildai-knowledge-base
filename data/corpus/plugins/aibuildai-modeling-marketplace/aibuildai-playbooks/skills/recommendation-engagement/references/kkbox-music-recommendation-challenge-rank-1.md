**1. Analysis of the Problem**

  Based on my understanding, this is a similar problem with Click Value Rate (CVR) predictions. Relistening is like purchasing, and first listening is like clicking. So if you are looking for some reference, I think "CTR prediction" is a more accurate keyword (since CTR/CVR predictions share similar models) compared with "recommendation" since some recommendation methods like latent-factor based or neighborhood-based collaborative filtering is not the best way for this problem.

  And since this is more like a CVR prediction, there are some properties that we can make use of for feature engineering or model construction, including:

**(1) Missing not at random**

  Some user-song pairs can be observed and some not. If a user-song pair is in the dataset, we can tell that the user has listened to the song at least once. This contains rich information about user preference and song characteristics.

**(2) Time-sensitive**

  Since the dataset covers a long range of time, the pattern might evolve a lot from the beginning to the end. This is important for the validation strategy and feature engineering.

**2. Overall Framework**

  Just the same as what @MrOoijer predicted, the final results is a 0.6 * LightGBMs and 0.4 * NNs, and the LightGBMs, as well as NNs, are all bagging ensembles of several predictions with a slightly different subset of features. I didn't use any external data.

  For LightGBMs, my best single model is 0.74440 on public LB with a learning rate of 0.1 and 0.74460 at 0.05, and bagging ensemble of LightGBMs can reach about 0.74584.

  For NNs, my best 30-ensemble on the same feature set can get 0.74215, and bagging ensemble of NNs on different feature set can get 0.74333.

  The predictions of LightGBMs and NNs are quite uncorrelated (correlation coefficient is about 0.92). The ensemble of single LightGBM and single 30-ensemble of NN can get 0.7489+. The ensemble of ensembles can reach 0.7498+.

  The reason why ensembling GBDTs with NNs can get a very significant boost is, I think, that GBDTs and NNs are better at the different listening flow. GBDT is more or less a greedy method. It always captures the head flow first, and then the trees behind can finally fit the user-song pairs in the tail flow. As a result, GBDT is better at finding the pattern in the head flow. NNs, in contrast, explore the broad combinations of features, so it's easier for NNs to fit the pattern in the tail flow, while the head flow might be influenced by the noise.

**3. Validation Strategy**

  I use the last 20% data as the validation set. What's need to be mentioned is that for validation, I use the features generated by the train.csv only, and for submission, I use the features generated with both train.csv and test.csv. 

  The problem is, since the data covers a long range of time if we use both train.csv and test.csv to generate features for validation, we are leaking information from the future to the past. This may give you some false positive results when doing feature selection.

**4. NN Models**

  The structure of the neural network is presented in the picture attached. There are some tricks about the model structure.

**(1) Field-aware**

  The inputs are divided into 3 groups, i.e., user field, song field, and context field. High-level features are extracted before we concatenate the features together. This can reduce the number of parameters and prevent some unexpected feature combinations.

**(2) Use trainable embeddings with L2 regularization for categorical features**

  Compared with one-hot encoding, this can also reduce the number of parameters. With the help of shared weights in latter layers and L2 regularization, we can have a better ability of generalization.

**(3) Allowing an offset for users between the final representations of a user and the predicted results from metadata**

  This is achieved by the layer "msno_embeddings". This is a commonly used trick from many academic papers. With an l2 regularization, the model can automatically lean that, if the data is sufficient, the representations of a user rely more on BP from the targets of the user, and if not, rely more on the metadata. This helps about 0.001 on public LB.

  I tried to do a similar thing with the songs, but got no improvements, mainly for that the data of songs are too sparse.

**(4) Use RMSProp as the optimizer**

  I find that momentum is not working well in this problem, while naive SGD is too slow.

**(5) Add dot layers for embeddings and representations of user-song pairs**

  It can fasten the convergence and give better results. Some papers suggest using element-wise multiplication or even outer product, but I only get more overfitting.

**(6) Use ensemble to check the results**

  I personally never submit predictions from a single NN. An average ensemble of at least 5 NNs will make the results a lot more reliable and repeatable.

**5. LightGBM**

  For LightGBM, there aren't many interesting things. I only notice that some features are very important according to feature_importance(), while do not make an equal influence on the validation score. This means that the model is fitting some data better, while other data worse. The average ensemble of LightGBM predictions with/without these features can give a significant boost.

  My final LightGBM model uses about 400 features. 

  Again I learn how powerful GBDT is. A simple GBDT can beat an ensemble of 30 carefully-designed NNs (of course GBDT is an ensemble model itself). While the advantage of NNs is that it's very fast compared with LightGBM. I can generate predictions in several minutes with a single GTX 1080, so I'm able to submit a lot and don't waste any changes for submission :D

**6. Feature Engineering**

  Here are some important features that I found.

**(1) Conditional probability features**

  P(source_type|msno), P(source_screen_name|msno), P(source_system_tab|msno), P(source_type|song_id), P(source_screen_name|song_id), P(source_system_tab|song_id), P(artist_name|msno), P(language|msno), P(first_genre_id|msno) and so on. I tried some smooth methods but found MLE probability give best results.

  They are useful when the number of different values of categorical features is large. Like msno and song_id.

**(2) Timestamp**

  Since the data is ordered chronologically, we can use the index as a timestamp.

**(3) SVD features with user-song matrix and user-artist matrix**

  As mentioned before, the data is missing-not-at-random, so constructing a user-song matrix and user-artist matrix and use SVD to get embeddings for users/songs/artist can help significantly.

  I also tried LDA and Gamma-Poisson Factorization but didn't get better results compared with SVD.

**(4) Other features**

  Including some count features, last song features, and next song features.

**7. Some Methods that Didn't Work**

**(1) [Pseudo labeling][2]**

  Using the ensemble predictions as pseudo labels for test set is helpful significantly, while the lost diversity just makes the results after ensemble not improving at all. This result disappointed me a lot, for I was hoping that NNs can learn something new from a different perspective than GBDTs.

**(2) DART mode**

  DART mode of LightGBM is really slow, and uncorrelated with gbdt. But its correlation coefficient with NNs is even larger than gbdt with NNs, and the ensemble of NN/gbdt/dart models doesn't give a significant difference compared with NN/gbdt ensembles.

**(3) FFM**

  I tried a little with libffm, and didn't get comparable results with LightGBM and NNs. Besides, libffm is too slow with this dataset.

**(4) Give larger weights to more recent records**

  After adding the timestamp to the feature set, this can only give very tiny help. So I didn't use it anymore.

**(5) Deep&amp;Wide model**

  I tried Deep&amp;Wide models a little and got significantly worse results than Deep only models. But I didn't use any cross features in the wide part, and I didn't spend much time tuning the Deep&amp;Wide model carefully. So there might be some room for improvements.

**8. Other Things that Come to My Mind**

  Here I want to share and discuss whatever comes to my mind.

**(1) The version of LightGBM matters**

  The version of LightGBM on my PC is 2.0.1, and the version on the server is 0.1, but I see repeatable results that the results from version 2.0.1 are worse than the results from version 0.1 by an AUC of about 0.01. I checked some default hyper-parameter modification but didn't fix the problem.

  Don't know why such thing happens and whether this is a special case or not. So if you are not doing well, it may be the bad of LightGBM version.

**(2) Drop the duplicated rows of user-song pairs between train.csv and test.csv**

  This gives a little but solid improvement.

**(3) Remaining problems**

  How to use the large set of songs? I only keep the songs that appear in train.csv/test.csv.

  I didn't try a lot of cross features. I think there is definitely some room for more feature engineering in this framework.

  Learn-to-Rank methods might be helpful, but it will cost much more computation.

**(4) Re-listening sequences features might be helpful (didn't try)**

  For online CVR prediction systems, they usually involve a lot of features about user's behavior, like purchasing or re-purchasing sequences. In this problem, the corresponding features are re-listening sequences. But I didn't try such features mainly for that in the testing set, we can't obtain the latest re-listening information. It might be helpful to design some features from this view, but it requires a lot of coding.

**(5) Is AUC the most suitable metric?**

  Usually, recommender systems recommend a fixed number of songs to every user. So here is the problem: is AUC the most suitable metric in this problem? In other words, if the model finds that User A always re-listen the songs while User B seldom re-listen the songs, the AUC might be good but is this really helpful? There are metrics like GAUC, which first calculate AUC scores over different users, then calculate the average of the AUC scores. I think this is a better metric, but it may require some extra effort when preparing the proper data.
