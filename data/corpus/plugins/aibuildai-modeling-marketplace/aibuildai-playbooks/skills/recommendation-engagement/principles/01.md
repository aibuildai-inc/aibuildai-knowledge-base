## Principle 1: Choose Base Model Architecture Based on Feature Density

*Consensus: Majority of CTR/click competitions (Avazu #1, Criteo #1, Outbrain #3/#4). Credit/transaction competitions favor GBMs (Home Credit top 10, Santander top 10).*

Field-aware Factorization Machines (FFM) excel with sparse, high-cardinality categorical features. Gradient boosting (LightGBM/XGBoost) dominates when aggregated features create dense representations.

**Why this matters:** FFM learns feature interactions at the field level (user × item × context), making it ideal for sparse one-hot encoded data where most features are zero. GBMs excel at capturing non-linear patterns in dense aggregated features but struggle with millions of raw categorical values. The wrong choice costs 0.01+ AUC.

**When to use:** Use FFM when: (1) features are mostly high-cardinality categoricals (user_id, item_id, publisher_id with 100k+ values), (2) few hand-crafted aggregations exist, (3) data is extremely sparse (>99% zeros in one-hot encoding). Use GBM when: (1) you've created hundreds of aggregated features (counts, ratios, statistics), (2) features are mostly numerical or low-cardinality categorical, (3) you have related tables to aggregate.

**When NOT to use:** Don't use FFM if your feature set is primarily aggregated statistics—it won't beat GBM and trains 10-100× slower. Don't use GBM alone on raw high-cardinality categoricals without embeddings or aggregations—it can't split effectively on millions of one-hot values.

**How to reason about it:**
Inspect your feature matrix sparsity. If >95% zeros after encoding and dominated by ID fields, start with FFM (libFFM with k=4). If you've built 500+ aggregated features from relational tables, use LightGBM. Both can coexist: FFM on raw sparse features, GBM on aggregations, ensemble them.
