## Principle 1: Adopt a Two-Stage Candidate-Rerank Architecture

*Consensus: All top solutions across all 7 competitions use this pattern*

Generate 100-500 candidates per user via fast retrieval methods, then rerank with a GBDT model using rich features. Never train one model on all items.

**Why this matters:** With millions of items, scoring all user-item pairs is computationally infeasible and produces extreme class imbalance (positive rate <0.001%). The candidate stage narrows the search space to ~100-500 items where positive rate rises to 1-5%, making GBDT training tractable and effective.

**When to use:** Always use for recommendation tasks with >10k items. The two-stage pattern is the dominant architecture across all competition types (e-commerce, travel, music, banking).

**When NOT to use:** Only skip if the item catalog is tiny (<1000 items) and you can afford to score all user-item pairs. Even then, candidate generation often improves results by focusing the model.

**How to reason about it:**
Ask: How many user-item pairs would I need to score? If it's >10M, you need candidate generation. Then ask: What recall@K (e.g., recall@100) can I achieve with simple retrieval methods? If you can get 60-80%+ recall in the candidate stage, the reranker can achieve strong final performance. The candidate stage is about coverage; the reranker is about precision.

# Stage 1: Generate candidates (example: top-N co-visitation)
from collections import Counter

def generate_candidates(user_history, covisit_matrix, top_n=100):
    candidates = Counter()
    for item in user_history:
        # Accumulate scores from co-visitation matrix
        candidates.update(covisit_matrix.get(item, {}))
    return [item for item, score in candidates.most_common(top_n)]
