## Principle 10: Maximize Batch Size for Stability with Rare Diseases

*Consensus: Several solutions reported that larger batches helped, including batch size 64 in a stroke clot-origin (Mayo STRIP AI) solution and gradient checkpointing for bigger batches in an abdominal trauma CT solution*

Use the largest batch size that fits in memory (64-128), leveraging mixed-precision training and multi-GPU setups. Larger batches improve training stability and CV scores, especially for imbalanced medical datasets.

**Why this matters:** With rare positive cases, small batches have high variance in positive/negative composition, destabilizing gradients. Batch norm statistics are unreliable with small batches. Larger batches smooth gradients and improve batch norm estimation. Some solutions reported gains from larger batches alone.

**When to use:** When class imbalance is severe and training is unstable. When you have access to GPUs with sufficient memory. When combined with upsampling to ensure positive cases in each batch. For most medical imaging tasks as a general best practice.

**When NOT to use:** When memory-constrained and gradient accumulation doesn't compensate well. When very large batch size (>256) causes optimization issues (may need to adjust learning rate). For small datasets where large batches mean very few iterations per epoch. When the architecture prefers small batches: one skin-lesion solution found vision transformers better with small batches and fixed the batch composition with resampling instead.

**How to reason about it:**
Calculate maximum batch size: Test with largest backbone and input size you plan to use. Use mixed-precision (fp16/bf16) to fit 2x larger batches. Multi-GPU: Use DataParallel or DistributedDataParallel to scale batch size linearly with GPU count. Gradient accumulation: If memory-limited, accumulate gradients over multiple small batches to simulate larger batch (less effective than true large batch for batch norm). Learning rate scaling: When increasing batch size, consider linear LR scaling (double batch → double LR) but tune carefully. Trade batch size against input size, tile count, and architecture, and measure the effect on validation.

```python
# Mixed precision for larger batch size
from torch.cuda.amp import autocast, GradScaler

scaler = GradScaler()
for images, labels in dataloader:  # batch_size=64 or 128
    optimizer.zero_grad()
    
    with autocast():  # fp16 computation
        outputs = model(images)
        loss = criterion(outputs, labels)
    
    scaler.scale(loss).backward()
    scaler.step(optimizer)
    scaler.update()

# Gradient accumulation if memory-limited
accum_steps = 4  # Simulate batch_size=128 with 32x4
for i, (images, labels) in enumerate(dataloader):  # batch_size=32
    loss = criterion(model(images), labels) / accum_steps
    loss.backward()
    if (i + 1) % accum_steps == 0:
        optimizer.step()
        optimizer.zero_grad()
```
