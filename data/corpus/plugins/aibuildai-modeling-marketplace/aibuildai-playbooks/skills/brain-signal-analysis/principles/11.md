## Principle 11: Probe Test Set Distribution and Align Validation Strategy Accordingly

*Consensus: Several solutions compared CV with the public LB to find mismatches: Melbourne seizure prediction teams found file-level CV did not track the LB, and a Parkinson's FOG team traced public-to-private shake to one subject with long recordings in the public data.*

Competition test sets may be filtered, resampled, or stratified in ways not obvious from the data description. Probing (submitting predictions with known properties and observing score patterns) or analyzing public LB shake reveals test set characteristics, allowing you to align CV strategy (e.g., validate only on the subset of data that matches the test set).

**Why this matters:** Parkinson's FOG: one team found that a single subject with long recordings produced many false positives, selected models on a score that excluded that subject, and concluded that the subject's presence in the public data caused many teams to overfit and shake down. Another FOG team saw CV and public score correlate at first and then stop correlating as the public score rose. In Melbourne seizure prediction, CV on individually treated files scored far above the LB; grouping files by recording sequence gave CV much closer to the LB.

**When to use:** Probe test set when: (1) your CV does not correlate with public LB despite grouping by patient (suggests CV and test distributions differ), (2) data description is vague about test set filtering (check if test is a high-quality or task-specific subset), (3) public/private LB gap is large (suggests class imbalance or distribution shift between public/private). Align validation: filter your validation set to match test set characteristics (e.g., high-quality labels, specific tasks, specific datasets).

**When NOT to use:** Do NOT probe if competition rules forbid excessive submissions (e.g., max 5 per day). Do NOT filter validation if you have clear evidence test set is unfiltered. Do NOT assume public LB is representative of private LB (shake is common)—but you can use public to rule out mismatches (if CV and public LB are uncorrelated, your CV is wrong).

**How to reason about it:**
Step 1: Check CV-LB correlation across several submissions. If they do not move together, investigate. Step 2: Read the data description for hints about how the test set was built. Step 3: Probe: submit predictions with known biases (e.g., all zeros, all uniform, class-skewed) and see if scores match expectations. Step 4: Check per-subject CV: if one subject dominates errors, report CV with and without that subject and decide which one to trust. Step 5: Align validation: build it the way the test set was built, for example by file, by sequence, or by subject. Step 6: Use public LB to guide model selection, but trust CV for ranking models when public/private may differ.
