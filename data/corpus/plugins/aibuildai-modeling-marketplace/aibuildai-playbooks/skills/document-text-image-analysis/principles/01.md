## Principle 1: Generate Synthetic Training Data to Cover Unseen Combinations

*Consensus: Recurring in top Bengali and Benetech graph solutions. Critical for competitions with combinatorial output spaces or domain shift.*

Create synthetic images programmatically to cover rare or unseen combinations of components that appear in test but not train data. Render using fonts/plotting libraries with diverse styles.

**Why this matters:** Real datasets are biased toward common combinations. Test data often contains valid but rare combinations (e.g., Bengali grapheme root + rare diacritic, graphs with uncommon formatting). Models memorize seen combinations and fail on valid unseen ones. Synthetic data forces the model to learn compositional rules rather than memorizing instances.

**When to use:** When the output space is compositional (components combine to form valid outputs), when train contains <20% of valid combinations, when CV >> LB suggests distribution shift, or when you can enumerate/generate valid outputs programmatically (fonts for text, matplotlib for graphs, domain-specific renderers).

**When NOT to use:** When test distribution matches train (no unseen combinations), when you cannot programmatically generate realistic samples (e.g., authentic historical paper texture), or when annotation is the bottleneck and synthetic data would need manual labeling. When every output class already appears in train with enough real samples, real data alone can suffice.

**How to reason about it:**
Ask: (1) Can I enumerate valid outputs not in train? (2) Can I render them realistically? (3) Does my CV-LB gap suggest unseen combinations hurt me? If yes to all three, generate synthetic data. Start with the rarest classes/combinations in train and render with maximum diversity (fonts, styles, noise levels). Validate that synthetic→real transfer works by holding out real data.
