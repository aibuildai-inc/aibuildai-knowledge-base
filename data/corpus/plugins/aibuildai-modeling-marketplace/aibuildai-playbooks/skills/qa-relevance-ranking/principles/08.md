## Principle 8: Use Siamese Encoders to Search Many Candidates and Joint Inputs to Rank the Shortlist

*Consensus: Eedi and LLM Science top solutions encoded questions and candidates separately with embedding models to retrieve, then read the shortlist jointly with the question (Eedi 1st: retrievers chosen by recall@32, then a 14B ranker)*

When a question must be compared with many candidates, encode the question and each candidate separately with one shared (siamese) encoder, so candidate embeddings are computed once and searched with a similarity score. When only a shortlist remains, give the question and each candidate to one model together, so attention can compare them token by token.

**Why this matters:** A joint input lets every question token attend to every candidate token. It is more accurate, but it costs one forward pass per pair. A siamese encoder costs one pass per text, so thousands of candidates are scored with one matrix product. Eedi 1st place fine-tuned several LLM-based embedding retrievers, kept the Qwen2.5-14B encoder with the best recall@32 instead of the encoder with the best MAP@25, and then ran a fine-tuned Qwen2.5-14B pointwise ranker over the 32-64 retrieved misconceptions. Eedi 2nd place had an LLM write an explanation for each short misconception, so that its embedding carried more meaning. LLM Science 1st place retrieved Wikipedia contexts with e5 and gte embedding models, then gave the question, options and contexts together to its LLMs.

**When to use:** When: (1) The candidate pool is large (hundreds or more per question) or shared across questions. (2) New candidates appear at test time - a siamese encoder embeds them without retraining. (3) Candidate texts are short - enrich them first (descriptions, generated explanations) so the embedding has enough to work with. Common in: misconception or label retrieval, passage retrieval for multiple choice, product search.

**When NOT to use:** Skip the siamese stage when each question has only a few candidates (for example 4-5 answer options): score them jointly from the start. Do not use siamese similarity as the final ranking when a joint reranker fits the inference time limit.

**How to reason about it:**
Compare: (1) Siamese retrieval alone. (2) Siamese retrieval of top-K plus a joint reranker. Tune the retriever for recall at K, not for the final metric, because the reranker can only reorder what the retriever returns. Train the encoder with a contrastive loss that uses the other candidates in the batch as negatives. Check recall when you add hard negatives: in Eedi 1st place they raised MAP@25 but not recall@32. Pick K from the inference time budget of the reranker.

```python
import torch
import torch.nn.functional as F

# Stage 1: siamese encoder - one shared model for questions and candidates
def embed(texts, encoder, tokenizer):
    batch = tokenizer(texts, padding=True, truncation=True, return_tensors='pt')
    hidden = encoder(**batch).last_hidden_state
    mask = batch['attention_mask'].unsqueeze(-1)
    return F.normalize((hidden * mask).sum(1) / mask.sum(1), dim=-1)  # mean pooling

cand_emb = embed(candidate_texts, encoder, tokenizer)      # computed once
q_emb = embed(question_texts, encoder, tokenizer)
topk = (q_emb @ cand_emb.T).topk(k=32, dim=-1).indices     # tune K for recall

# Training: contrastive loss with in-batch negatives
def contrastive_loss(q_emb, pos_emb, temperature=0.01):     # Eedi 1st used 0.01
    logits = q_emb @ pos_emb.T / temperature
    labels = torch.arange(q_emb.size(0))
    return F.cross_entropy(logits, labels)

# Stage 2: joint input - the reranker reads question and candidate together
for qi, cand_ids in enumerate(topk):
    pairs = [f"{question_texts[qi]}\n\nCandidate: {candidate_texts[c]}" for c in cand_ids]
    scores = reranker_score(pairs)                          # one forward pass per pair
```
