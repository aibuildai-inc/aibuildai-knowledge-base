## Principle 1: Branch Architecture by Task Structure, Not Just Data Type

*Consensus: 8/8 competitions show distinct architectural families*

QA relevance tasks require fundamentally different architectures depending on whether you're doing text matching (pre-transformer era), classification into a small fixed label set, or retrieval-based selection from a large candidate pool. The task structure dictates the model family.

**Why this matters:** Using a classification head for a task whose candidates come from a large and partly unseen pool, or a retrieval pipeline for a small fixed label set, misaligns the model's output structure with what the metric optimizes. Text-matching tasks (pre-2019) succeeded with heavy feature engineering; transformer-era tasks need pre-trained language models; knowledge-heavy tasks need retrieval + reranking pipelines.

**When to use:** At the start of every competition: identify which family your task belongs to. Text similarity/matching → feature engineering + gradient boosting (Home Depot). Small fixed label set → fine-tuned LLM or transformer with a classification head (MAP). Multiple choice with external knowledge, or a large candidate pool → retrieval + LLM reranking (LLM Science, Eedi).

**When NOT to use:** Don't force modern retrieval pipelines onto simple text-matching tasks with small vocabulary (waste of compute). Don't use pure classification when the task is fundamentally retrieval (you'll cap at the model's parametric knowledge).

**How to reason about it:**
Ask: (1) Do candidates come from a large external corpus or a small fixed set? Large corpus → retrieval pipeline. (2) Is the output a score, a label from a fixed set, or a choice among candidates? Score → regression. Fixed label → classification. Candidates → ranking. (3) Is domain knowledge required beyond the input text? Yes → retrieval or domain-specific pre-training. (4) Does test data hold labels or candidates never seen in training? Yes → a retrieval or ranking formulation that can score new candidates.
