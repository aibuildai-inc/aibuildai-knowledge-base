## Principle 5: Normalize Features by Temporal Subsets to Handle Data Drift

*Consensus: AmEx 2nd place, Elo 7th, and temporal competitions explicitly normalize by month/season to handle drift*

When data spans multiple time periods with distribution shifts (monthly statements, yearly seasons), normalize features within each temporal subset (month, season) and subset type (train/public/private test) separately to account for drift.

**Why this matters:** Feature distributions drift over time. Credit scores in January 2020 differ from January 2022 (economic conditions change). Global normalization (mean/std over all time) produces out-of-range values on recent data. Temporal normalization (mean/std per month) makes features stationary and improves generalization to future periods. AmEx 2nd place used (x - month_mean) / month_std per subset.

**When to use:** When data spans long time periods (>6 months) with potential drift, especially in finance, economics, and sports. Essential if you observe train-test distribution mismatch. Combine with temporal CV to validate that normalization helps.

**When NOT to use:** Skip if data is truly stationary (distribution plots show no drift over time) or if the time range is short (<3 months). Don't over-normalize if temporal shifts are the signal (e.g., predicting seasonal trends—normalizing out the season loses information).

**How to reason about it:**
Plot feature distributions over time (by month, quarter, season). Do they shift? Check mean and std stability. If unstable: normalize within time slices. Compute stats (mean, std) per (time_period, subset) where subset = {train, public_test, private_test} if splits are temporal. Apply: x_normalized = (x - mean[time, subset]) / std[time, subset]. For future periods without stats: use rolling window or last known period.
