## Overview

Our solution is based on the ensemble of different pretrained models and a bunch of different tricks to reach the final score. We used np.concatenate to join matches from different models. I assume most Kagglers taking part in this competition used similar approach.

All pretrained models that we tested are QuadTreeAttention, Loftr, SE2-Loftr, MatchFormer, DKM, SuperGlue, Patch2Pix, PDCNet, SGM, ASLFeat and AdaLam. 
Our final submission includes **QTA**, **Loftr**, **DKM**, and **SuperGlue**.

When QuadTreeAttention scored **0.812/0.817** (public/private) we were shocked. It was almost close to Gold Zone with only single model. And, now, when the competition finished, you could get a silver model using only one model.

## Ideas that worked out
- **Input image size** is super important. Certain models have specific characteristics. For instance, Loftr prefers images that have dimension multiplied by 8. Another example is QuadTreeAttention model that accepts images only dividable by 32. In first case, if it necessary we slightly reduced image size to be compatible with this ‘multiply 8’ rule. For QuadTreeAttention model we used zero-padding technique that makes possible to enlarge the image and keep the aspect ratio. In most cases bigger image size leads to better score.
- **Ensemble different models**. It may sound obvious but most boost comes from concatenating matches produced by completely different models (zero-shot, one-stage, two-stage) with different architectures. For example, QuadTreeAttention gives much better boost with SuperGlue than with Loftr. Most probably, the reason is that QuadTreeAttention has some common points with Loftr implementation and they both adhere Transformers approach. But I should admit that use of these three models in ensemble gives better score.
- Use of **filtering strategy** or, in other words, some kind of model ensemble weight. The idea is to filter matches using normalized confidence scores, produced by the models. For instance, you take 300 most confident matches generated by Loftr model with confidence at least 0.3. By the way, it helps to reduce number of matches, and, eventually, speedup F matrix calculation.
- **Test time augmentation (TTA)**. We tested rotation (15° and 45°) and scale ([0;2]) with Albumentations, and merged matches produced by them with the matches extracted from images w/o applying augmentation. We see that rotation works quite well, especially for SuperGlue model. So, with TTA applied three times score improved 0.735 -> 0.786, but in ensemble the result is not so noticeable. Scale helped to boost score of Loftr model, but not too much **0.774 -> 0.777**.
- **Mofidications in DKM library**. Initially, this library did not allow to use any image size and, internally, it resized every image to (512, 384). We changed this behavior and used (672, 896) as an input size for the model. It significantly boosted public score **0.672 -> 0.735 (private 0.688 -> 0.748)**. 
- **Multi threading**. In the middle of the competition, we realized that we are out of Kaggle time to run submission successfully. We experienced ‘Notebook timeout’ message for notebooks exploiting multiple models whereas some of them may run quite a lot time. To fix this situation, we implemented two important things. The first one is related to F matrix calculation. In the beginning we tested F matrix estimation in parallel, but, it did not work. I’m sure it is because of OpenCV limitations. Thereby, we decided to run inference and F matrix calculation in parallel. The idea is pretty simple. We first calculate matches for the 1st image pair, then we take the next image pair and calculate matches for current image pair and F matrix for the previous one, and then the process repeats. At the last step, it is important not to forget to calculate F matrix for matches belonging to the last image pair. Some multi-threading performance benchmarks are listed below:

Calculation of F matrix using multiple threads is faster by ~64% rather than if we run sequentially. We run experiments multiple times and the results are pretty stable for Kaggle platform. Tests for 30 images pairs:
In parallel:
- Total running time F Matrix: 24.9 s inference 78.1 s
- CPU times: user 1min 40s, sys: 7.61 s, total: 1min 47s
- Wall time: 1min 27s
Sequential run:
- CPU times: user 1min 35s, sys: 7.87 s, total: 1min 43s
- Wall time: 1min 43s

1 thread 103 sec = 1 min 43sec
2 threads, in parallel 87 sec = 1 min 27 s
Improvement: -16 sec

- **Release resources wisely**. One more performance related issue we found here is that resource release does not run instantly. I mean that gc.collect() and torch.cuda.empty_cache() may take time up to 0.30sec that is similar to how long SG runs. In order to save some computational resources and make the task more efficient, we employed resource release only on every 10th image pair.


##What did not work

- **Scene segmentation** and masking classes, including person, sky, vehicle. We tested this approach with Detectron2 and mseg_semantic.
- **RotNet to estimate a good rotation** for every image.
- **Run inference on the same image** having different sizes.
- **RANSAC USAC_ACCURATE** did not work out.
- **Crop image into multiple patches** (e.g., 2 x 2). Essentially, at first, we propose to crop image into multiple patches in the way that they overlap each other. On the next step we find matches on the cropped areas. Finally, we merge all matches found on these patches. We tested this method using Loftr model, score decreased **0.777 -> 0.745**.
- **Adaptive F/H strategy**. The main idea of this is to remove some wrong matches using Homography matrix. In contrast to Fundamental matrix, Homography assumes that points are planar. This kind of matrix could help to find matches on the flat building along the street. So, you have to calculate the F matrix and the H matrix, as well as their scores, that are symmetric transfer error, and compare it with the threshold. I tested this idea using only Loftr on the early stage and probably proper testing have to be done.
- Another idea is also related to **Homography matrix**. It has common points with the previous approach, but differs in calculation and outlier removal. During testing this idea on available image data, I made sure that matches presented by H matrix are quite stable and have minimum number of outliers. I implemented a function that replaces all matches found by F matrix with matches contained by H matrix in the neighborhood area of fixed radius whereas F matrix matches are located (tested with 3 px). You can think about it as an extra layer of outlier filtering strategy prior to RANSAC applying.
- Use of **different versions of the same model** (e.g., regular and lightweight weights of MatchFormer) did not show score improvement.
- **Removal of matches residing outside the image**. We noticed that sometime matches are placed outside the bounds of the image. We deleted such matches, but it did not help to boost score.
- **Inference multiple models in parallel** in order to reduce running time. Unfortunately, it almost immediately leads to the error of exhausting GPU memory in the notebook.
