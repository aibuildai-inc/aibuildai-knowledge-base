Note that in my explanation, the 0-indexed, y-th pixel from the top and x-th pixel from the left are represented as (y, x). The center pixel is (128, 128).

My solution is to solve the constrained TSP using Concorde and a genetic algorithm, then convert the resulting tour to configurations.
Before I describe the solution method in detail, I will explain the considerations that were necessary to arrive at this solution method.

First, some experiments show the following.

* The degree of freedom of the arm is high enough. For example, given a random pixel and a random configuration pointing to that pixel, the probability that we can move only one of the arms to the pixel to its right is quite high.

From this, as already discussed, it is a valid strategy to first solve the TSP and then construct the configurations to follow that path.

However, it does not seem to work to convert the solution obtained by solving the pure TSP directly into configurations.

I thought that this was largely due to the restriction of the longest arm. For example, initially, the longest arm is straight to the right. Since the left side of the card cannot be printed when the longest arm is pointing to the right, the area with x < 128 (left half) must be painted after the longest arm has been moved up (or down) at least 64 times from the initial state.

In addition, there seemed to be three cases where constraints other than the longest arm prevented the construction of an efficient configuration:

1. trying to paint x < 128 too early
  * This is the same as the above example, but actually has a slightly stricter constraint than when only the longest arm is considered.
2. going too far to the right too early
  * For example, since the arms are all pointing left or right in the initial configuration, the first move is limited to up or down, and moving to the right is impossible. (The constraint of the longest arm already eliminates the option of left.)
Moving up or down with the shortest arm on the first move allows two moves to the right, however, three moves, i.e., "down, right, right, right" from the initial state, still proves to be impossible.
3. moving along the second pixel from the outer edge
  * Perhaps due to an error in the algorithm that resizes the image, the outermost pixel is darker than the others, and the second outermost pixel is lighter than the others, so a pure TSP solution would contain a path along it. Of these, a path such as the second outer "冖" (e.g., (2, 1) → (1, 1) → (1, 2) → ... → (1, 254) → (1, 255) → (2, 255)) cannot be used to construct an efficient configuration. (the cost of TSP and the cost of arm movements cannot be matched.)

Based on the above considerations, I was able to reach the score 74075.7065416901 using the method described below.

First, solve the TSP using a Genetic Algorithm (GA).
At this time, the tours handled were always configurations that could be built. That is, each time a new tour was generated, the following check was performed, and if the result was False, the tour was immediately eliminated.

```python
def is_valid_tour(tour):
    if not simulate_longest_arm(tour):
        return False
    if left_side_pixel_in_beginning_or_end(tour):
        return False
    if far_right_pixel_in_first_or_last_paths(tour):
        return False
    if has_冖(tour):
        return False
    return True
```

`simulate_longest_arm()` uses dynamic programming to calculate the longest arm as being either not moving or moving one unit downward when moving down on a tour. (The same applies for directions other than down.)

Tours, the first generation of GAs, were generated using the following procedure:

1. Create a tour that satisfies the above conditions in some way.
2. extract up to about 2400 vertices from the tour and replace them with the TSP solution by Concorde over and over again. (If the replaced tour does not pass the is_valid_tour() check, it is not replaced.)

After about 100 tours are generated by this procedure, GA is performed.
The edge assembly crossover (EAX) was used as the crossover algorithm for GA. I implemented it based on [this paper](https://www.jstage.jst.go.jp/article/tjsai/22/5/22_5_542/_article/), which is available in the Japanese language, but it is rather old.

It would have been simpler if I could have modified LKH rather than implementing EAX on my own, but the LKH code was too complicated for me.

After a good tour is obtained by GA, it is converted to configurations.

The conversion from tours to configurations uses a beam search as follows:

```python
last_pixel = tour[0]
last_configuration_and_cost_candidates = {("64 0;-32 0;-16 0;-8 0;-4 0;-2 0;-1 0;-1 0", 0)}
for pixel in tour[1:]:
    delta = (pixel.y - last_pixel.y, pixel.x - last_pixel.x)
    configuration_and_cost_candidates = {}
    for last_configuration, last_cost in last_configuration_and_cost_candidates:
        for configuration, cost in compute_all_possible_next_configurations(last_configuration, delta):
            configuration_and_cost_candidates.add((configuration, cost))
    last_configuration_and_cost_candidates = narrow_down(configuration_and_cost_candidates)
    last_pixel = pixel
```

The beam search is a bit tricky to get it to work in practice; it seems that narrow_down() needs to include as many states of the longest arm as possible to find a good solution, rather than just picking the one with the smallest cost.

私の解説では、0-indexed で上から y 番目、左から x 番目のピクセルを (y, x) と表現することにご注意ください。中央のピクセルは (128, 128) となります。

私の解法は、Concorde と遺伝的アルゴリズムを使って制約付きの TSP を解いた後、得られたツアーを configurations に変換するものです。
解法を詳しく説明する前に、この解法に辿り着くために必要だった考察を説明します。

まず、いくつか実験を行うと、以下のようなことがわかります。

* アームの自由度は十分高い。例えば、適当なピクセルと、そのピクセルを指すランダムな configuration があったとして、そのうちの 1 つのアームだけを動かしてその右のピクセルに移動することができる確率はかなり高い。

このことから、既に discussion でも議論されているように、最初に TSP を解いて、その経路に沿うように configurations を構築するのは有効な戦略だといえます。

ただし、純粋な TSP を解くことによって得られた解をそのまま configurations に変換するのはうまくいかないようです。

この原因は最長のアームの制約によるものが大きいと考えました。例えば、初期状態で最長のアームは真っ直ぐ右に伸びています。最長のアームが右に伸びた状態ではカードの左側を印刷することができないため、x < 128 (左半分) の領域を塗るのは、初期状態から最長のアームを上 (または下) に少なくとも 64 回動かした後である必要があります。

また、最長のアーム以外の制約により効率の良い configuration が構築できないケースとして、以下の 3 つがあるようでした。

1. 早い段階で x < 128 を塗ろうとしてしまう
  * これは上記の例と同じものですが、実際には最長アームだけ考慮する場合よりも少し厳しい制約があります。
2. 早い段階で右に行きすぎる
  * 例えば、初期状態の configuration でアームは全て左右を向いているため、初手の移動は上か下に限定され、右に移動することは不可能です。(最長アームの制約により、左という選択肢は既に排除されています。)
初手で最短のアームを使って上か下に移動することで右に 2 回移動することができるようになりますが、3 回の移動、すなわち初期状態から「下→右→右→右」のように移動することはやはり不可能だとわかります。
3. 外周から 2 番目のピクセルに沿って移動する
  * 画像のリサイズを行うアルゴリズムのエラーのためか、最も外側のピクセルは他より暗い色に、2 番目に外側のピクセルは他より明るい色になっているため、純粋な TSP の解はそれに沿うようなパスを含みます。このうち、2 番目に外側の "冖" のようなパス (例: (2, 1) → (1, 1) → (1, 2) → … → (1, 254) → (1, 255) → (2, 255)) からは、効率の良い configuration を構築することができません (TSP のコストとアームの移動コストを一致させられません)。

上記の考察を踏まえて、私は以下に説明する方法でスコア 74075.7065416901 に到達できました。

まず、遺伝的アルゴリズム (GA) を使って TSP を解きます。
この時、扱うツアーは常に configurations を構築可能なものとします。すなわち、新しいツアーを生成するたびに以下のようなチェックを行い、結果が False の場合はそのツアーを即座に消去します。

```python
def is_valid_tour(tour):
    if not simulate_longest_arm(tour):
        return False
    if left_side_pixel_in_beginning_or_end(tour):
        return False
    if far_right_pixel_in_first_or_last_paths(tour):
        return False
    if has_冖(tour):
        return False
    return True
```

`simulate_longest_arm()` は、ツアー上で下に移動するとき最長のアームは動かないか下方向に 1 単位移動することが可能として、動的計画法を用いて計算します。(下以外の方向の場合も同様です。)

GA の最初の世代となるツアーは、以下の手順で生成しました。

1. 適当な方法で上記の条件を満たすツアーを作成する。
2. ツアーから最大 2400 個程度の頂点を抜き出し、Concorde により TSP の解を求めて置き換えるのを何度も繰り返す。(置き換えると is_valid_tour() でのチェックが通らなくない場合は置き換えない。)

2 では、ツアーの l 番目から r 番目までの頂点を抜き出す方法の他に、カード内の矩形領域を抜き出す方法も使っています。

この手順により 100 個程度のツアーを生成し、GA を行います。
GA の交叉アルゴリズムには、枝組立交叉 (edge assembly crossover, EAX) を使用しました。日本語で利用可能だった[この論文](https://www.jstage.jst.go.jp/article/tjsai/22/5/22_5_542/_article/)を参考に実装しましたが、やや古いです。

自力で EAX を実装するよりも、LKH を改造することができればよりシンプルな解法となったように思いますが、私には LKH のコードは難しすぎました。

GA により良いツアーが得られたら、それを configurations に変換します。

ツアーから configurations への変換には以下のようなビームサーチを用います。

```python
last_pixel = tour[0]
last_configuration_and_cost_candidates = {("64 0;-32 0;-16 0;-8 0;-4 0;-2 0;-1 0;-1 0", 0)}
for pixel in tour[1:]:
    delta = (pixel.y - last_pixel.y, pixel.x - last_pixel.x)
    configuration_and_cost_candidates = {}
    for last_configuration, last_cost in last_configuration_and_cost_candidates:
        for configuration, cost in compute_all_possible_next_configurations(last_configuration, delta):
            configuration_and_cost_candidates.add((configuration, cost))
    last_configuration_and_cost_candidates = narrow_down(configuration_and_cost_candidates)
    last_pixel = pixel
```

このビームサーチを実際に動かすには少しコツが必要で、narrow_down() では単にコストが小さいものを選ぶのではなく、なるべく多くの最長のアームの状態を含むようにしなければ、上手く解を見つけられないようです。
