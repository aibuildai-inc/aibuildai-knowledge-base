## Principle 10: Recognize When NOT to Use ML

*Consensus: Dominant in 11/11 Santa optimization competitions, explicit in chess/game-AI (mix MCTS + heuristics, not pure RL), and particle physics (geometry first, ML for refinement).*

Many niche problems are better solved by algorithms, heuristics, or hybrid approaches than end-to-end ML. Use ML to refine, score, or handle noise, but rely on domain algorithms for core logic when they exist and are tractable.

**Why this matters:** ML is a function approximator; if you have the exact function (a closed-form solver, a known algorithm), use it. Santa 2023's winner used group theory and breadth-first search to find 3-rotations, NOT ML. Chess AI winners used MCTS with learned value functions, not pure RL. TrackML used geometric helix fitting and cluster decomposition, then ML for outlier detection. Pure ML would waste compute learning what's already known and likely fail on out-of-distribution structure.

**When to use:** When the problem has a known optimal or near-optimal algorithm (planning, search, constraint satisfaction), when domain experts have established heuristics that work well, or when the problem is deterministic and combinatorial (permutations, routing, scheduling) with tractable state spaces.

**When NOT to use:** When the problem is perceptual or unstructured (vision, NLP), when domain knowledge is unavailable or contested, when optimal algorithms are NP-hard AND heuristics don't scale, or when you have abundant data and time to train end-to-end models.

**How to reason about it:**
Ask: Does a known algorithm solve this or a simpler version? Can I decompose it into algorithm + ML (e.g., geometry + outlier detection)? Is the problem deterministic or stochastic? For deterministic combinatorial problems: try search, DP, or heuristics first. For stochastic or perceptual: use ML. For hybrid: use algorithms for structure, ML for noise/refinement.
