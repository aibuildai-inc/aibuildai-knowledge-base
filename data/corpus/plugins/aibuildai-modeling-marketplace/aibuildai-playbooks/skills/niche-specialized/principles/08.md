## Principle 8: Engineer Features for Generalization, Not Memorization

*Consensus: Universal in fraud/risk tasks (5/5), critical in audio tasks with geographic shift (3/3 BirdCLEF solutions), and implicit in physics (TrackML used relative geometric features, not absolute positions).*

Create aggregated or relational features that capture patterns WITHOUT encoding entity identity. Use grouped statistics, relative positions, or distribution summaries instead of raw IDs or absolute coordinates.

**Why this matters:** Raw entity IDs or absolute coordinates let models memorize training entities instead of learning transferable patterns. IEEE Fraud's winner could NOT use client UID directly because 68% of test clients were unseen—but they COULD use grouped aggregations (mean, std, max) over client transaction history. This captured 'client behavior patterns' that generalized. TrackML used relative hit positions (angles, distances from trajectory) not absolute detector coordinates, so patterns learned on one event transferred to others.

**When to use:** When test data includes unseen entities (clients, locations, users), when entity IDs have high feature importance in adversarial validation (a red flag), or when the task requires generalizing learned patterns to new contexts.

**When NOT to use:** When entity identity IS the signal (user authentication, duplicate detection), when all test entities appear in training (rare), or when you're explicitly told to use IDs as features (e.g., user embeddings in a recommendation task).

**How to reason about it:**
If you have entity IDs: create grouped aggregations (mean, std, min, max, count) over entity subsets, then DROP the ID. For spatial data: use relative positions, distances, angles. For temporal data: use deltas, rolling statistics. For categorical: use target encoding with smoothing. Test: does your model work if you replace all training entity IDs with 'UNKNOWN'?
