## Principle 10: Optimize the Proposal Ceiling and Final Metric Separately

*Consensus: Metric structure drove both competitions: ARC's top-3 exact-match ranking and Foursquare's candidate max-IoU/Jaccard diagnostics were repeatedly reported by leading solutions.*

Track oracle performance of the candidate pool separately from realized performance, then tune ranking, thresholds, and loss for the actual set-level metric. Exact top-k tasks reward diverse complete hypotheses; Jaccard tasks require balancing false-positive and false-negative set members per query.

**Why this matters:** A better pairwise AUC or pixel accuracy may not improve exact-match or Jaccard score. Oracle coverage reveals whether the answer was never proposed, while the gap from oracle to final score quantifies verifier, calibration, and assembly errors.

**When to use:** Use this decomposition whenever evaluation is top-k, exact-match, IoU/Jaccard, F-score, ranking, or another non-decomposable metric. Consider differentiable metric surrogates only after proposal recall is adequate.

**When NOT to use:** Do not directly optimize a noisy set-level surrogate when it destabilizes learning or hides severe subgroup errors. BCE or log loss can remain useful for representation learning if final thresholds are selected on the target metric.

**How to reason about it:**
For each validation instance compute: candidate oracle score, score after local verification, and score after structural post-processing. If oracle is low, improve proposals; if oracle is high but final is low, improve ranking/calibration; if post-processing hurts, weaken its assumptions.
