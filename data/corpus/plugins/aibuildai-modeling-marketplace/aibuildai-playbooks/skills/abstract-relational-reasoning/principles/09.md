## Principle 9: Make Search and Inference Resource-Aware by Construction

*Consensus: Explicit acceleration, caching, deduplication, cascading, or batching appeared in at least 6/12 ARC and 10/16 substantive Foursquare writeups.*

Treat compute and memory limits as architectural constraints: hash equivalent symbolic states into a DAG, cache extracted objects, use shallow filters before expensive models, batch feature generation, and parallelize independent tasks. Measure useful proposal coverage per unit of memory and time.

**Why this matters:** More search depth or candidates help only if the pipeline finishes reliably. ARC's many operation sequences often collapse to identical grids, while entity matching repeatedly computes features for millions of mostly negative pairs; eliminating this redundancy directly expands the feasible hypothesis space.

**When to use:** Use deduplication whenever different derivations can yield the same state, and cascades whenever cheap features reject most candidates. Prefer optimized inference libraries or lower-level implementations only after profiling identifies the bottleneck.

**When NOT to use:** Do not sacrifice numerical fidelity, reproducibility, or candidate recall for an unmeasured speedup. Complex infrastructure is unnecessary when the full search already fits comfortably and iteration speed matters more.

**How to reason about it:**
Profile peak memory, stage latency, candidate count, and marginal coverage. Spend resources where extra depth or candidates add new valid hypotheses, not where duplicate states dominate. Include deterministic seeds, timeout handling, and a fallback output.

frontier = {hash_state(initial): initial}
