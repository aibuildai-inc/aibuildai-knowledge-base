## Principle 3: Separate Proposal, Verification, and Set Construction

*Consensus: 10/12 ARC writeups and 15/16 substantive Foursquare writeups used an explicit or implicit multi-stage pipeline of this form.*

Architect the solver as three distinct questions: which hypotheses are plausible, which fit the observed evidence, and how accepted local hypotheses form the required output. Keep interfaces between these stages explicit so each failure mode can be measured independently.

**Why this matters:** Proposal errors are irrecoverable, while verification errors and set-construction errors require different remedies. ARC solvers generated DSL programs or transformed pieces, checked them on demonstrations, and ranked outputs; Foursquare solvers blocked candidate pairs, scored them, and built match sets through graph processing.

**When to use:** Use this decomposition whenever the raw output space is combinatorial or quadratic and the metric evaluates complete outputs rather than isolated labels.

**When NOT to use:** A single-stage model can suffice when the output vocabulary is small, all candidates are enumerable, and predictions are independent. Even then, retain diagnostic equivalents such as top-k coverage and calibration.

**How to reason about it:**
Measure three ceilings: proposal recall, verifier quality conditional on proposal inclusion, and final metric after structural assembly. Improve the earliest stage whose ceiling blocks downstream progress rather than tuning the final threshold blindly.

```python
proposals = propose(instance, budget=proposal_budget)
proposal_recall = oracle_coverage(proposals, truth)  # validation only
scored = verifier.score(instance, proposals)
output = construct_valid_set(scored, constraints=relation_constraints)
```
