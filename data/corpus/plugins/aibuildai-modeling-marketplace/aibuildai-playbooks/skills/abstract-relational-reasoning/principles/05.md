## Principle 5: Route by Observable Geometry and Output Topology

*Consensus: At least 8/12 ARC writeups branched on object, tile, grid, or size relations; at least 11/16 substantive Foursquare writeups used graph-aware assembly or group-dependent decisions.*

Use observable structural signatures to select an appropriate reasoning family instead of asking one model to handle every relation. Grid tasks may branch on input-output size, panels, symmetry, or connected objects; matching tasks may branch on local density, expected cluster size, field availability, or country/language.

**Why this matters:** Different topologies imply different correspondences. A same-size grid supports pixel-local prediction, a tiled grid supports panel aggregation, and an enlarged grid needs one-to-many coordinate mapping; similarly, merging two singleton records is statistically different from joining two large clusters.

**When to use:** Use routing when regimes are detectable before seeing the hidden answer and each branch has enough validation support. Soft routing or trying several compatible branches is safer when signatures are ambiguous.

**When NOT to use:** Avoid brittle hard rules based on weakly supported correlations. A universal proposal stage followed by learned ranking can outperform routing when branch labels are noisy or data per branch is scarce.

**How to reason about it:**
Derive routing features only from information available at inference. For each prospective branch, test conditional coverage and error, and retain a fallback path. Treat output shape or cluster size as a latent variable when it cannot be inferred confidently.

```python
signature = inspect_structure(instance)
branches = []
if signature.same_shape_likely:
    branches.append(pixel_or_local_branch)
if signature.has_tiles_or_components:
    branches.append(object_or_tile_branch)
if signature.is_sparse_entity_graph:
    branches.append(pair_then_graph_branch)
proposals = deduplicate(p for branch in branches for p in branch(instance))
```
