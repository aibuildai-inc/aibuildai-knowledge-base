## Principle 3: Engineer Temporal Features That Respect the Forecasting Horizon

*Consensus: Every top solution uses lag and rolling features, but incorrectly computed ones cause the most common leakage failures. M5 top-3, Favorita 1st, Jane Street 1st all emphasize this.*

Create lag features (values from T-k), rolling statistics (mean/std/max over past N steps), and time-based encodings (day of week, month). Critical: lags must start AFTER the forecasting horizon—if predicting 28 days ahead, smallest lag is 29.

**Why this matters:** A lag-1 feature when predicting 28 days ahead leaks 27 days of future information. Rolling windows that include the target timestamp leak. These create a massive train-test distribution shift invisible in CV but catastrophic on LB. Proper lags let models learn autoregressive patterns without cheating.

**When to use:** Universal for forecasting and most sequence tasks. More critical when: (1) data has strong autocorrelation, (2) you're using GBDT (deep learning can learn lags implicitly), (3) forecast horizon > 1. Adjust lag range to domain—sales may need 7/14/28 day lags (weekly patterns), high-frequency signals need much shorter.

**When NOT to use:** Skip if your model architecture already handles sequences end-to-end (LSTMs, Transformers with full sequence input). Reduce if data is too noisy for lags to help (check ACF plots). In signal classification tasks without forecasting, you can use centered rolling windows that include past and future.

**How to reason about it:**
Forecasting horizon defines minimum lag: if predicting T+h, smallest lag is h+1. For rolling features, window must end BEFORE prediction point: rolling_mean(t - horizon - window : t - horizon). Check domain periodicity: daily/weekly/seasonal patterns suggest which lags to include. Validate: does your feature engineering code use ANY information from time >= target_time? If yes, it's leakage. Test: set target to a constant—do your features still vary? If yes, they might be leaking.

```python
# Correct lag features for 28-day ahead forecasting
horizon = 28
# WRONG: lag 1 leaks future
# df['lag_1'] = df.groupby('id')['sales'].shift(1)  # DON'T DO THIS

# CORRECT: lags start after horizon
for lag in [29, 30, 35, 42, 56]:  # 1, 2, 7, 14, 28 days past horizon
    df[f'lag_{lag}'] = df.groupby('id')['sales'].shift(lag)

# Rolling mean over past 7 days, ending at T-horizon-1
for window in [7, 14, 28]:
    df[f'rolling_mean_{window}'] = (
        df.groupby('id')['sales']
        .shift(horizon)  # shift to T-horizon first
        .rolling(window)
        .mean()
    )
```
