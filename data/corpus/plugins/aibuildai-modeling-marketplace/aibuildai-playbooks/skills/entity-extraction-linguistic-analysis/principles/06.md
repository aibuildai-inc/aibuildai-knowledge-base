## Principle 6: Invest Heavily in Post-Processing, Especially Boundary and Format Repair

*Consensus: Recurring across competitions - extensive post-processing in most top solutions, often worth as much as a new model*

After model prediction, apply rule-based post-processing to fix common errors: remove leading/trailing whitespace, validate entity formats (emails have '@', URLs have 'http'), apply domain constraints (names are title-cased), and repair split spans. Post-processing often provides as much gain as a new model.

**Why this matters:** Models learn patterns but violate hard constraints. A model may predict 'john' as NAME_STUDENT (violates capitalization), ' the ' as a name (violates article rule), or 'user@' as an email (invalid format). Post-processing enforces these constraints cheaply. NBME's 1st place: whitespace removal was critical. PII's 1st place: 7 post-processing rules were core to the solution.

**When to use:** Always apply post-processing. Essential steps: (1) Whitespace: strip leading/trailing spaces, remove spans that are only whitespace. (2) Format validation: for structured entities (email, URL, phone, ID), validate with regex; reject if invalid. (3) Domain constraints: names must start with capital (reject 'john'), IDs must have >N digits. (4) Span repair: if a span ends mid-word or before punctuation, extend to word boundary. (5) Consistency: if token X is predicted as entity in one place, propagate to all X in the document (works for names, datasets).

**When NOT to use:** Be cautious with aggressive post-processing when: (1) the domain is highly variable (dataset names can be all-lowercase), (2) over-tuning on public LB causes overfitting (keep rules general, not test-specific). Coleridge's top solutions noted that over-aggressive post-processing hurt. Balance rules with model trust.

**How to reason about it:**
Start with whitespace removal (universal). Analyze model errors on validation: what rule violations appear? For each error pattern seen >5 times, write a rule. Test each rule's impact on CV. Common rules: (1) Whitespace: if span[0] or span[-1] is space/newline, trim. (2) Format: if label is EMAIL and '@' not in span, reject. (3) Capitalization: if label is NAME and span[0].islower(), reject. (4) Length: if label is ID_NUM and len(span) < 4, reject. (5) Consistency: if span appears 3+ times in doc, label all occurrences. Apply in order: format validation → whitespace → repair → consistency.

```python
def postprocess_predictions(text, spans, labels):
    processed = []
    for span_text, label, (start, end) in zip(spans, labels, span_positions):
        # 1. Whitespace removal
        span_text = span_text.strip()
        if not span_text:  # Skip empty spans
            continue
        
        # 2. Format validation
        if label == 'EMAIL' and '@' not in span_text:
            continue  # Invalid email
        if label == 'URL_PERSONAL' and not span_text.startswith(('http', 'www')):
            continue
        if label == 'PHONE_NUM' and not re.match(r'\d{3}[-.\s]?\d{3}[-.\s]?\d{4}', span_text):
            continue
        
        # 3. Domain constraints
        if label == 'NAME_STUDENT':
            if not span_text[0].isupper() or any(c.isdigit() for c in span_text):
                continue  # Names are title-case, no digits
        
        # 4. Span repair: expand to word boundaries
        while start > 0 and text[start-1].isalnum():
            start -= 1
        while end < len(text) and text[end].isalnum():
            end += 1
        span_text = text[start:end]
        
        processed.append((span_text, label, (start, end)))
    
    # 5. Consistency: propagate high-confidence predictions
    confident_names = {s for s, l, _ in processed if l == 'NAME_STUDENT'}
    for name in confident_names:
        for match in re.finditer(re.escape(name), text):
            if match.span() not in [pos for _, _, pos in processed]:
                processed.append((name, 'NAME_STUDENT', match.span()))
    
    return processed
```
