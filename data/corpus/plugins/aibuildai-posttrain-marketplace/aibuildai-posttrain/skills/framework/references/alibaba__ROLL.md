# ROLL

Alibaba's Ray-native RL post-training library: one Ray cluster orchestrates separately-scaled training and generation workers, driven by a single YAML config, from one GPU to thousands.

ROLL (Reinforcement Learning Optimization for Large-Scale Learning) describes itself as "an efficient and user-friendly RL library designed for Large Language Models (LLMs) utilizing Large Scale GPU resources", built around "a multi-role distributed architecture with Ray for flexible resource allocation and heterogeneous task scheduling", and integrating Megatron-Core, SGLang, and vLLM to accelerate training and inference [1]. It is developed by Alibaba's TAOBAO & TMALL Group and Alibaba Group [1]. The repository lives at https://github.com/alibaba/ROLL [2], with an accompanying arXiv tech report [3]. The API surface is YAML-first: a pipeline (RLVR, Agentic, DPO, Distill, or SFT) reads a single config file that defines per-role workers (`actor_train`, `actor_infer`, `reference`, `critic`, `rewards`, ...), each with its own model, training, generation, and backend-strategy arguments, and is launched as `python examples/start_<pipeline>_pipeline.py --config_path <dir> --config_name <name>` [4].

**When to pick it**: cluster-scale, Ray-orchestrated RL post-training where training and generation roles need independent, heterogeneous device placement (colocated or fully disaggregated) - a different shape from trl's Accelerate-launched, one-model-per-process pattern (cross-reference; not covered here) and closer to verl's Ray-based design (cross-reference; not covered here), among Ray-based options weigh how each project's own docs and examples cover your target scale and hardware. ROLL ships worked example configs up to Qwen3 MoE 235B-A22B and documents AMD/ROCm and Ascend NPU support alongside CUDA [5][1].

**Methods it ships**: methods are organized as five pipeline types under `roll/pipeline/` - `agentic`, `rlvr`, `dpo`, `distill`, `sft` [6] - not as one trainer class per method. Within the RLVR pipeline, the RL algorithm is selected by the `adv_estimator` field of `RLVRConfig` (a `PPOConfig` subclass), whose enum values are `gae`, `reinforce`, `grpo`, `gigpo`, `step_reinforce`, and `agentic_reinforce`, read directly from `roll/configs/base_config.py` at commit `7f9d4d3` (the v0.3.0 release tag) [7]. The README additionally lists PPO, GRPO, Reinforce++, TOPR, RAFT++, and GSPO as algorithms supported "out-of-the-box" through this same config surface, plus LoRA fine-tuning and FP8 rollout as cross-cutting options [1]. The SFT pipeline is confirmed present in the source tree at v0.3.0 (`roll/pipeline/sft/`) [6] and the README's dated News entry says it shipped 2025-08-28 with a worked config [1]; a separate, undated line in the same README's Key-Features list still reads "SFT Pipeline under development" [1] - the two disagree, and the dated entry plus the presence of the pipeline directory and an example config are the stronger signal. This taxonomy is unrelated to trl's or verl's method lists and moves with the repo; recheck the source tree and README before citing pipeline coverage. Method-level math and defining papers live on each method's own card, not here.

**Scale it handles**: single GPU up to multi-node, launched entirely through Ray - `bash examples/<pipeline>_demo/run_..._single_node_demo.sh` on one machine, and on multiple machines a master node starts the Ray head while worker nodes join with `ray start --address='<master_ip>:<master_port>' --num-gpus=<n>` after `MASTER_ADDR`/`MASTER_PORT`/`WORLD_SIZE`/`RANK` are exported [8]. Training runs on FSDP2 or Megatron-LM (the latter through the bundled `mcore_adapter` package, offering tensor/pipeline/context/expert-parallel dimensions - "Training supports FSDP2, Megatron-LM 5D parallelism (mcore-adapter, dp/tp/pp/cp/ep)" [1]); generation runs on vLLM or SGLang; `device_mapping` lets each role reuse the same GPUs (colocate) or hold disjoint ones (separate mode) [9]. Multi-node is documented as a mechanism with worked commands for a 2-node/2-GPU-each example, not as a published multi-node benchmark [8].

**Install**: no PyPI package is documented or found in the release's packaging metadata - `setup.py` at the v0.3.0 tag declares `name="roll"`, `version="0.3.0"`, `python_requires=">=3.10"` with no `install_requires` list, and `pyproject.toml` at that tag carries only linter config [10]. The Installation page's own documented command is the generic `git clone https://github.com/alibaba/ROLL.git && cd ROLL && pip install -r requirements.txt` [11], but that literal file does not exist in the repository (fetching it returns a 404); the concrete, working form, shown on the Quick Start page, names one of several backend-specific requirements files at the repo root instead, e.g. `pip install -r requirements_torch260_vllm.txt`, each of which pulls in the shared `requirements_common.txt` [12]. Apache-2.0 licence [2]. Reading `requirements_common.txt` and `requirements_torch280_vllm.txt` at the v0.3.0 tag's commit `7f9d4d3` [13][14] (the screening row's commit, `370cb24`, is the repository's newest push and is ahead of this release - dependency claims below are read at the release tag, not the push): `ray[default,cgraph]==2.48.0`, `datasets==3.1.0`, `peft==0.12.0`, `trl==0.9.6`, `torch==2.8.0.*`, `transformers==4.57.0`, `accelerate==0.34.2`, `vllm==0.10.2` (a separate `requirements_torch280_sglang.txt` swaps in `sglang[srt,torch-memory-saver]==0.5.2` instead of vllm) [13][14]; the local `mcore_adapter` package is installed in-place via `./mcore_adapter` in `requirements_common.txt` [13]. The installation page's own prerequisites, read independently of the pinned files, are CUDA >= 12.4, cuDNN >= 9.1.0, PyTorch >= 2.5.1, SGLang >= 0.4.3, vLLM >= 0.7.3 (AMD: ROCm >= 6.3.4, PyTorch >= 2.6.0, vLLM >= 0.8.4) [11].

**Maintained by**: Alibaba's TAOBAO & TMALL Group and Alibaba Group [1]; 3,359 GitHub stars as a single dated count, not a ranking [15]; actively developed, with the latest GitHub release v0.3.0 dated 2026-06-18 [16] and the README's own News table showing entries dated as recently as 2026-06-16 [1].

## Quick start

ROLL has no Python-snippet quickstart comparable to trl's `SFTTrainer(...).train()`; its documented smallest complete run is a shell script over a YAML config. The single-GPU quick start [12]:

```bash
git clone https://github.com/alibaba/ROLL.git
cd ROLL
pip install -r requirements_torch260_vllm.txt -i https://mirrors.aliyun.com/pypi/simple/
bash examples/agentic_demo/run_agentic_pipeline_frozen_lake_single_node_demo.sh
```

The general CLI form behind any such script is `python examples/start_<pipeline>_pipeline.py --config_path <dir> --config_name <name>` [4]. A worked RLVR (GRPO) config, annotated field-by-field in the docs, sets `pretrain: Qwen/Qwen2.5-7B`, `adv_estimator: "grpo"`, `rollout_batch_size: 64`, `num_return_sequences_in_group: 8`, an `actor_train` role on `megatron_train` strategy and an `actor_infer` role on `vllm` strategy with `gpu_memory_utilization: 0.8`, and a `math_rule` reward worker class [9].

## Start it

- One process, one GPU: run the pipeline script directly, as in Quick start, with `device_mapping: list(range(0,1))` on every role and `num_gpus_per_node: 1` [12].
- Multiple GPUs on one machine: increase each role's `device_mapping` range; roles can overlap the same GPUs (colocate mode) or hold disjoint ranges (separate mode) [9].
- Multiple machines: the launcher is Ray itself, not a separate config-templated launcher like Accelerate or torchrun. Export `MASTER_ADDR`, `MASTER_PORT` (default 6379), `WORLD_SIZE`, `RANK`, `NCCL_SOCKET_IFNAME`, `GLOO_SOCKET_IFNAME` on every node; run the pipeline script on the master node (rank 0), and on each worker node run `ray start --address='<master_ip>:<master_port>' --num-gpus=<n>` to join the cluster before the master's script proceeds [8].
- Effective batch arithmetic differs by backend, per the FAQ page: for FSDP2, `global_batch_size = per_device_train_batch_size * gradient_accumulation_steps * world_size / ulysses_size`; for Megatron, `global_batch_size = per_device_train_batch_size * gradient_accumulation_steps * world_size / tensor_model_parallel_size / pipeline_model_parallel_size / context_parallel_size` (not divided by `expert_model_parallel_size`), where `world_size` is the length of `actor_train`/`critic`'s `device_mapping`. Separately, for the Megatron backend, `rollout_batch_size * num_return_sequences_in_group` must be an integer multiple of `gradient_accumulation_steps * per_device_train_batch_size * (world_size / tensor_model_parallel_size / pipeline_model_parallel_size / context_parallel_size)` [17].
- Config surface: `BaseConfig` (experiment name, seed, tracker settings, step/batch/sequence-length fields) is the parent of each `PipelineConfig` (`RLVRConfig`, `AgenticConfig`, `DPOConfig`, `DistillConfig`), which defines per-role `WorkerConfig`s, each carrying `model_args`, `training_args`, `data_args`, `generating_args`, and backend `strategy_args`; only fields explicitly present in the dataclasses are accepted, validated partly through each class's `__post_init__` [18]. Reading `roll/configs/base_config.py` at the v0.3.0 tag's commit `7f9d4d3` shows the RL-algorithm defaults a chooser would otherwise have to guess: `gamma=1`, `lambd=0.95` (GAE), `pg_clip=0.2` with separate `pg_clip_low`/`pg_clip_high` also defaulting to `0.2`, `value_clip=None`, `kl_penalty="kl"` with `init_kl_coef=0.2` and `target_kl=None`, `loss_agg_mode="seq-mean-token-mean"`, and `ppo_epochs=1`; setting `use_kl_loss` or a positive `init_kl_coef` forces `enable_reference=True` in `__post_init__` [7]. The worked GRPO example overrides several of these explicitly (`ppo_epochs: 1`, `use_kl_loss: true`, `kl_loss_coef: 0.001`, `loss_agg_mode: "seq-mean-token-sum"`, `whiten_advantages: true`, `advantage_clip: 2.0`, `dual_clip_loss: true`, `reward_clip: 10`) [9] - none of these are stated as ROLL-changed defaults away from a documented base, since ROLL's config classes are its own, not a subclass of an external trainer's arguments the way trl's `Config` classes subclass `TrainingArguments`.
- Out-of-memory first aid: the docs' own worked V100 example (2 GPUs) shows the concrete levers in one place - shrink `device_mapping` ranges per role, cut `rollout_batch_size` and `val_batch_size`, switch `actor_train`/`actor_infer`/`reference` `model_args.dtype` from `bf16` to `fp16` ("V100 has better native support for FP16 than BF16... Switching to FP16 can improve compatibility and stability while saving GPU memory" [8]), switch `strategy_name` from `fsdp2_train`/default to `megatron_train` with `recompute_granularity: full` and `use_distributed_optimizer: true`, and lower `max_actions_per_traj` / environment-group counts for agentic pipelines [8]. On the generation side, `strategy_config.gpu_memory_utilization` (0.8 in the worked GRPO example) is the vLLM-strategy memory knob [9].

## Watch it

This section is mechanics only; what a metric MEANS for a given RL algorithm lives on that method's own card.

- **Enable it**: set `track_with` to one of `tensorboard`, `wandb`, `swanlab`, `stdout`, or `trackio` at the top level of the YAML, with backend-specific `tracker_kwargs` (e.g. `log_dir` for TensorBoard, `api_key`/`project` for WandB) [19]. `stdout` needs no `tracker_kwargs` - it is the only backend documented with no external destination, so a run configured with none of the others still prints locally [19].
- **Metric names**: the Trackers and Metrics page groups the metrics the framework records by area [19]: validation (`val/score/mean`, `val/score/max`, `val/score/min`); value/critic (`critic/lr`, `critic/loss`, `critic/value`, `critic/vpred`, `critic/clipfrac`, `critic/error`); reward and advantage (`critic/score/mean|max|min`, `critic/rewards/mean|max|min`, `critic/advantages/mean|max|min`, `critic/returns/mean|max|min`, `critic/values/mean|max|min`); token-length (`tokens/response_length/mean|max|min`, `tokens/prompt_length/mean|max|min`); policy (`actor/lr`, `actor/ppo_ratio_high_clipfrac`, `actor/ppo_ratio_low_clipfrac`, `actor/ppo_ratio_clipfrac`, `actor/ratio_mean|max|min`, `actor/clipfrac`, `actor/kl_loss`, `actor/total_loss`, `actor/approxkl`, `actor/policykl`); evaluation (`critic/ref_log_prob/mean`, `critic/old_log_prob/mean`, `critic/entropy/mean`, `critic/reward_clip_frac`); PPO-loss (`actor/pg_loss`, `actor/weighted_pg_loss`, `actor/valid_samples`, `actor/total_samples`, `actor/valid_sample_ratio`, `actor/sample_weights_mean|min|max`); SFT-loss (`actor/sft_loss`, `actor/positive_sft_loss`, `actor/negative_sft_loss`); phase-duration timing (`time/rollout`, `time/ref_log_probs_values_reward`, `time/old_log_probs_values`, `time/adv`, plus per-phase `time/{phase}/total|execute|onload|offload` for `{phase}` in `train_step`, `generate`, `model_update`, `compute_log_probs`, `do_checkpoint`, `compute_values`, `compute_rewards`); system/throughput (`system/tps`, `system/samples`); and per-device GPU/CPU memory snapshots (`memory/{phase}/...` GPU figures, plus CPU `memory/cpu/{metric_infix}/start/rss`, `.../start/vms`, `.../end/rss`, `.../end/vms`) [19].
- **Sample-level logging of generations** is not documented on the Trackers and Metrics page or the Config System page read for this card; neither page names a completion-text logging field analogous to trl's `log_completions` [19][18].
- **Evaluation during training**: the worked checkpoint-guide example sets `eval_steps: 10` alongside `max_steps`, `save_steps`, and `logging_steps` as top-level `BaseConfig` step-cadence fields [20]; a `val_batch_size` field controls the validation batch size, exercised in the V100 OOM example [8].
- **Stopping**: no RL-specific stopping rule, threshold, or patience field was found in the three pages searched for this card (Trackers and Metrics [19], Checkpoint Saving and Resuming [20], FAQ [17]) as of 2026-08-11; the FAQ page's closest content is a list of common configuration-error assertions (e.g. `assert self.lr_decay_steps > 0`, `AssertionError: batch_size 32 < chunks 64`) with their fixes, not a training-stop criterion [17].

## Save it

- Checkpointing is configured via `checkpoint_config.type` (currently only `file_system` is documented) and `checkpoint_config.output_dir`; the framework saves periodically every `save_steps` steps, and automatically at training end [20]. The worked example names directories `checkpoint-<step>` (e.g. `checkpoint-300`, `checkpoint-500`) under `output_dir` [20]; the exact file inventory inside a checkpoint directory is not enumerated on this page and was not independently inspected on disk for this card.
- For the Megatron backend, checkpoints are saved in Megatron's own weight format by default, not Hugging Face format; converting to HF format is a separate step: `python mcore_adapter/tools/convert.py --checkpoint_path <megatron_ckpt> --output_path <hf_output>` [11][17]. No retention/optimizer-state-dropping flag (comparable to trl's `save_only_model`) is documented on the Checkpoint Saving and Resuming page read for this card [20].
- Resume: set `resume_from_checkpoint` to a checkpoint path (default `false`, meaning no resume); the docs list what a valid path restores as four separate items - loading model parameters, restoring optimizer state, restoring learning rate scheduler state, and restoring other training states such as training steps - so training continues from the saved step [20].
- LoRA changes what a save contains: the LoRA guide describes fine-tuned LoRA models as something that "can be easily merged into the original model" [21], but neither the LoRA guide nor the Checkpoint guide states, for this card's reading, whether a LoRA run saves adapter-only weights or an already-merged full model by default, or names the adapter file layout - that gap should be confirmed on disk or via the config docs before relying on it.
- Whether an evaluator can load a saved ROLL checkpoint directly is the loader's contract, not stated on the pages read for this card; for the Megatron-backend case the conversion step above (`mcore_adapter/tools/convert.py`) is a documented prerequisite to producing an HF-loadable directory [11].

## Find it in the docs

The docs are the live source; this section teaches the lookup, not the content.

- Address pattern: `https://alibaba.github.io/ROLL/docs/<Section>/<Subsection>/<page-slug>`, with spaces in section names left literal in the URL (percent-encoded as `%20` when linked from the README) - e.g. `https://alibaba.github.io/ROLL/docs/Getting%20Started/Installation/` and `https://alibaba.github.io/ROLL/docs/User%20Guides/Configuration/lora`, both fetched and confirmed loading (following an HTTP redirect from the un-encoded form) on 2026-08-11 [11][22]. No version-tag path segment is documented; the site does not appear to publish per-release doc snapshots the way `huggingface.co/docs/trl/<version>` does, so pages read here reflect the docs as they stood on the fetch date, not a pinned release.
- Section map, from the left-nav structure seen on every fetched page: Getting Started (Installation, Quick Start single/multi-node, Debugging Guide, FAQ) - User Guides (Configuration, Pipeline, Algorithms, Agentic, Advanced Features, Tracker & Metrics, Hardware Support) - Development (Architecture, Developer Guide) [22][11][17]. The Configuration section alone holds Configuration-System, Resource-Configuration, FP8-Quantization, FSDP2-Backend, LoRA, Megatron-Backend, Off-Policy-Algorithms, SGLang-Backend, and vLLM-Backend guides [22].
- Question-to-page map used to build this card: install prerequisites and the Megatron-to-HF conversion command -> Installation [11]; single/multi-node launch commands and V100 memory-constrained overrides -> Quick Start guides [12][8]; config-class hierarchy and a fully annotated example GRPO YAML -> ROLL Configuration System [18][9]; every logged metric name -> Trackers and Metrics [19]; checkpoint directory naming, save cadence, and resume semantics -> Checkpoint Saving and Resuming Guide [20]; batch-size arithmetic and common configuration-error fixes -> FAQ [17]; LoRA fields and the merge claim -> LoRA Fine-tuning Configuration Guide [21].
- Runnable references beyond the docs: the `examples/` tree in the repository holds one subdirectory per worked model/pipeline combination (e.g. `examples/qwen2.5-7B-rlvr_megatron/`, `examples/agentic_demo/`, `examples/dpo_examples/`, `examples/qwen2.5-7B-sft_megatron/`), each with a runnable shell script and YAML config used directly by the quick-start commands above [1][9]. `docs_roll/` in the repository is the source tree the rendered docs site is built from, in English and Simplified Chinese [1].
- Community layer: the README does not curate a community-tutorials page comparable to trl's; the closest official pointer is the README's own "Notable work based on ROLL" list, which links out to third-party papers and repositories that build on ROLL (e.g. TaoSR1, RecGPT, EARL) rather than tutorials [1]. No official curated blog list or MCP documentation endpoint was found for this card as of 2026-08-11; treat that absence as the honest answer, not an omission.
- Trap: the FAQ page's four documented common-error fixes are official maintainer documentation, not maintainer replies in closed GitHub issues, so they are reported here with that caveat rather than with an issue number and reply author: a `self.node2pg[node_rank] KeyError` means `device_mapping`'s GPU count doesn't match the requested total; `assert self.lr_decay_steps > 0` means `rollout_batch_size` divided across `actor_train` DP workers and then by `gradient_accumulation_steps` rounded to zero; `AssertionError: batch_size 32 < chunks 64` means `rollout_batch_size` is smaller than the DP size of `reference`/`actor_train`; and `TypeError: BackendCompilerFailed.__init__()` is worked around by setting `system_envs.NVTE_TORCH_COMPILE: '0'` in the YAML [17]. No GitHub-issue-sourced trap (with issue number, reply author association, and date) was searched for or found for this card.
- Honest boundary: the docs read for this card do not name an unsupported method, hardware floor beyond the CUDA/cuDNN/PyTorch/vLLM/SGLang versions in Install, or a scale ROLL is explicitly "not built for" [11]; the SFT-pipeline maturity conflict inside the README itself (flagged under Methods it ships) is the clearest documented rough edge found.
