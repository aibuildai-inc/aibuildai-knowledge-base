# RL-Factory

Repository: https://github.com/Simple-Efficient/RL-Factory

An agentic-tool-use RL post-training framework built as a thin layer on top of a vendored verl 0.5.0 core - pick it for multi-turn MCP tool-calling training, not as a from-scratch RL trainer.

RL-Factory's own README describes it as "an **easy** and **efficient** RL post-training framework for **Agentic Learning**" [1], and the repository's own GitHub description field reads "Train your Agent model via our easy and efficient framework" [3]. It is built and maintained under the Simple-Efficient GitHub account, which GitHub's own API records as a User account rather than an Organization [3]. Its own architecture page states plainly that the "Basic Layer" - the native RL training mechanism, the multi-turn tool-use interaction logic, and the model-judge infrastructure - is untouched verl, while RL-Factory's own code sits in an "Application Layer" (an `Env` class, an `mcp_tools.pydata` tool config, and a `compute_score` reward function that a user supplies) and an optional "Component Layer" for customizing pieces like the tool manager [4]. Concretely: RL-Factory's `verl/` directory is version 0.5.0 of Bytedance's verl, its `setup.py` and `pyproject.toml` still describe and link to `volcengine/verl` rather than this repo, and its SFT trainer (`verl/trainer/fsdp_sft_trainer.py`) carries an unmodified 2024 Bytedance copyright header [5][6][7].

**The deciding number**: the README's own benchmark table trains a search-agent on Natural Questions (NQ) and compares RL-Factory's GRPO runs against Search-R1 baselines built on plain verl, at matched hardware (8x A100) and 100 training steps: Search-R1-Qwen2.5-3B-Instruct-GRPO scores 0.356 in 266 s/step, Search-R1-Qwen2.5-7B-Instruct-GRPO scores 0.451 in 333 s/step, and Search-R1-Qwen3-4B-GRPO scores 0.420 in 286 s/step, versus RLFactory-Qwen3-4B-GRPO at 0.458 in 190 s/step and RLFactory-Qwen3-8B-GRPO at 0.463 in 207 s/step - the README states this is "1.5 to 2 times" faster wall-clock than the Search-R1-on-verl baselines at comparable or better NQ score [2].

**When to pick it**: you want multi-turn agentic tool-use training (MCP tool servers, async parallel tool execution, loss-masked tool-call tokens, and an optional model-judge reward worker) layered onto a familiar verl-style Hydra config and launch-script workflow, and you are willing to install and pin a vendored verl 0.5.0 stack yourself [4][8]. It is not a general-purpose RL library on its own terms: its own docs mark the multi-turn interaction logic and the RL training loop itself as unmodified verl [4], its DAPO and SPPO recipe directories are verbatim copies of verl's own recipes with verl's own authorship and reproduction numbers, not RL-Factory's [9][10], and only Qwen models are stated as tested [2]. Choosing between this and vendoring verl directly is a call this card does not make; weigh it against the verl and trl cards.

**Methods it ships**: the repository's own recipe and worker code demonstrates GRPO as its primary trained algorithm (`algorithm.adv_estimator=grpo` in the shipped `main_grpo.sh` launch script) and standard PPO with GAE and a critic (`algorithm.adv_estimator=gae` in `main_ppo.sh`) [8][11], both invoking `verl.trainer.main_ppo` with a `rl_factory_ppo_trainer` Hydra config that overlays RL-Factory's `env:` and `reward_rollout:` blocks on top of verl's own `ppo_trainer.yaml` [12]. `recipe/dapo/` and `recipe/sppo/` are present in the tree, but their own READMEs identify them as verl's upstream DAPO and SPPO implementations verbatim: the DAPO README instructs cloning `volcengine/verl` and checking out a specific verl branch/commit for its reported 52%-AIME-2024 reproduction, crediting Yuxuan Tong and Guangming Sheng [9]; the SPPO README instructs `git clone git@github.com:volcengine/verl.git` and credits Yuhao Yang and Chenyang Zhao as "verl Implementation Authors" for its reported MATH-dataset run [10]. `verl/trainer/fsdp_sft_trainer.py` supplies SFT and is verl's own unmodified file [6]. RL-Factory's own genuinely-added surface is the reward layer: `verl/workers/reward_manager/parallel.py` computes reward either via rule-based scoring (`_compute_score_with_rules`, user-editable, migratable from Search-R1's exact-match scorer) or via a dedicated model-judge vLLM worker group (`reward_rollout_wg`, activated by `reward_rollout.if_use_reward_rollout=True`, extracting a `<score>X.X</score>` tag from a QwQ-32B-style judge's output) [13]; and `environments/env_package/android/reward_evaluator.py` adds an Android GUI-agent `RewardEvaluator` that scores before/after screenshots in either a process-reward ("did the action make progress") or outcome-reward ("was the goal reached") mode via a multimodal LLM judge [14]. None of these methods are marked experimental in the docs read for this card, but there is no separate methods-taxonomy page to recheck the way trl has one - method status here is read off the launch scripts and recipe directories directly [8][9][10][13][14].

**Scale it handles**: single machine (`main_grpo.sh` defaults to `trainer.n_gpus_per_node=8`, `trainer.nnodes=1`) up to multi-node, launched the same way verl is - directly with `python3 -m verl.trainer.main_ppo` under Hydra overrides, with Ray as the underlying worker-placement layer [8][15]. A Megatron variant (`main_grpo_megatron.sh`) is documented as "tested in NNODES=1~4 * 96G H20 GPU" and exposes pipeline/virtual-pipeline/context/tensor/expert/expert-tensor parallelism degrees (`COMMON_PP/VPP/CP/TP/EP/ETP`) for MoE checkpoints such as the example `Qwen/Qwen3-30B-A3B` [16]. Multi-node setup itself is documented only in verl's own generic, unmodified `docs/workers/multinode.rst`, copied into this repo's docs tree: Ray head/worker start commands and a SLURM job template, but no RL-Factory-specific multi-node benchmark was found in the pages read for this card [17]. A separate Android agentic-environment feature (`environments/`) carries its own hardware floor, stated in the repo's own Android setup guide: 64-bit Linux, GLIBC >= 2.31, RAM >= 32 GB (64 GB recommended), disk >= 32 GB free, and CPU virtualization (VT-x/AMD-V) with `/dev/kvm` visible, needed to run eight parallel Android emulator instances [18].

**Install**: no `pip install rl-factory` package exists; the workflow is `git clone`, then a sequence of `pip3 install` commands from the README, which pins `deepspeed==0.16.4`, `flash-attn==2.7.0.post2`, `ray[default]==2.46.0`, `torch==2.6.0`, `transformers==4.51.3`, `tensordict==0.6`, `torchdata==0.10.0`, `mcp==1.9.3`, then separately `vllm==0.8.5`, then `qwen-agent[code_interpreter]`, then `pip3 install -e . --no-deps` [2]. The README states CUDA >= 12.0 (12.4 recommended) and Python >= 3.10 (3.10 recommended); vllm >= 0.8.3 (0.8.5 recommended) [2]. At the shortlisted commit, `install.sh` in the repo root pins a DIFFERENT set for the same packages - `ray==2.42.0`, `transformers==4.48.3`, and an unpinned `torch` with no `mcp` pin at all - so the two install paths in the same commit disagree; a reader should follow one source, not mix them [19]. The README's own Installation link (`docs/rl_factory/en/install.md`) 404s at this commit [2][20]. Licence is Apache-2.0 [21]. Only one GitHub release exists, `v0.1.0`, tagged at commit `216e841a`, published 2025-05-23 [22][23] - far behind the shortlisted commit `d0abc1db` (pushed 2025-12-05) [3], so none of the install pins above are release-pinned; they are read live off the `main` branch content at the shortlisted commit and can move.

**Maintained by**: the Simple-Efficient GitHub account (a User account, not an Organization, per GitHub's own API) [3]; the repository's own Release Log records two rounds of dated feature work - v0.1 (environment/RL decoupling, Qwen3 support) and v0.2, which lists an Android environment addition, a tool-response cache, an eval-script addition, and an "Upgrade to VeRL-0.5" branch merge as already-landed items alongside still-planned items (a WebUI, AsyncLLMEngine support, process reward) [2]. A companion technical report, "RLFactory: A Plug-and-Play Reinforcement Learning Post-Training Framework for LLM Multi-Turn Tool-Use" (arXiv 2509.06980, submitted 2025-08-31, authors including Jiajun Chai and Guojun Yin), is linked from the README's citation block [24][1].

## Quick start

RL-Factory's own tutorial walks through reproducing a Search-R1-style search-agent run, not a minimal toy script [25]. Its three steps, quoted from the tutorial: define a tool by writing an MCP server (an `envs/tools/search.py` file registering a search function with `mcp.server.fastmcp.FastMCP`) and listing it in `envs/configs/mcp_tools.pydata`; define a reward by subclassing `Env` in `envs/search.py` with a `_compute_score_with_rules` scoring function and registering it in `envs/__init__.py`'s `TOOL_ENV_REGISTRY`; then start training [25]. The training command itself, from the README, is:

```bash
bash main_grpo.sh
```

and evaluation/inference is:

```bash
bash main_eval.sh
```

[2]. `main_grpo.sh` is the full runnable script behind that command: it sets `MODEL_PATH`, `REWARD_MODEL_PATH`, `TRAIN_DATA`/`TEST_DATA` environment variables and invokes `python3 -m verl.trainer.main_ppo --config-name=rl_factory_ppo_trainer` with a long list of Hydra overrides (`algorithm.adv_estimator=grpo`, `actor_rollout_ref.env.name=search`, `actor_rollout_ref.env.config_path=envs/configs/mcp_tools.pydata`, ...) [8]. There is no separate minimal single-file example shorter than this in the pages read for this card.

## Start it

- One GPU or one machine: run `main_grpo.sh` (GRPO) or `main_ppo.sh` (PPO+GAE with a critic) as-is; both set `trainer.n_gpus_per_node=8` and `trainer.nnodes=1` by default, so trim those overrides for a smaller box [8][11].
- Multiple nodes: the same `python3 -m verl.trainer.main_ppo` invocation with `trainer.nnodes` raised, on top of a Ray cluster started per verl's own (unmodified, copied-in) multi-node docs page - `ray start --head` on the head node, `ray start --address=<address>` on workers, or the page's SLURM job template [17]. The Megatron-backend variant `main_grpo_megatron.sh` additionally exposes `NNODES`/`NGPUS_PER_NODES` env vars and the `COMMON_PP/VPP/CP/TP/EP/ETP` parallelism-degree overrides, and is stated as tested up to 4 nodes of 8 GPUs each [16].
- Effective batch arithmetic follows verl's own PPO conventions: `main_grpo.sh` sets `data.train_batch_size=128`, `actor_rollout_ref.actor.ppo_mini_batch_size=32`, `.ppo_micro_batch_size_per_gpu=16`, and rollout `n=4` samples per prompt [8]; the Megatron script's defaults are larger (`train_prompt_bsz=512`, `n_resp_per_prompt=16`, `train_prompt_mini_bsz=128`) [16].
- Generation is a separate vLLM-backed rollout inside the same worker group: `main_grpo.sh` sets `actor_rollout_ref.rollout.name=vllm`, `.gpu_memory_utilization=0.75`, `.max_turns=2`, `.free_cache_engine=True` [8]. The optional model-judge reward path runs its OWN vLLM instance with independent knobs - `reward_rollout.rollout.tensor_model_parallel_size`, `.gpu_memory_utilization` (0.65 in `main_grpo.sh`), `.model_name` - only spun up when `reward_rollout.if_use_reward_rollout=True` [8][13].
- Config surface is verl's `ppo_trainer.yaml` Hydra config, overlaid by RL-Factory's own `rl_factory_ppo_trainer.yaml`, which adds an entire `env:` block (tool manager, MCP mode, tool timeout/concurrency limits, a tool-response cache with `single`/other cache modes) and a `reward_rollout:` block, and changes two of verl's own defaults: `actor_rollout_ref.actor.state_masking` from unset to `False` at the config level (though `main_grpo.sh` re-overrides it to `True` at launch) and `rollout.temperature`/`top_p` to 0.7/0.95 [12]. `main_grpo.sh` itself further overrides verl's base defaults at launch: `trainer.logger=['tensorboard']` where verl's own `ppo_trainer.yaml` defaults to `['console', 'wandb']` - a silent change of where anything gets logged at all if you don't notice it - `trainer.val_before_train=False` where verl defaults to `True`, and `trainer.total_epochs=5` where verl defaults to `30` [8][26].
- Out-of-memory first aid is not spelled out as a dedicated troubleshooting page in any file read for this card; the closest documented levers are the same ones exposed at launch - lower `ppo_micro_batch_size_per_gpu`, lower rollout `n` (fewer generations per prompt), and lower `rollout.gpu_memory_utilization` / the reward-rollout's own `gpu_memory_utilization` when the model-judge path is active [8][13].

## Watch it

This section covers only how signals reach you and what they are named; what a metric value MEANS for GRPO or PPO training health lives on those methods' own cards, not here.

- **Enable it**: `trainer.logger` selects the backend(s); `main_grpo.sh` sets it to `['tensorboard']`, so a run started from that script writes only to TensorBoard, not Weights & Biases, even though verl's own base config defaults to `['console', 'wandb']` [8][26]. The tutorial confirms the resulting workflow is `tensorboard --logdir=./` after training [25].
- **Metric names**: RL-Factory's own docs tree carries no dedicated metrics-reference page (only `docs/perf/device_tuning.rst`, `docs/perf/perf_tuning.rst`, and `docs/workers/ray_trainer.rst` touch logging, and all three are verl's own unmodified pages copied into this repo) [27]. `docs/workers/ray_trainer.rst` walks the training-loop source and shows the metric keys it builds: per-step `timing/gen`, `timing/ref`, `timing/values`, `timing/adv`, `timing/update_critic`, `timing/update_actor`, `timing/testing`; validation metrics re-prefixed `val/<key>`; a `compute_data_metrics(batch=batch)` call whose own returned keys are not enumerated on this page; and critic/actor metrics merged in via `reduce_metrics(...meta_info['metrics'])` from each worker's own output [27]. Because this is a walkthrough of illustrative training-loop code rather than a rendered metrics-reference page, it is read here as a partial, code-level list, not a complete one - RL-Factory publishes no page enumerating the full metric set the way trl's `grpo_trainer`/`logging` pages do.
- **Sample-level logging**: not found in any of the docs pages read for this card (tutorial, framework design, tools guide, rewards guide, `ray_trainer.rst`); no `log_completions`-style flag was located.
- **Evaluation during training**: `trainer.test_freq` in the base `ppo_trainer.yaml` controls validation cadence (verl default `-1`, i.e. disabled unless set); `main_grpo.sh` sets `trainer.val_before_train=False`; a validation pass writes into the `val/*` metric namespace shown above [8][26][27].
- **Reward sparsity is a documented, quotable behavior, not a bug**: RL-Factory's own rewards guide states, "In the current version, result reward calculation is still used, i.e., reward is only provided at the last token, with zeros elsewhere" - reward is assigned only at each sequence's last valid response token via a `step_mask`, everywhere else is zero [13].
- **Stopping-rule / health-limit search**: no RL-Factory-published stopping rule, patience field, or divergence-detection threshold was found in the tutorial, framework-design, tools, or rewards pages, nor in `ray_trainer.rst`; RL-Factory adds no stopping mechanism of its own on top of verl's, and verl's own base config carries none in the fields read (`ppo_trainer.yaml`'s validation and save-frequency fields are cadence, not stopping, controls) [8][12][25][26][27].

## Save it

- FSDP-backend checkpoints (verl's own layout, documented on the unmodified, copied-in `docs/checkpoint.rst` page) land per training step at `checkpoints/${trainer.project_name}/${trainer.experiment_name}/global_steps_${i}/actor/`, with per-rank shard files named `model_world_size_{ws}_rank_{r}.pt`, `optim_world_size_{ws}_rank_{r}.pt`, `extra_state_world_size_{ws}_rank_{r}.pt`, plus a HuggingFace-format copy under `actor_huggingface/`; the `critic/` subtree mirrors this when a critic is used [28]. Megatron-backend checkpoints instead nest under `actor/{huggingface, model/mp_rank_xx_yyy/model_states.pt, optim/distrib_optim_pp{a}_tp{b}_cp{c}_dp{d}.pt, rng_states}` [28].
- Retention trades off resumability: the same page states, "Notice that the `checkpoint.contents` field has no effect to FSDP checkpoint except `hf_model`, the other 3 fields are binded together to save and load. We recommend to include `model`, `optimizer` and `extra` all" [28] - dropping optimizer/extra state from that set is the flag that kills a clean resume; the exact YAML location and default of this `checkpoint.contents` field was not found in `ppo_trainer.yaml` in the reading done for this card, so treat the quoted contract as the ground truth and verify the field's current default in your own config before relying on it.
- `main_grpo.sh` sets `trainer.save_freq=20` (verl's own base default is `-1`, meaning no periodic save unless set) [8][26]; the training-loop code shown on `docs/workers/ray_trainer.rst` calls `actor_rollout_wg.save_checkpoint(...)` (and `critic_wg.save_checkpoint(...)` when a critic exists) at that cadence [27].
- Cross-format conversion is a separate tool, not automatic: `scripts/model_merger.py merge --backend {fsdp,megatron} --local_dir <ckpt dir> --target_dir <out dir>` converts an FSDP or Megatron checkpoint into a plain HuggingFace directory, inherited unmodified from verl [28].
- Resume and load-as-HF-model calls specific to RL-Factory's own trainer entry point were not located in the pages read for this card (the tutorial and rewards/tools guides do not cover resume); rely on verl's own `docs/checkpoint.rst` contract above, since RL-Factory's docs state its RL training loop is unmodified verl [4][28].
- No PEFT/LoRA adapter-saving path was found documented in the pages read for this card.
- Whether an evaluator can load a saved checkpoint directly depends on which artifact you point it at: the `actor_huggingface/` (FSDP) or converted `model_merger.py` output (either backend) is a standard HuggingFace directory; the raw sharded `model_world_size_*` / `mp_rank_*` files are not, and need the merger tool first [28].

## Find it in the docs

RL-Factory has no separate hosted docs site; its documentation lives as Markdown/reST files inside the GitHub repository tree, viewable at `https://github.com/Simple-Efficient/RL-Factory/blob/<ref>/<path>` or fetched raw at `https://raw.githubusercontent.com/Simple-Efficient/RL-Factory/<ref>/<path>`, where `<ref>` is a branch (`main`) or a commit SHA - verified working for both forms at this commit while writing this card.

- Four genuinely RL-Factory-authored guides sit under `docs/rl_factory/en/`: `main_tutorial.md` (the Search-R1 reproduction walkthrough used above) [25], `framework_design.md` (the Application/Component/Basic-Layer architecture) [4], `tools.md` (MCP tool definition, parsing, and parallel-execution internals) [30], and `rewards.md` (rule-based vs. model-judge reward, `verify_tool`) [13]. The README's own Installation link, `docs/rl_factory/en/install.md`, is dead (404) at this commit - do not follow it [2][20].
- Everything under `docs/checkpoint.rst`, `docs/start/install.rst`, `docs/start/multinode.rst`, and `docs/workers/ray_trainer.rst` is verl's own generic documentation, copied into this repo largely unmodified; read it as verl documentation living at this repo's path, not as an RL-Factory-specific guide [17][27][28].
- Runnable references beyond the docs: `main_grpo.sh`, `main_ppo.sh`, `main_grpo_megatron.sh`, and `main_eval.sh` at the repo root are the canonical runnable launch scripts [8][11][16]; `recipe/dapo/` and `recipe/sppo/` are runnable but are verl's own recipes, not RL-Factory examples (see Methods it ships) [9][10]; `environments/README_android.md` is a from-scratch environment-setup guide for the Android agent feature, including exact hardware-check commands [18].
- No curated community-tutorials page (comparable to trl's `community_tutorials`) or official MCP documentation-query endpoint was found in the pages read for this card.
- Honest boundary: only Qwen models are stated as tested [2]; the Android environment feature has a documented, non-trivial hardware floor (virtualization, 32-64 GB RAM) separate from the core training stack [18]; searching the repository's 30 most recently closed issues at the time of this reading turned up no issue with a maintainer reply describing a specific failure mode - two relevant-looking titles (#113, "eval script won't start"; #111, "Search-R1 reproduction issue") both show zero comments - so no maintainer-confirmed trap is reported here [29].
