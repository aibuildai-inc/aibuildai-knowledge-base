# RLinf

A Ray-scheduled, dual-backend (FSDP or Megatron) RL infrastructure purpose-built for embodied and agentic AI, with PPO/GRPO-family algorithms and a hybrid execution mode for simulator-in-the-loop training.

RLinf is "a flexible and scalable open-source RL infrastructure designed for Embodied and Agentic AI," where the name's "inf" stands for both "Infrastructure" and "Infinite," meant to signal open-ended, continuously scaling training [1]. It is built by RLinf Contributors under the RLinf Project/organization [2][3], with an accompanying paper on arXiv (2509.15965, cited in the repo but not fetched for this card, since the card does not restate method math) [1]. Its API is workflow/config-driven rather than a trainer-class library: users edit a Hydra YAML recipe (cluster/runner/algorithm/rollout/actor/reward/critic sections) and launch it through a shell entry script per workload (`run_embodiment.sh`, `run_main_grpo_math.sh`, etc.), with training and rollout/generation run as separate Ray-scheduled worker groups [4][5][6]. It lives at https://github.com/RLinf/RLinf [3].

**When to pick it**: embodied RL (robot/simulator-in-the-loop VLA training) or agentic RL where you need Ray-scheduled multi-node scaling and a choice between an FSDP backend ("rapid adaptation to new models and algorithms, ideal for beginners and fast prototyping") and a Megatron backend ("optimized for large-scale training, delivering maximum efficiency for expert users with demanding workloads"), each paired with SGLang or vLLM for generation [7]. RLinf's own README reports its hybrid execution mode reaching "up to 2.434× throughput compared to existing frameworks" for embodied RL [7] — this is the library's own claim, not a third-party or card-deck measurement, so it cannot be treated as a settled cross-framework comparison here; it is reported only as RLinf's own published number. The package's own PyPI classifiers mark it "Development Status :: 2 - Pre-Alpha" [8], a signal worth weighing against more mature sibling libraries for production-critical work.

**Methods it ships**: the docs' own Reference > Algorithms index groups nine algorithms, each with a one-line summary and its own page: PPO, GRPO, DAPO ("Decoupled-clip and dynamic-sampling policy optimization"), Reinforce++ ("An enhanced REINFORCE baseline"), SAC, CrossQ ("Sample-efficient off-policy RL without target networks"), RLPD ("RL with prior data"), IQL (offline RL), and Async PPO ("Asynchronous, pipelined PPO") [9]. The README's own Examples tables use a wider, differently-scoped grouping that also lists SFT variants (full-parameter, LoRA, VLM, DAgger, HG-DAgger), a Reward Model track, and a World Action Model track, and includes a few algorithm names (SAC-Flow, DSRL) that the README cites only to external arXiv papers rather than to an RLinf docs page — treat the Reference > Algorithms index [9] as the canonical, docs-backed method list and the README table as a broader example catalog, not an equivalent taxonomy. This taxonomy can move over time; recheck the live index [9]. This card does not restate any method's objective or math — that lives on each method's own methodology card.

**Scale it handles**: single GPU up to multi-node, all coordinated by Ray (`ray[default]>=2.47.0` at the v0.3 release) [10][11]. Multi-node is started by exporting `RLINF_NODE_RANK` on each node, then either manually running `ray start --head`/`ray start --address=...`, or a shared-filesystem helper script (`ray_utils/start_ray.sh`), followed by `ray status` (or `ray_utils/check_ray.sh <total_gpus>`) to confirm the cluster before launching the same entry script from any joined node [11]. When workers do not share a filesystem, `RLINF_CODE_WORKING_DIR=auto` (or an explicit path) turns on Ray task-level code sync that ships only the `rlinf/` package subtree — not `examples/`, `docs/`, models, or datasets, which must still be reachable via shared storage on every node [11]. Sharding options are backend-specific: FSDP/FSDP2, and Megatron's own tensor/expert/pipeline parallelism (surfaced through the checkpoint convertor's `--tp-size`/`--ep-size`/`--pp-size` flags) [12]. The docs guide gives multi-node as a documented mechanism with a worked 2-node/16-GPU verification example but no published multi-node throughput benchmark on that page [11]; the one published scale number the docs surface is the single-machine, embodied-RL 2.434× hybrid-execution figure noted above, which is not a multi-node benchmark [7].

**Install**: `pip install rlinf` [13]; PyPI version 0.3.0, GitHub release v0.3 published 2026-07-15 (GitHub `published_at` 2026-07-15T13:33:16Z, PyPI upload 2026-07-15T13:54:45, ~21 minutes later — the same release event) [14][15]. Requires Python >= 3.10 [13][15]; Apache-2.0 [3][15]. This card resolves the v0.3 release tag to its commit (0505431899574619da86f551bad70b71e0ea2177) and reads dependency pins there [16] — that commit is NOT the repository's newest push at screening time (c69eecbaa7eb6db06aa3318f103305703f3266c5); the screening commit is ahead of the v0.3 release. ## Quick start

The smallest complete run in the docs' own VLA quickstart is a 4-step, config-then-launch flow (OpenVLA variant), quoted/paraphrased from the Quick Start page [4]:

```bash
# Step 1: download the pretrained model
hf download gen-robot/openvla-7b-rlvla-warmup \
  --local-dir /path/to/model/openvla-7b-rlvla-warmup/

# Step 2: download ManiSkill3 simulator assets (run from <RLinf repo>/rlinf/envs/maniskill)
hf download --repo-type dataset RLinf/maniskill_assets --local-dir ./assets

# Step 3: edit examples/embodiment/config/maniskill_ppo_openvla_quickstart.yaml,
# setting rollout.model.model_path and actor.model.model_path to the
# downloaded checkpoint path

# Step 4: launch
bash examples/embodiment/run_embodiment.sh maniskill_ppo_openvla_quickstart
```

An OpenVLA-OFT variant follows the same shape but downloads a base checkpoint plus a separate LoRA checkpoint (`RLinf/RLinf-OpenVLAOFT-ManiSkill-Base-Main`, `RLinf/RLinf-OpenVLAOFT-ManiSkill-Base-Lora`), sets an additional `actor.model.lora_path` and `actor.model.is_lora: True` in `maniskill_ppo_openvlaoft_quickstart.yaml`, and launches with `bash examples/embodiment/run_embodiment.sh maniskill_ppo_openvlaoft_quickstart` [4]. The cheat-sheet page condenses the same shape for install plus a training call: `bash requirements/install.sh embodied --model openvla --env maniskill_libero` then `bash examples/embodiment/run_embodiment.sh maniskill_ppo_openvla_quickstart`, plus an evaluation call `bash evaluations/run_eval.sh libero/libero_spatial_openpi_pi05_eval` [6].

## Start it

- **One process, one node**: run the entry script directly, e.g. `bash examples/embodiment/run_embodiment.sh maniskill_ppo_openvla_quickstart`; GPU count for that single node is controlled by the config's `cluster.component_placement`, e.g. `actor,env,rollout: 0-3` for 4 GPUs [4][20].
- **Multi-GPU / multi-node** goes through Ray, not a bundled launcher script of its own: export `RLINF_NODE_RANK` on every node (unique, head is usually 0); optionally `RLINF_COMM_NET_DEVICES` to pin the network interface; start the head with `ray start --head --port=6379 --node-ip-address=<head_ip>` and each worker with `ray start --address='<head_ip>:6379'` (or the shared-filesystem helper `bash ray_utils/start_ray.sh` with `RANK=0`/`RANK=1`/...); verify with `ray status` or `bash ray_utils/check_ray.sh <total_gpu_count>`; then launch the same entry script from any node that has joined the cluster, with `cluster.num_nodes` in the YAML matching the actual node count [11]. A documented caveat: Ray freezes the Python interpreter path and environment at `ray start` time, so the virtualenv must be activated and dependencies installed on each node *before* `ray start` — packages installed afterward are invisible to Ray workers [11].
- **Effective batching**: the Config surface exposes `algorithm.group_size` (responses per prompt, group baselines), `rollout.gpu_memory_utilization`, and `runner.val_check_interval`/`save_interval`, but the basic-config reference page does not spell out a single "effective batch size" formula the way a `per_device × devices × grad_accum` trainer-class library would — batch composition is set per-component (`algorithm.val_rollout_batch_size_per_gpu`, `algorithm.logprob_forward_micro_batch_size`) [20].
- **Config surface**: RLinf's own basic-config reference documents `cluster.component_placement` (accepts `all`, a single accelerator index, a comma list, a hyphen range, or a combination, mapping components like `rollout`/`actor` to GPU ranks) [20], `runner.*` (task_type, logger fields, `max_epochs`/`max_steps`, `val_check_interval`, `save_interval` default 50, `seq_length`, `resume_dir`) [20], `algorithm.*` (`group_size` default 2, `loss_type` default `ppo`, `kl_beta` default 0.0, `kl_penalty_type` default `low_var_kl`, `ratio_clip_eps` default 0.2, `adv_type` default `grpo`, `normalize_advantages` default True, `early_stop_imp_ratio` default 5.0 — this stops an individual update early if the importance ratio exceeds the threshold, not a training-level stopping rule) [20], and `rollout.*` (`gpu_memory_utilization` default 0.55, `model.model_path`, `model.model_type`, `recompute_logprobs`) [20]. No changed default is flagged by the docs as a silent hardware assumption on this page beyond the training-precision behavior of the chosen backend, which this reference page does not itself state — check the backend-specific config guides before assuming a precision default.
- **Out-of-memory first aid**: the reference pages read for this card do not carry an OOM-specific troubleshooting section; the closest published knob is `rollout.gpu_memory_utilization` (target fraction of GPU memory reserved for the generation backend, default 0.55) [20], which the FAQ page's CUDA-issues entries also point at indirectly (see Watch it, below, for the FAQ's own troubleshooting text).

## Watch it

This section covers the mechanics only — what each metric means for a given algorithm lives on that method's own methodology card, not here.

- **Enable it**: set `runner.logger.logger_backends` to a YAML list; the default at the docs' own example is `["tensorboard"]`, and the reference table calls out `tensorboard`, `wandb`, `swanlab` as the supported values — a run with no `logger_backends` set produces no external record beyond that default TensorBoard directory [20][21]. Enabling W&B or SwanLab requires a one-time `wandb login` or `swanlab login` per machine; RLinf then "automatically start[s] a new run and stream[s] all metrics" once the backend is listed, and the docs state "All three loggers run in parallel" if listed together [21]. Logs land under `log_path/experiment_name/`, with a subdirectory per active backend: `checkpoints/`, `converted_ckpts/`, `log/`, plus `swanlab/`, `tensorboard/`, `wandb/` for whichever backends are active [21].
- **Metric names**: the Reference > Metrics page defines three namespaces — `train/` (per-actor-update policy/value stats: `train/actor/approx_kl`, `train/actor/clip_fraction`, `train/actor/clipped_ratio`, `train/actor/grad_norm`, `train/actor/lr`, `train/actor/policy_loss`, `train/critic/value_loss`, `train/critic/value_clip_ratio`, `train/critic/explained_variance`, `train/entropy_loss`, `train/loss`), `rollout/` (`rollout/advantages_max`, `rollout/advantages_mean`, `rollout/advantages_min`, `rollout/rewards`), and `env/` (`env/success_once`, `env/episode_len`, `env/return`, `env/reward`) [22]. The page's own opening sentence promises a fourth namespace — "train/, rollout/, env/, and time/" — but no `time/` section is defined anywhere on that page; treat `time/` as advertised but currently undocumented on this page [22]. Separately, the VLA quickstart page's own "View Training Results" section tells readers to watch `rollout/env_info/return` and `rollout/env_info/success_once` in TensorBoard [4] — names that do not match the Reference > Metrics page's `env/return` and `env/success_once` (different prefix, no `env_info` substring on the metrics page). These two official pages have drifted apart; check which naming your installed version actually emits before wiring a dashboard to either spelling.
- **The one metric the docs flag as most informative**: for embodied tasks, the metrics page's own tip singles out `env/success_once` as "the unnormalized episodic success rate," adding that under sparse rewards, "most other env/* values are hard to read directly" — `env/return` is "near-zero until the terminal success step" and `env/reward` is length-normalized in a way that "makes it hard to read as real performance" [22].
- **Evaluation during training**: `runner.val_check_interval` controls how often a validation rollout launches (`-1` disables it) [20]; `algorithm.val_rollout_batch_size_per_gpu` sets its micro-batch [20].
- **Stopping**: the pages read for this card (Reference > Metrics [22], Basic Configuration [20], FAQ [23]) publish no training-level early-stopping rule or patience value. The only threshold-shaped field found is `algorithm.early_stop_imp_ratio`, and its own description scopes it to a single PPO/GRPO update — "Stop an update early if ratios exceed this threshold" [20] — not a run-level stopping criterion.
- **Documented health limits**: the FAQ page's Numerical Precision note states that the default SGLang attention backend is `flashinfer`, and recommends switching to `rollout.attention_backend: triton` "for stability or compatibility" [23] — a published, if narrow, health-related recommendation rather than a hard limit.

## Save it

- **Layout differs by backend.** With Megatron as the training backend, checkpoints land under `output_dir/experiment_name/checkpoints/`; with FSDP/FSDP2, under `log_path/experiment_name/checkpoints/` [24][12]. Both use per-step subdirectories named `global_step_<N>/` [24].
- **Megatron layout**: `global_step_50/actor/iter_0000050/mp_rank_00/{distrib_optim.pt, model_optim_rng.pt}` (per-tensor-parallel-rank shards), plus `latest_checkpointed_iteration.txt` and `data/data.pt` for the dataloader state — the docs describe the optimizer/RNG state as guaranteeing "bit-for-bit reproducibility after resume," and `data.pt` as ensuring "no samples are skipped or repeated" [24].
- **FSDP/FSDP2 layout**: `global_step_10/actor/dcp_checkpoint/__*.distcp` (PyTorch `torch.distributed.checkpoint` shards, each holding "a slice of model parameters, optimizer state, and RNG state") plus `global_step_10/actor/model_state_dict/full_weigths.pt`, a complete (non-sharded) weights file the docs say "can be used to evaluate checkpoints (set `runner.ckpt_path` to this file path), or continue converting to safetensors format" [24][12].
- **Neither raw format is HuggingFace-loadable as-is.** Converting to safetensors is an explicit, separate step: for FSDP, `python convert_dcp_to_pt.py --dcp_path <DCP_PATH> --output_path <OUTPUT_PATH>` (only needed if `model_state_dict/full_weigths.pt` was not already saved by newer code), then edit `rlinf/utils/ckpt_convertor/fsdp_convertor/config/fsdp_model_convertor.yaml` (`convertor.save_path`, `convertor.merge_lora_weighs`, `convertor.ckpt_path`, `model.model_type`, `model.model_path`, `model.is_lora`), then run `python -m rlinf.utils.ckpt_convertor.fsdp_convertor.convert_pt_to_hf --config-path <...> --config-name fsdp_model_convertor` [12]. For Megatron, run `python -m rlinf.utils.ckpt_convertor.megatron_convertor.convert_mg_to_middle_file --load-path <CKPT_PATH_MG> --save-path <CKPT_PATH_MF> --model <name> --tp-size <n> --ep-size <n> --pp-size <n> ...` followed by `convert_middle_file_to_hf`, pointed at a base HuggingFace checkpoint for the tokenizer/config scaffolding [12].
- **Retention**: `runner.save_interval` (default 50 in the docs' YAML examples) sets checkpoint cadence [20][24]; the reference pages read for this card do not document a retention flag that discards optimizer/RNG state to save disk (unlike, e.g., a `save_only_model`-style flag) — every saved `global_step_*` directory carries full optimizer/RNG/dataloader state by default [24].
- **Resume**: edit `runner.resume_dir` to point at the checkpoint directory, e.g. `${runner.output_dir}/${runner.experiment_name}/checkpoints/global_step_10`, and relaunch the same entry script after starting Ray; RLinf auto-detects `resume_dir` and "restores model shards, optimizer, RNG and dataloader state on every node/rank" [24]. One inconsistency on this same docs page worth flagging before trusting either number: the body text says resuming from `global_step_10` with `save_interval=10` means "your next saved checkpoint will be `global_step_20`," but the page's own verification Tip immediately after says "If the next training step starts at 30, then the resume is working well!" — 20 and 30 do not agree within the same worked example, so confirm against your own logged step count rather than either number on this page [24].
- **Loader handoff**: only the converted safetensors output (or, for FSDP, the raw `full_weigths.pt` when set as `runner.ckpt_path` for RLinf's own evaluation path) is confirmed loadable — whether an external evaluator can load either directly is that evaluator's contract, not documented on the pages read for this card; the safetensors conversion output is the safer target for a generic HuggingFace loader [12].

## Find it in the docs

The docs are the live source; this section teaches the lookup pattern, not the content itself.

- **Address pattern**: `https://rlinf.readthedocs.io/en/<version>/rst_source/<section>/<page>.html`. `<version>` is `latest` for the development docs. Verified by fetch (2026-08-11): the version-tag form is `release-v0.3`, not `v0.3` — `en/v0.3/rst_source/start/installation.html` returns 404, while `en/release-v0.3/rst_source/start/installation.html` returns 200 [25]. A Chinese-language mirror exists at `https://rlinf.readthedocs.io/zh-cn/latest/` [1].
- **Page-slug recipes**: algorithm pages live under `rst_source/reference/algorithms/<name>.html` (`ppo`, `grpo`, `dapo`, `reinforce++`, `sac`, `crossq`, `rlpd`, `iql`, `async-ppo`), with `rst_source/reference/algorithms/index.html` as the canonical summary table [9]. Config reference is `rst_source/reference/configuration.html` (overview + per-workload config-file locations) and `rst_source/guides/basic-config.html` (the full parameter tables) [5][20]. Metrics: `rst_source/reference/metrics.html` [22]. Checkpointing: `rst_source/guides/data-checkpoints/checkpoint-conversion.html` and `.../resume.html` [12][24]. Logging: `rst_source/guides/logging.html` [21]. Multi-node: `rst_source/guides/launch-scale/multi-node.html` [11].
- **Question-to-slug map**: "how do I install it" -> `start/installation.html` [19]; "smallest working run" -> `start/vla.html` (the actual quickstart; note `start/quickstart.html` 404s despite being a plausible guess) [4]; "condensed commands" -> `start/cheat-sheet.html` [6]; "what does my config field do" -> `guides/basic-config.html` [20]; "what breaks and why" -> `resources/faq.html` [23].
- **Runnable references beyond the docs**: the repo's `examples/embodiment/`, `examples/reasoning/`, `examples/agent/` trees hold the entry scripts and per-recipe YAML configs cited throughout this card; the README's own Examples tables catalog dozens of simulator/model/algorithm combinations (ManiSkill, LIBERO, BEHAVIOR, MetaWorld and others) with matching example configs, and describe RLinf's example gallery as providing recipes to "reproduce or match state-of-the-art (SOTA) RL results out of the box" [7]. Known-good smoke-test assets are named explicitly in the quickstart: the `RLinf/maniskill_assets` Hub dataset and the `gen-robot/openvla-7b-rlvla-warmup` / `RLinf/RLinf-OpenVLAOFT-ManiSkill-Base-Main` Hub models [4].
- **Community layer / official curation**: the docs' own left-nav lists a "Why RLinf" page and a "Blog" section, including a "Comparison with VeRL" post and system-optimization write-ups (e.g., a BEHAVIOR benchmark post) [21] — these were seen only in the page navigation read for this card, not opened and read in full, so their content is not otherwise reported here; open them directly before relying on any claim inside.
- **MCP**: no official Model Context Protocol endpoint for RLinf was found in the pages fetched for this card (README, FAQ, and configuration reference contain no mention of MCP); the docs site does run a Sphinx-integrated AI search widget (visible in each page's injected `SPHINX_AI_CONFIG` script, backed by a Typesense index), but this is an in-page search tool, not an MCP server, and is not documented as a queryable external endpoint [23].
- **Honest boundary**: the package's own PyPI classifier marks it "Development Status :: 2 - Pre-Alpha" [8]. The Training Pipeline Mode documented for embodied FSDP training is explicitly scoped: it "currently supports only `gae`" for `algorithm.adv_type` and "is not supported for `embodied_sac`, `embodied_dagger`, or `embodied_nft`" [4] — a documented scale/method boundary a reader would otherwise discover only after attempting it with an unsupported algorithm.
