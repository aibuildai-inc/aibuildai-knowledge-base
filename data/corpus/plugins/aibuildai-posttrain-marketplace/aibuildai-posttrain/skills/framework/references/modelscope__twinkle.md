# twinkle

ModelScope's client-server post-training framework: one `TwinkleModel` API that runs unchanged under `torchrun`, Ray, or as an HTTP training service, with a Tinker-compatible client path.

Twinkle is "a lightweight, client-server training framework engineered with modular, high-cohesion interfaces" that, whether run locally with `torchrun` or scaled across Ray clusters, "eliminates infrastructure friction by encapsulating training logic into standardized APIs", and additionally serves as "a robust backend and gateway to enable serverless Training-as-a-Service (TaaS)" through an API surface that is a superset of Tinker's, so a Twinkle service can be driven by either a Tinker client or Twinkle's own client [1]. It is built and maintained by ModelScope [1][2], and its API shape is a small set of abstract `TwinkleModel` methods (`forward`, `forward_backward`, `clip_grad_and_step`, `set_loss`, `set_optimizer`, `save`, `load`, ...) implemented by a concrete `TransformersModel` class, which a training script calls directly inside a plain Python loop; `TransformersModel` additionally exposes its own `resume_from_checkpoint` method beyond the abstract base [3][4]. It lives at https://github.com/modelscope/twinkle [2].

**When to pick it**: post-training on ModelScope-hosted (`ms://`) or Hugging Face (`hf://`) models when you want to write your own training loop against a small, explicit method-call API rather than a config-driven trainer class, and want the same script to scale from one GPU (`torchrun`) to a Ray cluster to a standing HTTP training service without rewriting it [1][5]. The project's own docs draw the contrast explicitly: pick twinkle if you are new to large models and want to see the training mechanics, want to customize models or methods, want to write custom training loops, or need an enterprise/commercial training platform; pick ms-swift instead if you just want to hand over a dataset and train without touching the loop, need broader model/dataset coverage, need Embedding/Reranker/Classification training, need inference/deployment/quantization tooling, or need day-0 support for brand-new model releases [5]. This is the library's own positioning, not an independently measured comparison, and no cross-framework throughput or convergence numbers are published on the pages read for this card.

**Methods it ships**: grouped by the `twinkle.loss` module, which is what a training script imports from [6][7][8]. SFT/pretraining: `CrossEntropy`, `ChunkedCrossEntropy` [7]. DPO: `DPOLoss` [7]. GRPO family (`from twinkle.loss import GRPOLoss`, `clip_range=0.2`, `beta` as the KL-penalty coefficient default `0.01`, settable to 0 to disable, handling both plain and packed sequences): `GRPOLoss` plus five variants sharing the same clip_range/beta signature — `GSPOLoss` (sequence-level importance weights), `SAPOLoss` (adds a sigmoid gate parameter `tau=1.0` on the advantage), `CISPOLoss` (explicit importance-weight clipping), `BNPOLoss` (batch-normalized per-token loss), `DRGRPOLoss` (fixed-denominator normalization) [6]. GKD distillation: `GKDLoss` [7]. Embedding/contrastive: `InfoNCELoss` [7]. An `MSELoss` class is also listed in the Loss component directory, but its method-level use is not documented on the pages read for this card [9]. The README's own tutorial table separately confirms GRPO (Megatron backend), DPO full/LoRA/multi-LoRA (Transformers backend), and GKD on-policy/off-policy (Megatron backend) each have a runnable cookbook script [1]. The taxonomy is a component directory, not a stable list; the live index is at `docs/source_en/Components/Loss/index.rst`, fetched at the v0.5.0 tag for this card [9].

**Scale it handles**: single GPU (`TransformersModel`, no device mesh) up to multi-node, launched through `torchrun` for local multi-GPU (`torchrun --nproc_per_node=N train.py` with `twinkle.initialize(mode='local', global_device_mesh=...)`) or through Ray for multi-node and for separating training GPUs from generation GPUs (`twinkle.initialize(mode='ray', groups=device_groups, ...)`), with FSDP2, DDP, and (in Megatron mode) tensor/pipeline/expert parallelism selected via `DeviceMesh.from_sizes(fsdp_size=..., dp_size=..., tp_size=..., pp_size=..., ep_size=...)` [3][4][10]. A standing HTTP training service is a third mode, started with `twinkle-server launch --config server_config.yaml`, itself running on a pre-started Ray cluster (`ray start --head --num-gpus=N`, then workers with `ray start --address=<head>:6379 --num-gpus=N`, including CPU-only worker nodes for the data processor) [11]. Multi-node is documented as mechanism — per-service `device_group`/`device_mesh` blocks in the server YAML, with components "automatically assigned to different Nodes" [11] — with no published multi-node throughput benchmark on any page read for this card. Hardware support is qualified, not unconditional, and the two docs pages disagree on how: the README's Supported Hardware table gives a blanket "Support for BF16/Flash-Attn may be incomplete in earlier GPUs" note for all Nvidia GPUs [1], while the Installation page's Supported Hardware table names the exclusion concretely — "GPU T4/V100 — Does not support bfloat16, Flash-Attention" — separately from newer cards (A10/A100/H100/RTX), which carry no such note [12]; a reader on T4/V100 should trust the Installation page's specific wording over the README's blanket line.

## Quick start

Smallest complete run, from the Quick-Start guide's Single GPU example, verbatim in shape [16]:

```python
from peft import LoraConfig
from twinkle import get_device_placement, get_logger
from twinkle.dataloader import DataLoader
from twinkle.dataset import Dataset, DatasetMeta
from twinkle.model import TransformersModel
from twinkle.preprocessor import SelfCognitionProcessor

logger = get_logger()

def train():
    dataset = Dataset(dataset_meta=DatasetMeta('ms://swift/self-cognition', data_slice=range(1000)))
    dataset.set_template('Qwen3_5Template', model_id='ms://Qwen/Qwen3.5-4B')
    dataset.map(SelfCognitionProcessor('twinkle LLM', 'ModelScope Community'))
    dataset.encode()
    dataloader = DataLoader(dataset=dataset, batch_size=8)
    model = TransformersModel(model_id='ms://Qwen/Qwen3.5-4B')

    lora_config = LoraConfig(r=8, lora_alpha=32, target_modules='all-linear')
    model.add_adapter_to_model('default', lora_config, gradient_accumulation_steps=2)
    model.set_optimizer(optimizer_cls='AdamW', lr=1e-4)
    model.set_lr_scheduler(scheduler_cls='CosineWarmupScheduler', num_warmup_steps=5, num_training_steps=len(dataloader))
    logger.info(get_device_placement())
    logger.info(model.get_train_configs())
    for step, batch in enumerate(dataloader):
        model.forward_backward(inputs=batch)
        model.clip_grad_and_step()
        if step % 20 == 0:
            metric = model.calculate_metric(is_training=True)
            logger.info(f'Current is step {step} of {len(dataloader)}, metric: {metric}')
    model.save('last-checkpoint')

if __name__ == '__main__':
    train()
```

Run it with plain `python train.py` [16]. To switch to full-parameter training, remove the `add_adapter_to_model` call (and the LoraConfig import); everything else is unchanged [16]. There is no separate CLI subcommand for this path — `twinkle.cli.CLI.from_args()` is a config-resolution helper you call from inside your own script, not a `twinkle train` command [17].

## Start it

- One GPU: the script above, as-is [16].
- Several GPUs on one or more machines via `torchrun`: add `device_mesh = DeviceMesh.from_sizes(fsdp_size=4, dp_size=2)` and `twinkle.initialize(mode='local', global_device_mesh=device_mesh)` before constructing the model, keep the rest of the script identical, and launch with `CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 torchrun --nproc_per_node=8 train.py` [16]. Twinkle's docs state that Ray-related dependencies are not required in this mode [16].
- Cluster / online-RL layout via Ray: start the Ray cluster first — head node `ray stop && CUDA_VISIBLE_DEVICES=0,1,2,3 ray start --head --num-gpus=4 --port=6379`, worker nodes `ray start --address=<head-ip>:6379 --num-gpus=4` (or `--num-gpus=0` for a CPU-only processing node) — then call `twinkle.initialize(mode='ray', groups=device_groups, ...)` and run the script with plain `python train.py` [11][18]. GRPO's separate generation engine is a second `DeviceGroup`/`DeviceMesh` pair passed to `vLLMSampler(..., engine_args={'gpu_memory_utilization': 0.8, 'max_model_len': 4096, 'max_lora_rank': 32, 'enable_lora': True}, device_mesh=sampler_mesh, remote_group='sampler')`, kept on GPUs disjoint from the model's `DeviceGroup`; weights move from trainer to sampler each step via `CheckpointEngineManager(model=model, sampler=sampler)` and `ckpt_manager.sync_weights(merge_and_sync=False)`, and `merge_and_sync=False` requires vLLM's `enable_lora=True`, while `merge_and_sync=True` (or full-parameter training) requires it `False` [18][19]. A standing multi-tenant HTTP service is started separately with `twinkle-server launch --config server_config.yaml` (or `python -m twinkle.server launch --config server_config.yaml`) on top of an already-running Ray cluster, with `check-config` to validate the YAML without starting, `print-config --format yaml|json` to see the normalized config, and `clear persistence` to drop saved server state [11].
- Effective batch, from the Ray GRPO example: `BATCH_SIZE` is the global prompt-level batch; the global completion-level batch is `BATCH_SIZE * num_generations * dp_size`; `MINI_BATCH_SIZE` is the global completion-level mini-batch used per `forward_backward`/`clip_grad_and_step` pair; `MICRO_BATCH_SIZE` is the per-device micro-batch passed as `micro_batch_size=` into `forward_backward`; `GRADIENT_ACCUMULATION_STEPS` additionally scales the dataloader's batch size [18].
- Configuration surface: the `twinkle.cli.CLI` module resolves config from, in increasing priority, dataclass defaults, a `.env` file, `TWINKLE_`-prefixed (or bare) environment variables, a `--config path.yaml` file, then CLI `--key value` overrides, into a typed `Args` object with per-topic groups (`model`/`ModelArgs`, `lora`/`LoraArgs`, `training`/`TrainingArgs`, `optimizer`/`OptimizerArgs`, `loss`/`LossArgs`, `infra`/`InfraArgs`, `rl`/`RLArgs`, `checkpoint`/`CheckpointArgs`, and others) [17]. `TransformersModel`'s own constructor default worth flagging as a hardware assumption is `mixed_precision='bf16'`, which the component docs say is "recommended to keep unchanged if you have GPUs with 30 series or above" — i.e. the default silently assumes a bf16-capable GPU [4].
- Out-of-memory first aid: no dedicated OOM-knobs section is published on the pages read for this card. The mechanism available is lowering `MICRO_BATCH_SIZE` (per-device micro-batch) while raising `GRADIENT_ACCUMULATION_STEPS` to hold the effective batch constant, as shown in the Ray GRPO example's own env-var layout [18]; on the generation side, `vLLMSampler`'s `engine_args` expose vLLM's own `gpu_memory_utilization` (0.8 in the example) as the lever for the sampler's GPU share [18]. `TransformersModel` also exposes `memory_efficient_init` (default `False`), which under FSDP loads full weights on rank 0 only and broadcasts sharded parameters, reducing peak init memory, "only applies to transformers <= 4.57.6; for transformers >= 5.0.0, it may lead to negative performance impact" [4].

## Watch it

This section covers the mechanics only — what a metric value means for GRPO or DPO training health is not restated here.

- **Training-loop metrics** are read by calling `model.calculate_metric(is_training=True)` (or a standalone metric object's `.calculate()`) inside the loop and printing/logging the returned dict yourself — the Quick-Start examples call `logger.info(...)` / `print(...)` directly, with no built-in tracker integration shown on the pages read for this card [16][18].
- **GRPO metric names**, from `GRPOMetric` (params `epsilon=0.2`, `epsilon_high=None` defaulting to `epsilon`, `temperature=1.0`, `top_k_kl=0`, `ignore_index=-100`): `train/policy_confidence`, `train/mean_new_logp`, `train/mean_old_logp`, `train/logp_diff_mean`, `train/approx_kl` (a Schulman K3 estimator of KL(old‖new)), `train/token_kl_max`, `train/token_ratio_max`, `train/entropy`, `train/clip_ratio`, `train/clip_ratio_low` (ratio below `1-epsilon` with negative advantage), `train/clip_ratio_high` (ratio above `1+epsilon` with positive advantage); the `GSPOMetric` and `CISPOMetric` variants report the same family at sequence level / with an unconditional clip rate respectively [20].
- **DPO metric names**, from `DPOMetric`: `chosen_logps`, `rejected_logps`, `ref_chosen_logps`, `ref_rejected_logps`, `rewards/chosen`, `rewards/rejected`, `accuracy`, `margin`; the class does DP-aware aggregation across data-parallel ranks and supports both interleaved and separate chosen/rejected batch formats [21].
- **Generic metrics**: `TrainMetric` reports `lr`, `step`, `gradient_accumulation_steps` and needs no device_mesh/inputs/outputs context; `LossMetric` reports `loss` and `grad_norm` [22][23]. For RL rollouts, `CompletionRewardMetric` reports `generation_time`, `weight_sync_time`, `mean_reward`, `mean_completion_length`, DP-aggregated across ranks, and is what the Ray GRPO example accumulates per-step reward/length data into before printing [24][18].
- **Sample-level generation logging**: no `log_completions`-style dedicated field is documented on the metric or model pages read for this card; the Ray GRPO example itself prints per-step scalar metrics only, not raw completions [18].
- **Evaluation during training**: no `eval_dataset`/`eval_steps`-style built-in evaluation loop is documented on the pages read for this card; the Quick-Start examples show only training loops.
- **Server-side observability** is a separate, opt-in OpenTelemetry pipeline, disabled by default (`telemetry.enabled: false`) [25]. Enabling it means setting `telemetry: {enabled: true, otlp_endpoint: http://localhost:4317}` in `server_config.yaml`, installing `opentelemetry-api opentelemetry-sdk opentelemetry-exporter-otlp`, and pointing an OTel Collector at it (the repo ships a one-command `docker compose up -d` LGTM stack under `cookbook/observability`, explicitly documented as "for local development and demos only" for production) [25]. The provisioned "Twinkle Server Overview" Grafana dashboard covers HTTP request rate and P95 latency per deployment (Gateway/Model/Sampler/Processor), active resource counts (sessions, models, sampling sessions, futures), task queue depth and execution/wait P95, and rate-limit rejections and task completions by status [25]. Metric names are dot-notation OpenTelemetry names that Prometheus ingestion converts to underscores (e.g. `twinkle.http.requests.total` → `twinkle_http_requests_total`); the docs give one explicit health-limit-adjacent warning, quoted: "The `*.active` resource gauges report absolute values. Do NOT wrap them with `rate()` or `increase()`." [25]. The Troubleshooting section on the same page — the search that reached runtime-tuning content, not only a metrics list — documents three named failure shapes with concrete diagnostics: "Grafana shows 'No data'" (check `telemetry.enabled: true`, check for a `Worker telemetry initialized` log line, toggle `debug: true` to confirm spans reach the console); "Twinkle can't reach the Collector" (the `otlp_endpoint` must be reachable from the Twinkle process — use the Docker network address, e.g. `http://twinkle-lgtm:4317`, if containerized); "Resource gauges stuck at 0" (only the cleanup-leader worker pushes resource counts — if gauges stay at 0 past `export_interval_ms × 2` after startup, check logs for a "became cleanup leader" message) [25]. No RL-specific stopping rule, threshold, or patience value is published on any page read for this card (the Quick-Start, TransformersModel, CLI, and metric component pages); shapes of what is logged are published, thresholds for when to stop are not.
- **Traps**: a search of the repository's closed issues (state=closed, most recent 20 items, fetched 2026-08-12) returned zero results that were not themselves pull requests, so no maintainer-confirmed trap from a closed issue is available to cite here.

## Save it

- `model.save(name, output_dir=None, ...)` is the base call; a resumable checkpoint additionally passes `save_optimizer=True` and `consumed_train_samples=dataloader.get_state()['consumed_train_samples']`, which together save weights plus optimizer, scheduler, scaler, RNG state, and a `trainer_state.json` [4][26]. `dataloader.get_state()` returns `{'consumed_train_samples': int}`, tracked automatically by the `DataLoader` [4].
- Resume: `model.resume_from_checkpoint(checkpoint_dir)` restores weights, optimizer, scheduler, scaler and RNG state and returns `{'cur_step', 'consumed_train_samples', 'gradient_accumulation_steps'}`; passing `resume_only_model=True` loads weights only and skips optimizer-state restoration, still returning the progress dict [4]. `dataloader.resume_from_checkpoint(consumed_train_samples)` skips already-consumed samples so training doesn't repeat data [4]. The Quick-Start guide's fuller resume section gives the retention contract as a table over two flags: `RESUME_ONLY_MODEL=False, IGNORE_DATA_SKIP=False` (default) does a full resume with data skipped; `RESUME_ONLY_MODEL=True, IGNORE_DATA_SKIP=False` restores weights only but still skips consumed data, restarting optimization fresh; `RESUME_ONLY_MODEL=True, IGNORE_DATA_SKIP=True` restores weights only and restarts the dataset from the beginning [26] — so `RESUME_ONLY_MODEL=True` is the retention flag that silently drops optimizer/scheduler/RNG state and kills exact-state resume, while the data-skip behavior is a separate, independent choice.
- LoRA vs full-parameter resume differ only in what `model_id` is set to: for a LoRA/adapter run, construct `TransformersModel(model_id='ms://Qwen/Qwen3.5-4B')` (the base model from the hub) and call `resume_from_checkpoint(resume_path)`, since the checkpoint holds only adapter weights plus training state; for full-parameter training, construct `TransformersModel(model_id=resume_path)` directly, since the checkpoint holds the complete weights, then call the same `resume_from_checkpoint(resume_path)` — every subsequent call is identical between the two cases [26][4].
- The docs read for this card do not enumerate the exact file layout inside a checkpoint directory (e.g. which file holds the weights versus `trainer_state.json` versus optimizer state) beyond naming `trainer_state.json` as one of the saved files [4]; inspect a checkpoint directory on disk to confirm the rest.
- RL weight synchronization is a distinct mechanism from on-disk save/load: `CheckpointEngine` (implementations `NCCLCheckpointEngine` for GPU-GPU NCCL transfer and `HCCLCheckpointEngine` for Ascend NPUs) moves weights from the trainer process to the sampler/inference process in memory, not through disk, via `send_weights`/`receive_weights` methods used inside `CheckpointEngineManager.sync_weights(merge_and_sync=...)` [19]. `merge_and_sync=True` merges the LoRA into the base model before sending it and pairs with vLLM's `enable_lora=False`; `merge_and_sync=False` sends only the LoRA weights (used for multi-tenant serving of several LoRAs against one base model) and pairs with vLLM's `enable_lora=True` [19].
- Loader handoff: the docs read for this card do not state whether an external evaluator can load a twinkle checkpoint directory directly via a plain `from_pretrained`-style call, beyond the resume path documented above (constructing a fresh `TransformersModel` with the checkpoint directory as `model_id`); whether that constitutes "loadable by another framework" versus "loadable only by twinkle itself" is not addressed on any page read for this card.
