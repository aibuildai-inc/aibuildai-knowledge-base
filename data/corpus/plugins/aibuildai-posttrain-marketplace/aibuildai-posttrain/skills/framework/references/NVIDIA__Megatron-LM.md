# Megatron-LM / Megatron Core

NVIDIA's GPU-optimized library for training transformer models at scale, from a single GPU up to thousand-GPU clusters, driven through raw torchrun/argparse CLI flags rather than a trainer-class API.

The repository bundles two components: "Megatron-LM" is a reference example with pre-configured training scripts, aimed at research teams and quick experimentation, while "Megatron Core" is the composable, pip-installable library of GPU-optimized building blocks (transformer layers, parallelism, mixed precision) that framework developers build custom training pipelines on [1]. It is built and maintained by NVIDIA [1][2], and its API shape is script-and-flag: a training entry point such as `pretrain_gpt.py` reads its configuration from command-line arguments (`--tensor-model-parallel-size`, `--num-layers`, ...) generated from typed config dataclasses, and is launched with `torchrun` [1][3][4]. A separate NVIDIA-NeMo repository, Megatron Bridge, does Hugging Face <-> Megatron checkpoint conversion and is not covered here [1]. It lives at https://github.com/NVIDIA/Megatron-LM [2].

**When to pick it**: large-scale pretraining or continued pretraining where you need every parallelism axis (tensor, pipeline, context, expert, and sharded data parallelism) and are willing to drive training through CLI flags and a bespoke checkpoint format rather than a Hub-native trainer class; across its published 2B-462B-parameter sweep on H100 clusters the repository reports up to 47% Model FLOP Utilization overall, with MFU rising to 47-48% specifically at the largest model sizes, though no MFU figure is published for the largest individual run (462B parameters on 6,144 H100 GPUs) by itself [1]. Its native RL/post-training path (Megatron-RL, covering GRPO-style training) is explicitly marked by the maintainers as not yet usable by external users as of the README dated in its own source file, so pick this repository for pretraining-scale parallelism, not yet for production RL post-training [5]. This card does not compare it against other post-training libraries; that comparison lives on the card deck.

**Methods it ships**: the base repository ships pretraining and SFT-style fine-tuning through its example scripts (e.g. the multimodal NVLM SFT example, `examples/multimodal/nvlm/sft_blend.yaml`) [6], and adds a native RL package under `megatron/rl/` with a GRPO training example (`examples/rl/`) built around a DAPO-style dataset and reward configuration (`examples/rl/environment_configs/dapo.yaml`) and a `RewardOnlyAgent` that returns rollouts scored by a fixed reward function (`megatron/rl/agent/reward_only_agent.py`) [7][8][9]. The maintainers' own `megatron/rl/README.md`, dated 08/27/2025 in the file, states plainly: "Megatron-RL is actively under development. While it is functional internally at NVIDIA, it is not yet usable by external users because not all required code has been released" [5]. The official docs page for this feature repeats the experimental status and points readers to NeMo RL for a production RL path instead [10]. Method definitions and math (GRPO, DAPO) are not restated here; they live on their own method cards.

**Scale it handles**: single GPU up to multi-node clusters, launched with `torchrun`, combining five parallelism axes documented with their own CLI flags: tensor parallelism (`--tensor-model-parallel-size`), pipeline parallelism (`--pipeline-model-parallel-size`, with virtual pipeline stages via `--num-layers-per-virtual-pipeline-stage`), context parallelism (`--context-parallel-size`) for long sequences, expert parallelism (`--expert-model-parallel-size`) for MoE models, and Megatron-FSDP sharded data parallelism (`--use-megatron-fsdp --data-parallel-sharding-strategy {optim,optim_grads,optim_grads_params}` for ZeRO-1/2/3-style sharding) [11]. The docs give total GPU count as TP x PP x CP x EP x DP and publish worked reference configurations, e.g. LLaMA-3 70B on 64 GPUs at TP=4/PP=4/CP=2/DP=2, and Mixtral 8x7B on 64 GPUs at EP=8 [11]. Multi-node launch itself (rank/master-address env vars for `torchrun --nnodes`) is shown as a shell-script pattern rather than a dedicated multi-node benchmark in the docs read for this card [3][11]; the repository's own large-scale benchmark separately reports the 6,144-H100, 462B-parameter run above (with no MFU figure attached to that run specifically), a weak-scaling result of 47-48% MFU at the largest model sizes, and a strong-scaling test from 96 to 4,608 H100 GPUs where MFU falls from 47% to 42% as communication becomes more exposed [1].

**Install**: `uv pip install megatron-core`, version 0.18.2, released 2026-07-21, resolved from tag `core_v0.18.2` to commit `571370c829ca768fe37244f4e2e7f28d8accc4ab` [12][13]. ## Quick start

The docs' own "Your First Training Run" page gives two runnable forms, both quoted with their CLI invocation [3]:

Minimal example, mock data, 2 GPUs:
```
torchrun --nproc_per_node=2 examples/run_simple_mcore_train_loop.py
```
This script is real code: it builds a small `GPTModel` via `megatron.core.models.gpt.gpt_model`, sets up distributed process groups with `parallel_state.initialize_model_parallel`, and trains against a `MockGPTDataset` [17].

LLaMA-3 8B with FP8 precision, 8 GPUs, mock data by default (real tokenizer/data paths are optional positional arguments):
```
./examples/llama/train_llama3_8b_h100_fp8.sh
```
The script's defaults are `MICRO_BATCH_SIZE=1`, `GLOBAL_BATCH_SIZE=128`, `SEQ_LENGTH=8192`, `TP_SIZE=1`, `PP_SIZE=1`, `CP_SIZE=1`, and it invokes `torchrun` with `--nproc_per_node`, `--nnodes`, `--node_rank`, `--master_addr`, `--master_port` set from environment variables [18].

To train on real data, the docs' data-preparation steps are: write a JSONL file with a `text` field per line, then run `python tools/preprocess_data.py --input data.jsonl --output-prefix processed_data --tokenizer-type HuggingFaceTokenizer --tokenizer-model /path/to/tokenizer.model --workers 8 --append-eod` to produce the `.bin`/`.idx` binary files Megatron expects [3].

## Start it

- One GPU: run the training script directly (`python pretrain_gpt.py ...` or the quick-start scripts above with `--nproc_per_node=1`).
- Several GPUs, one node: `torchrun --nproc_per_node=<N> <script>.py <flags>` [3][18].
- Multiple nodes: the same `torchrun` invocation with `--nnodes`, `--node_rank`, `--master_addr`, `--master_port` set per node, as shown in the LLaMA-3 example script's `DISTRIBUTED_ARGS` block [18]; no ready-made SLURM template was found in the pages read for this card.
- Parallelism is composed with CLI flags rather than a launcher config file: tensor (`--tensor-model-parallel-size`, plus `--sequence-parallel` when combined with TP), pipeline (`--pipeline-model-parallel-size`, `--num-layers-per-virtual-pipeline-stage`), context (`--context-parallel-size`, `--cp-comm-type p2p`), expert (`--expert-model-parallel-size`, `--num-experts`, `--moe-grouped-gemm`; the docs warn that combining EP with TP requires `--sequence-parallel`), and Megatron-FSDP (`--use-megatron-fsdp --data-parallel-sharding-strategy {optim,optim_grads,optim_grads_params} --ckpt-format fsdp_dtensor --init-model-with-meta-device`) [11]. Effective GPU count is `TP x PP x CP x EP x DP`, e.g. the docs' own LLaMA-3 70B example sets TP=4, PP=4, CP=2, DP=2 for 64 GPUs [11]. Effective batch size is `--global-batch-size`, set independently from `--micro-batch-size` and the parallelism degrees.
- Config surface: training behavior is set through typed dataclasses (`TrainingConfig`, `LoggerConfig`, `CheckpointConfig` in `megatron/training/config/training_config.py`) that auto-generate the CLI flags read at the pinned release [13][19]; this repository does not change a framework-level precision default the way a trainer-class library would - precision is selected explicitly per run via flags such as `--bf16`/`--fp8-format`, with no single global default asserted in the pages read for this card.
- OOM first aid: no dedicated "reducing memory" checklist page was found in the docs read for this card; the mechanism-level knobs available are `--micro-batch-size 1` with a larger `--global-batch-size` (relying on gradient accumulation across micro-batches), activation recomputation (`--recompute-granularity` with `--recompute-method`, or `--recompute-activations` for selective recompute - the older `--checkpoint-activations` flag is deprecated in favor of these), and increasing TP/PP/CP/EP degree, or switching on Megatron-FSDP's `optim_grads_params` sharding strategy (ZeRO-3-style) [11][20].

## Watch it

Mechanics only - what a given metric means for a training run is a method-card concern, not covered here.

- **Enable it**: logging is off by default; TensorBoard is enabled by setting `--tensorboard-dir <path>` (`LoggerConfig.tensorboard_dir`, default `None`), and Weights & Biases by setting `--wandb-project`, with `--wandb-exp-name`, `--wandb-save-dir`, `--wandb-entity` as companions (`LoggerConfig.wandb_project`, default `None` - "Ignore wandb by default") [19]. A run with neither flag set writes no metrics record at all beyond stdout. `--log-interval` (default 100) sets the base reporting cadence; `--tensorboard-log-interval` (default 1) sets a separate TensorBoard cadence [19].
- **Metric names**: read directly from the training loop's write call sites in `megatron/training/training.py` at the pinned screening commit [21] - both writers (`get_tensorboard_writer`, `get_wandb_writer`) log the same event stream in parallel, once a writer exists and on the configured `tensorboard_log_interval` cadence. Written whenever a writer is configured, with no separate `LoggerConfig` boolean gating them: `learning-rate` (when a learning rate is available), `batch-size`, `samples vs steps` (wandb only), `skipped-train-samples` (only when `>0`), per-key entries from the loss dictionary (keyed by loss name), and `grad-norm` (whenever a grad norm was computed) [21]. Gated by their own `LoggerConfig` boolean fields, each of which defaults to `False` in `training_config.py` except where noted, and silent unless explicitly turned on: `num-zeros` (`log_num_zeros_in_grad`), `params-norm` (`log_params_norm`), `max_attention_logit` (`log_max_attention_logit`), `world-size` (`log_world_size_to_tensorboard`), `iteration-time` (`log_timers_to_tensorboard`), `loss-scale` (`log_loss_scale_to_tensorboard`, this one defaults `True`), `mem-reserved-bytes`/`mem-allocated-bytes`/`mem-max-allocated-bytes`/`mem-allocated-count` (`log_memory_to_tensorboard`), `throughput` in TFLOP/s/GPU, written to TensorBoard/W&B only when both `log_throughput` AND `log_timers_to_tensorboard` are set (`log_throughput` alone only adds it to the text log line, not to TensorBoard/W&B), and `iter-energy/gpu`/`power/gpu` (`log_energy`) [19][21]. MoE runs add `load_balancing_loss`, `seq_load_balancing_loss`, `global_load_balancing_loss` (when an MoE aux loss coefficient is set) and `z_loss` (when `--moe-z-loss-coeff` is set); multi-token-prediction runs add metrics via `MTPLossLoggingHelper`; sparse-attention runs with a DSA indexer loss add metrics via `DSAIndexerLossLoggingHelper` [21]. RL/GRPO training adds `grpo_collection_iteration` and sequence-packing metrics, plus separate RL token-throughput metrics logged through `rl_utils.log_rl_throughput_metrics` [21]. Other `LoggerConfig` booleans such as `log_l2_norm_grad_to_tensorboard` and `log_validation_ppl_to_tensorboard` name further gated metrics whose exact call sites were not individually traced for this card [19].
- **Validation/eval during training**: `log_validation_ppl_to_tensorboard` writes validation perplexity when validation runs; cadence is set by the `ValidationConfig` dataclass fields `eval_interval` (default `None`) and `eval_iters` (default 100) in `megatron/training/config/training_config.py`, the same auto-generated config surface as `LoggerConfig`/`CheckpointConfig`, not a hand-written argparse flag [19].
- **Sample-level logging of generations**: not found in the pages read for this card (`training.py`'s write call sites, `LoggerConfig`) [19][21]; RL rollout inspection appears to be the responsibility of the `megatron/rl/` package rather than the base logger, and was not read in detail here.
- **Stopping / health limits**: no published early-stopping or reward-threshold field was found in `LoggerConfig`, `TrainingConfig`, or `CheckpointConfig` (`megatron/training/config/training_config.py`) [19] - training stops on `--train-iters`/`--train-samples` or `--exit-interval`/`--exit-duration-in-mins`, not on a metric threshold. This is a shapes-published, thresholds-not-published situation: metric names are documented via the source above, but no RL-specific stopping rule was found in the pages read.

## Save it

- Checkpoints are named by directory, not by a single stateless flag: `get_checkpoint_name()` in `megatron/training/checkpointing.py` builds `<save>/iter_<7-digit-step>/mp_rank_<TP rank>[_<PP rank>][_<EP rank>]/model_optim_rng.pt` (a `release` checkpoint substitutes the literal directory name `release` for the step number) [22]. The distributed optimizer's state is written to a sibling file, `distrib_optim.pt`, alongside `model_optim_rng.pt` [22]. `--save <dir>` and `--save-interval <N>` (also accepted as `--persistent-save-interval`) control where and how often persistent checkpoints are written; `--ckpt-format` selects the on-disk layout, one of `torch`, `torch_dist` (Megatron's own distributed format, the default), `torch_dcp` (`torch.distributed.checkpoint`), or `fsdp_dtensor` (for Megatron-FSDP runs) [19].
- **Retention trades resumability for size, silently**: `--no-save-optim` and `--no-save-rng` (backing fields `save_optim`/`save_rng`, both default True) drop optimizer and RNG state from the saved checkpoint to shrink it; a checkpoint saved this way cannot resume training state, only initialize model weights [19][23]. `--save-retain-interval` governs how many checkpoints are kept before older ones are deleted; the `CheckpointConfig` dataclass also carries a `most_recent_k` retention field, but it is explicitly excluded from the CLI-flag auto-generation list in `arguments.py` and has no other `add_argument` call, so it is a config-dataclass-only field with no exposed CLI flag in this revision [19][20].
- Reload is controlled by the mirrored `--load <dir>`, `--no-load-optim`, `--no-load-rng` flags, plus `--finetune` (loads weights only, resets iteration to 0, skips optimizer/RNG state - documented as assumed when loading a release checkpoint) and `--exit-on-missing-checkpoint` (exit rather than silently random-initialize if `--load` points nowhere) [19][23].
- Resume is the same `--load <dir>` flag pointed at a training run's own `--save` directory; the tracker file `latest_checkpointed_iteration.txt` under that directory records which `iter_*` subdirectory to resume from [22].
- This card found no PEFT/LoRA adapter-only save path in the files read (`checkpointing.py`, `training_config.py`); every checkpoint written by the mechanism above is full-model weights plus (unless suppressed) optimizer and RNG state, not an adapter directory.
- Loader handoff: a `torch`-format `model_optim_rng.pt` is a raw PyTorch state dict inside Megatron's own directory-and-rank-sharded layout, not a Hugging Face `from_pretrained`-loadable directory; converting to/from Hugging Face format is the job of the separate Megatron Bridge repository, not this one [1]. Whether an evaluator can load a given saved checkpoint directly is the loader's contract - check that contract before assuming portability.
