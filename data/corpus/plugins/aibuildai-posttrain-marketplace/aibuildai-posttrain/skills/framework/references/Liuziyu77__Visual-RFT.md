# Visual-RFT

The paper code release for GRPO-based reinforcement fine-tuning of Qwen2-VL/Qwen2.5-VL on visual perception and agentic-tool-use tasks — a fork of Hugging Face's open-r1 with a custom vision-language GRPO trainer, not a general-purpose post-training library.

This repository is the official release for two papers by the same authors, run from one codebase: **Visual-RFT** (Visual Reinforcement Fine-Tuning), described as "the first comprehensive adaptation of Deepseek-R1's RL strategy to the multimodal field," using Qwen2-VL-2/7B with rule-based verifiable rewards inside a GRPO fine-tuning framework for visual perception tasks (open-vocabulary detection, few-shot detection, reasoning grounding, fine-grained classification) [1], and **Visual-ARFT** (Visual Agentic Reinforcement Fine-Tuning), which extends the same GRPO approach to give Qwen2.5-VL agentic web-search and code-execution tool use, evaluated on the authors' own MAT (Multi-modal Agentic Tool Bench) [2]. It is built and maintained by Ziyu Liu, Zeyi Sun, and coauthors at Shanghai AI Laboratory-affiliated groups [1][2], accepted at ICCV 2025 [1]. Both sub-projects share one API shape: a single `torchrun`-launched training script (`grpo.py` or `grpo_agent_search.py`) that takes a Hub or local dataset and a Qwen-VL checkpoint path via `TrlParser`-parsed CLI arguments, built on a `Qwen2VLGRPOTrainer` class that subclasses `transformers.Trainer` directly (not trl's `GRPOTrainer`) [3][4]. It lives at https://github.com/Liuziyu77/Visual-RFT [5].

**When to pick it**: reproducing the Visual-RFT/Visual-ARFT papers' GRPO recipe on Qwen2-VL or Qwen2.5-VL, or as a worked example of rule-based (IoU, confidence, format) reward functions for visual perception GRPO [3]. It is not a general-purpose trainer: the package installs as `open-r1` version `0.1.0.dev0` [6], its `setup.py` is copyrighted "The HuggingFace Team" and its `url` field still points at `github.com/huggingface/open-r1` [6], and its main-loop `reward_funcs` are hardcoded in code rather than left as a CLI choice (`grpo.py` overwrites `script_args.reward_funcs` to `['accuracy_iou','accuracy_confidence','format']` right before building the reward list, ignoring whatever the CLI passed) [3]. For a maintained, general-purpose trl-based GRPO trainer with a wider method menu, weigh trl itself instead (cross-reference; not covered here).

**Methods it ships**: GRPO only, in two task-specialized codepaths that do not share a class hierarchy with each other beyond both subclassing `transformers.Trainer`: `Qwen2VLGRPOTrainer` / `Qwen2VLGRPOVLLMTrainer` in `src/virft/src/open_r1/trainer/grpo_trainer.py` and `vllm_grpo_trainer.py` for Visual-RFT's perception tasks [3][4], and a separate copy of the same trainer files under `Visual-ARFT/src/visual_arft/src/open_r1/trainer/` for the agentic tasks, confirmed present in the repository's git tree at the pinned commit [10]. `vllm_grpo_trainer.py` is selected automatically when the `--use_vllm` training flag is set, giving accelerated rollout generation on the same or separate GPUs [3]. No PPO, DPO, SFT-trainer, or other trl-style method is implemented here — SFT baselines are explicitly delegated to the external LLaMA-Factory project [1]. GRPO itself is not defined on this card; its math lives on the method's own card.

**Scale it handles**: single-GPU `torchrun --nproc_per_node=1` up to one 8-GPU node with `--nnodes=1 --node_rank=0` in the README's own GRPO example and in `src/scripts/example.sh` [7][8]. A separate script, `src/virft/local_scripts/train_aria_moe.sh`, launches `torchrun` with dynamic multi-node arguments read from environment variables (`--nproc_per_node="${ARNOLD_WORKER_GPU}" --nnodes="${ARNOLD_WORKER_NUM}" --node_rank="${ARNOLD_ID}" --master_addr="${METIS_WORKER_0_HOST}"`), an internal cluster-scheduler naming convention (`ARNOLD_*`/`METIS_*`) that a reader outside that cluster must translate to their own scheduler's env vars before it runs [9]. The repo ships 19 shell scripts in total per the git tree [10]; only five of them (the README's inline block, `example.sh`, `2B_base65cate_6k.sh`, `setup.sh`, and `train_aria_moe.sh`) were read for this card, so this card does not claim to know the launch form of the other fourteen. Sharding goes through DeepSpeed, with three ready configs in `src/virft/local_scripts/`: `zero2.json` (stage 2, no offload), `zero3.json` (stage 3, no offload, `stage3_gather_16bit_weights_on_model_save: true`), and `zero3_offload.json` (stage 3 with both optimizer and parameter state offloaded to CPU) [11]. Evaluation scripts for COCO, LVIS, and classification each state they require at least two GPUs [12]. There is no published throughput or memory benchmark for any of these configurations in the docs read for this card — only the mechanism (which DeepSpeed stage or launch form to pass) is documented [12][9].

**Install**: `git clone https://github.com/Liuziyu77/Visual-RFT.git`, then `bash setup.sh` inside a `conda create -n Visual-RFT python=3.10` environment [13]. `setup.py` declares `python_requires=">=3.10.9"` and license `"Apache"` [6] (the repo's GitHub-reported licence is Apache-2.0 [5]); its `install_requires` list (the packages actually installed by `pip install -e .`) floors `deepspeed==0.15.4`, `liger_kernel==0.5.2`, `accelerate>=1.2.1`, `datasets>=3.2.0`, and unpinned `transformers @ git+.../transformers.git@main` and `trl @ git+.../trl.git@main`; `torch>=2.5.1` and `vllm==0.6.6.post1` sit in the broader `_deps` catalogue that `setup.py` draws from but are NOT selected into `install_requires` or the `dev` extra, so plain `pip install -e .` does not pin torch at all, and `setup.sh` never mentions torch either — torch is left entirely unpinned by both files [6][13]. `setup.sh`, which is the actual install path the README instructs a reader to run, DOES override `setup.py`'s declared `vllm==0.6.6.post1` and the `install_requires` version of `transformers`: after the `pip install -e ".[dev]"` step it force-installs `vllm==0.7.2`, then reinstalls `transformers` from the pinned commit `336dc69d63d56f232a183a3e7f52790429b871ef`, plus `wandb==0.18.3`, `tensorboardx`, `qwen_vl_utils`, `torchvision`, and `flash-attn` (via `--no-build-isolation`) [13]. `setup.py`'s own declared `vllm==0.6.6.post1` is therefore never the version that ends up installed by the documented setup path — `setup.sh`'s `vllm==0.7.2` is [13][6]. No CUDA or GPU-hardware minimum is stated anywhere in the fetched setup files; `flash-attn` and `vllm` both carry an implicit CUDA-GPU requirement that the repo does not spell out [13].

**Maintained by**: Ziyu Liu and coauthors [1][2]; the repository's `pushed_at` timestamp is 2025-10-29 [5], matching the README's own News entry for that date announcing that VLMEvalKit added MAT-Bench evaluation support [2] — the most recent dated sign of activity found.

## Quick start

The smallest complete Visual-RFT run, from the README's own GRPO example (dataset and checkpoint paths are placeholders the reader fills in after downloading from the Hub) [7]:

```bash
# There's no need for prolonged training. For a dataset with only a few hundred samples, 200 steps should be sufficient.
export DEBUG_MODE="true"
export LOG_PATH="./debug_log_2b_GRPO_coco_base65cate_6k.txt"

export DATA_PATH=./share_data/ViRFT_COCO_base65   ### your local dataset downloading from huggingface
export CKPT_PATH=./share_models/Qwen2-VL-2B-Instruct    ### Qwen2-VL-2B checkpoint path
export SAVE_PATH=./share_models/Qwen2-VL-2B-Instruct_GRPO_coco_base65cate_6k    ### save path

torchrun --nproc_per_node="8" \
    --nnodes="1" \
    --node_rank="0" \
    --master_addr="127.0.0.1" \
    --master_port="12345" \
    src/open_r1/grpo.py \
    --output_dir ${SAVE_PATH}  \
    --model_name_or_path ${CKPT_PATH} \
    --dataset_name ${DATA_PATH} \
    --deepspeed local_scripts/zero3.json \
    --max_prompt_length 1024 \
    --per_device_train_batch_size 1 \
    --gradient_accumulation_steps 2 \
    --logging_steps 1 \
    --bf16 \
    --report_to wandb \
    --gradient_checkpointing false \
    --attn_implementation flash_attention_2 \
    --max_pixels 401408 \
    --num_train_epochs 1 \
    --run_name Qwen2-VL-2B_GRPO_coco_base65cate_6k \
    --save_steps 100 \
    --save_only_model true \
    --num_generations 8 '
```

(The trailing stray quote after `--num_generations 8` is a typo in the README's own fenced block, reproduced here verbatim [7].)

The repo's own `src/scripts/example.sh` differs from this README block in one field: it sets `--num_train_epochs 2` where the README's inline block above sets `1` — both are real, current files, and this card does not resolve the discrepancy for the reader; check which script you run [7][8]. The README notes: "There's no need for prolonged training. For a dataset with only a few hundred samples, 200 steps should be sufficient" [7]. The Visual-ARFT sibling script (Agentic Search, `Qwen2.5-VL-7B-Instruct`) runs `--num_train_epochs 400` with `--deepspeed .../zero3_offload.json`, and its README states "Running 200 steps on 8 GPUs takes approximately 2 hours" [2].

## Start it

- One GPU: drop `--nproc_per_node` to `1` in the `torchrun` command above; the README's own GRPO block and `src/scripts/example.sh` are otherwise written for 8 GPUs on one node [7][8].
- Multiple GPUs on one node: the `torchrun --nproc_per_node=N --nnodes=1` form shown above, with `--deepspeed` pointed at one of the three ready configs in `src/virft/local_scripts/` (`zero2.json`, `zero3.json`, `zero3_offload.json`) [11][7].
- Multi-node: `src/virft/local_scripts/train_aria_moe.sh` launches `torchrun` with `--nnodes="${ARNOLD_WORKER_NUM}" --node_rank="${ARNOLD_ID}" --master_addr="${METIS_WORKER_0_HOST}" --master_port="${port_in_cmd}"`, reading the rendezvous topology from environment variables set by an internal cluster scheduler rather than hardcoding them; outside that scheduler, set the equivalent variables yourself before launching [9].
- Effective batch is `per_device_train_batch_size (1) x devices x gradient_accumulation_steps (2)` in the README's GRPO block and `example.sh` — retune both together if you change GPU count [7][8].
- Generation-layout choice: setting `--use_vllm` at training time switches `grpo.py`'s trainer class from `Qwen2VLGRPOTrainer` to `Qwen2VLGRPOVLLMTrainer` for vLLM-accelerated rollouts; the exact colocate/server GPU split is implemented in `vllm_grpo_trainer.py`, which was fetched but not read in enough depth for this card to state its default memory-utilization knob with a citation — read that file directly before relying on a specific vLLM memory default [3].
- The GRPO trainer hardcodes generation temperature to 1 regardless of any config value passed in — `self.generation_config = GenerationConfig(..., temperature=1, # HACK ...)` in `grpo_trainer.py` — so a reader cannot change sampling temperature through the CLI [4].
- Config surface is trl's `GRPOConfig` (via `TrlParser((GRPOScriptArguments, GRPOConfig, ModelConfig))` in `grpo.py`) [3]; the KL coefficient `self.beta = args.beta` is read straight from that trl-defined field, so its default is trl's, not this repo's, and is not restated here [4].
- Out-of-memory first aid, from the README's own numbered OOM Tips [7] (identical tips appear in the Visual-ARFT README [2]): (1) pass `--deepspeed .../zero3.json`, and if still short on memory, `.../zero3_offload.json`; (2) lower `--num_generations` (README default 8, can go to 4) — "a smaller `--num_generation` may lead to worse performance"; (3) set `--gradient_checkpointing true` to allow a higher `--num_generations`, at the cost of training speed; (4) reduce training-image resolution if still OOM.
- A maintainer-confirmed threshold on tip (2): in closed issue #146, a user training with `num_generations=2` on 4x RTX 4090 reached only 34.1 accuracy after 800 steps on `coco_8_cate_4_shot`, about 7 points below the paper's reported number; collaborator SunzeY (COLLABORATOR) replied "num_generations很重要，建议8起步" (num_generations matters a lot; start from 8), 2025-03-27 [14].

## Watch it

This section is the mechanics only — what a healthy GRPO reward or KL curve looks like is method-card territory, not repeated here.

- **Enable it**: pass `--report_to wandb`, used in the README's own GRPO block, `example.sh`, the Visual-ARFT README's example, and `train_aria_moe.sh` — the four launch scripts read for this card [7][8][2][9]; `Qwen2VLGRPOTrainer.log()` merges the trainer's own running metrics dict into whatever `logs` transformers' base `Trainer.log()` receives before forwarding to the configured tracker, then clears its metrics buffer [4]. None of those four scripts leaves `--report_to` unset, so none demonstrates the no-tracker default; that default is trl's `GRPOConfig`, not restated here.
- **Metric names**, read directly from `grpo_trainer.py`'s `compute_loss`/`log` methods [4]: `completion_length` (mean generated-token count per group, gathered across processes); one `rewards/<name>` entry per active reward function, where `<name>` is `reward_func.__name__` for a Python reward function (so `rewards/accuracy_reward_iou`, `rewards/accuracy_reward_confidence`, `rewards/format_reward` under the hardcoded default reward set) or the reward model's short Hub name if a `PreTrainedModel` reward is used instead; `reward` (mean of the combined, group-normalized reward); `reward_std` (mean of the per-group reward standard deviation); `kl` (mean per-token KL against the reference model, only meaningful when `beta` is non-zero). This list comes from reading the trainer's own `compute_loss` method, not from a metrics-reference doc page — none exists for this repo.
- **Sample-level logging of generations**: controlled by the `DEBUG_MODE` environment variable and `LOG_PATH`, set in the README's own GRPO block, `example.sh`, and the Visual-ARFT README's example (`export DEBUG_MODE="true"`, `export LOG_PATH="./debug_log_....txt"`) [7][8][2]. The logging itself lives in `grpo.py`'s reward functions, not in the trainer class: `accuracy_reward_iou` and `accuracy_reward_confidence` each check `os.getenv("DEBUG_MODE") == "true"` and, if set, open `LOG_PATH` in append mode and write the reward value, the model's raw completion (`content`), and the ground-truth solution (`sol`); the IoU reward additionally writes the predicted and ground-truth bounding boxes and the computed IoU when a box was parsed out of the completion [3].
- **Evaluation during training**: `grpo.py`'s `main()` conditionally passes `eval_dataset=dataset[script_args.dataset_test_split] if training_args.eval_strategy != "no" else None` into the trainer constructor, so evaluation during training is wired in and gated by the standard trl/transformers `eval_strategy` field (its own default and cadence are not restated here) [3]. The README's separate Evaluation section is a fully separate, post-hoc, offline pipeline (per-benchmark inference scripts plus a notebook), covered under "Find it in the docs" below, and is not this in-loop mechanism.
- **Stopping**: no early-stopping, patience, or reward-threshold field appears in `grpo.py`, `grpo_trainer.py`, or the README's OOM Tips / GRPO sections read for this card — training runs for the configured `--num_train_epochs` or `--max_steps` and stops there; "none found" is the honest answer, and the files searched are `grpo.py`, `grpo_trainer.py`, and README.md [3][4][7].
- A maintainer-published reference number for one specific run: in closed issue #177, collaborator SunzeY (COLLABORATOR) stated that the maintainers' own 8xA100 run reaches "final accuaracy_reward around 1.4" on the LISA reasoning-grounding dataset, and suggested testing the full test set to check whether GPU count affects the result, 2025-04-15 [15].

## Save it

- `--save_steps 100 --save_only_model true` controls checkpoint cadence and content in the README's own GRPO block, `example.sh`, and the Visual-ARFT README's example [7][8][2]; `train_aria_moe.sh` instead passes only `--save_total_limit 8`, leaving `save_steps`/`save_only_model` at their defaults, so this pairing is not universal across every script read for this card [9]. `save_only_model` is a `transformers.TrainingArguments` field (inherited via trl's `GRPOConfig`), not redefined in this repo, and transformers' own docs state its contract plainly: it will "save only model weights, not optimizer/scheduler/RNG state," which "significantly reduces checkpoint size but prevents resuming training from the checkpoint," and "you can only load the model using `from_pretrained` with this option set to `True`" [16] — so the README's own quick-start GRPO command, which passes `--save_only_model true`, produces checkpoints that cannot be resumed with `resume_from_checkpoint` and can only be reloaded for inference, not continued training.
- `main()` in `grpo.py` calls `trainer.save_model(training_args.output_dir)` unconditionally after `trainer.train()` returns, and `trainer.push_to_hub(dataset_name=script_args.dataset_name)` only when `training_args.push_to_hub` is set [3].
- No explicit resume-from-checkpoint call is made in `grpo.py`'s `main()` in the code read for this card — `trainer.train()` is called with no `resume_from_checkpoint` argument, so resuming a run is left to whatever transformers' base `Trainer.train()` does with that argument unset; this repo does not add its own resume logic on top [3].
- Whether an evaluator can load a saved checkpoint directly is the loader's contract, not this repo's — the README's own evaluation scripts (see below) load a saved `model_path` alongside the original `model_base` checkpoint rather than the saved directory alone, e.g. `model_path = "./share_models/Qwen2-VL-2B-Instruct_RL/"` and `model_base = "./share_models/Qwen2-VL-2B-Instruct/"` together in `Qwen2_VL_coco_infere.py` [12] — check the specific evaluation script's loading code before assuming a bare `from_pretrained()` on the output directory is sufficient.

## Find it in the docs

There is no hosted documentation site for this repository — the README, the Visual-ARFT sub-README, and the source files themselves are the only "docs," so this section is a map of the repo rather than a URL-pattern recipe.

- Root README: https://github.com/Liuziyu77/Visual-RFT/blob/main/README.md, covering Visual-RFT setup, training, and evaluation [1][7]. Visual-ARFT README: https://github.com/Liuziyu77/Visual-RFT/blob/main/Visual-ARFT/README.md, covering the agentic sub-project's own setup, dataset, and training script [2].
- Dataset construction on your own data: `dataset/build_dataset.ipynb`, referenced by the README as "you can refere to `dataset/build_dataset.ipynb`. Just provide a `json` file with `image`, `promble` and 'solution'" (the README's own wording, including its typos) [7].
- Ready-made training datasets: the README lists eight Hugging Face dataset repos under the `laolao77` org (e.g. `laolao77/ViRFT_COCO`, `laolao77/ViRFT_COCO_base65`, `laolao77/ViRFT_CLS_flower_4_shot`) plus the separately-hosted LISA reasoning-grounding dataset, collected at https://huggingface.co/collections/laolao77/virft-datasets-67bc271b6f2833eccc0651df [7]. Visual-ARFT's training data is `laolao77/MAT` on the Hub, specifically `MAT/MAT-Training/rft_agent_search_20.json` (63 samples derived from 20 originals) and `MAT/MAT-Training/rft_agent_code_1_2k.json` (3400 samples derived from 1200 originals) [2].
- Evaluation, entirely offline post-training scripts, each documented with exact line numbers to edit in the README rather than as CLI flags: COCO (`coco_evaluation/Qwen2_VL_coco_infere.py` then `coco_evaluation/evaluation.ipynb`, needs at least 2 GPUs, edit lines 167-168 for model paths, 182 for the annotation path, 224 for the image path, 231-241 for evaluated categories, 350 for the results path) [12]; LVIS (`lvis_evaluation/Qwen2_VL_lvis_infere.py` then `lvis_evaluation/lvis_evaluation.ipynb`, same 2-GPU minimum, analogous line numbers 169-170/184/228/234-242/346) [12]; classification (`classification/Qwen2_VL_classification_infere.py`, edit lines 61-63, validation-set sizes stated as Flower102: 2463, Pets37: 3669, Stanford Cars: 8041, FGVC-Aircraft: 3333) [12]. The tree at commit `2ffad63b` also contains a separate `lisa_evaluation/` folder (not mentioned by name in the README's Evaluation section) [10]. Visual-ARFT's evaluation folders are `Visual-ARFT/evaluation_coding/` and `Visual-ARFT/evaluation_search/` on disk [10] — note the Visual-ARFT README's own Evaluation section spells the second one "evaluatin_search," a typo in the README text itself; the actual on-disk folder name is `evaluation_search` [2][10].
- SFT baselines are not implemented in this repo: the README states SFT uses the external LLaMA-Factory project, with only a note that "you can convert the downloaded dataset into the corresponding Qwen SFT format for training" [7].
- Confirmed maintainer replies (closed issues, with author association and date): use `use_cache=True` during inference to fix incorrect/slow outputs — owner Liuziyu77 (OWNER), 2025-04-15, in issue #175, matching the identical tip already given in the README's Classification Evaluation section [17][12]; `num_generations` should start at 8, not lower — collaborator SunzeY (COLLABORATOR), 2025-03-27, in issue #146 [14]; the maintainers' own 8xA100 LISA-grounding run reaches accuracy_reward around 1.4 — collaborator SunzeY (COLLABORATOR), 2025-04-15, in issue #177 [15].
- Honest boundary: this repo implements exactly one method (GRPO) for two base-model families the README documents (Qwen2-VL / Qwen2.5-VL) [1][2], plus a third, undocumented-in-the-README path: a substring-matched `AriaForConditionalGeneration` branch in the trainer's model-loading logic [4] that IS exercised by `src/virft/local_scripts/train_aria_moe.sh` (`--model_name_or_path rhymes-ai/Aria`) [9]; it ships no published stopping rule, as detailed above.
