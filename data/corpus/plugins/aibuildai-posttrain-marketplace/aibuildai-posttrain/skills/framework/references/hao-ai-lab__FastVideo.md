# FastVideo

A YAML-configured post-training and inference framework for video diffusion models - start a single-GPU LoRA or full finetune from a config file, scale the same config to multi-node distillation runs with FSDP-family sharding.

FastVideo describes itself as "a unified post-training and real-time inference framework for accelerated video generation" [1]. It is built and maintained by the Hao AI Lab (hao-ai-lab) [2][3]. The framework centers on two things: `VideoGenerator`, a class that loads a pretrained diffusion pipeline and exposes `.generate_video(prompt, ...)` for inference [1], and a YAML-driven `Trainer` that reads a five-section config (models / method / training / callbacks / pipeline) and runs one of several pluggable training methods via `bash examples/train/run.sh <config.yaml>` [4]. It lives at https://github.com/hao-ai-lab/FastVideo [3].

**When to pick it**: post-training and serving diffusion-based video generators (Wan, Hunyuan, Cosmos, LTX and similar DiT-based video models) when you want one framework to cover full finetuning, LoRA, knowledge distillation, and distribution-matching distillation (DMD2/Self-Forcing) for video-specific attention sparsity (VSA) and sequence-parallel long-video training, all launched from the same YAML config surface [4]. It ships two training code paths side by side: a newer YAML/`Trainer`-based system (`fastvideo/train/`) that the docs say is where new development belongs, and an older CLI-flag system (`fastvideo/training/`) that the docs say "still works for basic fine-tuning" [4]. This card treats the newer system as primary. It is not a general-purpose LLM/text post-training library (contrast trl, verl) - its methods, dataset formats, and pipeline plumbing are video-diffusion-specific.

**Methods it ships**: at the v0.2.0 release tag, the `fastvideo/train/methods/` package holds five working, importable methods, confirmed by reading the release tree at commit `c62a8514b08871bdead5441f4d4d7df09b0848ee` [5]: `FineTuneMethod` and `DiffusionForcingSFTMethod` (DFSFT, per-chunk timesteps for causal/streaming models) under `fine_tuning/`; `DMD2Method` and `SelfForcingMethod` (causal DMD for streaming generation) under `distribution_matching/`; `KDMethod` under `knowledge_distillation/`. All five are re-exported from the top-level `fastvideo.train.methods` package via a lazy shortcut, so `from fastvideo.train.methods import DMD2Method` works directly [6]. The release's `consistency_model/` package is an empty stub (`__all__: list[str] = []`) - no consistency-distillation method ships in this release [7]. At the newer screening commit `1b2b2a0161bc6b3b80158d1fa6380a051c6530c7` (2026-07-28, about 54 days ahead of the v0.2.0 release), three more methods exist that are absent from the release tree: `TeacherForcingSFTMethod`, `StreamingLongTuningMethod`, `AnyFlowMethod`/`AnyFlowPretrainMethod`, and a `CausalConsistencyDistillationMethod` implementation, plus a new `rl/` subpackage holding `DiffusionNFTMethod` [8]. None of `AnyFlowMethod`, `AnyFlowPretrainMethod`, `StreamingLongTuningMethod`, or `DiffusionNFTMethod` is re-exported at the top level even at that commit - they must be imported from their submodule package directly, e.g. `from fastvideo.train.methods.distribution_matching import StreamingLongTuningMethod` or `from fastvideo.train.methods.rl import DiffusionNFTMethod` [9][10]. The legacy `fastvideo/training/` script system separately documents full finetuning and LoRA finetuning (`--lora_training True --lora_rank {16,32,64,128}`) as CLI flags, not as `Trainer` methods [11].

**Scale it handles**: single GPU up to multi-node. The `Trainer` launches via `bash examples/train/run.sh <config.yaml>` (env vars `NUM_GPUS`/`NNODES`/`NODE_RANK`/`MASTER_ADDR`/`MASTER_PORT` override the defaults) or directly via `torchrun --nproc_per_node=<N> fastvideo/train/entrypoint/train.py --config <yaml>` [4]. Sharding is HSDP (`hsdp_replicate_dim` x `hsdp_shard_dim` must equal `num_gpus`; shards parameters within a shard-dim group, replicates across replicate-dim groups), plus separate tensor-parallel (`tp_size`) and sequence-parallel (`sp_size`, splits video frames across GPUs for long videos) dimensions, all set under `training.distributed` [4]. This has a documented mechanism and a published multi-node benchmark: the distillation docs report three completed Sparse-Distill training runs on H200 GPUs - Wan2.1 1.3B on "4 nodes with 32 H200 GPUs" (global batch 64, gradient accumulation 2, LR 1e-5, VSA sparsity 0.8, 4000 steps, ~12 hours); Wan2.1 14B on 8 nodes / 64 H200 GPUs (global batch 64, SP size 4, gradient accumulation 4, LR 1e-5, VSA sparsity 0.9, 3000 steps, ~52 hours, HSDP shard dim 8); Wan2.2 5B on 8 nodes / 64 H200 GPUs (global batch 64, SP size 1, gradient accumulation 1, LR 2e-5, 3000 steps, ~12 hours, HSDP shard dim 1) [12]. Note a discrepancy in that same page: the 1.3B section's prose says "4 nodes with 32 H200 GPUs" but the SLURM script comment reproduced right below it reads "# Multi-node training (8 nodes, 64 GPUs total)" for the same run - the two numbers disagree and the page does not resolve which is correct [12].

**Install**: `pip install fastvideo` (or `uv pip install fastvideo`); version 0.2.0, uploaded to PyPI 2026-06-05 [13]; `requires-python >= 3.10` [13][14]; Apache-2.0 license, per the GitHub repo's own `license` metadata field and the release `pyproject.toml`'s classifier - PyPI's own `license` metadata field is empty for this release [3][14]. At the v0.2.0 release tag (commit `c62a8514b08871bdead5441f4d4d7df09b0848ee`), `pyproject.toml` hard-pins `torch==2.11.0`, `gradio==5.32.0`, and `fastvideo-kernel==0.2.6`, and floors `transformers>=4.57.3`, `diffusers>=0.33.1`, `peft>=0.15.0`, `wandb>=0.21.0`, `ray>=2.49.1`, `datasets>=4.0.0` [14]. Extras include `lint`, `test`, `eval*`, `dev`, `prompt-safety`, `prompt-enhancer`, `streaming`, `dreamverse`, `rocm` (all confirmed in the release `pyproject.toml`'s `[project.optional-dependencies]`) [14]; the live tracker docs also instruct `uv pip install "fastvideo[swanlab]"`, but no `swanlab` extra exists in the v0.2.0 release's dependency list - another live-docs-vs-release-pins gap [16][14]. Hardware/CUDA: not stated in `pyproject.toml` itself; the live installation docs (same 2026-08-11 fetch) list NVIDIA GPUs needing "CUDA 12.6+ with compute capability 7.0+", Apple Silicon needing macOS 14.0+ (M1-M4), and CPU x86_64 for CPU-only inference, and give install commands selecting a PyTorch CUDA build via `UV_TORCH_BACKEND=cu126` or `cu130` [15].

## Quick start

Minimal inference, quoted from the README's own quickstart, a complete program (needs `fastvideo` installed) [1]:

```python
from fastvideo import VideoGenerator

def main():
    generator = VideoGenerator.from_pretrained(
        "FastVideo/FastWan2.1-T2V-1.3B-Diffusers",
        num_gpus=1,
    )
    prompt = "A curious raccoon peers through a vibrant field of yellow sunflowers, its eyes wide with interest."
    video = generator.generate_video(prompt)

if __name__ == "__main__":
    main()
```

Minimal training launch, the new system's documented CLI form - point it at any of the repo's example YAML configs, e.g. a fine-tuning config under `examples/train/configs/fine_tuning/` [4]:

```bash
bash examples/train/run.sh examples/train/configs/fine_tuning/hunyuan/t2v.yaml
```

or directly with `torchrun`:

```bash
torchrun --nproc_per_node=8 fastvideo/train/entrypoint/train.py --config <path/to/config.yaml>
```

The legacy script system's equivalent full-finetune launch is a per-model shell script under `examples/training/finetune/`, e.g. `bash examples/training/finetune/wan_t2v_1.3B/crush_smol/finetune_t2v.sh`, driven by CLI flags such as `--max_train_steps` [11].

## Start it

- One GPU: `bash examples/train/run.sh <config.yaml>` with `NUM_GPUS=1`, or the `torchrun --nproc_per_node=1 ...` form above [4].
- Multiple GPUs / multiple nodes go through the same `run.sh` entrypoint or a raw `torchrun` invocation, controlled by `NUM_GPUS`, `NNODES`, `NODE_RANK`, `MASTER_ADDR`, `MASTER_PORT` env vars, plus the `training.distributed` YAML block's `num_gpus`, `sp_size`, `tp_size`, `hsdp_replicate_dim`, `hsdp_shard_dim` (the last two must multiply to `num_gpus`) [4]. Additional CLI flags on the entrypoint: `--config`, `--resume-from-checkpoint`, `--override-output-dir`, `--dry-run` [4].
- Effective batch size is set through `training.data.train_batch_size` (per-device) and `training.loop.gradient_accumulation_steps`; the published Sparse-Distill runs above used a global batch size of 64 achieved via `sp_size`/gradient-accumulation combinations that differ per model [12].
- Config surface: five top-level YAML sections. `models` (role-based DiT/VAE/text-encoder entries, each with `_target_` class path, `init_from`, `trainable`, `disable_custom_init_weights`, `flow_shift` default 3.0, `enable_gradient_checkpointing_type`, `attention_backend`); `method` (`_target_` plus method-specific keys, e.g. DMD2's `rollout_mode`, `dmd_denoising_steps`, `generator_update_interval` default 1, `real_score_guidance_scale` default 1.0, `fake_score_learning_rate`); `training` (typed sub-blocks `distributed`, `data` - including `data_path`, `num_latent_t`, `num_height`, `num_width`, `num_frames`, `seed` - `optimizer`, `loop`, `checkpoint`, `tracker`, `model`, and a `vsa` block with `sparsity`, `decay_rate`, `decay_interval_steps`); `callbacks` (pluggable hooks, see Watch it); `pipeline` (inference-pipeline overrides used during validation, e.g. `pipeline.dit_config.quant_config: nvfp4_qat_train` for the LTX-2 NVFP4-QAT recipe) [4]. `training.data.data_path` can also be a mapping of dataset path to an integer repeat count to mix datasets with different weights, e.g. `data/zeldam2-clean: 1, data/multi3d_games: 2` roughly doubles exposure to the second dataset [4]. Video diffusion training with `bf16`/`fp16` is not called out as a changed default anywhere in the pages read for this card; the docs give per-role precision through `models.*` rather than a single global flag [4].
- Out-of-memory first aid is spread across two pages with different focuses. The debugging page (2026-07-26) is inference-oriented: it documents `dit_layerwise_offload` (single GPU), `use_fsdp_inference` (multi-GPU), and `vae_cpu_offload` / `image_encoder_cpu_offload` / `text_encoder_cpu_offload`, plus reducing `height`/`width`/`num_frames`/`num_inference_steps` [17]. For training-time OOM, the training-infrastructure and finetune pages point at raising `sp_size` to shard activations across more GPUs and reducing `training.data.num_latent_t` (fewer video latent frames per batch) [4][11].

## Watch it

Mechanics only - what a value means for a given method is not covered here.

- Tracking backends are Weights & Biases (bundled by default) or SwanLab (docs instruct `uv pip install "fastvideo[swanlab]"`, though no `swanlab` extra exists in the v0.2.0 release's `pyproject.toml` [14][16]), selected via YAML `training.tracker.trackers: [wandb]`, `[wandb, swanlab]` (both at once), or `[none]`; leaving `trackers` empty while `project_name` is set defaults to W&B [16]. Tracking runs only on global rank 0; local tracker files also land under `<output_dir>/tracker` [16].
- The `Trainer.run()` loop, read at the screening commit `1b2b2a0161bc6b3b80158d1fa6380a051c6530c7`'s `fastvideo/train/trainer.py` (ahead of the v0.2.0 release, but this loop is not one of the release-absent methods so the code shape should match), logs a metrics dict to the tracker once per step on rank 0 only [18]. Two metric keys are guaranteed present for every method because the loop sets them itself: `step_time_sec` (wall-clock seconds for that step) and `vsa_sparsity` (the current VSA sparsity value) [18]. Beyond those two, each training method's own `loss_map` and `step_metrics` return values become additional logged keys (e.g. a `loss` entry), and the pages read for this card do not carry one central, per-method enumeration of those names the way trl's `grpo_trainer`/`logging` pages do - a reader has to read the method's own class or its config-reference doc page to see them [18].
- Sample-level logging of generations happens through the `ValidationCallback`, which runs inference at `every_steps` (default 100), saves generated videos, and logs them to the tracker; SwanLab specifically only accepts GIF artifacts, so FastVideo auto-converts MP4/in-memory video arrays to GIF using the caller-supplied or source frame rate, falling back to 16 FPS if neither is available [16][4].
- Evaluation during training is the same `ValidationCallback`: config keys are `pipeline_target`, `dataset_file` (a JSON list of prompt strings), `every_steps`, `sampling_steps`, `sampling_timesteps`, `guidance_scale` (default 5.0), `rollout_mode` (`parallel` or `streaming`); it swaps in EMA weights automatically for the forward pass if `EMACallback` is enabled [4].
- No published RL-specific or general training stopping-rule, threshold, or patience value was found. Search performed 2026-08-11 over the three pages most likely to carry one: the training-infrastructure page's Config Format, Checkpointing, and VSA sections list no such field [4]; the debugging/OOM page is inference-focused and carries none [17]; the distillation page's "Key Configuration" blocks give fixed step counts, not a stopping rule [12]. FastVideo publishes shapes (fixed `max_train_steps`) but no adaptive stopping threshold in the sources read.

## Save it

- Checkpoints use PyTorch Distributed Checkpoint (DCP) format, compatible with FSDP/HSDP-sharded state, written under `<output_dir>/checkpoint-<step>/` [4]. Each checkpoint saves model weights for every model role, optimizer states for every role, LR scheduler state, RNG state (for exact resume reproducibility), EMA shadow weights if `EMACallback` is enabled, and the training step counter [4]. The docs read for this card do not enumerate a retention flag that drops optimizer state the way trl's `save_only_model` does; retention is controlled by `training.checkpoint.checkpoints_total_limit` (0 keeps all checkpoints, otherwise a rolling window of the most recent ones) [4].
- Resume: pass `--resume-from-checkpoint <path>` on the CLI (works with both `run.sh` and a direct `torchrun` invocation) or set `training.checkpoint.resume_from_checkpoint` in the YAML; the entrypoint restores model, optimizer, scheduler, and RNG state from that checkpoint [4].
- Reproducibility: the training entrypoint sets `torch.backends.cudnn.benchmark = False`, `torch.backends.cudnn.deterministic = True`, and `torch.use_deterministic_algorithms(True)`, and seeds a shared CUDA RNG generator from `training.data.seed`, threading it through random ops so that ranks within a sequence-parallel group see identical noise [4].
- LoRA (legacy script system): finetuning with `--lora_training True --lora_rank {16,32,64,128}` saves an adapter, not a full model, and the docs recommend a 10-20x higher learning rate for LoRA than for full finetune (1e-4 to 2e-4 vs. 1e-5 to 5e-5) [11]. Companion tooling under `scripts/lora_extraction/`: `extract_lora.py --base <path> --ft <path> --out <adapter.safetensors> --rank <r>` extracts a LoRA adapter from a full finetuned checkpoint against its base; `merge_lora.py --base <path> --adapter <path> --output <path>` merges an adapter back into a full model; `lora_inference_comparison.py --base <path> --ft <path> --adapter <path or NONE> --output-dir <dir> --prompt "<text>" [--compute-ssim] [--compute-lpips]` compares outputs [11]. An adapter directory produced this way is not a full model - it must be merged with `merge_lora.py`, or loaded together with the base model, before it can stand in for one.
- Loader handoff: whether a downstream evaluator can load a saved checkpoint directly depends on that evaluator's own loading contract (a DCP-sharded checkpoint directory is not the same shape as a single-file `from_pretrained`-loadable model); the pages read for this card do not document a `from_pretrained`-style loader for `Trainer` checkpoints separate from the `VideoGenerator.from_pretrained` inference path shown in Quick start [1][4].

- Runnable references beyond the docs: the repo's `examples/train/configs/` tree holds ready YAML configs per method and model (fine_tuning/cosmos, fine_tuning/hunyuan, etc.); `examples/training/finetune/` holds the legacy per-model shell scripts; `examples/distill/` holds the SLURM/shell scripts behind the published multi-node runs above [3][12][11].
- No dedicated curated community-tutorials page exists in the docs (checked against the full `sitemap.xml` page listing, which has no such slug) [19]. The closest analog is the README's "Awesome work using FastVideo or our research projects" list: SGLang (a diffusion-inference fork), DanceGRPO (GRPO for visual generation, code based on FastVideo), SRPO (diffusion-trajectory human-preference alignment, code based on FastVideo), DCM (a dual-expert consistency model, code based on FastVideo), and HY-WorldPlay (an action-conditioned world model trained using FastVideo) [1].
- No official MCP endpoint for querying these docs was found in the sources read for this card.
- One documented trap from a maintainer-facing page rather than an issue thread: the LTX-2 NVFP4-QAT recipe's validation callback needs `callbacks.validation.attn_qat_infer: false` set explicitly on GB200 hardware, because its NVFP4 inference kernel is sm120-only and the callback otherwise silently switches attention backends during validation [4].
- A trap from a closed GitHub issue: VSA (Variable Sparse Attention) training can produce NaN loss during backpropagation when the input's latent height or width is not divisible by the VSA block size of 4 - reported on Wan2.2 low-noise VSA training in issue #886, reproduced by multiple users across several VSA-kernel point releases, and fixed by a collaborator in PR #1094 ("I've submitted a fix in PR #1094 regarding the NaN issue caused by input padding (specifically when the resolution/latent size is not divisible by the VSA block size)"), merged per a second collaborator's follow-up comment [22]. Pick `training.data.num_height`/`num_width` so the resulting latent size divides evenly by 4 when using VSA.
