# Nan-Do/code-search-net-python

455,243 Python functions from the CodeSearchNet corpus, each carrying its original GitHub docstring plus a machine-generated one-line `summary` column, packaged as a single Parquet file.

**Nan-Do/code-search-net-python** takes the Python portion of the CodeSearchNet Corpus - functions with documentation scraped from open-source GitHub repositories, introduced by the CodeSearchNet Challenge paper [1] - and adds a `summary` column generated by Salesforce T5 summarization models over each function's code [2]. The dataset card gives no homepage, paper, or leaderboard of its own beyond that description [2]. It lives at https://huggingface.co/datasets/Nan-Do/code-search-net-python . **The `summary` field is a model generation, not a human annotation, and the card says the annotations were cleaned to remove repetitive or meaningless summaries but that "some may still be present" [2]; the original human-written `docstring` column is served alongside it for comparison.**

**Use it for**: code-to-text SFT pairs - `code` (or `original_string`) as input, `summary` (model-written, one line) or `docstring` (original, human-written, often longer) as target - not a chat format (`chat_dialect: none` on the shortlist row) and not preference data. Maps to the SFT method card as a plain text2text pair, not the implicit-prompt preference format.

**Licence**: Apache-2.0 (`cardData.license` is `apache-2.0`), ungated (`"gated": false`, `"private": false`) [2][3]. The one catch: this Apache-2.0 grant covers Nan-Do's packaging, not necessarily every underlying function - the upstream CodeSearchNet corpus's own card states each example is extracted from a GitHub repository under that repository's own license, and that "example-wise license information is not (yet) included" in the corpus, so a user must determine per-example licensing itself [4].

**Shape**: 455,243 rows, one config (`default`), one nominal Hub split `train`, 13 columns - but a `partition` column inside that split still carries the original CodeSearchNet train/test/valid labels as contiguous blocks [3][5].

**Hold out**: the rows where `partition` is `test` or `valid`. Binary search on the served row order (config `default`, split `train`) found `partition` switches from `train` to `test` at row 410,175 and from `test` to `valid` at row 432,266, giving 410,175 `train` rows, 22,091 `test` rows, and 22,977 `valid` rows out of 455,243 [5].

**Origin**: built by Hugging Face user Nan-Do in May 2023 from the CodeSearchNet Corpus, with `summary` generated by Salesforce T5 summarization models [2]; Hub API at the check date: `downloads` 4,239, `downloadsAllTime` 27,298, `likes` 30 [3].

**Trained-on-by**: no fine-tuned LLM was found tagging this dataset. One Hub repository, `victormay/code-serach-net-python-tokenizer`, tags `datasets: Nan-Do/code-search-net-python` in its metadata, but its card has no other content describing what was trained or how [6].

**Introduced by**: no paper for this derived release - the dataset card [2]; the underlying corpus it summarizes is introduced by Husain et al., "CodeSearchNet Challenge: Evaluating the State of Semantic Code Search" [1].

## Quality

- The `summary` column is machine-generated by Salesforce T5 summarization models, not human-written; the original human-written GitHub docstring survives separately in the `docstring` column [2].
- The card states the generated summaries "have been cleaned to make sure there are no repetitions and/or meaningless summaries", but adds that "some may still be present in the dataset" [2] - a stated, unquantified residual-noise rate.
- No source states a measured contamination rate, duplicate rate, or inter-annotator agreement figure for this release; none is invented here.
- Comparing against the official CodeSearchNet Python config confirms this is a near-copy rather than an exact one: the official `code-search-net/code_search_net` dataset's `python` config serves 412,178 train / 22,176 test / 23,107 validation rows (457,461 total) [9], versus 410,175 / 22,091 / 22,977 (455,243 total) here [5] - 2,218 fewer rows overall, with no source stating why.

## Load it

Single config, single Hub split; filter on `partition` to reconstruct the original CodeSearchNet train/test/valid split before training. Pin the revision this card's numbers were read at (the Hub API's `sha` for `main` at the check date; the repo was last modified 2023-05-15) [3]:

```python
import datasets

REV = "39db91866dd0f251f3b0c7f42c0f85634101df6e"  # main at the check date
ds = datasets.load_dataset("Nan-Do/code-search-net-python", revision=REV, split="train")
train = ds.filter(lambda r: r["partition"] == "train")  # 410,175 rows
test = ds.filter(lambda r: r["partition"] == "test")    # 22,091 rows - hold out
valid = ds.filter(lambda r: r["partition"] == "valid")  # 22,977 rows - hold out
```

**Trap**: the Hub-level split is a single `train` split of all 455,243 rows; loading `split="train"` without also filtering on the `partition` column silently mixes the original CodeSearchNet test and validation functions into training data [3][5].

- `code-search-net/code_search_net` - the official CodeSearchNet Corpus this release derives from, with all six languages; its `python` config alone (412,178/22,176/23,107 across train/test/validation) is close to but not identical to the partition counts in this release, and it has no `summary` column [9][13].

This corpus (the plain code+summary Python release) is the base for the two instructional/reasoning releases above; prefer those two directly if the target training shape is chat-style instruction pairs rather than raw code/summary pairs.

## Where it came from

The base corpus is the Python portion of the CodeSearchNet Corpus, introduced by "CodeSearchNet Challenge: Evaluating the State of Semantic Code Search" [1], which collected functions with documentation from public, non-fork, popularity-ranked open-source GitHub repositories and tokenized them with Treesitter [13]. Nan-Do's card states it built this release in May 2023 by taking that Python portion and adding the `summary` column, generated with Salesforce T5 summarization models over each function's code, then cleaning the generated summaries "to make sure there are no repetitions and/or meaningless summaries" [2]. The card links a Kaggle mirror of the source CodeSearchNet data and a sample notebook of the annotation process on GitHub [2].
