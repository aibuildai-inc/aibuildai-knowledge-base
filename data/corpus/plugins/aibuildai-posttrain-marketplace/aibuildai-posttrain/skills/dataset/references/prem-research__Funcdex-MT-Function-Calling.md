# prem-research/Funcdex-MT-Function-Calling

https://huggingface.co/datasets/prem-research/Funcdex-MT-Function-Calling

1,787 synthetic multi-turn tool-use conversations over 10 individual API toolkits and 5 multi-toolkit bundles, each conversation paired with a JSON tool schema and a rich system prompt.

**Funcdex-MT-Function-Calling** was built by prem-research using their own Funcdex-Synthesizer pipeline, a multi-agent generation process that samples tool combinations, drafts a user scenario and persona, outlines a conversation, and then prompts an LLM (the pipeline recommends `openai/gpt-oss-120b`, served locally) under grammar-constrained decoding to produce a ReAct-style dialogue turn by turn, with a second LLM pass scoring and rejecting conversations below a `tool_use_quality` threshold of 4 [1]. There is no separate paper; the dataset card is the only description [2], and the generation code and method are documented in the Funcdex-Synthesizer repository [1]. Each row is a full multi-turn conversation (user/assistant/tool turns) grounded in a fixed tool schema for one toolkit or toolkit bundle, intended for supervised fine-tuning of tool-calling assistants. **The dataset's own README states two coverage limits: "No Sequential Tool Use" and "No Parallel Tool Use" [2], and the Funcdex-Synthesizer repository separately states its generated conversations are "happy paths" that do not teach error recovery, and that it has no support for parallel function calling [1].**

**Use it for**: multi-turn tool-calling SFT - conversations of interleaved `user`/`assistant`/`tool` turns grounded in a `tools` schema, i.e. the SFT method card's tool-calling chat format. The served schema needs light reshaping before use (see Load it): the conversation column is named `conversations`, not `messages`, and the system prompt is a separate `system` string column rather than a leading message in the turn list.

**Licence**: MIT (`cardData.license` is `"mit"`, repo tag `license:mit`, and the README's License section states "The dataset is licensed under MIT License") [2][3]. No further catch: the licence is ungated (`"gated": false`, `"private": false`) [3].

**Shape**: 1,787 rows in one config (`default`), split `train` 1,487 / `test` 300, four columns (`conversations`, `tools`, `system`, `toolkit`) [4][5].

**Hold out**: `test` (300 rows). The dataset's own README reports the Funcdex-1.7B model's headline numbers - 0.43 Exact Match and 0.81 String Ratio - "on the test set" [2], so this split has already been used to evaluate models the corpus may also compare against; treat it as held out rather than folded into training.

**Origin**: built by prem-research; conversations and system prompts are LLM-generated (the pipeline's recommended generator is `openai/gpt-oss-120b`), not human-written or human-labeled [1]. Hub API at the check date: `downloads` 410, `downloadsAllTime` 4,210, `likes` 3 [3].

**Trained-on-by**: the dataset's own README lists the Funcdex model family as trained on it - Funcdex-1.7B on all toolkits, and ten Funcdex-0.6B toolkit-specific plus five Funcdex-0.6B bundle-specific LoRA models, one per toolkit/bundle value in the `toolkit` column [2]. The Funcdex-Synthesizer repository's own evaluation table shows what that training buys on its Function Call Match metric: Funcdex-1.7B scores 0.81 versus 0.51 for GPT-OSS-120B (medium) - the model the pipeline itself recommends as its conversation generator - 0.59 for GPT-5 (minimal), 0.58 for GPT-5 Mini (medium), and 0.69 for Qwen3-1.7B, the one comparison model whose parameter count (1.7B) matches Funcdex-1.7B's; a 0.12-to-0.30-point gap over these other models, at a fraction of the cost ($5.64 versus $9.32-$205.45 to evaluate 300 conversations) [1]. The source states no other parameter counts for these models, so no wider size comparison is drawn. No adoption outside prem-research's own Funcdex models was found.

**Introduced by**: no paper - the dataset card [2], generated by the Funcdex-Synthesizer codebase [1].

## Quality

- The Funcdex-Synthesizer repository states that a plain LLM-prompting approach without constrained decoding rejects over 90% of generated conversations for violating the pipeline's dialogue-markup rules (every tool call needs a matching tool response, etc.), which is why the pipeline uses grammar-constrained decoding to force valid conversation structure [1].
- Accepted conversations are filtered by an LLM-as-judge score on a `tool_use_quality` rubric, keeping only conversations scoring 4 or above; no absolute pass/fail rate for this dataset's own generation run is stated [1].
- The same repository lists known generation limitations that apply to this release: conversations are "happy paths" that do not teach error recovery, there is no support for parallel function calling (only sequential, multi-step calls), deduplication is done with an embedding model that the authors say produces both false positives and false negatives even with a strong reranker, and tool calls requiring file content produce placeholder arguments like `"content": "<base64-encoded-content>"` [1].
- No source states a measured contamination or duplicate rate for this release; none is invented here.

**Trap**: the README's "Dataset Structure" section and its formatting code both document rows with keys `messages` and `system_prompt` [2], but the columns actually served are `conversations`, `tools`, `system`, and `toolkit` [5][6] - a reader who copies the README's `format_conversation_for_tokenization` function verbatim will hit a `KeyError` on `conversation['messages']` and `conversation['system_prompt']`, since the real row has no such keys. To reuse that function, first rename `conversations` to `messages` and `system` to `system_prompt` (or edit the function to read the real keys), then call `json.loads` on the `tools` string before passing it to `tokenizer.apply_chat_template(..., tools=tools)` as the README's own code does [2]. Within `conversations`, each turn's `tool_calls` field is `None` except on assistant turns that call a tool, where it holds a JSON-encoded string (not a parsed list) that itself needs `json.loads` before use [6].

## Where it came from

prem-research built this dataset with their Funcdex-Synthesizer codebase, which ships roughly 14,000 tool definitions covering more than 600 applications, drawn from Composio.dev's tool-definition catalog [1]. For each conversation, the pipeline samples a combination of tools, generates (or accepts a supplied) natural-language workflow description, deduplicates similar scenarios with an embedding model, generates a user persona, outlines a conversation disposition, and then prompts an LLM under grammar-constrained decoding to produce the dialogue turn by turn in the pipeline's own "Dialog Markup Language"; a separate LLM pass then generates the system prompt and an LLM-as-judge scores and filters the result on a `tool_use_quality` rubric, keeping conversations that score 4 or above [1]. The repository states this generation run took roughly 15 hours on 4 H200 GPUs to produce about 1,700 conversations [1].
