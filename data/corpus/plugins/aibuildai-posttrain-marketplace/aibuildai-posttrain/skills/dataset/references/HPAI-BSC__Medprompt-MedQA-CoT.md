# HPAI-BSC/Medprompt-MedQA-CoT

10,081 chain-of-thought justifications over MedQA multiple-choice questions, generated by Llama-3.1-70B-Instruct and kept only when the model's own final answer matched the ground truth, shipped as a single non-tabular JSON file rather than a Hub-viewer-parsed split.

**Medprompt-MedQA-CoT** was built by HPAI-BSC (Jordi Bayarri Planas, curator) as one of the two retrieval databases behind their Medprompt-style context-retrieval system for medical multiple-choice QA, introduced in "Pareto-Optimized Open-Source LLMs for Healthcare via Context Retrieval" [1]. The paper states the database was built by prompting Llama-3.1-70B-Instruct to generate chain-of-thought answers "for each question in the training set" of MedQA, curated "to ensure the accuracy of the generated responses and their alignment with the ground truth answers" [1]. The dataset card describes the same process at the row level: the model is given the question, the options, and the correct answer, asked to analyze each option and conclude by re-identifying the correct choice, and the card states the dataset "excludes responses where the generated reasoning led to incorrect conclusions" [2]. **This is a retrieval-pool artifact, not a ready SFT set: the card frames it as a "retrieval-augmented database" for retrieval-augmented generation over medical MCQA, not as instruction-tuning data [2], and it is shipped as one JSON file that the Hub row-viewer cannot parse, so `load_dataset` and the datasets-server API both fail on it [3][4].** It lives at https://huggingface.co/datasets/HPAI-BSC/Medprompt-MedQA-CoT .

**Use it for**: as a retrieval pool for a Medprompt-style context-retrieval pipeline over MedQA-style MCQA, per the card's own framing [2]; the CoT-justification text in each row is also usable as reasoning-trace SFT source material, mapping to the SFT method card, but only after building a loader for the file's own nested JSON shape (see Load it) since no split or table is served by the Hub [3][4].

**Licence**: the repository's YAML metadata and tag both record `license: llama3.1` (a custom agreement) [5], but the card body's own "License" line states "Apache 2.0" [2] - the two contradict each other and neither is a Hub gate (`gated: false`) [5].

**Shape**: one file, one JSON object of 10,081 keyed records, no columns or splits recognized by datasets-server (`train` split is declared but empty) [3][4].

**Hold out**: nothing within this file itself is declared as a split to hold out, but the file's own row ids (`medqa_train_llama31_0` … `medqa_train_llama31_10177`) index only MedQA's official train split (10,178 rows) and not its 1,273-row test split [6][7] - evaluate against MedQA's official test split, not against any subset of this file.

**Origin**: HPAI-BSC (Barcelona Supercomputing Center); questions and gold answers from MedQA, CoT justifications generated by Llama-3.1-70B-Instruct [1][2]; 177 downloads, 1 like as of the check date [5].

**Trained-on-by**: none found - the origin paper's own Medprompt experiments are the only documented use of this database [1]; the paper does not name a downstream model fine-tuned on this file, and it is separate from HPAI-BSC's `medqa-cot-llama31` SFT set, which the Aloe-Beta model card cites for training [8].

**Introduced by**: [1].

## Shape

The repository holds three files: `.gitattributes`, `README.md`, and `medprompt_medqa_cot_llama31.json`, the last an LFS-tracked JSON file of 37,397,513 bytes [9]. Neither `datasets-server`'s `/info` nor `/size` endpoint can parse it: both fail with `config-info`/`config-size` errors and report `num_rows: 0` for the `default` config [3][4]; the `/first-rows` endpoint fails with an Arrow type error, because the file's top level is a JSON *object* keyed by UUID strings rather than a list of row records [10]. The shortlist's own `viewer_gap` field records the same thing: "size endpoint serves 0 rows."

Reading the raw file directly (fetched in full, 37,397,513 bytes) shows 10,081 top-level entries, each keyed by a UUID and holding six fields: `id` (a string like `medqa_train_llama31_0`), `question` (string), `correct_answer` (one of the letters `A`-`D`), `options` (an object with exactly four letter-keyed strings in every one of the 10,081 entries), and `generations` (a list, of length exactly 1 in every entry read). Each generation object has `response` (string, 1,064-4,530 characters, average 2,457, across all 10,081 entries), `result` (one of `A`-`D`), `api_calls`, `prompt_tokens`, and `generated_tokens`. Reading every entry in the file, `api_calls`, `prompt_tokens`, and `generated_tokens` are 0 in all 10,081 records - these instrumentation fields were not populated by the generation pipeline. `result` equals `correct_answer` in all 10,081 entries, confirming the card's stated exclusion of incorrect chains [2]. No sequence-length or token statistic beyond character counts is stated by any source for this file.

The `id` field's numeric suffix runs from 0 to 10,177 with 97 gaps (10,081 present of a possible 10,178) - one gap per excluded, incorrect-conclusion chain. This range matches the train split of `GBaker/MedQA-USMLE-4-options`, a Hub mirror of the MedQA-USMLE-4-options benchmark, which datasets-server reports as 10,178 train rows and 1,273 test rows [7]; this file's ids track only that train split's row indices.

## Quality

- The paper states the database was "carefully curated to ensure the accuracy of the generated responses and their alignment with the ground truth answers" [1], and the card states the dataset "excludes responses where the generated reasoning led to incorrect conclusions" [2]; reading all 10,081 entries in the served file confirms every retained `result` equals the row's `correct_answer` - there is no discrepancy between the two.
- No source, including the file itself, states a measured hallucination rate, duplicate rate, or human-agreement figure for the retained chains beyond the final-answer match described above.
- The card and paper give no annotation process beyond model generation plus automated answer-matching; no human review step is stated [1][2].
- The paper's own reference run shows what retrieving from this CoT database buys downstream: for Llama-3.1-8B-Instruct answering MedQA open-ended (not multiple-choice), Table 10 reports 53.34% zero-shot accuracy with no retrieval at all, and 52.40% when given five CoT few-shot examples without the full retrieval pipeline; Table 11 reports the OM-ER ensemble-refining pipeline built on this CoT database (alongside the sibling ToT database) reaching 56.17%-59.31% accuracy across ensemble sizes N=3-20, and Table 12 reports the OM-SR self-reflection pipeline reaching as high as 60.88% at N=15 [1].

## Load it

The file is not a Hub dataset split; `datasets.load_dataset` on the repo returns 0 rows because datasets-server cannot infer a schema from the JSON object [3][4]. Fetch the raw file and load it as a plain JSON object, pinned to the commit this card's numbers were read at:

```python
import json
from huggingface_hub import hf_hub_download

REV = "d121a17c371c24523d1c9b60d07f67f16ebb64aa"  # main at the check date
path = hf_hub_download(
    repo_id="HPAI-BSC/Medprompt-MedQA-CoT",
    filename="medprompt_medqa_cot_llama31.json",
    repo_type="dataset",
    revision=REV,
)
records = json.load(open(path))          # dict of 10,081 UUID-keyed entries
rows = list(records.values())            # each: id, question, correct_answer, options, generations
```

**Trap**: calling `load_dataset("HPAI-BSC/Medprompt-MedQA-CoT")` does not raise - it silently returns an empty dataset (0 rows), because the Hub's streaming JSON reader expects a list of row objects and this file is a single top-level dict; the datasets-server API shows the same silent failure via its `config-size`/`config-info` errors rather than a row count [3][4]. There is no `data_dir` or config argument that fixes this - the file must be downloaded and parsed manually as shown above.

## Neighbors

HPAI-BSC hosts several related MedQA reasoning-trace releases; all row counts below were read live at the check date [11][12].

- `HPAI-BSC/Medprompt-MedQA-ToT` - the Tree-of-Thoughts counterpart from the same paper, built the same way (Llama-3.1-70B-Instruct, MedQA training set, incorrect chains excluded) but with three simulated experts collaborating instead of single-pass CoT [1][13]; it has the same unparseable-by-viewer JSON shape as this file (`config-size` fails, 0 rows served) [12].
- `HPAI-BSC/Medprompt-MedQA-R1` - a reasoning-trace variant generated using DeepSeek-R1 rather than Llama-3.1-70B-Instruct, per its own card [14]; it also fails datasets-server's size/info endpoints the same way [12].
- `HPAI-BSC/medqa-cot-llama31` - a separate release from a different paper, "The Aloe Family Recipe for Open and Specialized Healthcare LLMs" [8], covering all 10,178 MedQA train questions (not filtered to correct-only) reshaped into three columns (`system_prompt`, `question`, `response`) that load cleanly as a Hub dataset with 10,178 rows [15]. Its own card states it was used to train the Aloe-Beta model [8], and its response text for the same first question matches this file's response text for `medqa_train_llama31_0` word for word, confirming the two releases share the same underlying Llama-3.1-70B-Instruct generations even though `medqa-cot-llama31` keeps incorrect chains and drops the retrieval-oriented `options`/`generations` structure [15]. Prefer `medqa-cot-llama31` for direct SFT because it loads as a normal Hub split; prefer this repository only when the Medprompt retrieval-pool shape (with `options` and per-question metadata) is specifically needed.
- `HPAI-BSC/MedQA-Mixtral-CoT` - a Mixtral-8x7B-generated CoT set over the same MedQA train split (10,178 rows, 4 columns), using a different generating model than this file's Llama-3.1-70B-Instruct [11]. No source states which release came first.

## Where it came from

HPAI-BSC (Barcelona Supercomputing Center) built this file for the Medprompt-style context-retrieval system described in "Pareto-Optimized Open-Source LLMs for Healthcare via Context Retrieval" [1]. The underlying multiple-choice questions and gold answers are MedQA's, linked from the card as the `jind11/MedQA` GitHub benchmark [2]. The paper states the database was built by using Llama-3.1-70B-Instruct to generate CoT answers "for each question in the training set", curated for alignment with the ground truth [1]; the card gives the prompt-construction detail at the row level, stating the model was given the question, the options, and the correct answer, then instructed to analyze each option and conclude by re-identifying the correct choice, keeping only chains whose final answer matched the ground truth [2].

## Appendix: screening record

### Screening verdict

Usable as a Medprompt retrieval pool or as reasoning-trace source text, not as a ready-to-load Hub dataset: the file's own row ids track only MedQA's train split, so it carries no eval-overlap risk against the official 1,273-row test split, but the Hub viewer and `load_dataset` cannot parse it, so any use requires downloading and parsing the raw JSON file directly, as shown in Load it.

### The screening row

The row's own note [16]: "A Medprompt retrieval pool of chain-of-thought justifications over MedQA multiple-choice questions, generated by Llama-3.1-70B-Instruct given the question, the options and the correct answer, keeping only chains that reached the right conclusion; shipped as the single file medprompt_medqa_cot_llama31.json under the llama3.1 licence, the card names no MedQA split, and the viewer serves 0 rows." The row carries no flag.
