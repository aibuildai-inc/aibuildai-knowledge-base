# newfacade/LeetCodeDataset

2,869 Python LeetCode problems, each carrying a runnable assert-based test harness, 100+ generated test cases, and a model-generated (query, response) pair for supervised fine-tuning, split by problem release date into a training pool and a held-out temporal test set.

**newfacade/LeetCodeDataset** was built by the authors of "LeetCodeDataset: A Temporal Dataset for Robust Evaluation and Efficient Training of Code LLMs" [1] by curating Python problems from the LeetCode platform, pairing each with a canonical reference solution retrieved from open-source GitHub repositories and re-verified on LeetCode's own execution environment, and augmenting it with a sandboxed test-case generator and a separately model-generated, verified (query, response) pair for chat-style SFT [1]. **The `test` split (228 rows) is a temporal hold-out - the paper defines the cutoff as problems released after July 1, 2024 - built for contamination-free evaluation and must not be used for training; only `train` (2,641 rows) is safe to train on** [1][2]. It lives at https://huggingface.co/datasets/newfacade/LeetCodeDataset .

**Use it for**: chat-style SFT on the `query`/`response` pair (a natural-language coding prompt and a model-generated, LeetCode-verified explanation-plus-solution reply), or code-completion SFT on the `prompt`/`completion` pair (import boilerplate plus a GitHub-sourced canonical solution); the paper also uses each row's `test` function and `input_output` cases as a reward verifier for RL training [1]. Train only on `train`; never on `test`. Maps to the SFT method card (chat pairs) or an RL-with-verifiable-rewards method card (test-case verifier).

**Licence**: Apache-2.0 for the dataset itself (`cardData.license` is `"apache-2.0"`, repo tag `license:apache-2.0`), ungated [3]. The one catch: this covers only the Hub dataset repository; the companion GitHub evaluation-framework repository ships its own `LICENSE` file under the MIT license, so the data and the eval code carry two different licenses [4].

**Shape**: 2,869 rows, one config (`default`), split `train` 2,641 / `test` 228, 14 columns [5][6].

**Hold out**: `test` (228 rows) - the paper's temporal hold-out, defined as problems released after July 1, 2024; do not train on it. `train` (2,641 rows) is the safe part [1][2].

**Origin**: builder newfacade / the paper's authors (Yunhui Xia et al.) [1]; `completion` solutions are GitHub-sourced and LeetCode-verified, `query`/`response` pairs are model-generated and verified, and `test`/`input_output` cases are generated by the paper's own sandboxed pipeline [1]. Hub API at the check date: `downloads` 2,209, `downloadsAllTime` 39,961, `likes` 77 [3].

**Trained-on-by**: the origin paper's own SFT experiment trains directly on this dataset's pre-2024-07 rows [1] (see the deciding number below). The repository's GitHub README lists external work built on it, without independent verification here: a Policy Filtration for RLHF paper on code generation [7], and three other named projects/preprints ("Pre-SFT", "Preference Modeling: Binary Discrimination Versus Imitation Learning", "AdaptiveStep") plus a code repository ("code-r1") [4].

**Introduced by**: [1] (Xia et al.).

## Quality

- Canonical `completion` solutions were pulled from two open-source GitHub repositories and then re-verified for a 100% acceptance rate on LeetCode's own execution environment, establishing them as ground truth [1].
- Test-case inputs were generated purely by prompting an LLM: one-shot prompting for an initial set, then a second prompt aimed at more complex inputs, applied multiple times to construct an average of over 100 inputs per problem, reducing the risk of false positives [1]. A sandboxed execution environment then computed each canonical solution's output on those inputs to produce the test cases [1].
- The `query`/`response` SFT pairs are separately model-generated and verified correct, distinct from the canonical `completion` [1].
- The paper's own contamination check follows LiveCodeBench's temporal methodology: it tracks each evaluated model's monthly pass rate against problem release date, treating a post-release accuracy decline as a contamination signal; it reports no measured contamination rate for this dataset, only the methodology and the resulting monthly pass-rate figure [1].
- The deciding number: on the SFT ablation in the paper's Table 4, training on 2.6K pre-2024-07 rows with model-generated `response` text reaches 79.9% HumanEval / 77.5% MBPP, against only 55.5% / 53.4% for the same 2.6K rows with human-written responses - despite both being verified correct - and against 77.4% / 74.1% for a 111.1K-row baseline (Magicoder Evol-Instruct-110K) [1]. That gap is why the model-generated `response` field, not `completion`, is the one to train an SFT chat model on.

## Load it

Train on `train`, hold out `test`, and pin the revision this card's numbers were read at:

```python
import datasets

REV = "215604aeed660029df7de2fea5a4d7b6ed476a08"  # main at the check date
train = datasets.load_dataset("newfacade/LeetCodeDataset", revision=REV, split="train")  # 2,641 rows
test = datasets.load_dataset("newfacade/LeetCodeDataset", revision=REV, split="test")    # 228 rows - hold out
```

**Trap**: every row, in both splits, also carries a column literally named `test` - a Python `check(candidate)` assert function for grading a submission, unrelated to the `test` split name. Loading `split="test"` and then reading `row["test"]` are two different "tests"; do not confuse a reference to one with the other. A second trap: `input_output` and the `test` column encode the same test cases in two different shapes (a structured input/output list versus an assert-based function) - pick the one your evaluation harness expects rather than concatenating both.

## Where it came from

Built by newfacade / the paper's authors, who as of end of March 2025 identified roughly 3,505 LeetCode problems, of which 3,115 supported Python submissions, and aggregated 2,869 of them into this dataset with metadata, canonical solutions, and generated test cases [1]. Metadata (question id, title-slug task id, description, starter code) was scraped directly from the platform; release dates were estimated from LeetCode's public weekly-contest release schedule and question IDs [1]. Canonical solutions were retrieved from the GitHub repositories `doocs/leetcode` and `walkccc/LeetCode` and re-verified on LeetCode's execution environment [1]. Test-case inputs were generated purely by prompting an LLM (one-shot, then a second prompt for more complex inputs, applied multiple times), and a sandboxed execution environment then computed each canonical solution's output on those inputs to produce the test cases, handling special data structures (binary trees, linked lists) separately [1]. The `query`/`response` SFT pairs were then separately generated by a model and verified for correctness [1].
