# GDPO

GRPO for multi-reward RL with one change: normalize each reward dimension's group statistics separately before summing, instead of summing rewards first and normalizing once, so distinct reward combinations no longer collapse onto the same advantage.

**GDPO** (Group reward-Decoupled Normalization Policy Optimization) is an online-RL method for fine-tuning an LLM policy against several per-response reward signals at once, introduced by Liu et al. (NVIDIA) as a fix to a failure mode they identify in GRPO when GRPO is applied to a summed multi-reward signal [1]. The paper is at https://arxiv.org/abs/2601.05242 [1]. Its parent is GRPO [2], which itself removes PPO's value network and instead uses the group's own reward mean and std as the baseline [2]; GDPO keeps that group-relative structure but moves the mean/std normalization earlier, applying it to each reward component individually rather than to the pre-summed total [1]. The paper's own argument for existing: (1) when GRPO sums rewards before normalizing, distinct rollout reward combinations can map to identical normalized advantages, which the paper calls reward signal collapse, and it traces an observed correctness-reward decline after roughly 400 training steps to this effect [1]; (2) the natural fix of dropping the std term (as Dr.GRPO [3] and DeepSeek-V3.2 do) only slightly increases the count of distinct advantage groups as the number of rollouts or rewards grows [1]; (3) in the paper's own tool-calling ablation, that std-dropping fix converges the correctness reward about as well as GDPO but produces a 0% correct-format rate, versus GDPO's 80.66%, showing the fix does not by itself solve the collapse problem [1].

The paper is new (submitted 2026-01-08) and reports no third-party adoption; its own results are the only evidence available. In the originating paper's tool-calling experiments (Qwen2.5-Instruct, verl, five runs each), GDPO raises average BFCL-v3 accuracy from 30.18% to 32.81% and correct-format ratio from 76.33% to 80.66% for the 1.5B model, and from 39.20% to 40.87% accuracy for the 3B model, versus GRPO [1]. In its math-reasoning experiments (DeepSeek-R1-1.5B/7B, Qwen3-4B-Instruct, DeepScaleR data), GDPO improves DeepSeek-R1-1.5B AIME accuracy from 23.1% to 29.4% while cutting the length-exceed rate from 10.8% to 6.5%, and for DeepSeek-R1-7B cuts AIME length-exceed from 2.1% to 0.2% while lifting accuracy from 50.2% to 53.1% [1]. verl's own advantage-estimator source code independently confirms the paper's identity, citing "GDPO (https://arxiv.org/abs/2601.05242)" by name in its implementation's docstring [4]. Lineage: PPO (2017 [5]) -> GRPO (DeepSeekMath, 2024 [2]) -> GDPO (2026 [1]); the paper positions itself alongside, not as a successor to, GSPO [6], DAPO [7] and GFPO [8], and reuses DAPO's token-mean loss, higher clip thresholds and dynamic sampling, plus DLER's [9] reward-conditioning technique, in its own math/coding training recipe [1]. The right paper was confirmed by matching the exact title against the arXiv abstract page (2601.05242) and independently corroborated by verl's `core_algos.py` docstring, which names the same arXiv ID [1][4].

**When to pick it**: pick GDPO over plain GRPO [2] specifically when training against two or more reward components at once (e.g., accuracy plus format, or accuracy plus a length constraint) and the components can trade off against each other; the paper's own ablation shows that GRPO's single normalization of the summed reward can silently erase which component drove a given total, and that removing GRPO's std term (Dr.GRPO-style [3]) does not fix it, since that variant converged correctness but produced 0% correct-format compliance in the tool-calling task while GDPO reached 80.66% [1]. For a single scalar reward, GDPO reduces to running GRPO per-dimension on one dimension plus an added batch-level whitening step, so plain GRPO [2] is the simpler choice. Nearest offline alternative is DPO [10], which needs preference pairs rather than fresh rollouts and cannot combine several independently-scored reward signals inside a group in the way GDPO does. Nearest online neighbor besides GRPO is DAPO [7], which changes GRPO's clipping and loss aggregation but still normalizes a single summed reward per group, not each reward dimension separately [7].

**Variant of**: GRPO [2], itself a variant of PPO [5].

**Data it needs**: prompts plus, for each rollout, a vector of per-reward-dimension scalar scores (e.g. a format score and a correctness score), not a single pre-summed reward — GDPO's advantage estimator requires the individual reward keys to normalize each one within the group before summing [1][4]. On-policy: each step samples fresh completions from the current policy, exactly as in GRPO [1]. Training scale in the paper's own runs: the tool-calling stage used ToolRL's dataset of 2k ToolACE + 1k Hammer + 1k xLAM samples, 4 rollouts per prompt, batch size 512, for 100 steps [1]; the math/coding stage used the 40k-problem DeepScaleR set (500 steps) or the 24k-problem Eurus-2-RL coding set (400 steps), 16 rollouts per prompt, batch size 512 [1].

**Extra models**: none required by the method's own definition beyond what GRPO needs — no value network, since GDPO only changes how the group-relative advantage is computed from already-scored rollouts [1][4]. A KL-loss term against a frozen reference policy is optional and framework-controlled, not a structural requirement of GDPO's math: verl's actor config disables it by default (`use_kl_loss: false`) [11], and the GDPO paper's own tool-calling run instead applies a reward-shaping KL coefficient of 0.001 via `algorithm.kl_ctrl.kl_coef` rather than the loss-term KL [12]; the paper's math/coding recipe explicitly sets a loss-term `kl_loss_coef` of 0.0005 with `kl_loss_type: mse` [1]. Whichever KL path is used, it needs the same frozen reference-policy forward pass GRPO does. If any reward component is itself a reward model rather than a rule-based scorer, that model is an extra forward-pass cost, but this is a property of the reward source, not of GDPO.

**Shipped by**: verl, as an advantage estimator (`algorithm.adv_estimator=gdpo`, function `compute_gdpo_outcome_advantage` in `verl/trainer/ppo/core_algos.py`, registered under `AdvantageEstimator.GDPO`) [4], paired with a dedicated reward manager (`reward.reward_manager.name=gdpo`, class `GDPORewardManager`) that verl currently ships under its experimental reward-loop path (`verl/experimental/reward_loop/reward_manager/gdpo.py`), not the stable trainer path [13]. verl's example script and README for this recipe are at `examples/gdpo_trainer/` [14][15]. trl also ships it natively inside its existing `GRPOTrainer`, not as a separate trainer: `GRPOConfig(multi_objective_aggregation="normalize_then_sum")` switches the trainer's multi-reward aggregation from its default (sum the weighted per-function rewards, then normalize once) to GDPO's per-function group normalization followed by a batch-level whitening pass, implemented directly in `_generate_and_score_completions` [16]. trl's own config docstring names this option as the paper's own suggested approach [16]. Separately, the paper's authors also publish an unofficial, paper-repository implementation patched into trl 0.18.0 (`NVlabs/GDPO/trl-GDPO`) [19], but that repo is not needed given trl's native support.

## How it works

Per step: sample a group of G completions per prompt from the current policy; score each completion on each of n reward dimensions; normalize each reward dimension within its own group; sum the per-dimension normalized advantages; whiten the summed advantage across the whole training batch; then run GRPO's clipped surrogate update on that final advantage [1].

**GRPO's summed-reward baseline (what GDPO replaces)**. For question $q_i$ with $G$ sampled responses and $n$ reward objectives, GRPO first sums the objectives per response (Eq. 1) [1]:

$$ r_{\text{sum}}^{(i,j)} = r_1^{(i,j)} + \cdots + r_n^{(i,j)} $$

then normalizes the summed reward within the group (Eq. 2) [1]:

$$ A_{\text{sum}}^{(i,j)} = \frac{r_{\text{sum}}^{(i,j)} - \operatorname{mean}\{r_{\text{sum}}^{(i,1)},\ldots,r_{\text{sum}}^{(i,G)}\}}{\operatorname{std}\{r_{\text{sum}}^{(i,1)},\ldots,r_{\text{sum}}^{(i,G)}\}} $$

The paper's own worked example: with two binary rewards ($r_1, r_2 \in \{0,1\}$) and two rollouts per group, the six possible unordered reward-pair combinations produce only two distinct values of $A_{\text{sum}}$ under this formula — $(0,1)$, $(0,2)$ and $(1,2)$ (using total-reward notation) all normalize to $(-0.7071, 0.7071)$, while $(0,0)$, $(1,1)$ and $(2,2)$ all normalize to $(0,0)$ — even though a total of 2 should signal a stronger response than a total of 1 [1].

**GDPO's per-dimension normalization**. Instead of summing first, GDPO normalizes each reward dimension $k$ within the group before combining them (Eq. 4) [1]:

$$ A_k^{(i,j)} = \frac{r_k^{(i,j)} - \operatorname{mean}\{r_k^{(i,1)},\ldots,r_k^{(i,G)}\}}{\operatorname{std}\{r_k^{(i,1)},\ldots,r_k^{(i,G)}\}}, \quad k = 1,\ldots,n $$

then sums the per-dimension advantages, unweighted in the base recipe (Eq. 5) [1]:

$$ A_{\text{sum}}^{(i,j)} = A_1^{(i,j)} + \cdots + A_n^{(i,j)} $$

then applies a second, batch-level whitening pass across every rollout in the training batch (not just the group) so the final advantage's scale does not grow as more reward dimensions are added (Eq. 6) [1]:

$$ \hat{A}_{\text{sum}}^{(i,j)} = \frac{A_{\text{sum}}^{(i,j)} - \operatorname{mean}\{A_{\text{sum}}^{(i',j')} \mid i' \in D_{\text{Batch}}, j'=1,\ldots,G\}}{\operatorname{std}\{A_{\text{sum}}^{(i',j')} \mid i' \in D_{\text{Batch}}, j'=1,\ldots,G\} + \epsilon} $$

Worked example continuing the paper's own two-reward, two-rollout case: normalizing $r_1$ and $r_2$ separately (before batch-level whitening) turns the combination $(0,1)$ into per-dimension advantages that sum to $(-0.7071, 0.7071)$, and turns $(0,2)$ into $(-1.4142, 1.4142)$ — now distinguishable, where GRPO's summed normalization gave both the same value [1]. The paper reports (Fig. 3) that as the number of rollouts or reward dimensions grows, GDPO retains substantially more distinct advantage values than either GRPO or the std-dropped GRPO variant, though it does not publish the exact counts in the text, only the qualitative trend [1].

**Policy update**. GDPO plugs $\hat{A}_{\text{sum}}^{(i,j)}$ into the same clipped surrogate objective GRPO uses [1][2]:

$$ \mathcal{J}(\theta) = \mathbb{E}\left[\frac{1}{G}\sum_{j=1}^{G}\frac{1}{|o_j|}\sum_{t=1}^{|o_j|} \min\left(s_{i,t}(\theta)\,\hat{A}_{\text{sum}}^{(i,j)},\; \operatorname{clip}(s_{i,t}(\theta), 1-\epsilon, 1+\epsilon)\,\hat{A}_{\text{sum}}^{(i,j)}\right)\right] $$

where $s_{i,t}(\theta) = \pi_\theta(o_j^t|q,o_j^{<t}) / \pi_{\theta_{\text{old}}}(o_j^t|q,o_j^{<t})$; the paper states this formulation omits the KL term for clarity [1]. verl's implementation computes each dimension's normalized score by calling its own GRPO advantage function once per reward key, sums the (optionally weighted) results, and applies `masked_whiten` for the batch-level step — matching the paper's three-step structure [4].

**Priority weighting and reward conditioning**. Section 3.2 extends the base recipe with an optional per-dimension weight $w_k$, applied to the same normalized advantages as an alternative to Eq. 5 (Eq. 7) [1]:

$$ A_{\text{sum}}^{(i,j)} = w_1 A_1^{(i,j)} + \cdots + w_n A_n^{(i,j)} $$

The paper reports that raising $w_k$ on a harder objective does not reliably shift model behavior toward it when one objective is much easier than the others — the model keeps favoring the easy objective even at large weight differences [1]. Its fix, borrowed from prior work, is to gate the easier reward on the harder one clearing a threshold $t$ (Eq. 8) [1]:

$$ r_k = \begin{cases} r_k, & \text{if } r_l \ge t \\ 0, & \text{otherwise} \end{cases} $$

so the model only earns the easy reward once it has already satisfied the prioritized one [1]. Neither trl nor verl's default reward-manager code implements this conditioning automatically; it is a reward-function design choice the paper applies in its own `compute_score` for the math/coding experiments [1].

## Cost

**Theory, from the method's own math**: GDPO's advantage computation adds, relative to GRPO, one normalization pass per reward dimension plus one extra batch-level whitening pass over the summed advantage [1]; these are all reductions over already-computed scalar rewards, not extra forward or backward passes through the policy, so they do not add generation or gradient cost. GDPO needs no extra trained model beyond what GRPO needs — no value network — because, like GRPO, its baseline comes entirely from group statistics of scalar rewards [1]. The only per-dimension cost is scoring each rollout on each reward dimension, which is a property of however many reward functions or reward models the run configures, not of GDPO's advantage math itself.

**In practice, per framework**:

- verl [4][11][12]: `algorithm.adv_estimator=gdpo` requires `algorithm.gdpo_reward_keys`, a list of the reward-component keys `compute_score` must return; the assertion in `compute_gdpo_outcome_advantage` fails the run immediately if a listed key is missing from the batch [4]. `algorithm.gdpo_reward_weights` is optional and defaults to equal weighting across dimensions ($w_k=1$ for all $k$) when unset [4]. `algorithm.norm_adv_by_std_in_grpo` (default `True` in `ppo_trainer.yaml`) [11] is passed through to each per-dimension normalization call, so setting it `False` switches every dimension to Dr.GRPO-style mean-only normalization inside GDPO's own per-dimension step. The reward-scoring side runs through `reward.reward_manager.name=gdpo` (`GDPORewardManager`), currently shipped under verl's experimental `reward_loop` path rather than its stable trainer path [13] — a reader who imports it as if it were a stable-path trainer will not find it there.
- trl [16]: `GRPOConfig.multi_objective_aggregation` defaults to `"sum_then_normalize"` (GRPO's summed-then-normalized behavior); setting it to `"normalize_then_sum"` runs GDPO instead, adding one normalization per reward function across the group plus a batch-level renormalization of the summed advantage, all reductions over already-computed reward tensors inside the existing `GRPOTrainer` loop — no new forward or backward pass, and the option only changes behavior once more than one reward function is configured [17].

## How to use it

- Reward functions must return per-dimension scores, not a single pre-summed scalar, because `gdpo_reward_keys` reads named components out of the batch's non-tensor data [4]. In the paper's tool-calling setup this means two separate scores per rollout: a binary format score $\mathcal{R}_{\text{format}} \in \{0,1\}$ and a correctness score $\mathcal{R}_{\text{correct}} \in [-3,3]$ built from tool-name, parameter-name and parameter-content matching [1]; in its math/coding setup, an accuracy score and a length-constraint score, plus a third bug-ratio score in the three-objective coding experiment [1].
- Reward weighting: set `algorithm.gdpo_reward_weights` only after checking whether the easier objective needs conditioning first (Eq. 8 above) — the paper found weighting alone insufficient when difficulty differs sharply between objectives [1].
- Key knobs, with each source's own value. The paper ran two different hyperparameter sets for its two task families; "not stated" means the source was checked and does not give the value, "not checked" means this card did not verify that source's key:

| knob | verl default [11][18] | paper — tool-calling (Appendix D) [1] | paper — math/coding (Appendix E) [1] |
| --- | --- | --- | --- |
| group size (`rollout.n`) | 1 [23] | 4 | 16 |
| train batch size | not checked | 512 | 512 |
| mini-batch size | `ppo_mini_batch_size` 256 [18] | 128 | 64 |
| learning rate | `lr` 1e-6 [18] | 1e-6 | 1e-6 |
| clip range $\epsilon$ (low / high) | 0.2 / 0.2 [18] | not stated | 0.2 / 0.28 |
| KL mechanism† | `use_kl_loss: false` [18] | reward-shaping‡, `kl_ctrl.kl_coef` 0.001 | loss-term§, `kl_loss_coef` 0.0005, `kl_loss_type: mse` |
| `norm_adv_by_std_in_grpo` | True [11] | not stated | not stated |
| max response length | not checked | 1024 | 8000 |
| max prompt length (`data.max_prompt_length`) | not checked | 2048 | 1024 |

  † The three cells in this row are not the same quantity: verl's `use_kl_loss` toggles whether a KL loss term is added to the policy loss at all (off by default) [18]; ‡ `kl_ctrl.kl_coef` in the tool-calling recipe is a reward-shaping coefficient subtracted from the environment reward before advantage computation, not a loss-term coefficient [1][12]; § `kl_loss_coef` in the math/coding recipe is a loss-term coefficient added directly to the policy-gradient loss, the same mechanism `use_kl_loss` toggles [1][18]. Do not read the row as three settings of one knob.

  Two readings of that table: the paper's own two recipes differ from each other in group size (4 vs 16), KL mechanism, and clip range, so "the paper's setting" is not a single row — match the recipe to the task family, not to GDPO generically. The math/coding recipe's asymmetric clip (`clip_ratio_high` 0.28 vs `clip_ratio_low` 0.2) and its dynamic sampling / token-mean loss are carried over from DAPO [7] via the DLER recipe [9], not part of GDPO's own definition [1].
- Group size trade-off is inherited unchanged from GRPO: larger G gives steadier per-dimension group statistics at higher rollout cost per prompt; GDPO adds no new group-size consideration beyond needing enough rollouts per group for each dimension's std to be meaningful (a group of 1 breaks GDPO's per-dimension normalization the same way it breaks GRPO's).
- Framework install, launch flags, and parallelism settings beyond the knobs above belong to the verl framework card, not this one.

## While it runs

- Signals and their healthy shapes: the paper's own diagnostic is the count of distinct advantage groups a batch produces — it reports this rising with GDPO relative to GRPO and GRPO-without-std as rollout count or reward count grows, though only as a qualitative trend in its own figures, not a logged training-time metric name [1]. Beyond that, monitor each reward dimension's curve separately (format vs correctness, or accuracy vs length): the paper's own tool-calling curves show GRPO's format reward and GDPO's format reward diverging even while their correctness curves stay close, which a combined-reward curve would hide [1].
- Published reference runs: the paper's own Table 1 (Qwen2.5-Instruct 1.5B/3B, BFCL-v3, five runs each) and Table 3 (DeepSeek-R1-1.5B/7B and Qwen3-4B-Instruct on MATH/AIME/AMC/Minerva/Olympiad) are the only published reference curves for this method; no third-party reference run exists yet given the paper's 2026-01-08 submission date [1].
- Degeneracies and defaults: a group of one rollout gives every per-dimension std a divide-by-zero degenerate case, same as GRPO. Setting `algorithm.gdpo_reward_weights` to skew heavily toward one dimension without reward conditioning reproduces the priority-weighting failure the paper documents — the model keeps optimizing the easier reward regardless of weight [1]. The paper's own ablation shows that simply dropping the std term from GRPO (matching Dr.GRPO's [3] fix, without adopting GDPO's per-dimension structure) reaches a similar correctness reward to GDPO but a 0% correct-format rate on BFCL-v3, versus GDPO's 80.66% — evidence that std-removal alone does not solve the collapse problem GDPO targets [1]. The paper also reports (Appendix A, referenced in the main text) that removing its batch-level whitening step (Eq. 6) occasionally causes convergence failure, though the appendix table itself was not read for this card [1].
- Named successors: a Semantic Scholar citations search on the paper's arXiv ID (2601.05242, queried 2026-08-09) returns two direct successors. SMOPD reports that GDPO still struggles to balance reward signals of different granularity — a dense 0.1-1.0 reward alongside a sparse binary reward — because the sparse reward's signal is too weak to reinforce its capability, and reports that SMOPD outperforms GDPO across 1.5B, 3B and 7B backbones on its tool-calling and helpful/harmless settings [20]. GD²PO (Group-Dynamic reward-Decoupled Policy Optimization) reports that GDPO's per-dimension decoupling still lets a single rollout receive positive advantage on one reward dimension and negative on another, so the opposing per-dimension signals cancel during aggregation, and adds a DAPO-style [7] conflict-aware filter that masks rollouts with severe cross-dimension disagreement [21].
- Known failure modes: the paper's own limitations are the two documented above (priority weighting failing under large difficulty gaps without conditioning; std-removal alone not fixing collapse) [1]. A GitHub issue search for GDPO in trl (`repo:huggingface/trl GDPO`, queried 2026-08-09) surfaces trl issue #4853, a feature request to add Eq. 8's reward-conditioning gate as a built-in `ConditionedReward` utility; a trl maintainer declined it, stating the conditioning gate is already expressible in a user-space reward function that computes the primary signal once and reuses it to gate the secondary, and that trl instead adopted only the decoupled-normalization half of GDPO via `multi_objective_aggregation` [22].
- What the gain is — and is not: the paper's own analysis frames the gain as more accurate advantage estimation under multiple reward objectives, evidenced by higher accuracy on the harder AIME benchmark alongside a lower length-exceed rate rather than a trade-off between the two (e.g., DeepSeek-R1-1.5B: AIME accuracy 23.1% to 29.4%, length-exceed 10.8% to 6.5%, both improving together relative to GRPO) [1]. The paper does not claim GDPO adds capability beyond what the reward functions can express — it only claims better resolution and stability of the training signal derived from those same rewards.
