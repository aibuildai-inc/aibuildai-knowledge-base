# WPO

Take ordinary DPO on off-policy preference pairs, but multiply each pair's loss by the current policy's own length-normalized probability of the chosen and rejected outputs, so pairs that already look like something the policy would generate count more.

**WPO** (Weighted Preference Optimization) is an off-policy preference-optimization method for RLHF, introduced by Zhou et al. to close the gap between off-policy and on-policy preference optimization "by simulating on-policy learning with off-policy preference data" [1]. Its parent is DPO [2], which turns a Bradley-Terry preference objective into a closed-form policy loss without a separate reward model or explicit RL loop, but which treats every preference pair identically regardless of how likely the current policy is to have produced it [1]. WPO keeps the DPO loss and multiplies each pair by a weight $w(x,y_w)\,w(x,y_l)$ built from the policy's own token probabilities, so pairs a policy would plausibly generate itself dominate the gradient, approximating what would happen if the preference data had been collected on-policy in the first place [1]. Two reasons the paper gives for existing: off-policy data is cheaper and more scalable to collect than on-policy rollouts, but the resulting distributional gap between the data-generating policy and the target policy makes optimization less effective; and the reweighting scheme adds this correction "without incurring additional costs" - no extra generation, no extra model [1].

The paper is at https://arxiv.org/abs/2406.11827 [1]. WPO is a research method rather than one adopted by a named production system at the time of this card; its own reported gains are the adoption evidence. On Mistral-Base (7B) with off-policy Ultrafeedback data, WPO reaches a 24.4% length-controlled win rate on AlpacaEval 2 versus 20.6% for DPO trained the same way, and in the hybrid (off-policy + on-policy) setting on Llama-3-Instruct (8B) it reaches 45.8% length-controlled win rate versus 44.2% for DPO (Table 1) [1]. In a separate condition that augments the hybrid setting by adding back prompts missing from the hybrid set using Ultrafeedback pairs, the paper reports a new state-of-the-art 48.6% length-controlled win rate against GPT-4-turbo for Llama-3-Instruct - a distinct, richer-data condition from plain hybrid WPO, not the same comparison as the 45.8%/44.2% pair above [1]. Fine-tuning Gemma-2-9b-it with WPO in a similar hybrid setup reaches a 76.7% length-controlled win rate against GPT-4-turbo [1]. Lineage: DPO (2023 [2]) -> WPO (EMNLP 2024 [1]) -> shipped as an optional weighting mode inside Hugging Face trl's `DPOTrainer` [3]. The paper was confirmed via top-cited match under an exact title search on arXiv for "WPO: Enhancing RLHF with Weighted Preference Optimization" and cross-checked against trl's own citation of the same arXiv ID (2406.11827) inside its `DPOConfig` source [4].

**When to pick it**: pick WPO over plain DPO [2] when you must train on off-policy preference pairs (data labeled on outputs from other models, e.g. GPT-4) and want a way to down-weight pairs the current policy would never plausibly produce, at no extra compute cost [1]. It is still an offline, off-policy method: it does not close the full gap to genuinely on-policy training, and the paper's own hybrid setting - mixing on-policy self-samples into the off-policy set - beats WPO-on-off-policy-alone on both models tested [1]. Nearest offline alternative: SimPO [5], a reference-free offline loss that WPO's own Table 1 outperforms on Mistral-Base off-policy AlpacaEval 2 (24.4% vs 21.5% length-controlled) [1]. Nearest online neighbor: GRPO [6], an on-policy method that samples fresh completions from the current policy every step and needs no offline preference dataset at all, unlike WPO which trains on a fixed pre-collected pair set [1].

**Variant of**: DPO [2].

**Data it needs**: a preference dataset of prompt, chosen-response, rejected-response triples, the same shape DPO needs, no reward model or value network required to compute the loss. The paper's off-policy experiments use the 63k-pair binarized Ultrafeedback dataset, with pairs generated by models other than the one being trained (e.g. GPT-4, Llama-2) [1]; its hybrid experiments add self-sampled completions from the SFT model plus one GPT-4-turbo completion per prompt, scored and paired by GPT-4-turbo [1]. WPO itself is off-policy/offline: it is defined to operate on a static preference dataset, not on samples drawn fresh from the training policy each step, though the paper's hybrid setting mixes in on-policy samples collected once before training, not per step [1].

**Extra models**: none required by the method's own definition - WPO computes its pair weights from the policy model being trained, using its own token log-probabilities, no reference model, value network, or reward model in the loss itself [1]. In practice it inherits DPO's implicit reward reparameterization, so a training run still needs whatever the base loss requires; trl's `DPOTrainer`, which is what ships WPO's weighting, loads a frozen reference model for the DPO KL term by default unless a PEFT config or `precompute_ref_log_probs`/`reference_free` style option removes it (see the framework's own docs for that default; not re-verified for this card beyond the weighting flag itself). See Cost.

**Shipped by**: trl [3], as `use_weighting` (bool, default `False`) on `DPOConfig`, consumed inside `DPOTrainer.dpo_loss` — trl documents it as applying "WPO-style weighting... to preference pairs using the policy's length-normalized sequence probabilities" and cites arXiv:2406.11827 directly in the config docstring [4]. `DPOConfig` and `DPOTrainer` are both top-level exports of the `trl` package [7]. verl's documented algorithm set at commit `d33ddd7140f4` of the `main` branch (2026-08-09T17:31:32Z) (`docs/algo/`: baseline, dapo, dppo, dro, entropy, gpg, grpo, opd, opo, otb, ppo, rollout_corr, rollout_corr_math, spin, sppo) does not include DPO or WPO, and its README points users to a generic "Extend to Other RL(HF) algorithms" guide rather than a shipped DPO/WPO trainer [8]; verl is not counted as shipping this method. The paper's own reference implementation is a research repo built on Hugging Face's alignment-handbook and princeton-nlp/SimPO codebases, not a maintained library, with training-config YAMLs for Mistral-Base and Llama-3-Instruct reproductions [9].

## How it works

Each step: take a mini-batch of (prompt, chosen, rejected) triples from the fixed dataset, compute the DPO loss per pair, multiply it by a policy-derived weight for the chosen and rejected sequence, and take the gradient [1].

**The DPO loss it builds on** [2], with $r^*(x,y) = \beta\log\frac{\pi_\theta(y|x)}{\pi_{ref}(y|x)} + \beta\log Z(x)$ substituted into the Bradley-Terry model:

$$ \mathcal{L}_{DPO} = -\mathbb{E}_{(x,y_w,y_l)\sim D}\left[\log \sigma\!\left(\beta\log\frac{\pi_\theta(y_w|x)}{\pi_{ref}(y_w|x)} - \beta\log\frac{\pi_\theta(y_l|x)}{\pi_{ref}(y_l|x)}\right)\right] $$

**The WPO objective** (Eq. 1) [1]:

$$ \mathcal{L}_{WPO} = -\mathbb{E}_{(x,y_w,y_l)\sim D}\left[w(x,y_w)\,w(x,y_l)\,\log p(y_w \succ y_l | x)\right] $$

where $\log p(y_w \succ y_l|x)$ is the same DPO log-sigmoid term above, and $w(x,y)$ is detached from backpropagation - it reweights the loss, it is not itself trained [1]. The paper derives this reweighting from a thought experiment: resample the dataset by drawing prompts uniformly and generating a fresh output pair with the current policy, keeping a pair only if it happens to match an existing preference label; over infinite resampling a pair's occurrence rate is proportional to $\pi_\theta(y_w|x)\,\pi_\theta(y_l|x)\,p(x)$, and reweighting by that quantity on the original dataset is mathematically equivalent to this resampling, without ever generating anything [1].

**Length-normalized weight** (used directly, before alignment) [1]:

$$ w(x,y) = \exp\!\left(\frac{1}{|y|}\sum_{t=1}^{|y|}\log \pi_\theta(y_t|x,y_{<t})\right) $$

**Weight alignment (Eq. 2), the paper's default** [1]: raw sequence probabilities of on-policy outputs are not uniformly close to 1 (low-confidence prompts get low weight even for genuinely on-policy text), so the paper calibrates each token's log-probability against the expected log-probability of a token sampled at temperature 1, $\sum_{v\in V}\pi_\theta(v|x,y_{<t})^2$:

$$ w(x,y) = \exp\!\left(\frac{1}{|y|}\sum_{t=1}^{|y|}\log\frac{\pi_\theta(y_t|x,y_{<t})}{\sum_{v\in V}\pi_\theta(v|x,y_{<t})^2}\right) $$

The paper calls this "sampled alignment" and reports it as the best-performing of three variants it tests - no alignment, greedy alignment (compare to the top-probability token instead of the sampled-token expectation), and sampled alignment - on Mistral-Base off-policy AlpacaEval 2: 22.0% vs 23.0% vs 24.4% length-controlled win rate respectively (Table 2) [1]. trl's implementation computes exactly this Eq. 2 form: it evaluates `logsumexp(2*logits) - 2*logsumexp(logits)` per token (an equivalent log-space computation of $\log\sum_v \pi_\theta(v|\cdot)^2$), subtracts it from each token's log-probability, averages over the completion, and exponentiates to get the weight, with a comment in-source reading "Eq (2) of the WPO paper" [3].

**Worked micro-example**: a length-2 completion with per-token log-probs $\log\pi_\theta(y_1)=-0.5$, $\log\pi_\theta(y_2)=-1.5$ gives an unaligned weight $w=\exp(\tfrac{1}{2}(-0.5-1.5))=\exp(-1)\approx0.37$. If a chosen sequence gets $w(x,y_w)\approx0.8$ and a rejected sequence gets $w(x,y_l)\approx0.5$, the pair's DPO loss is scaled by $0.8\times0.5=0.4$ relative to plain DPO's implicit weight of 1 - this pair's gradient contribution shrinks because the policy currently finds this exact rejected continuation only moderately likely to begin with (arithmetic worked here to illustrate Eq. 1's product form; not taken from the paper's own numbers) [1].

**Gradient structure and the paper's own asymmetry finding**: WPO's gradient is $-\beta w(x,y_w)w(x,y_l)\,\sigma(\hat r(x,y_l)-\hat r(x,y_w))\left[\nabla\log\pi(y_w|x) - \nabla\log\pi(y_l|x)\right]$, pushing the policy toward $y_w$ and away from $y_l$ exactly as DPO does, only rescaled [1]. The paper ablates two partial variants, $\mathcal{L}_{WPO_W}$ (weight only $y_w$) and $\mathcal{L}_{WPO_L}$ (weight only $y_l$), and finds $WPO_L$ tracks full WPO closely while $WPO_W$ underperforms even plain DPO in most settings - the paper's stated conclusion is "the dispreferred data should be on-policy, the preferred data benefits less" [1].

## Cost

**Theory, from the method's own math**: WPO adds no new forward pass and no new model beyond what DPO already needs - the weight $w(x,y)$ is read off the same per-token log-probabilities the DPO loss already computes for $y_w$ and $y_l$ under $\pi_\theta$, and it is detached, so it costs no extra backward-pass compute either [1]. The one addition is per-token bookkeeping for the alignment normalizer ($\log\sum_v \pi_\theta(v|\cdot)^2$), which needs the full vocabulary logits already produced by the forward pass - a memory-neutral reduction over an existing tensor, not a new tensor of model size. WPO is exactly as memory-heavy as the DPO run it wraps: one trained policy plus, if the base loss uses one, one frozen reference model for the KL term.

**In practice, per framework**:

- trl `DPOTrainer` [3][4]: `use_weighting` is a boolean flag on `DPOConfig`, default `False`; enabling it adds the logsumexp-based weight computation inside the existing `dpo_loss` call, guarded to raise `NotImplementedError` if combined with `loss_type` in `{"aot", "aot_unpaired"}` because those losses sort samples in a way that would misalign the per-pair weights [3]. No separate model, dataloader, or generation step is added; cost is governed by whatever `loss_type` and reference-model settings the surrounding `DPOTrainer` run already uses (framework-level detail, not re-derived here).
- No other framework in this corpus ships WPO (see Shipped by), so there is no second practice entry to compare against.

## How to use it

- Data: identical preparation to DPO - a dataset of (prompt, chosen, rejected) triples, off-policy or hybrid. The paper's off-policy setup uses Ultrafeedback pairs labeled from other models' outputs [1]; its hybrid setup samples 5 completions per prompt from the SFT model at temperature 0.7, top-p 0.95, adds one GPT-4-turbo completion, scores all 6 with GPT-4-turbo using an additive scoring prompt, and forms a pair from an output scoring 5 or 6 as chosen against a random output scoring at least one point lower as rejected, discarding prompts where no such pair exists [1].
- In trl, enabling WPO is one flag: set `use_weighting=True` on `DPOConfig`; every other DPO knob (loss type, `beta`, batch size) is unchanged, since WPO only rescales the existing per-pair loss [3][4].
- Key knobs, with each source's own value ("not stated" = the source was checked and does not give the value):

| knob | trl `DPOConfig` default [3] | paper (Mistral-Base) [1] | paper (Llama-3-Instruct) [1] |
| --- | --- | --- | --- |
| `use_weighting` | `False` | on (WPO is the method) | on |
| $\beta$ | `0.1` | `0.01` | `0.01` |
| learning rate | `1e-6` | `5e-7` | `1e-6` |
| epochs | not checked | 1 | 2 |
| batch size | not checked | 128 | not stated |

  trl's default $\beta$ of 0.1 is ten times the paper's own tuned value of 0.01 for both model families tested [1][3] - carrying trl's default into a WPO reproduction changes the KL strength the paper did not use. trl's default learning rate of `1e-6` exactly matches the paper's own Llama-3-Instruct value but is double the paper's Mistral-Base value of `5e-7` [1][3].
- Trade-off from the paper's own comparison of RL settings: off-policy WPO is cheapest (no sampling needed) but on Llama-3-Instruct the hybrid setting - adding on-policy self-samples - reaches a higher length-controlled win rate than off-policy WPO alone (45.8% vs 33.8%, Figure 3/Table 1) [1]; for Mistral-Base the ordering flips slightly, with the paper attributing this to the lower quality of Mistral-Base's self-sampled outputs making on-policy data less informative for that weaker model [1]. A run designer choosing between pure off-policy WPO and a hybrid mix should expect the answer to depend on how good the base policy's own samples already are.

## While it runs

- Signals and their healthy shapes: the paper's own ablation (Table 2, Figure 2) uses the weight distribution itself as a diagnostic - sampled alignment produces a more concentrated distribution of $w(x,y)$ for genuinely on-policy outputs than greedy alignment or no alignment, and that concentration tracks with downstream benchmark performance [1]. No first-hand guidance beyond this was found in the paper or in trl's docs specifically for `use_weighting`; trl's general DPO logging guidance (reward margins, rewards/accuracies) applies unchanged since WPO only rescales the DPO loss, but this card does not re-verify that guidance under `use_weighting=True` specifically.
- Published reference runs: Table 1 of the paper is the reference curve set - 5-seed average and standard deviation for DPO and WPO on Mistral-Base and Llama-3-Instruct, off-policy and hybrid, on AlpacaEval 2 and MT-bench, with underlined entries marking statistically significant gains at p<0.05 [1].
- Degeneracies and defaults: the weighting is detached and multiplicative, so a pair the current policy assigns near-zero probability to both $y_w$ and $y_l$ gets a near-zero weight and contributes almost nothing to the gradient - the paper does not name a floor or clamp on $w(x,y)$, so this card cannot confirm whether near-zero weights are guarded against in the reference formula; trl's implementation computes the weight via `torch.exp` of a log-space quantity, which underflows toward 0 rather than producing NaN, but is not clamped either as read in this source pass [3]. Default divergence to note: trl's `DPOConfig.beta` default (0.1) is 10x the paper's tuned value (0.01); leaving `use_weighting` at its own default of `False` silently runs plain DPO instead of WPO [3][4].
- Named successors: a Semantic Scholar citations query against the paper's arXiv ID (2406.11827) returned all 52 papers citing WPO, matching this corpus's own recorded citation count for the item [10]. Scanning their titles, MWPO (Xu et al., ACL Findings 2025) is the clearest candidate: its related-work section groups WPO together with DPO, GPO, and KTO and states that none of these methods account for the potential noise introduced by similar responses, then proposes a preference-strength and length reweighting scheme to address exactly that gap [11]. This is a related-work characterization and a compared baseline, not a claim that MWPO is built as a direct fix specifically for WPO: MWPO's own Table 1 (Mistral-7B-Base) reports WPO beating DPO (23.5% vs 15.1% length-controlled win rate on AlpacaEval 2) while MWPO edges out WPO (23.8%), and Table 2 (Llama3-8B-Instruct) shows WPO underperforming DPO (33.04% vs 43.12% vs GPT-4) while MWPO improves on both (49.48%) [11].
- Known failure modes: the paper's own Limitations section states that WPO does not fully close the performance gap between off-policy and on-policy preference optimization - off-policy WPO can still underperform on-policy and hybrid training - and that its experiments used only the Ultrafeedback dataset (helpfulness/truthfulness/instruction-following, no safety data) and single-turn conversations, so generalization to safety-focused or multi-turn preference data was not tested [1]. No trl-issue-level failure report specific to `use_weighting` was checked for this card.
- What the gain is - and is not: the paper's own analysis (Table 1, Figure 3) shows WPO's gain is in closing part of the off-policy-vs-on-policy performance gap for a fixed off-policy dataset, and in the hybrid setting improving further by weighting a mix of on- and off-policy pairs - it is a reweighting of existing preference data, not a source of new information, and the paper explicitly states it does not eliminate the disparity with genuinely on-policy training [1].
