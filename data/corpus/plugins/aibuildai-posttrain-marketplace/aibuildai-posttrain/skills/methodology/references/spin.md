# SPIN

Fine-tune an already-SFT'd LLM to tell its own past-iteration generations apart from the ground-truth SFT completions, using only the existing SFT dataset — no preference labels, reward model, or new data collection needed.

**SPIN** (Self-Play fIne-tuNing) is a fine-tuning method, introduced by Chen, Deng, Yuan, Ji and Gu, that "starts from a supervised fine-tuned model" and grows a strong LLM out of a weak one "without the need for acquiring additional human-annotated data" [1]. Its parent is standard supervised fine-tuning (SFT) on a dataset of prompt/response pairs $(x,y)$ [1]; SPIN's own paper notes that repeating plain SFT on the same data becomes ineffective and can even hurt performance [1]. At the heart of SPIN is a self-play mechanism: a "main player" LLM is trained to distinguish the ground-truth SFT response from a response the model itself generated in the previous iteration (the "opponent"), and the opponent is then updated to the newly trained weights before the next iteration [1]. The paper gives two reasons beyond avoiding new labels: without human/AI feedback there is no preference dataset to run RLHF or RLAIF on top of the SFT stage, and repeated SFT alone saturates quickly [1]. When the paper's general convex, monotonically-decreasing loss $\ell$ is specialized to the logistic loss, the resulting per-iteration training objective becomes structurally the same as Direct Preference Optimization's pairwise loss, with the ground-truth response as the chosen completion and the model's own prior-iteration sample as the rejected one [1][2] — the paper is explicit that despite this resemblance, SPIN and DPO "are fundamentally different" in what data they need and whether they iterate [1].

The paper's own gains, measured on the HuggingFace Open LLM Leaderboard average score starting from `zephyr-7b-sft-full` (itself Mistral-7B SFT-tuned on UltraChat200k): 58.14 (SFT) → 60.80 (SPIN iter 0, +2.66) → 62.12 (iter 1, +1.32) → 62.97 (iter 2, +0.85) → 63.16 (iter 3, +0.19) [1, Table 4]. The per-iteration gain shrinking toward zero is the paper's own signal that the model is approaching a limiting point [1]. As a second reference point, `zephyr-7b-dpo-full` — the same SFT checkpoint trained instead with DPO on 62k UltraFeedback preference pairs — reaches only 61.31, below SPIN's iteration-1 score of 62.12, despite SPIN using no new preference data at all [1, Table 3]. This confirmed match was checked against the top-cited paper under an exact title search for "Self-Play Fine-Tuning Converts Weak Language Models to Strong Language Models", which returned this paper as the clear top hit among several unrelated "self-play fine-tuning" name collisions. Lineage: SFT -> SPIN (2024, [1]) -> reproduced as a recipe "inspired by" the paper in verl [4] -> named successor SPPO (2024, [3]), which reframes self-play alignment as approximating a Nash equilibrium to fix the Bradley-Terry model's inability to capture intransitive preferences [3]. No further landmark production system's technical report was checked for SPIN adoption for this card; the sources checked are the paper itself, the verl and trl framework docs, and the SPPO abstract.

**Paper**: https://arxiv.org/abs/2401.01335 [1].

**When to pick it**: pick SPIN when you have only an SFT dataset of prompt/response pairs — no preference labels, no reward model, and no budget to collect either — and you want a cheap iterative boost on top of SFT [1]. Prefer plain DPO [2] when you already have (or can afford to collect) real chosen/rejected preference pairs; DPO trains directly on those pairs in a single pass and needs no iterative generate-then-train loop [2]. The nearest online neighbor is online/iterative DPO with an actual reward or ranking source (this is exactly what verl's SPIN recipe substitutes in place of the paper's fixed-SFT-target self-play, see Extra models and How it works) [4][5]: it generates fresh completions and labels them from a reward function each round instead of always pitting the model against the static SFT ground truth [4].

**Variant of**: SFT [1], with a per-iteration loss that becomes DPO's pairwise objective under the logistic-loss choice, using the SFT ground truth as the fixed "chosen" side [1][2].

**Data it needs**: only the existing SFT dataset $(x,y)$ pairs — prompt and a single ground-truth completion, no chosen/rejected pairs and no scalar reward column [1]. The paper's own runs sampled 50k prompts from UltraChat200k at iteration 0, and reused 50k of the prior iteration's synthetic responses plus 50k newly generated ones at iterations 1–3 (100k total), training 2 epochs per iteration over 4 iterations (0–3) on `zephyr-7b-sft-full`/Mistral-7B [1]. It is semi-online: a fresh synthetic "rejected" set is sampled from the current opponent policy once per iteration, then the model trains multiple offline epochs on that fixed batch before the opponent is updated and the next iteration's data is sampled [1] — not per-step on-policy like PPO/GRPO, and not fully offline like DPO on a static human-labeled set.

**Extra models**: by the paper's own definition, none beyond the single LLM being trained: the "opponent" is just a frozen copy of the same model's previous-iteration weights, reused as both the log-probability reference in the loss and the generator of rejected samples — no separate value network, reward model, or judge [1]. verl's recipe, by contrast, does not reproduce this: because it replaces the fixed SFT target with online preference labeling, it requires an explicit reference policy (`ref_policy_wg`, periodically refreshed from the actor via `ref_update_freq`) and an optional reward-model config for ranking generations [4]. See Cost.

**Shipped by**: no framework ships the paper's original algorithm as a top-level trainer. verl provides an experimental recipe (`recipe/spin`, kept in the separate `verl-recipe` git submodule, entry point `SpinTrainer` via `main_spin.py`) described as a recipe "inspired by" the SPIN paper rather than a reproduction of it — it substitutes iterative online DPO with dynamically-generated preference labels for the paper's fixed-target self-play [4][5]. trl's current docs table of contents lists no SPIN trainer among its supported or experimental trainers [7]. Building the paper's own method from scratch on top of an existing DPO-style trainer would mean adding: (a) a per-iteration synthetic-generation step from the current opponent snapshot, and (b) an outer loop that copies the just-trained weights into the frozen opponent/reference before the next round — a loss reuse plus an iteration-management wrapper, not a new sampling algorithm.

## How it works

Each iteration $t{+}1$: freeze the previous iteration's weights $\theta_t$ as the opponent, sample synthetic responses $y' \sim p_{\theta_t}(\cdot|x)$ for every SFT prompt $x$, then train the main player to prefer the SFT ground truth $y$ over $y'$ [1].

**The end-to-end training objective** [1, Eq. 4.7]:

$$ \mathcal{L}_{SPIN}(\theta,\theta_t) = \mathbb{E}_{x\sim q(\cdot),\, y\sim p_{data}(\cdot|x),\, y'\sim p_{\theta_t}(\cdot|x)}\; \ell\!\left(\lambda \log\frac{p_\theta(y|x)}{p_{\theta_t}(y|x)} - \lambda \log\frac{p_\theta(y'|x)}{p_{\theta_t}(y'|x)}\right) $$

$q(\cdot)$ is the prompt distribution, $p_{data}$ the SFT ground-truth distribution, $p_{\theta_t}$ the current opponent (previous-iteration policy); $\lambda>0$ is a regularization strength derived from a KL penalty against $p_{\theta_t}$ that the paper shows has this log-ratio form as its closed-form solution [1, Eq. 4.3–4.6]; $\ell$ is any convex, monotonically-decreasing loss (correlation, hinge, exponential, or logistic) [1, Assumption 5.1]. Update rule per iteration: $\theta_{t+1} = \arg\min_\theta \sum_i \ell\!\left(\lambda\log\frac{p_\theta(y_i|x_i)}{p_{\theta_t}(y_i|x_i)} - \lambda\log\frac{p_\theta(y_i'|x_i)}{p_{\theta_t}(y_i'|x_i)}\right)$, then the opponent is set to $\theta_{t+1}$ for the next round [1, Algorithm 1].

With the logistic loss $\ell(t)=\log(1+\exp(-t))$, this is algebraically the same shape as DPO's pairwise loss with implicit reward $\lambda\log\frac{p_\theta(y|x)}{p_{\theta_t}(y|x)}$, chosen = SFT ground truth, rejected = self-generated sample, and $p_{\theta_t}$ playing the role of DPO's reference policy [1][2] — except $p_{\theta_t}$ is updated every iteration instead of staying fixed at the SFT checkpoint for the whole run [1].

The paper proves (Theorem 5.2) that for any $\lambda\ge0$, $\theta_t$ is a global minimum of $\mathcal{L}_{SPIN}$ if and only if $p_{\theta_t}(\cdot|x) = p_{data}(\cdot|x)$ — the optimization is only guaranteed to stop once the trained policy exactly matches the fixed target distribution of the SFT data [1, Theorem 5.2].

Worked example with the logistic loss, $\lambda=1$: suppose at some prompt $\log p_\theta(y|x) - \log p_{\theta_t}(y|x) = 2.0$ (the model is getting more confident on the ground truth relative to the opponent) and $\log p_\theta(y'|x)-\log p_{\theta_t}(y'|x) = -1.0$ (less confident on its own old sample). The logit is $2.0-(-1.0)=3.0$, and the loss is $\log(1+e^{-3.0})\approx0.049$ — small, because the model already separates the two; if instead both log-ratios were equal (logit $=0$), the loss would be $\log 2\approx0.693$, the maximum-uncertainty point. This arithmetic follows only the paper's own formula and is not attributed to any framework's implementation.

**verl's shipped mechanism is a different algorithm under the same name** [4]: its `compute_online_dpo_loss` is the standard sigmoid-form DPO loss $-\log\sigma\big(\beta[(\log\pi_\theta(y_w) - \log\pi_\theta(y_l)) - (\log\pi_{ref}(y_w)-\log\pi_{ref}(y_l))]\big)$ (with an `ipo` loss-type alternative), read from `spin/core_algos.py` at commit `ba246418f4de12b845a09bba975f1a5242adc898` [5]. Chosen/rejected are not fixed as (SFT ground truth, self-sample); instead `compute_onlinedpo_pref` dynamically ranks freshly generated responses using a reward source such as rule-based math-correctness ranking [5], which the docs describe as exploring the paper's own Section 7 suggestion to move beyond a fixed target distribution [4].

## Cost

**Theory, from the method's own math:**
- Time: one synthetic-generation pass over every SFT prompt per iteration (paper: 50k–100k generations per iteration, 4 iterations) [1], plus 2 training epochs per iteration over the (growing) synthetic+SFT dataset [1]. A naive reading says generation should dominate wall-clock since it is autoregressive; the paper's own measured breakdown contradicts that (see below).
- Memory: the trained policy $p_\theta$ plus one frozen copy $p_{\theta_t}$ for the log-ratio terms — the same two-model footprint as DPO, no value network and no reward model by the paper's own definition [1].

**Paper's own measured cost** (not a framework, but the defining paper's own reproduction numbers, on 8×A100 80GB): per 64 examples, generation took 6.69s versus 10s training; over full iterations, generation was 1.45h per iteration versus training of 4.32h (iter 0) and 8.64h (iters 1–3, on the doubled 100k dataset) — the paper states "the generation time is dominated by the training time," the opposite of the naive time-theory reading above [1, Table 2 and surrounding text].

**In practice, per framework:**
- verl [4][5]: "No Critic: Unlike PPO, we omit the value function critic" is stated explicitly; an "explicit reference policy (`ref_policy_wg`)" is held for the DPO loss, refreshed from the actor at a configurable cadence (`ref_update_freq`, default `1` in `spin/config/spin_trainer.yaml` at the pinned commit, meaning the reference is updated every iteration) [6]. An optional `reward_model` config adds a further model only if reward-based (rather than rule-based) preference labeling is used [4].
- trl: no SPIN trainer exists to report a cost profile for [7].

## How to use it

- Data prep: reuse an existing SFT dataset of $(x,y)$ pairs; no chosen/rejected labeling pipeline is needed for the paper's own method [1]. The paper's prompting template was `"### Instruction: {prompt}\n\n### Response: "`, and for multi-turn UltraChat200k data it kept only the first conversation round as the prompt/completion pair [1].
- Knobs, paper vs. the only shipped implementation (verl's recipe, which is a different reward-labeling mechanism, not a value-for-value match on every knob):

| knob | paper [1] | verl `spin_trainer.yaml` (pinned, see Sources) [6] |
| --- | --- | --- |
| regularization strength ($\lambda$ / `dpo_beta`) | 0.1 (iters 0–2), raised to 5.0 at iter 3 as training approaches convergence | `dpo_beta`: 0.1 |
| loss function $\ell$ | logistic (used for all reported results) | `dpo_loss_type` not read at this commit — `core_algos.py` supports `sigmoid` (default arg) and `ipo` [5] |
| learning rate | peak 5e-7 (iters 0–1), decayed to 1e-7 (iters 2–3) | not read at this commit |
| optimizer | RMSProp, no weight decay | not read at this commit |
| batch size | 64 (global), 10% warmup | not checked |
| opponent/reference update cadence | every iteration, by definition of the algorithm | `ref_update_freq`: 1 (every iteration) |
| epochs per iteration | 2 stated in the main text — but the paper's own maintainer states 6 is needed to reproduce results (see While it runs) | not checked |
| max sequence length | 2048 tokens | not checked |

- Trade-off a run designer faces: reusing the previous iteration's synthetic data alongside newly generated data (as the paper does from iteration 1 onward) doubles the per-iteration training set and roughly doubled the paper's own training time (4.32h → 8.64h) [1]; a maintainer reply also states that using the previous two iterations' data (not just the latest one) reproduced results better than a single iteration's data [8].

## While it runs

- Signals and healthy shapes: no first-hand monitoring guidance (dashboard metric names, healthy ranges) was found for SPIN specifically in the sources checked (the paper's main text and appendix, and verl's SPIN recipe docs) — the paper's only stated live signal is qualitative: the per-iteration improvement should shrink toward zero as the policy approaches the fixed SFT target distribution, and near-zero cross-iteration gain indicates the run has reached its limiting point [1].
- Published reference run: the paper's own Table 4 curve is the reference to compare against — Open LLM Leaderboard average 58.14 (SFT) → 60.80 → 62.12 → 62.97 → 63.16 across SPIN iterations 0–3 on `zephyr-7b-sft-full` [1, Table 4]; as a control, plain continued SFT on the same data for one more epoch scored 57.23, below the 58.14 starting point, showing that repeating SFT (rather than SPIN's self-play) degrades performance [1, Table 5].
- Degeneracies and defaults: verl's recipe requires an explicit reward or rule-based ranking source to label preferences online, which the original paper's method never needed (it always used the fixed SFT ground truth as chosen) — omitting or misconfiguring that ranking source changes the shipped recipe's behavior in a way the paper's own algorithm has no analogue for [4].
- Named successors: SPPO (Self-Play Preference Optimization) reframes self-play alignment as approximating a Nash equilibrium of a constant-sum two-player game rather than matching a fixed data distribution, explicitly motivated by the Bradley-Terry model's inability to capture intransitive/irrational preferences [3].
- Known failure modes: from the official `uclaml/SPIN` GitHub repository, several users opened issues reporting they could not reproduce the paper's numbers (issues #36, #39, #24, queried via the repo's issue list on 2026-08-09) [8]. A paper author (`angelahzyuan`) replied on issue #36 that reproduction requires: the exact `zephyr-7b-sft-full` checkpoint at a pinned HF revision, HF's own generation rather than vLLM ("VLLM generation differs from what we used in the paper"), 6 total training epochs rather than the 2 stated in the main text, and `lm-evaluation-harness` v0.4.0 [8] — a concrete gap between the paper's stated hyperparameters and what the authors say is actually needed to reproduce the paper's own numbers. The paper's own Section 7 limitations state that convergence is only guaranteed to the fixed human-authored SFT target distribution, which "inherently imposes a ceiling" on performance, and that generating synthetic data at scale is resource-intensive [1].
- What the gain is — and is not: the paper's own analysis is that SPIN lets an SFT model extract more benefit from data it has already been trained on, converging toward (not beyond) the ground-truth SFT distribution [1, Theorem 5.2] — it is not shown to add capability the SFT data doesn't already encode, and per-iteration gains shrink toward zero rather than continuing to compound [1, Table 4].
