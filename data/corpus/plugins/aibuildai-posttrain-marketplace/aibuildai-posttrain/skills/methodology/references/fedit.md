# FedIT

https://arxiv.org/abs/2305.05644

Instruction-tune an LLM without centralizing anyone's data: each client LoRA-finetunes a shared base model on its own local instructions, and a server FedAvg-averages the LoRA adapters every round.

**FedIT** (Federated Instruction Tuning) is introduced by Zhang et al. as "a new approach called Federated Instruction Tuning (FedIT), which leverages federated learning (FL) as the learning framework for the instruction tuning of LLMs," described as the first exploration of FL-based instruction tuning for LLMs [1]. Its parent is Federated Averaging (FedAvg), defined by McMahan et al. as an algorithm that "combines local stochastic gradient descent (SGD) on each client with a server that performs model averaging" [2]. FedIT keeps FedAvg's client-update/server-aggregate loop but restricts local training to a LoRA adapter on a frozen pretrained LLM, so only the adapter matrices are sent back and averaged [1]. The paper gives three reasons to build it: collecting large volumes of human-written instructions is costly, privacy concerns limit access to real user conversations that would otherwise be valuable training signal, and companies treat their own instructions as proprietary and are reluctant to share them [1].

The paper releases a companion GitHub repository, Shepherd, as the reference implementation, described in the paper as "a foundational framework for exploring federated fine-tuning of LLMs using heterogeneous instructions across diverse categories" [1]; no larger downstream system's adoption of FedIT was found in the sources checked for this card (arxiv.org full-text search restricted to this paper and to citing works was not performed; only the paper, its repo, and the top-cited alternate candidate were read). In the paper's own qualitative study, a LLaMA-7B model trained with FedIT across 100 simulated clients (Shepherd-7B) scored 131.7 against a no-instruction-tuning LLaMA baseline's 114.0 under GPT-4 pairwise auto-evaluation on 20 held-out questions, and reached 76% of ChatGPT's relative score versus 67% for the untuned LLaMA baseline, while remaining below a CentralizedModel upper bound trained on the pooled data (142.2 vs. 130.7, Table 3 and Figure 3) [1]. Lineage in one line: FedAvg (McMahan et al., 2017 [2]) + LoRA (Hu et al., 2021 [3]) -> FedIT (2023 [1]) -> named successor FewFedPIT (2024 [4]), which the successor paper frames as fixing FedIT's "scarcity of instructional data and risk of exposure to training data extraction attacks" [4]. The right paper was confirmed by ranking the two candidates surfaced under the name "Federated Instruction Tuning": this paper carries 266 citations against 4 for the other candidate, FewFedPIT, whose own abstract frames FedIT as the prior work it extends rather than as itself the origin of the name [4].

**When to pick it**: pick FedIT when instruction data must stay on separate devices or organizations for privacy or proprietary reasons, and you can accept a LoRA-only, FedAvg-averaged update rather than full-parameter training [1]. Prefer plain centralized instruction tuning (e.g., the parent LoRA/Alpaca-style SFT pipeline FedIT builds local training on [1]) whenever the data can legally and practically be pooled, since the paper's own centralized baseline outscored FedIT's federated model (142.2 vs. 130.7, Table 3) [1]. There is no offline/preference-pair alternative to contrast here: FedIT is itself an SFT-stage method, not a preference-optimization method, so the natural non-federated neighbor is single-node instruction tuning with LoRA [1], and the nearest online neighbor within the federated-LLM line is FewFedPIT, which adds synthetic data generation and parameter isolation on top of a FedIT-style federated loop [4].

**Variant of**: FedAvg [2], specialized to LoRA-adapter-only local updates for LLM instruction tuning [1].

**Data it needs**: per-client instruction-tuning records in the Alpaca prompt format used by the paper's repo -- an instruction, an optional input/context, and a response, filled into the "Prompt Input" / "Prompt No Input" templates given in Table 1 of the paper [1]. The paper's own experiments partition the public Databricks-dolly-15k instruction dataset (about 15,000 records across 8 behavioral categories) across 10 or 100 simulated clients to emulate non-IID local data [1]; the method itself expects each real client to hold its own private local dataset that never leaves the device [1]. Local training is on-policy in the trivial supervised sense (each round trains on the client's own fixed local data with the client's own optimizer state), and the overall federated loop is round-based and synchronous: the server selects a client subset each round, waits for their local updates, and aggregates before the next round begins (Algorithm 1) [1].

**Extra models**: none beyond the one shared base LLM. FedIT's definition trains a single global LLM whose weights are frozen while a LoRA adapter (matrices A and B) is trained locally and aggregated by FedAvg at the server; the paper reports the trainable LoRA parameters are 0.26% of the 7B base model's original parameter count (Table 2) [1]. No reference model, value network, reward model, or judge is part of the method; the paper's own evaluation uses GPT-4 as an external auto-evaluator, not as a component of training [1].

**Shipped by**: this card did not fetch or check trl, verl, OpenRLHF, or any other post-training library's docs or source for a FedIT trainer, so it makes no claim about whether one exists there; the only implementation this card found is the authors' own research repository, Shepherd (`JayZhang42/FederatedGPT-Shepherd`, Apache-2.0, 252 stars, last pushed 2023-07-07) [5], which is a standalone client/server simulation script (`main.py`) rather than an adapter registered inside a larger training framework. Building this elsewhere means writing two things on top of an existing LoRA/PEFT SFT trainer: a round-based client-selection and local-training loop, and a FedAvg-style adapter-averaging step at the server -- not a new loss, since the local objective is ordinary supervised instruction-tuning cross-entropy [1].

## How it works

Each communication round: the server selects a subset of clients, each selected client freezes the base LLM and trains only its LoRA adapter on its own local instructions, clients send their adapter matrices back, and the server averages them into the new global adapter (Algorithm 1) [1].

**LoRA local update.** For a frozen pretrained weight matrix $W_0 \in \mathbb{R}^{d\times k}$, the update is constrained to a low-rank decomposition $W_0 + \Delta W = W_0 + BA$ with $B \in \mathbb{R}^{d\times r}$, $A \in \mathbb{R}^{r\times k}$, and rank $r \ll \min(d,k)$; for a linear layer the forward pass becomes $h = W_0 x + BAx$ [1]; this formula was checked against FedIT's own restatement of it, not against LoRA's defining paper, which was fetched here only as its abstract page and does not itself carry the formula [3]. Only $B$ and $A$ are trained and communicated; $W_0$ never moves [1]. The paper initializes $A$ with random Gaussian values and $B$ at zero, so $BA = 0$ at the start of training [1]; this initialization scheme was likewise checked only against FedIT's own restatement, not against LoRA's defining paper [3].

**Server aggregation.** The paper states aggregation is done "by FedAvg" [1]; McMahan et al.'s Algorithm 1 defines the server step as a weighted average of the client updates,

$$ w_{t+1} \leftarrow \sum_{k \in S_t} \frac{n_k}{m_t}\, w_{t+1}^k, \qquad m_t = \sum_{k \in S_t} n_k $$

where $S_t$ is the set of clients selected in round $t$, $w_{t+1}^k$ is client $k$'s locally updated parameters, and $n_k$ is client $k$'s local example count, so larger local datasets are weighted more heavily in the average [2]. FedIT applies this same weighted-average rule to the LoRA matrices $(A,B)$ instead of to the full model, which the paper depicts as "Model update by LORA module (A, B)" arriving at the server from each client (Figure 1, Algorithm 1) [1].

**Worked example.** Two clients, ranks and full weight matrices aside, contribute local adapter deltas $\Delta W_1 = B_1 A_1$ and $\Delta W_2 = B_2 A_2$ after one round of local training, with $n_1 = 300$ and $n_2 = 100$ local examples. FedAvg's weighting gives the aggregated update $\Delta W = \tfrac{300}{400}\Delta W_1 + \tfrac{100}{400}\Delta W_2 = 0.75\,\Delta W_1 + 0.25\,\Delta W_2$ [2]; this is the arithmetic implied by combining the paper's LoRA parameterization [1] with FedAvg's weighted-average server step [2], not a convention this card verified against Shepherd's own averaging code.

**Client selection.** Only a fraction of clients train each round: the server "updates M using specific strategies" to pick the participating subset before each round (Algorithm 1) [1]; the paper's own experiments use random selection of 5% of 100 clients per round [1], and the Shepherd repo's client-participation-scheduling module is described in the paper as a vanilla random-selection implementation, with efficiency-driven selection left as future work [1].

## Cost

**Theory, from the method's own math:** local training cost per round scales with the number of participating clients times one local LoRA fine-tuning pass per client (no value network, reference model, or reward model is added by the method's own definition [1]); the base LLM's weights are frozen, so only the low-rank $B,A$ matrices need gradients and optimizer state, not the full parameter count [1]. Communication cost per round scales with the number of participating clients times the size of the transmitted adapter, not the size of the base model, since "clients only need to transmit the B and A matrices of parameters to the server" [1]. A naive reading of the FL loop suggests wall-clock cost scales with the number of communication rounds times a synchronous wait for the slowest selected client per round; the paper's own implementation sidesteps concurrent-client cost by training selected clients one at a time rather than in parallel (see the practice bullet below), so its reported wall-clock time does not reflect true multi-device concurrency [1].

**In practice, per framework:** Shepherd [5] runs local training of selected clients sequentially rather than concurrently, which the paper explains is done "to make it feasible for researchers with limited resources" to simulate FL "computationally expensive" concurrent training [1]. Under this sequential simulation, the paper reports training a 7B LLaMA-based Shepherd-7B model (LoRA applied to all linear layers, rank 8, adapter 0.26% of original parameters) for 20 communication rounds x 5 clients x 1 local epoch on a single NVIDIA Titan RTX (24GB) in 2 hours total, using 23GB of GPU memory (Table 2, Section 4.1) [1]. This is a single-GPU sequential-simulation number, not a distributed-systems benchmark; it says nothing about network communication latency or true concurrent multi-device cost, which the paper's own Future Directions section flags as still an open communication-and-computation-overhead problem for deploying FL with LLMs [1].

## How to use it

- Client data preparation: give each client its own instruction/input/response records in the Alpaca-style template of Table 1 [1]; the reference implementation's `client_data_allocation.py` module splits a source dataset into per-client shards using one of two non-IID partitioning schemes (unbalanced class counts with roughly equal totals, or additionally unbalanced totals) [1].
- Reward/label convention: there is none beyond the instruction-tuning target text itself -- FedIT is supervised instruction tuning distributed across clients, not a reward- or preference-based method [1].
- Key knobs, with each source's own value ("not stated" = the source was checked and does not give the value; "not checked" = this card did not verify that source's key):

| knob | paper's own setting [1] | Shepherd repo default (`main.py` CLI, as documented in its README) [5] |
| --- | --- | --- |
| total clients | 100 | `--num_clients` 10 (example command) |
| clients selected per round | 5 (5%) | `--client_selection_frac` 0.1 (example command) |
| communication rounds | 20 | `--num_communication_rounds` 10 (example command) |
| local epochs per round | 1 | `--local_num_epochs` 2 (example command) |
| LoRA rank $r$ | 8, applied to all linear layers | `--lora_r` 8, `--lora_target_modules` `[q_proj,k_proj,v_proj,o_proj]` (example command) |
| local batch size | 32 | `--local_batch_size` 64, `--local_micro_batch_size` 32 (example command) |
| local learning rate | 1.5e-4 (Adam) | `--local_learning_rate` 0.0003 (example command) |
| max sequence length | 512 | not checked |

  The README's own commands are worked examples in its usage section rather than a documented default config file, so the values above are what the README shows, not a verified default -- re-check the repository's argument parser before relying on them [5].
- Group-size / round trade-off: selecting more clients per round gives the server a more representative aggregate but raises per-round compute and communication cost linearly in the number of participants; the paper's own choice of 5% of 100 clients per round is explicitly a resource-constrained simulation choice, not a tuned optimum [1].
- Install and launch mechanics (dependency list, `pip install -r requirements.txt`, `bitsandbytes` build notes) belong to the Shepherd repository itself and are not repeated here beyond noting they exist [5].

## While it runs

- Signals and their healthy shapes: the paper's own qualitative study monitors GPT-4 pairwise auto-evaluation scores of the aggregated global model against baselines (a no-tuning LLaMA, three single-client "Local" models, and a CentralizedModel upper bound) rather than a training-time loss curve; no loss curve, reward margin, or token-level metric is reported by the paper itself [1]. This card found no first-hand guidance in the paper or the Shepherd repository on the shape of the local training loss during FedIT rounds.
- Published reference runs: the paper's own Table 3 and Figure 3 comparison (Shepherd-7B vs. LLaMA, three single-client Local baselines, and CentralizedModel, each scored against GPT-3.5-turbo/ChatGPT) is the closest thing to a reference run and is the number to compare against in the absence of any other published FedIT run [1].
- Degeneracies and defaults: the paper's own analysis attributes Shepherd-7B's gap to the CentralizedModel upper bound partly to "the local models aggregated at the server side are trained on instructions with substantially different distributions, which can cause their local models to learn different representations of the instructions," i.e., statistical heterogeneity across clients degrades the aggregated model even though the paper elsewhere frames heterogeneity as beneficial for diversity [1]. No config default that silently breaks the method (e.g., a single-client round, or all-identical local data collapsing FedAvg's weighting) was found stated in either source; this reflects a gap in what the two sources document, not a confirmed absence of the failure mode.
- Named successors: FewFedPIT, which frames itself as fixing FedIT's data scarcity and its exposure to training-data-extraction attacks by adding synthetic data generation, parameter isolation training, and mixed public/private parameter aggregation before upload [4].
- Known failure modes: the paper's own Future Directions section (not a formal limitations section, but the paper's closest equivalent) names four open problems it does not solve: (1) communication and computation overhead of exchanging model updates at LLM scale, which it calls "not acceptable" for FL systems in its current form; (2) the risk of malicious clients injecting crafted instructions to bias or degrade the global model, with no defense built into FedIT itself; (3) the need for personalization methods, since a single averaged global model may not fit each client's distinct language, domain, or task distribution; (4) susceptibility to gradient-based text-recovery/data-extraction attacks against the transmitted updates, for which the paper notes existing defenses such as gradient pruning and DPSGD "often come at the cost of significant utility loss" [1]. No maintainer-reported failure modes were found in the Shepherd repository: this card did not query the repository's issue tracker, so absence of maintainer-reported traps here reflects that this search was not performed, not a confirmed absence.
- What the gain is -- and is not: the paper's own analysis shows FedIT lets a federated model trained on privacy-preserving, siloed local data approach (but not match) the quality of a hypothetical centralized model trained on the pooled data (130.7 vs. 142.2, Table 3) [1]; the gain is access to diverse instructions that could not otherwise be centrally collected, not a capability improvement beyond what centralized training on the same underlying data would already achieve, and the paper's own results show centralized training remains the upper bound [1].
