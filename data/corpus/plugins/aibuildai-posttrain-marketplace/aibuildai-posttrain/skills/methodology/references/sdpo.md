# SDPO

GRPO with the scalar reward swapped for a token-by-token distillation signal: reprompt the model with its own failed attempt plus feedback (a runtime error, or another rollout's correct solution), then distill that "self-teacher" distribution back into the model that produced the attempt.

**SDPO** (Self-Distillation Policy Optimization) is an online post-training method for LLMs, introduced in "Reinforcement Learning via Self-Distillation" as a way to convert per-token feedback into a dense training signal without an external teacher or reward model [1]. Its parent is GRPO [2], and the SDPO paper's own comparison describes GRPO's advantage as a single group-normalized scalar reward per rollout, held constant across every token of that rollout [1, Sec. 2.1]. SDPO instead prompts the current policy a second time with the question, the model's own attempt, and feedback about that attempt (an environment output or a peer rollout's correct solution), and treats the resulting "self-teacher" distribution $\pi_\theta(\cdot\mid x,f)$ as a token-level target that the original policy is distilled toward via a KL loss with the teacher's gradient stopped [1]. The paper gives two reasons for this design: scalar RLVR rewards create "a severe credit-assignment bottleneck" because only the final token of an attempt carries information, and many verifiable environments already emit rich textual feedback (runtime errors, judge output) that RLVR discards [1]. A third motivating fact from the paper's own experiments is that GRPO advantages collapse to zero whenever every rollout in a group gets the same reward, stalling learning on that group [1].

No third-party adopters of SDPO were found in the paper's own text, its GitHub repository, or its arXiv listing as read for this card; it was introduced in 2026 and released with its own reference implementation, built on top of a recent version of verl [1][3]. Against a GRPO baseline extended with several recent stabilizers (asymmetric clipping, unbiased length normalization, off-policy correction) [2][4][5][6], the paper reports SDPO reaching the same LiveCodeBench v6 accuracy as that baseline in 4x fewer generations, and a final accuracy of 48.8% versus GRPO's 41.2% with Qwen3-8B [1, Fig. 1]. On chemistry question-answering with Olmo3-7B-Instruct, SDPO reaches GRPO's 5-hour accuracy in 50 minutes of wall-clock training (a 6x speedup) and ends more than 10 percentage points higher [1, Sec. 3.2, Fig. 6]. Aggregated across its five no-feedback tasks (science QA and tool use), combined over both Qwen3-8B and Olmo3-7B-Instruct runs, SDPO reaches 70.2% final accuracy against the augmented GRPO baseline's 66.6% [1, Sec. 3]. Lineage in one line: PPO (2017 [7]) -> GRPO (DeepSeekMath, 2024 [2]) -> SDPO (2026 [1]), with on-policy distillation from an external teacher (GKD, 2024 [8]) as a sibling idea SDPO borrows its stability trick from (symmetric Jensen-Shannon loss) [1]. The paper was confirmed as the right match by checking its arXiv abstract page: the title "Reinforcement Learning via Self-Distillation" matches the shortlist row's title field exactly [1].

**When to pick it**: pick SDPO over its parent GRPO [2] when the environment already returns rich per-attempt feedback (compiler errors, unit-test tracebacks, judge rationales) and the base model is large enough to use that feedback in-context — the paper finds the gain over GRPO grows with model scale and can flip negative on a 1.5B model [1, Sec. 4.1]. Prefer on-policy distillation from an external teacher [8] when a stronger model than the student is available to supervise it; SDPO is designed for the case where no such teacher exists and the model must supervise itself [1]. Prefer DPO [9] when training data is a fixed set of preference pairs and fresh rollouts are not available each step; DPO is offline and needs no sampling from the policy during training [9], whereas SDPO samples on-policy every step, like GRPO [1].

**Variant of**: GRPO [2], which is itself a variant of PPO [7].

**Data it needs**: prompts only, no pre-collected labels — SDPO samples G rollouts per prompt from the current policy each step, exactly like GRPO [1]. It additionally needs a source of "feedback" text per rollout: either genuine environment output (compiler/runtime errors, the paper's coding experiments) or, when the environment returns only a scalar reward, another rollout in the same group that succeeded on the same question, used as an implicit sample solution [1]. The paper's rich-feedback experiments (LiveCodeBench v6, Qwen3-8B) used a batch of 32 questions x 8 rollouts, max response length 8192; its no-feedback experiments (SciKnowEval science QA, ToolAlpaca tool use) used the same batch shape [1, Table 12]. On-policy: every gradient step consumes rollouts sampled from the current policy that same step; the paper's reported results use strictly one gradient step per generation batch, though it notes off-policy multi-step updates as future work [1, Sec. 3.2]. On-policy sampling is not incidental to the gain: an ablation that instead does SFT on the initial self-teacher's outputs (off-policy) reaches only 42.7% on the training task, versus SDPO's 48.8% (see While it runs) [1, Sec. 4.4, Table 5].

**Extra models**: no separate value network and no explicit reward model — SDPO's advantage comes from the self-teacher, which is the same weights as the student, reprompted [1]. It does use a second copy of the policy's logits: a "teacher" that the paper regularizes against fast drift, either as an exponential moving average (EMA) of the student's own weights or by interpolating with the initial teacher (trust-region), so an EMA copy of the model's weights must be held/updated alongside the trained one [1, Sec. 2.3]. The reference implementation keeps this EMA teacher on verl's `RefWorker` [3]. See Cost for what this and the extra forward pass cost in practice.

**Shipped by**: only the paper's own code, `lasgroup/SDPO`, a repository the README states is built on top of a recent version of verl and which adds `actor.policy_loss.loss_mode = "sdpo"` plus an `actor.self_distillation` config block on top of that base [3]. GitHub's own repository metadata marks it as not a fork (`"fork": false`) [3], so it is a standalone codebase derived from verl rather than a forked/linked repository in GitHub's sense. This card did not fetch trl or the upstream `volcengine/verl` repository, so it cannot state whether either has since added SDPO; the only source read is `lasgroup/SDPO` itself, and running SDPO today means installing that repository (`pip install -e .` after cloning) [3].

## How it works

The loop, per step: sample G rollouts per prompt from the current policy, evaluate each for feedback (an environment message or a peer's successful rollout), reprompt the same policy with question + feedback + the original attempt to get the self-teacher's next-token distribution over that attempt, and take a gradient step on the KL between student and (stop-gradient) teacher [1, Algorithm 1].

**The loss** [1, Eq. 1]:

$$ \mathcal{L}_{\mathrm{SDPO}}(\theta) := \sum_t \mathrm{KL}\big(\pi_\theta(\cdot \mid x, y_{<t}) \,\|\, \mathrm{stopgrad}(\pi_\theta(\cdot \mid x, f, y_{<t}))\big) $$

$x$ is the prompt, $y_{<t}$ the model's own attempt up to token $t$, and $f$ the feedback (environment output and/or a sample solution) appended to the teacher's context; $\mathrm{stopgrad}$ blocks gradients through the teacher term so training cannot collapse by making the teacher regress toward the student instead of learning from $f$ [1]. $\mathrm{KL}(p\|q) = \sum_i p(i)\log(p(i)/q(i))$ is the standard forward KL used as the distance between the two next-token distributions [1].

**The gradient**, derived from that loss [1, Eq. 2 / Prop. 2.1]:

$$ \nabla \mathcal{L}_{\mathrm{SDPO}}(\theta) = \mathbb{E}_{y \sim \pi_\theta(\cdot|x)}\left[\sum_{t=1}^{|y|} \mathbb{E}_{\hat y_t \sim \pi_\theta(\cdot|x,y_{<t})}\left[ \log\frac{\pi_\theta(\hat y_t|x,y_{<t})}{\pi_\theta(\hat y_t|x,f,y_{<t})} \cdot \nabla_\theta \log \pi_\theta(\hat y_t|x,y_{<t}) \right]\right] $$

The paper reads this as a policy gradient with a logit-level advantage: comparing it to GRPO's advantage term makes the connection explicit [1, Sec. 2.1]:

$$ A^{\mathrm{GRPO}}_{i,t} := r_i - \mathrm{mean}\{r_i\}_{i=1}^G \ \text{(constant in } t\text{)}, \qquad A^{\mathrm{SDPO}}_{i,t}(\hat y_{i,t}) = \log\frac{\pi_\theta(\hat y_{i,t}|x,f_i,y_{i,<t})}{\pi_\theta(\hat y_{i,t}|x,y_{i,<t})} $$

GRPO's advantage is one number per rollout, applied to every token of that rollout equally; SDPO's advantage is one number per token per candidate next-token (not just the sampled one), positive where the teacher finds a token more likely than the student did and negative where less likely, and zero only where student and teacher exactly agree [1, Sec. 2.1]. In practice, computing this for the full vocabulary is approximated by top-$K$ distillation: only the top-$K$ student logits plus a tail-probability bucket are distilled, giving $|y|\cdot(K+1)$ advantages per sequence rather than $|y|\cdot|\mathcal{V}|$ [1, Sec. 2.2, Sec. 4.2].

Worked example, from the paper's own qualitative figure: a coding attempt has a bug where a returned range can contain $n$; reprompting the same model with the unit-test failure as feedback makes the teacher assign higher probability to the tokens of the corrected boundary condition and lower probability to the original (buggy) tokens the student actually emitted, so the per-token advantage is positive at the corrected tokens and negative at the emitted buggy ones — a sparse, token-localized signal rather than one constant number over the whole response [1, Sec. 4.2, Fig. 9]. When no rich feedback exists, the paper substitutes another rollout's successful attempt to the same question as the sample solution shown to the teacher [1, Sec. 3.1].

**Variants the paper defines**: a per-token gradient estimator (used for all reported results) that treats the sampling distribution over $y$ as fixed, and a sequence-level estimator that additionally accounts for how an early token changes the prefix distribution over later tokens; the paper tried the sequence-level estimator and found no measurable gain over its added complexity, so it is not what the reference implementation runs by default [1, App. A.1]. For the distillation divergence itself, the paper interpolates between forward KL and reverse KL via a Jensen-Shannon-style mixture, adopting the symmetric JS divergence because prior on-policy-distillation work found it more stable than a plain KL [1, Sec. 2.3][8]. The reference implementation exposes this as `self_distillation.alpha` (0.0 = forward KL, 1.0 = reverse KL, 0.5 = JSD) [3].

## Cost

**Theory, from the method's own math**: each step needs the same G rollouts per prompt as GRPO, so generation cost is identical to GRPO's [1]. Training additionally requires one extra forward pass per step: the self-teacher's log-probabilities over the (frozen, already-generated) attempt, conditioned on the feedback-augmented prompt [1, Algorithm 1, step 6]. No value network and no reward model forward/backward are needed [1]. Naively, computing the KL against the full vocabulary distribution requires holding both models' full logits in memory; the paper avoids this specifically with top-$K$ distillation rather than by any change to the loss itself [1, Sec. 2.2].

**In practice, per framework**: the paper itself, whose experiments run on the `lasgroup/SDPO` codebase built on verl, reports that the only computational overhead of SDPO relative to its GRPO baseline is the extra self-teacher log-prob computation, which is faster than sequential generation because it can be run in parallel rather than autoregressively [1, Sec. 2.2, Fig. 5]; at a micro-batch size of 2, this overhead is described as relatively small, and the paper notes it can shrink further with larger micro-batches [1, Sec. 2.2]. The teacher's EMA weights are held on verl's `RefWorker` when `teacher_regularization="ema"` [3]. This card did not fetch trl or upstream `volcengine/verl`, so it cannot report cost figures for those two libraries specifically.

## How to use it

- Prompts only; SDPO does not require preference pairs or a scored dataset, but it does need an evaluable environment (unit tests, a scoring function, or a way to detect success) to generate the feedback text that becomes $f$ [1, Sec. 3.1, Sec. 4].
- Reward/label convention in the reference implementation: a rollout counts as a "successful demonstration" usable as a sample solution for other rollouts when its sequence reward is at least `success_reward_threshold` (default 1.0) [3]. `environment_feedback_only_without_solution` (default True) uses raw environment output only when no successful peer solution exists for that question, preferring a full correct solution over an error message when both are available [3]. `dont_reprompt_on_self_success` (default True) stops a successful rollout from being reprompted with itself as its own solution [3].
- Key knobs, with each source's own value (paper values are the two configurations actually reported; the reference repo has no separate "framework default" distinct from the paper since it is the paper's own code):

| knob | SDPO, rich-feedback setting (Sec. 4) [1, Table 12] | SDPO, no-feedback setting (Sec. 3) [1, Table 12] | GRPO baseline (Sec. 3) [1, Table 13] |
| --- | --- | --- | --- |
| rollouts per question (G) | 8 | 8 | 8 |
| distillation divergence | reverse-KL | Jensen-Shannon | n/a |
| top-$K$ distillation | 20 | 100 | n/a |
| teacher-EMA update rate | 0.01 | 0.05 | n/a |
| learning rate | $1\times10^{-6}$ | $1\times10^{-5}$ | $1\times10^{-6}$ (default) / $1\times10^{-5}$ (on-policy) |
| clip advantages | n/a$^\dagger$ | n/a$^\dagger$ | n/a |
| GRPO clip range ($\epsilon$-high) | n/a | n/a | 0.28 |
| GRPO KL coefficient | n/a | n/a | 0.0 |

  $^\dagger$Table 12 marks "Clip advantages" with a dash for both the rich-feedback and no-feedback settings, the same dash the paper uses elsewhere in that table for parameters that do not apply to a given setup; the paper only assigns clip advantages a value (5.0) in its separate test-time-training configuration, which is outside this card's scope [1, Table 12]. The divergence and top-$K$ settings differ between the two experimental setups reported in the paper itself, not between a paper value and a framework default — there is no independent "framework default" here since the repository is the paper's own reference code [1, Table 12].
- Group-size trade-off is the same shape as GRPO's: the paper uses G=8 in its main runs [1, Table 12], and a larger group gives more candidate solutions for the implicit-feedback case (Sec. 3) at proportionally higher rollout cost.
- Install and launch mechanics (Docker vs. pip, vLLM/SGLang inference backend choice, cluster configuration) belong to the reference repo's own README, not this card [3].

## While it runs

- **Signals and their healthy shapes**: the paper reports that SDPO's responses are consistently shorter than GRPO's at equal or higher accuracy — more than 3x shorter on average across its tasks, and 11x shorter on the chemistry task with Olmo3-7B-Instruct — and attributes GRPO's longer responses to "filler phrases like 'Hmm' and 'Wait'" and circular repeated reasoning that SDPO's dense per-token advantage avoids [1, Sec. 3.3]. No separate SDPO-specific metric name (analogous to GRPO's clip-fraction) is defined in the paper for live monitoring beyond accuracy and response length; the reference repo logs to Weights & Biases but this card does not certify specific dashboard names beyond what the paper's text states [1][3].
- **Published reference runs**: the paper's own Figure 1 (Qwen3-8B on LiveCodeBench v6) and Figure 6 (Olmo3-7B-Instruct and Qwen3-8B on SciKnowEval Chemistry) are the cited reference curves, each averaged over 3 seeds with reported standard deviation/error bands, plus a public W&B project the repo links to [1, Fig. 1, Fig. 6][3].
- **Degeneracies and defaults**: the paper names two specific failure conditions its design targets — GRPO advantages collapsing to zero when every rollout in a group gets the same reward (SDPO's implicit-feedback mode is proposed as a fix, using a peer's success as feedback for failures instead of a flat zero advantage) [1, Sec. 3, Sec. 1], and unregularized teacher drift, which the paper found needs an EMA or trust-region constraint on the teacher for stable training [1, Sec. 2.3]. GRPO's own KL-coefficient default in the paper's baseline is 0.0 (no KL penalty against a reference model) [1, Table 13], a separate knob from SDPO's teacher-regularization mechanism.
- **Named successors**: none found — the paper is dated January 2026 and this card's search was limited to the paper's own text, its GitHub repository, and its arXiv listing as of this reading; no successor paper is cited by name in any of these sources.
- **Known failure modes**: from the paper's own limitations section — SDPO's benefit is tied to the base model's in-context learning ability, and it can underperform GRPO on weaker models (the paper reports this on Qwen2.5-1.5B) [1, Sec. 4.1, Sec. 7 Limitations]; SDPO's gain also depends on feedback quality, and the paper states that if the environment gives "uninformative or misleading feedback," the model may not learn from it via SDPO [1, Sec. 7 Limitations]; SDPO adds a small compute overhead versus GRPO for the teacher log-prob pass, which the paper says may be proportionally larger for smaller models with shorter generations, where generation itself is cheap [1, Sec. 7 Limitations].
- **What the gain is - and is not**: the paper's own analysis is about efficiency and reasoning style, not new capability: SDPO reaches a given accuracy in fewer generations and produces shorter, less repetitive reasoning traces than GRPO at equal or better accuracy [1, Sec. 3.2, Sec. 3.3]. The paper's own ablation isolates why: training an SFT baseline directly on the initial self-teacher's outputs (an off-policy imitation of the same self-distillation signal, no on-policy loop) reaches only 42.7% on the training task LCBv6, barely above GRPO's 41.2% and far below SDPO's 48.8%, and it forgets more on held-out tasks (41.4% average holdout accuracy versus SDPO's 42.4%) [1, Sec. 4.4, Table 5]. That comparison is the paper's own evidence that on-policy resampling every step, not just the self-teacher's feedback signal itself, is what produces most of SDPO's gain.
