# ToRL

Item: https://arxiv.org/abs/2503.23383

GRPO run from a base model with a code interpreter spliced into the rollout: when the model emits a code block the sandbox executes it and the output is fed back into the same completion, and the reward adds a code-executability term on top of GRPO's answer-correctness reward.

**ToRL** (Tool-Integrated Reinforcement Learning) is an RL recipe for training an LLM to invoke a code interpreter during reasoning, introduced by Li, Zou, and Liu as a framework "designed to train large language models (LLMs) to autonomously utilize computational tools through scaling reinforcement learning directly from base models" [1]. Its parent is GRPO, defined by Shao et al. as a variant of Proximal Policy Optimization (PPO) [2] that replaces the value network with a group-relative reward baseline [3]; ToRL runs GRPO unmodified as the optimizer and changes what happens inside the rollout and the reward [1]. During generation, whenever the model outputs a code-termination marker the system pauses, executes the most recent code block in an isolated sandbox, and inserts the result back into the context so generation continues conditioned on it, repeating until a final answer or a fresh code block appears [1]. The paper gives two reasons for building it this way rather than following prior Tool-Integrated Reasoning (TIR) work: existing TIR systems such as ToRA and MathCoder distill trajectories from a stronger model and then apply supervised fine-tuning, which restricts models to predetermined tool-use patterns [1][4][5]; and RL directly on a base model, with no SFT stage, lets the model discover tool-use strategies through open-ended exploration instead of imitating fixed patterns [1]. The identity of the paper was confirmed by an exact-title search on arXiv for "ToRL: Scaling Tool-Integrated RL" returning a single candidate [1].

The paper reports its own gains rather than citing external landmark adopters: on Qwen2.5-Math-7B-Base, ToRL-7B reaches 43.3% pass@1 on AIME24 versus 26.7% for Qwen2.5-Math-7B-Instruct-TIR (the strongest prior TIR baseline they test) and 33.3% for SimpleRL-Zero (GRPO-style RL with no tool), and reaches 30.0% on AIME25 versus 16.7% and 6.7% respectively (Table 3) [1]. This card did not find, in the sources fetched, any later system that names ToRL as a component it adopted; the checks were the paper's own text [1] and the GAIR-NLP/ToRL GitHub repository page [6], neither of which lists downstream adopters. Lineage in one line: PPO (2017 [2]) -> GRPO (DeepSeekMath, 2024 [3]) -> ToRL (2025 [1]).

**When to pick it**: pick ToRL's rollout-and-reward pattern when the task is machine-verifiable (a checkable final answer, as in competition math) and precise computation is the bottleneck for a pure chain-of-thought policy, and you are willing to run RL directly from a base model rather than an instruction-tuned one [1]. Its parent, plain GRPO on chain-of-thought with no tool, is the nearer choice when the task does not benefit from code execution [3]. The nearest offline alternative is SFT-based Tool-Integrated Reasoning such as ToRA, which builds a training set of worked examples showing a model reasoning with a code interpreter and then fine-tunes on those examples directly, rather than letting the policy explore tool use on its own [4]. The nearest online neighbor is tool-free zero-RL such as SimpleRL-Zero, which the ToRL paper itself lists in its Table 3 results as an RL baseline with no tool column checked, i.e. chain-of-thought RL from a base model with no interpreter in the loop [1].

**Variant of**: GRPO [3], with the policy-update math untouched and the rollout/reward changed [1].

**Data it needs**: prompts only, each with a checkable final answer, no chosen/rejected pairs or step-level annotations. The paper's own training set is 28,740 competition-math questions, filtered from an initial 75,149 verifiable questions sourced from NuminaMATH, MATH, and DeepScaleR, then downselected with the LIMR data-distillation technique for a balanced difficulty spread [1]. Training used Qwen2.5-Math-1.5B-Base and Qwen2.5-Math-7B-Base with no prior SFT, a rollout batch size of 128 prompts, and 16 sampled completions per prompt [1]. On-policy: every step samples fresh completions, each interleaved with live sandbox calls, from the current policy [1].

**Extra models**: none beyond the policy being trained. GRPO's value network is absent, per its own definition [3]. Unlike vanilla GRPO configurations that keep the KL term, ToRL's own experiments "omit the KL loss" entirely [1], so no frozen reference model is loaded either. Beyond the neural policy, the method requires a non-model service: an isolated code-execution sandbox; the paper tested the qwen-agent Python executor for its low latency but rejected it because it lacks isolation from the training process, and instead adopted Sandbox Fusion for stability despite its higher latency [1]. See Cost for what the sandbox costs in wall-clock time.

**Shipped by**: no framework ships a trainer named ToRL. The paper's own reference implementation is the GAIR-NLP/ToRL GitHub repository, which is not a GitHub fork of verl (its own repository metadata records `fork: false`) but bundles a full copy of verl inside the repo and patches `verl/workers/rollout/vllm_rollout/vllm_rollout_spmd.py` to call an external Sandbox Fusion server mid-rollout; it is launched via a training script rather than an installable package entry point [6]. Two frameworks now ship generic multi-turn tool-calling infrastructure that the method could be rebuilt on: trl's `GRPOTrainer` exports an `environment_factory` / `tools` mechanism where a Python method (e.g. `run_code`) is exposed to the model as a callable tool during generation, bounded by a `max_tool_calling_iterations` parameter that plays the same role as ToRL's own tool-call cap [7]; verl's mainline docs describe a general sglang-backed multi-turn rollout (`rollout.multi_turn: True`) with custom tools built on `verl.tools.base_tool.BaseTool`, and document a Sandbox Fusion integration pattern explicitly as "a reimplementation of retools" (a different, later tool-RL system) — though verl's own in-tree `SandboxFusionTool` reference implementation has since been removed from the codebase [8]. Building ToRL today means writing a code-execution tool and a correctness/executability reward on top of one of these generic multi-turn GRPO trainers, not writing a new sampling loop from scratch.

## How it works

Each step: sample completions for a batch of prompts under GRPO's usual group-sampling loop, but let each completion's generation be interrupted by code execution; score each completion with a rule-based reward; normalize rewards within the group and update the policy with GRPO's clipped objective [1][3].

**Rollout with tool calls.** Given model $M$, code interpreter $I$, and question $Q$, the paper formalizes the reasoning trajectory built at step $k$ as [1]:

$$ s_k = r_1, c_1, o_1, \dots, r_k, c_k, o_k, \qquad (r_k, c_k) = M(Q \oplus s_{k-1}), \qquad o_k = I(c_k), \qquad s_k = s_{k-1} \oplus r_k \oplus c_k \oplus o_k $$

where $r_i$ is a natural-language reasoning span, $c_i$ is generated code, and $o_i$ is that code's execution result; generation continues until the model emits a final answer [1]. Error messages from failed executions are returned to the model rather than discarded, on the hypothesis that seeing its own errors improves subsequent code quality [1]. Because unrestricted tool calls make rollout throughput fall as call frequency rises, ToRL introduces a hyperparameter $C$, the maximum number of tool calls allowed in one response; once exceeded, further code-execution requests are ignored and the model is forced into pure-text reasoning for the rest of that completion [1]. Sandbox output tokens ($o_i$) are masked out of the loss so the model is not trained to memorize execution outputs [1].

**Reward.** A rule-based scheme: a correct final answer scores $+1$, an incorrect one scores $-1$; optionally, a response whose code fails to execute takes an additional $-0.5$ penalty, called the Code Executability Reward [1]. The paper's default experiments use only the correctness term, not the executability penalty, which they find in an ablation does not help (see While it runs) [1].

**Advantage and update: unmodified GRPO.** ToRL's own text states only that it employs the GRPO algorithm [1]; the group-relative advantage and clipped-ratio objective are exactly GRPO's, as defined in Shao et al.: each of $G$ sampled completions per prompt gets a scalar reward $r_i$, normalized within the group as $\tilde r_i = (r_i - \mathrm{mean}(\mathbf r))/\mathrm{std}(\mathbf r)$, which becomes every token's advantage in that completion [3].

**Worked example.** Take a group of $G=4$ completions to one prompt, scored under ToRL's default reward (correctness only, no executability penalty): two correct answers, one incorrect answer, and one completion whose code fails to execute but that nonetheless lands on the correct final answer. Rewards are $\{1, 1, -1, 1\}$ (the executability penalty is off by default, so the failed-code completion still scores $+1$ for correctness) [1]. Group mean is $0.5$, population std is $\sqrt{\big((0.5)^2\cdot3+(1.5)^2\big)/4} = \sqrt{3/4}\approx0.866$; each correct completion gets advantage $(1-0.5)/0.866\approx+0.577$, and the incorrect one gets $(-1-0.5)/0.866\approx-1.732$, per GRPO's normalization formula [3]. If the executability penalty were switched on, the failed-code-but-correct completion's reward would instead be $1-0.5=0.5$, changing the group's mean and every completion's advantage — the ablation in While it runs is exactly about whether that switch helps.

## Cost

**Theory, from the method's own math:**

- Time: on top of GRPO's per-completion generation cost, every code block triggers a pause-execute-resume round trip to an external sandbox process; the paper states the resulting GPU idle time scales with tool-call frequency, and caps it with the $C$ hyperparameter [1]. This is a training-time-only cost — the RL objective and gradient computation are unchanged from GRPO [3].
- Memory: identical to GRPO minus the value network [3], and with the paper's default of omitting the KL loss, minus the reference model too [1] — so the naive reading is that ToRL trains and holds only the policy, plus whatever memory the reward computation (verifying a final answer, checking code executability) needs, which is negligible next to model memory.

**In practice, per framework:**

- The authors' bundled, patched copy of verl [6]: step time was measured directly at $C=0$: 118 s, $C=1$: 237 s, $C=2$: 288 s per step on an 8×A800 system (Table 4) [1] — going from no tool calls to one roughly doubles step time, and a second call adds about another fifth on top. The sandbox choice trades latency for isolation: Sandbox Fusion is slower than the qwen-agent executor the authors first tried, but was kept because the qwen-agent executor's lack of process isolation risked crashing the training run on illegal-memory-access errors from generated code [1].
- trl `GRPOTrainer` [7]: tool-calling turns are bounded by `max_tool_calling_iterations`, unlimited by default (generation stops only when the model emits a turn with no tool calls or hits `max_model_length`) [7]; as in plain GRPO, `beta=0.0` by default means the reference model is not loaded at all, cutting memory versus a KL-regularized run [7].
- verl mainline's generic multi-turn/tool path [8]: enabling `rollout.multi_turn: True` switches the rollout engine to sglang for tool interaction; cost inside one rollout step is bounded by the batch-size and micro-batch settings documented on the verl GRPO page, not by the tool itself [9]. Framework-level batching/parallelism detail beyond this stays on the verl skill's own cards.

## How to use it

- Data prep: start from questions with a machine-checkable final answer; the paper filtered proof-based and ambiguously-verifiable problems out of its NuminaMATH/MATH/DeepScaleR pool before applying LIMR-based difficulty balancing [1]. No chosen/rejected pairs or per-step labels are needed.
- Reward convention (paper's default): $+1$ for a correct final answer, $-1$ for incorrect, evaluated by the same rule-based checker used at evaluation time; the optional $-0.5$ code-executability penalty is defined but left off by default because the authors found it does not improve results [1].
- Sandbox setup is a prerequisite, not a training knob: the authors' repo requires standing up a separate Sandbox Fusion service and pointing the patched vLLM rollout at its URL before training starts [6].

| knob | ToRL paper default [1] | trl `GRPOTrainer` default [7] | verl GRPO default [9] |
| --- | --- | --- | --- |
| max tool calls per response ($C$) | 1 (ablated at 2) | `max_tool_calling_iterations` unlimited (`None`) | not stated (no built-in $C$-equivalent; bounded by turn budget in custom tool config) |
| group size $G$ / samples per prompt | 16 | `num_generations` 8 | `rollout.n` 1 (must be raised for GRPO) |
| KL coefficient | KL loss omitted (no $\beta$ used) | `beta` 0.0 (KL off, reference model not loaded) | `kl_loss_coef` 0.001, but `use_kl_loss` defaults to False |
| rollout batch size (prompts) | 128 | not stated | `train_batch_size` not stated (paired with `rollout.n`) |
| sampling temperature | 1 ("to enhance model exploration") | `temperature` 1.0 | not checked here |
| code-executability penalty | 0 (off by default; defined as $-0.5$, ablated) | not applicable (no built-in reward) | not applicable (no built-in reward) |

  Two readings of that table: the paper turns the KL term off entirely, which trl's own default (`beta=0.0`) already matches, but verl's GRPO recipe defaults to the term being off too (`use_kl_loss=False`) even though its nonzero `kl_loss_coef` might suggest otherwise — the coefficient only applies once the flag is turned on [9]; and neither framework has a first-class $C$-style tool-call cap matching the paper's own knob, so reproducing the paper's $C=1$ default means configuring it yourself in `max_tool_calling_iterations` (trl) or in a custom tool's turn-budget logic (verl) [7][8].
- Trade-off the paper measured directly: raising $C$ from 1 to 2 improved average accuracy by roughly 2 percentage points but pushed step time from 237 s to 288 s (Table 4) — more tool calls help, but rollout speed pays for it linearly-ish, requiring an explicit performance/efficiency trade-off [1].

## While it runs

- Signals and their healthy shapes, from the paper's own training-dynamics analysis (§3.3.1) [1]: **Code Ratio**, the fraction of responses containing code, rose from about 40% to about 80% over the first 100 steps, meaning the model progressively adopts tool use over the SFT-free RL run — a flat or falling Code Ratio would mean the model is not learning to use the tool. **Pass Ratio**, the fraction of executed code that runs without error, trended upward continuously, tracking growing coding competence. The **Pass Ratio of correct vs. incorrect responses** diverges: correct final answers correlate with higher code-execution success, so a persistent gap where incorrect responses have much lower pass rates than correct ones is the expected healthy pattern, not a bug. **Effective Code Ratio** tracks two separate metrics that both rose over training: the executed-code ratio (code that runs without error) and, independently, the before-final-answer code ratio (code generated before the final answer rather than as post-hoc verification) [1].
- Published reference runs: Figure 1 in the paper plots AIME24 accuracy against training step (16-step moving average) for both ToRL-1.5B and ToRL-7B against a no-tool RL baseline and against Qwen2.5-Math-Instruct-TIR, showing ToRL ahead throughout training by up to 12 points (1.5B) and 14 points (7B) [1]; the final-checkpoint numbers are the Table 3 comparison already given above. No separate raw-log release for these curves was checked beyond the paper's own figures and the GitHub repository's released checkpoints [6].
- Degeneracies and defaults: a group of one (`rollout.n` left at verl's default of 1) removes GRPO's baseline entirely, exactly as for plain GRPO [9]. The paper's own ablation (§3.3.2, Table 4 and surrounding text) found that turning on the Code Executability Reward — penalizing non-executable code — did not improve performance, and the authors hypothesize this pushes the model toward "overly simplistic code to minimize errors," at the cost of problem-solving ability [1] — so enabling that reward term is a documented way to make training worse, not better.
- Named successors: this card did not find, among the sources fetched, a paper that explicitly names itself as fixing a bias documented in the ToRL paper; verl's own docs describe their generic Sandbox Fusion tool integration as a reimplementation of a separate, later system called "retools," not as a ToRL successor [8], and this card has not fetched a defining source for that system.
- Known failure modes: from the paper's own analysis — increasing the tool-call cap $C$ buys accuracy but costs training throughput, a trade-off the authors present as a limitation of scaling tool-call frequency rather than a free improvement [1]; and the Code Executability Reward ablation itself is a documented failure mode of adding execution-penalty shaping (see above) [1]. No maintainer-reported issue on the GAIR-NLP/ToRL repository was checked for this card beyond the README and top-level file listing [6]; that search was not performed, so no closed-issue failure modes are reported here.
- What the gain is — and is not: the paper attributes ToRL's improvement to giving the model access to precise computation during RL exploration, evidenced by the Code Ratio and Pass Ratio trends showing the model autonomously learning when tool use helps [1]; it does not claim the RL stage teaches new mathematical knowledge beyond what the base model and interpreter jointly make reachable, and the comparisons throughout are against SFT-based TIR and no-tool RL baselines on the same base models, not against a claim of new reasoning capability [1].
