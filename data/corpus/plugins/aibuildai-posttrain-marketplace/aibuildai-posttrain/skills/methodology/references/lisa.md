# LISA

Full-parameter AdamW fine-tuning where, every few steps, all transformer layers except the embedding and the LM head are frozen and only a small random subset of the remaining layers is left trainable, so gradients and optimizer state exist for a fraction of the model at a time.

Paper: https://arxiv.org/abs/2403.17919 [1].

**LISA** (Layerwise Importance Sampled AdamW) is a memory-efficient full-parameter fine-tuning method for LLMs, defined by its paper as an optimization algorithm that randomly freezes layers of an LLM based on a given probability, proposed as an alternative to LoRA [1]. Its parent is standard AdamW full-parameter fine-tuning [2]; LISA does not add adapters the way LoRA does [3], it instead trains the original weights but keeps most of the network frozen at each step, reactivating a fresh random subset of intermediate layers every few hundred steps while the embedding and head stay trainable throughout [1]. The paper gives two motivations beyond memory: it observed that LoRA's per-layer weight norms are heavily skewed toward the bottom and top of the network, suggesting the "middle" layers matter less and can be visited less often; and it derives a sampling probability per layer, $p^{(\ell)} = \tilde{\mathbf{w}}^{(\ell)}/\mathbf{w}^{(\ell)}$, designed so that randomly freezing layers with this probability reproduces LoRA's expected per-layer update magnitude in a full-parameter run [1]. The check on the confirmation: the row's title matched a single candidate on arXiv, id 2403.17919 [1], and the paper's own text and equations were read directly rather than relying on a summary.

LISA is shipped by two open-source fine-tuning toolkits, both letting a user turn it on with a couple of config keys rather than writing training code [4][5]. A file-path search of the full repository trees of Hugging Face's trl and hiyouga's LLaMA-Factory (no "lisa" match in either) shows neither framework implements a LISA trainer or callback; this establishes only that those two frameworks do not ship the method, not whether any large-model technical report used it. In the originating paper, on LLaMA-2-7B with the Alpaca-GPT4 instruction data, LISA scored 4.94 on MT-Bench versus 4.45 for LoRA (rank 128), 4.75 for full fine-tuning, and 3.29 for the untuned base model (Table 3) [1]; on LLaMA-2-70B it scored 6.72 versus LoRA's 6.10, full fine-tuning's 6.25, and the base model's 5.19 (Table 5) [1]. Lineage: AdamW full-parameter fine-tuning [2] and LoRA [3] -> LISA (2024) [1] -> shipped by axolotl and LMFlow [4][5] -> MISA (2025), which targets a documented limitation of LISA-style layer-wise sampling [6].

**When to pick it**: pick LISA for supervised or continued-pretraining fine-tuning of a single model on labeled or plain-text data when you want full-parameter-level quality on a LoRA-level memory budget, especially on models too large to fully fine-tune (the paper scales to LLaMA-2-70B) [1]. Prefer full-parameter fine-tuning [2] if memory is not the constraint, since it is the ceiling LISA and LoRA are both compared against [1]. Prefer LoRA [3] if you need merge-and-swap adapters or multiple task-specific deltas on one base model; LoRA confines the update to a low-rank subspace, which the LISA paper argues caps its quality relative to full-parameter training in large-scale settings [1]. GaLore is the nearest gradient-space alternative: it projects gradients into a low-rank subspace to cut optimizer-state memory while still updating all parameters, rather than freezing whole layers [7]; the LISA paper's own MT-Bench table shows LISA ahead of GaLore on Mistral-7B (4.85 vs 4.36) and LLaMA-2-7B (4.94 vs 4.63), but behind GaLore on TinyLlama (2.57 vs 2.61) (Table 3) [1].

**Variant of**: not a formal variant of LoRA — the paper presents it as an alternative to LoRA [1] — but algorithmically it is AdamW full-parameter fine-tuning [2] with a random layer-freezing schedule layered on top, so its true parent is full-parameter AdamW training.

**Data it needs**: any labeled fine-tuning set (prompt/response pairs, e.g. the paper's 52K-pair Alpaca-GPT4 instruction data) or plain unlabeled text for continued pretraining (the paper used a 1.5-billion-token OpenWebMath subset) [1]; there is no reward or preference-pair requirement, since training is ordinary supervised next-token or instruction-tuning loss. It is offline in the reinforcement-learning sense — no fresh generation from the model during training — training scale in the paper ran up to LLaMA-2-70B on the instruction and domain-QA tasks [1].

**Extra models**: none. LISA trains a single model's own parameters; the paper's Algorithm 1 requires no value network, reference model, reward model, or judge [1].

**Shipped by**: axolotl, config keys `lisa_n_layers` and `lisa_step_interval` (plus `lisa_layers_attribute`, default `model.layers`), read from `src/axolotl/utils/schemas/integrations.py` and wired into the trainer via `lisa_callback_factory` in `src/axolotl/utils/callbacks/lisa.py`, tree read at commit `93dcd622f1ceddaabce272569736ec0f205fba4d` on `main` [4]. LMFlow, the paper authors' own toolkit, via `--use_lisa 1` and `--lisa_activated_layers`, plus a layer-switching-interval flag whose name its own README gives inconsistently (`--lisa_interval_steps` in the worked bash example, `--lisa_step_interval` in the surrounding prose) [5]; its README states the LISA script is currently only tested on a single GPU [5]. Neither trl nor LLaMA-Factory has a "lisa" match anywhere in its repository file tree as of the trees checked [4][5] (see While it runs for the multi-GPU caveat that may explain the narrower adoption).

## How it works

Every `K` steps: freeze every layer except the embedding and the LM head, draw `γ` intermediate layers uniformly at random and unfreeze them too, then run `K` steps of ordinary AdamW with only those layers' parameters receiving gradients [1].

**Algorithm 1** [1], with $N_L$ the number of layers, $T$ the total number of iterations, $K$ the sampling period, $\gamma$ the number of sampled layers, and $\eta_0$ the initial learning rate:

for $i = 0$ to $T/K - 1$: freeze all layers except the embedding and language-modeling-head layer; randomly sample $\gamma$ intermediate layers to unfreeze; run AdamW for $K$ iterations with learning rates $\{\eta_t\}_{t=ik}^{ik+k-1}$ [1].

The paper motivates the specific choice of $\gamma$ intermediate layers via an importance-sampling argument: to make a full-parameter run's expected per-layer update match LoRA's, it derives a per-layer probability

$$ \{p_\ell\}_{\ell=1}^{N_L} = \{1.0,\ \gamma/N_L,\ \gamma/N_L,\ \dots,\ \gamma/N_L,\ 1.0\} $$

where the two endpoints (bottom and top of the network) are always kept active because LoRA's own weight norms are largest there, and every other layer is unfrozen with probability $\gamma/N_L$ [1]; in practice this is implemented by always keeping the embedding and head active and sampling exactly $\gamma$ of the intermediate layers per period rather than sampling each independently, "to further control the memory consumption in practical settings" [1].

Worked example: LLaMA-2-7B has $N_L = 32$ decoder layers (Table 14) [1], and the paper's moderate-scale instruction-tuning runs use $\gamma = 2$ (the "E+H+2L" configuration) [1]. Each of the 32 decoder layers is therefore unfrozen with marginal probability $\gamma/N_L = 2/32 = 6.25\%$ per resampling period, while the embedding and LM head are trainable at every step regardless of the draw. For a 122-step run the paper's own ablation uses periods $K = \lceil T/125\rceil$, $\lceil T/25\rceil$, $\lceil T/5\rceil$, and $K=T$ (i.e., $T=122$: sample once every 1, 5, 25, or 122 steps) — the middle setting $K=\lceil T/25\rceil$ scored highest on MT-Bench for both TinyLlama and LLaMA-2-7B at both $\gamma=2$ and $\gamma=8$, while never resampling ($K=T$) scored lowest in every case (Table 6) [1].

There is one variant defined in the paper beyond the outcome-style layer sampling above: the sampling probability $p^{(\ell)}$ is itself derived to match LoRA's observed layerwise update pattern, but the paper's own implementation approximates it with the simpler fixed two-tier scheme above rather than computing per-layer weight norms live [1]. axolotl's shipping implementation uses this fixed scheme: its callback samples `lisa_n_layers` indices uniformly without replacement from `model.layers` every `lisa_step_interval` steps and leaves everything outside that attribute (embedding, head) untouched by the freeze/unfreeze logic, reading `src/axolotl/utils/callbacks/lisa.py` on `main` [4]. LMFlow's README describes only the tunable knobs (`--lisa_activated_layers`, the step interval), not the sampling mechanics, and its training-script source was not read for this card, so whether it matches axolotl's uniform-without-replacement scheme is not established here [5].

## Cost

**Theory, from the method's own math**: LISA runs the same number of forward and backward passes over the training data as ordinary full-parameter fine-tuning — every layer still participates in the forward pass and the backward pass down to the frozen layers — the savings are in which layers accumulate gradients and hold optimizer state, not in the number of passes [1]. Memory is bounded by the largest ever-active parameter set: the embedding, head, and up to $\gamma$ intermediate layers at a time, each carrying gradients plus AdamW's two per-parameter moment buffers [1][8], while the frozen layers hold weights only, no gradients or optimizer state. A naive reading might assume the memory savings come from skipping computation in frozen layers, but the paper's own numbers (Table 1) show only a modest reduction versus LoRA rather than the deep cut skipping forward compute would imply, because the forward pass still runs through the full network [1].

**In practice, per framework**: axolotl wires `lisa_n_layers` and `lisa_step_interval` straight into a `TrainerCallback` that toggles `requires_grad` on `model.layers` entries at `on_step_begin`, so the memory and compute profile of a run is whatever the surrounding training-argument choices (batch size, gradient checkpointing, `optimizer: adamw_bnb_8bit` in its own example config) dictate — the LISA callback itself only changes which layers receive gradients (`src/axolotl/utils/callbacks/lisa.py`, `main`) [4]. LMFlow's own README reports that its LISA-enabled finetuning script allows training a 7B model in 24GB of GPU memory without offloading, and that the script is currently only tested on a single GPU [5].

## How to use it

- Data: any instruction or plain-text dataset the base fine-tuning recipe already uses — LISA is a drop-in change to the optimizer/freezing schedule, not a new data format. The paper's own runs used Alpaca-GPT4 (52K pairs) for instruction tuning, OpenWebMath (1.5B tokens) for continual pretraining, and GSM8K/PubMedQA for domain fine-tuning [1].
- Reward/label convention: standard supervised next-token loss on the labeled response tokens (or, for continued pretraining, on all tokens); LISA changes nothing about how the loss itself is computed [1].
- Key knobs, with each source's own value ("not stated" = the source was checked and does not give the value; "not checked" = this card did not verify that source's key):

| knob | axolotl example config [4] | LMFlow example flags [5] | paper [1] |
| --- | --- | --- | --- |
| sampled intermediate layers $\gamma$ | `lisa_n_layers: 4` | `--lisa_activated_layers 1` (or `2` in the alternate example) | 2 (7B-scale), 4 (70B) |
| resampling period $K$ (steps) | `lisa_step_interval: 20` | `20`, passed as `--lisa_interval_steps` in the README's bash example or `--lisa_step_interval` in its prose (the README uses both names for the same flag) | grid search over $K \in \{1,3,5,10,50,80\}$, aiming to keep update steps per sampling period within 10 to 50 (Appendix B.3); $K=13$ was optimal for a 7B model on Alpaca-GPT4 (Appendix A.4.2) |
| learning rate | `5e-5` ("recommendation from lisa paper for 7b" per the example config's own comment) | not stated | $10^{-5}$ in the Table 6 ablation; a 5e-6 to 3e-4 sweep was used overall (Appendix B.1) |
| always-active layers | not a separate knob — `lisa_layers_attribute` names only the pool sampled from (`model.layers`); embedding/head are outside that pool and stay trainable | embedding/head handling not documented in the README beyond the flags shown | embedding layer and LM head, per Algorithm 1 |

- Trade-off in $\gamma$: a larger $\gamma$ increases the number of trainable parameters (and memory) per step and, in the paper's own ablation, always scored at least as well as the smaller setting at matched $K$ (Table 6) [1] — so $\gamma$ is chosen against a memory ceiling, not tuned down for quality.
- Trade-off in $K$: too-frequent resampling ($K=\lceil T/125\rceil$) and too-infrequent resampling (never resampling, $K=T$) both scored worse than an intermediate period ($K=\lceil T/25\rceil$) in the paper's own 122-step ablation (Table 6) [1]; treat the paper's own tuned ratio as the anchor rather than either extreme.

## While it runs

- Signals: the paper monitors task benchmarks (MT-Bench, GSM8K, PubMedQA, MMLU, AGIEval, WinoGrande) and evaluation loss rather than a training-time reward signal, since LISA is a supervised fine-tuning optimizer, not an RL method [1]. Its own randomness study (Table 7) reports MT-Bench varying by at most 0.13 across three random seeds for layer selection on TinyLlama, Mistral-7B, and LLaMA-2-7B, calling the method "quite resilient to different random seeds" [1]. axolotl's callback logs the newly-activated layer indices to the training log every time layers switch, via `LOG.info` in `switch_active_layers` (`src/axolotl/utils/callbacks/lisa.py`, `main`) [4] — this is the only run-time signal specific to the method exposed by either shipping framework's source, as checked here.
- Published reference runs: the paper's own Tables 3 and 5 (cited above) are the reference numbers to compare a new run against; no separate public training log or curve was found in the sources checked.
- Degeneracies and defaults: the KL-free, reward-free nature of the method means there is no equivalent of a uniform-reward degeneracy; the closest failure mode is an unlucky $\gamma$-layer draw combined with a short $K$, which the paper's own ablation shows costs a few tenths of a point on MT-Bench relative to the tuned period (Table 6) [1]. The paper's own default sampling scheme (uniformly random among intermediate layers) is explicitly called out by the authors as likely suboptimal, since it does not account for the data source or model architecture [1].
- Named successors: MISA (Module-wise Importance Sampling), found via a Semantic Scholar citation search on arXiv:2403.17919, splits each transformer layer into smaller modules with per-module importance scores rather than freezing whole layers, and states that layer-wise sampling of LISA's kind provides only limited memory savings, as at least one full layer must remain active during optimization [6] — directly targeting the theory-layer memory floor noted in Cost above.
- Known failure modes: the paper's own limitations section states that LISA shares LoRA's core bottleneck — the full model must still be held in memory for the forward pass, so memory consumption remains significant, and the authors suggest combining LISA with QLoRA-style quantization as future work [1]; the same section also flags that the uniform-random intermediate-layer sampling used in practice, rather than a data- or architecture-aware importance weighting, may not be the optimal strategy [1]. Separately, axolotl's maintainers closed a bug report of LISA failing under multi-GPU DistributedDataParallel: the reported error states that the module has "parameters that were not used in producing loss" and points to PyTorch's "unused parameter detection" flag as a possible fix [9]; after `ddp_find_unused_parameters: true` and other workarounds failed, the maintainers recommended running LISA on a single GPU only [9] — consistent with LMFlow's own README statement that its LISA script is currently only tested on a single GPU [5].
- What the gain is - and is not: the paper's own analysis of its instruction-tuning results finds LISA's advantage over LoRA concentrated in memorization-heavy tasks (e.g., writing, and depicting fine image detail in a separate image-generation experiment), with a much smaller gap on reasoning-heavy tasks like code or math, and attributes this to LISA emphasizing layer width while LoRA emphasizes depth [1]. It also reports that LISA can outperform full-parameter fine-tuning on some instruction-following benchmarks, which the authors attribute to an implicit regularization effect from restricting the number of unfrozen layers, similar to dropout, rather than to any added capability [1].
