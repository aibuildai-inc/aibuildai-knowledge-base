# TTRL

**Item home:** https://arxiv.org/abs/2504.16084

Turn majority-vote consensus among a model's own sampled answers into a reward, then run standard on-policy RL (by default GRPO) on that reward — no ground-truth labels needed.

**TTRL** (Test-Time Reinforcement Learning) is a method for training an LLM policy with RL on data that carries no explicit labels, introduced to solve the problem of "How to obtain rewards for RL at test-time?" [1]. It is defined by sampling a set of candidate outputs for a question, taking their majority-voted answer as an estimated label, and using that estimate to compute a rule-based reward that drives an otherwise ordinary on-policy RL update [1]. The paper implements TTRL by independently applying GRPO [2] on each benchmark, and separately shows the same reward can drive PPO [3] or PRIME [4] with closely aligned performance trajectories [1]. The paper's own Introduction gives its motivation in two parts: most existing RL methods still rely heavily on labeled data, and as real-world tasks grow in complexity and volume, large-scale annotation for RL becomes increasingly impractical [1]; and the paper frames TTRL as a form of test-time training, adapting the model to previously unseen test-time data by generating its own experiences and estimating its own rewards rather than requiring ground truth [1]. Separately, in its later analysis of why the method works despite an imperfect label estimate, the paper reports that training against this noisy self-generated reward lets the model exceed its own starting majority-vote accuracy rather than just matching it, the ceiling that caps traditional self-training [1]. Citation count for this paper: 213; next-highest count among colliding `full_name` entries: 27.

The reference implementation, released by the paper's authors as the PRIME-RL/TTRL GitHub repository, is a fork of verl configured to run TTRL experiments [6]; the repository's own changelog states that as of verl v0.4.1 the upstream verl trainer exposes a `+ttrl.enable=True` flag, though this card could not independently confirm that flag in the current verl mainline build (see Shipped by) [6]. In the paper's own headline result, TTRL applied to Qwen2.5-Math-7B raises AIME 2024 pass@1 from 12.9 to 40.2, a 211.6% relative gain, with an average 76.5% relative gain across AIME 2024, AMC, MATH-500, and GPQA (Table 1) [1]. Lineage in one line: majority voting for test-time scaling and GRPO for RLVR [2] combine into TTRL (2025) [1], with the same team's follow-on Unsupervised RLVR (URLVR, accepted ICLR 2026) named in the project repo as a direct successor investigating the same mechanism [6].

**When to pick it**: pick TTRL when you have a batch of unlabeled prompts (often literally a benchmark's test split) that you can sample repeatedly, and you want the model to improve on that specific distribution without any ground-truth labels or reward model [1]. Its parent GRPO [2] needs a real, verifiable reward per completion; TTRL substitutes a majority-vote pseudo-label for that verifier. Its nearest offline alternative is majority-vote-supervised self-training (SFT on self-generated, vote-filtered chain-of-thought), whose performance ceiling is the base model's own maj@n accuracy — the paper shows TTRL's RL loop surpasses that ceiling rather than just reaching it [1]. Its nearest online neighbor is ordinary GRPO/RLVR training on a labeled corpus with a real verifier, the setting GRPO's own defining paper trains under [2]; TTRL trades that label requirement for majority-vote noise, and the paper's own failure analysis shows it needs the base model to already have enough prior knowledge on the target task for voting to produce a usable signal (Q3, Table 3: on the hardest MATH-500 difficulty tier the accuracy gain shrinks to 75.3% relative versus 175.3% on the easiest tier) [1].

**Variant of**: not a new RL algorithm but a new reward function layered on an existing one; the paper's main experiments run it through GRPO [2], and it demonstrates compatibility with PPO [3] and PRIME [4] with closely aligned accuracy and entropy curves over training steps (Figure 5) [1].

**Data it needs**: prompts only, no labels or preference pairs — a set of questions repeatedly sampled by the current policy. The paper's main runs sample 64 responses per question for majority-vote label estimation and downsample 32 of those per prompt for the training update [1]. It is on-policy: the pseudo-label and reward are recomputed from fresh samples of the current policy at every step, so a pre-collected response set cannot be substituted [1]. The paper applies it directly to benchmark test sets — AIME 2024, AMC, MATH-500, GPQA-Diamond [1] — training scale is one benchmark at a time, for 10, 30, or 80 episodes depending on dataset size, on 8×A100 80GB GPUs [1].

**Extra models**: none beyond whatever the underlying RL algorithm requires — the paper's own text does not discuss a KL term or reference model for its GRPO runs at all; with the PPO variant, a learned state-value function is required, since PPO's own algorithm (given as "PPO, Actor-Critic Style") combines a policy surrogate loss with a value-function error term [3]. There is no separate reward model: the reward is the policy's own majority vote over its own samples, i.e., a self-referential signal computed with the policy being trained, not a frozen judge [1].

**Shipped by**: the PRIME-RL/TTRL GitHub repository, the authors' own verl fork built for reproducing the paper's experiments, is the confirmed working implementation [6]. The same repository's changelog claims mainline verl (from release v0.4.1) added a `+ttrl.enable=True` flag for enabling TTRL inside the standard trainer [6]; a direct check of verl's current `main`-branch `verl/trainer/config/ppo_trainer.yaml` and its `recipe/` directory listing (fetched 2026-08-09) shows no `ttrl` key and no `recipe/ttrl` entry, so this card cannot confirm that flag is present in the current mainline build [7][8]. trl's trainer package (checked 2026-08-09) exports no TTRL trainer [9]. Building TTRL on any existing GRPO or PPO trainer is a reward-function swap rather than a new training loop: the paper presents the majority-vote reward as a short function (Listing 1) meant to drop into an existing rollout loop [1].

## How it works

The loop, per training step: sample N candidate outputs for a question from the current policy; extract each output's predicted answer; take the majority answer as an estimated label; score every output 1 or 0 against that estimated label; feed those rewards into a standard RL update (GRPO by default) [1].

**Reward function** [1], Eq. 3: given a question $x$, generate $N$ outputs, extract predicted answers $P = \{\hat{y}_i\}_{i=1}^{N}$, and estimate a label $\bar{y}$ as the majority answer in $P$:

$$ R(\hat{y}_i, \bar{y}) = \begin{cases} 1, & \text{if } \hat{y}_i = \bar{y} \\ 0, & \text{otherwise} \end{cases} $$

**RL objective** [1], Eq. 1–2: given state $x$ and policy $\pi_\theta(y\mid x)$, generate $y$ and reward $r(y, y^*)$ against the estimated consensus $y^*$, and maximize the expected reward by gradient ascent:

$$ \max_\theta \; \mathbb{E}_{y \sim \pi_\theta(\cdot \mid x)}\left[ r(y, y^*) \right], \qquad \theta \leftarrow \theta + \eta \, \nabla_\theta \, \mathbb{E}_{y \sim \pi_\theta(\cdot \mid x)}\left[ r(y, y^*) \right] $$

where $\eta$ is the learning rate [1]. In the paper's implementation this expectation is optimized with GRPO's group-relative, clipped-ratio update rather than plain REINFORCE-style gradient ascent; the equations above state only the general RL objective TTRL is built on, not GRPO's own advantage or clipping formulas (see the GRPO method card for those) [1][2].

**Consensus selection** is the general test-time-inference scoring rule the paper reuses from prior work, Eq. 4: given $N$ candidates $\{y_1,\dots,y_N\}$ and a scoring function $s(y,x)$, pick $y^* = \arg\max_{y_i} s(y_i, x)$; majority voting instantiates $s$ by counting how often each candidate answer recurs [1]. TTRL uses majority voting specifically, not the paper's other named instances of $s$ (best-of-N with a reward model, or weighted MV+BoN) [1].

Worked example, N = 8 with extracted answers $\{1,1,2,2,2,4,5,6\}$ (the paper's own toy case, Figure 10): the majority answer is 2 (3 of 8), so the estimated label $\bar y = 2$; every output predicting 2 gets reward 1 and every other output gets reward 0, giving estimated rewards $\{0,0,1,1,1,0,0,0\}$. If the true label is 3, the true rewards are all 0 (no output equals 3), so the estimated rewards agree with the true rewards on 5 of 8 outputs, a 62.5% reward hit rate despite the estimated label itself being wrong — the paper calls this a "Lucky Hit" and identifies it as a reason the method tolerates an inaccurate majority vote [1].

## Cost

**Theory, from the method's own math**: TTRL's reward computation needs $N$ sampled outputs per question purely to form the majority vote, on top of whatever the wrapped RL algorithm already generates for its own rollout — the paper's own numbers show these are not automatically the same $N$: 64 samples are drawn for voting and only 32 of them are kept for the training update [1]. There is no separate reward model or judge to hold in memory: the reward computation is a deterministic vote-and-compare over completions the policy already produced [1]. Beyond that extra sampling-for-voting cost, memory and compute follow whichever underlying algorithm is used — GRPO drops the value network, PPO keeps one (see each algorithm's own cost profile) [2][3].

**In practice, per framework**: the only confirmed shipping implementation is the PRIME-RL/TTRL verl fork; its README gives no separate cost breakdown beyond stating all reported experiments ran on 8×NVIDIA A100 80GB GPUs, matching the paper's own hardware note [1][6]. No cost claim is made here for the `+ttrl.enable=True` mainline-verl path since this card could not confirm its presence in the current verl main branch (see Shipped by) [7][8].

## How to use it

- Prompts: any set of questions you can sample repeatedly from the current policy; the paper trains one benchmark's test set at a time (AIME 2024, AMC, MATH-500, GPQA-Diamond) rather than a separate curated training split [1].
- Answer extraction and voting: extract a predicted answer from each of $N$ sampled outputs, take the plurality answer as the estimated label, and score every output 1/0 by exact match against that estimated label (Listing 1, Eq. 3) [1].
- Key knobs, with the paper's own values as the only documented anchor (no independently confirmed framework default exists for this method; see Shipped by):

| knob | paper value [1] |
| --- | --- |
| rollout samples for voting | 64 |
| samples kept for training update | 32 |
| optimizer | AdamW, cosine LR schedule, peak LR $5\times10^{-7}$ |
| sampling temperature (voting/training) | 0.6 (1.0 for Qwen2.5-Math and LRMs) |
| top-p | 0.95 (evaluation); not stated for training rollout |
| max generation length | 3,072 tokens (32,768 for LRMs) |
| episodes | 10 (MATH-500), 30 (AMC), 80 (AIME 2024), scaled by dataset size |
| underlying RL algorithm | GRPO for main results; PPO and PRIME also tested |

- Vote-then-sample trade-off: sampling more responses for voting (64) than are used for training (32) is the paper's own way of cutting compute while keeping the vote reliable; the paper states this reduces computational cost while still achieving strong performance, without publishing a sweep over the two counts [1].
- Sensitivity: the paper's own failed-run comparisons (Figure 11) found training collapses (persistently high entropy that never falls) when temperature is set to 0.6 instead of 1.0, or when the training batch size is set to 256 instead of the paper's successful setting, on AIME 2024 specifically [1]. Treat temperature and episode count as the two hyperparameters to tune first, per the paper's own account of what it identified as critical [1].

## While it runs

- **Signals and their healthy shapes**, first-hand from the paper's own Appendix B metric list [1]: Entropy (generation uncertainty — the paper's failed runs show entropy staying persistently high instead of falling, Figure 11) [1]; Majority Voting Reward (the rule-based reward computed from the estimated label — this is the actual training signal, watch it rise) [1]; Majority Ratio (how often the plurality answer recurs in a rollout — the paper's base-model runs on AIME 2024 start near 16.6% majority ratio, i.e. highly scattered predictions) [1]. Two further metrics need ground-truth access and are for offline analysis, not live monitoring without labels: Label Accuracy (does the estimated label match the true one) and Reward Accuracy (does the estimated reward match the true-label reward) [1]. On AIME 2024 with Qwen2.5-Math-7B the paper's own Figure 9 shows label accuracy rarely above 50% while reward accuracy stays above 75% throughout training — a large, first-hand-documented gap that the paper attributes to the "Lucky Hit" effect described in How it works [1].
- **Published reference runs**: the project repository reports three independent reproduction runs of its preview code on AIME 2024, two reaching pass@1 (greedy) 43.3 and one reaching 46.7, with raw Weights & Biases logs linked from the repository [6].
- **Degeneracies and defaults**: a rollout of one sample cannot vote — majority voting requires the multi-sample rollout the paper uses (64 samples), and a single-output rollout removes the "Lucky Hit" robustness the paper documents (an output-level property, not the group-of-completions concept from GRPO's own advantage normalization) [1]. The paper's own two documented training failures are temperature set too low (0.6 rather than 1.0) and training batch size set to 256, both producing persistently high, non-decreasing entropy on AIME 2024 [1].
- **Named successors**: the project repository names Unsupervised RLVR (URLVR) as a direct follow-on investigating the same mechanism for test-time training and for quantifying model priors, accepted to ICLR 2026 [6].
- **Known failure modes**, from the paper's own Q3 section (Section 4.3) [1]: TTRL "inherits" standard RL failure modes — sensitivity to data difficulty, reliance on the base model's priors, and risk of collapse — and these are amplified because TTRL estimates labels via majority voting on sparse, previously-unseen test data with no curriculum or data-filtering mechanism. The paper's own ablation on MATH-500's five difficulty tiers shows both the accuracy gain and the response-length reduction shrink monotonically as difficulty rises (Table 3: accuracy gain 175.3% relative on the easiest tier down to 75.3% on the hardest), which the paper attributes directly to insufficient prior knowledge on harder questions [1]. No maintainer-reported failure mode is recorded here: only the PRIME-RL/TTRL GitHub repository's README was read (fetched 2026-08-09), and it contains no discussion of failure modes or issues; the repository's closed-issues history itself was not queried (an attempted grep.app code search and DuckDuckGo search for related discussion returned no usable results), so this is an absence in the one document read, not a completed issues search [6].
- **What the gain is — and is not**: the paper's own analysis (Section 4.1) finds TTRL can exceed the initial model's majority-vote (maj@n) upper bound and closely approach a second, higher upper bound it defines as running RL directly on the test data with its real ground-truth labels, which it calls RL (leakage) [1]. Separately, in its Q2 analysis of why the method works, the paper attributes its robustness to reward noise partly to prior work showing RL generalizes better than SFT, which tends to memorize training data [5], citing that specific claim to Chu et al. [5]. TTRL is explicitly framed by its authors as "a preliminary step toward RL with self-labeled rewards" rather than a finished, general-purpose training recipe, and the paper states plans for further work on hyperparameter sensitivity and theoretical convergence analysis [1].
