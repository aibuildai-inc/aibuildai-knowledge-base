# GSPO

Paper: https://arxiv.org/abs/2507.18071

GRPO with the importance ratio and clipping moved from per-token to per-sequence: instead of re-weighting every token by its own likelihood ratio, GSPO weights an entire response by one length-normalized sequence-level ratio, clipped as a whole.

**GSPO** (Group Sequence Policy Optimization) is an online-RL method for fine-tuning an LLM policy against a per-response reward, introduced by the Qwen Team as a GRPO variant that "defines the importance ratio based on sequence likelihood and performs sequence-level clipping, rewarding, and optimization" [1]. Its parent, GRPO, is introduced by Shao et al. as "Group Relative Policy Optimization (GRPO), a variant of Proximal Policy Optimization (PPO), that enhances mathematical reasoning abilities while concurrently optimizing the memory usage of PPO" [2]. As restated in the GSPO paper, GRPO bypasses PPO's value model by computing each response's advantage relative to a group of G responses sampled for the same query, then applies that group-level advantage through a *per-token* importance ratio [1]. GSPO keeps GRPO's group-relative advantage but replaces that per-token ratio with a single ratio per response, computed as the length-normalized geometric mean of the token-level likelihood ratios, and clips that one ratio per response instead of clipping each token [1]. The paper gives two reasons for the change: it argues GRPO's per-token ratio is a theoretical misuse of importance sampling, because importance sampling needs many samples to correct a distribution mismatch, while GRPO estimates one token-level ratio from a single sampled token, injecting high-variance noise that grows with response length and is amplified by clipping, occasionally causing irreversible model collapse in the paper's own large-model runs [1]; and it holds that the unit of optimization should match the unit of the reward, which is granted to the whole sequence, not to individual tokens [1].

The paper reports that GSPO stabilized Qwen's own Mixture-of-Experts (MoE) RL runs without the "Routing Replay" workaround GRPO needed, and states that these gains contributed to the Qwen3 models' RL improvements — a self-reported adoption claim; the GSPO paper (July 2025) postdates the Qwen3 technical report (May 2025), so this card treats the claim as self-reported by the GSPO paper only and does not use the (unfetched) Qwen3 report as independent corroboration [1]. The paper gives no numeric benchmark table; its own headline comparison is a clip-fraction figure showing GSPO clips roughly two orders of magnitude more tokens than GRPO (about 0.0013 for GRPO against a bar reaching roughly 0.13-0.15 for GSPO, read off Figure 2's axis) while still reaching higher training reward and benchmark scores over the same training compute (Figure 1) — the paper's evidence that GRPO's token-level ratios are noisy even when few tokens get clipped [1]. Lineage in one line: PPO (2017 [3]) -> GRPO (DeepSeekMath, 2024 [2]) -> GSPO (Qwen Team, 2025 [1]), with a token-level variant GSPO-token defined in the same paper for cases needing per-token advantages [1].

**When to pick it**: choose GSPO over its parent GRPO [2] when training runs slightly off-policy (multiple gradient-update mini-batches drawn from one rollout batch, or repeated importance-sampling steps over the same batch) and, per the paper, especially for large or Mixture-of-Experts models, where GRPO's token-level ratio destabilizes training [1]; trl's docs state the sequence-level ratio "only has an effect when training goes slightly off-policy... otherwise it is effectively equivalent to no modification" [4]. Prefer DPO [5] when you have static chosen/rejected preference pairs and no way to score fresh samples: DPO trains offline on such pairs, with no reward model needed at training time [6]. Prefer PPO [3], the nearest online neighbor that still trains a value network, when a learned per-token critic is worth its extra memory and compute rather than a group-relative baseline.

**Variant of**: GRPO [2], which is itself a variant of PPO [3].

**Data it needs**: prompts from the target distribution plus a per-response scalar reward — the paper's own preliminaries define a query-response pair as scored by a verifier producing a reward in [0, 1], the same reward structure both GRPO and GSPO consume [1]; the paper's own MoE runs used a cold-start model fine-tuned from Qwen3-30B-A3B-Base, with no query-set size, learning rate, or group size G given in the text [1]. On-policy: each step samples a fresh group of G responses from the current policy; GSPO only departs from strict on-policy sampling within the off-policy slack introduced by splitting one rollout batch into several gradient-update mini-batches, which is the regime the method is designed to correct for [1].

**Extra models**: none required by the objective itself — like GRPO, GSPO has no value network [1]. The paper's own formulas omit the KL term "for brevity, as it is not the focus of this paper" [1], and neither framework's reproduction default keeps a reference model on for GSPO: trl's documented GSPO configuration explicitly sets `beta=0.0` ("GSPO set KL regularization to zero"), citing a verl pull-request discussion for that reading [4]; verl's `use_kl_loss` defaults to `false` for every algorithm, GSPO included [7]. Setting a nonzero KL coefficient in either framework adds a frozen reference-model forward pass; details in Cost.

**Shipped by**: trl, via `GRPOTrainer` configured with `importance_sampling_level="sequence"` (there is no separate `GSPOTrainer` class) [8][4]; a GSPO-token variant ships as an experimental trainer under `trl.experimental.gspo_token.GRPOTrainer` [9]. verl, via a registered policy-loss function `compute_policy_loss_gspo`, selected by setting `actor.policy_loss.loss_mode: "gspo"` (default is `"vanilla"`, i.e. GRPO/PPO-style per-token clipping) [10][7]; verl's own documentation site has no dedicated GSPO algorithm page, so this reading is from the source file and the actor config only, at the commit noted in Sources.

## How it works

Each step: sample a group of G responses per prompt from the current policy snapshot $\pi_{\theta_{old}}$; score each response; turn scores into group-relative advantages exactly as in GRPO; compute one length-normalized importance ratio per response; clip that one ratio per response and update [1].

**The objective** [1, Eq. 5]:

$$ J_{GSPO}(\theta) = \mathbb{E}_{\,x \sim D,\ \{y_i\}_{i=1}^{G} \sim \pi_{\theta_{old}}(\cdot|x)}\; \frac{1}{G} \sum_{i=1}^{G} \min\!\left[ s_i(\theta)\,\hat{A}_i,\; \operatorname{clip}\!\left( s_i(\theta), 1-\varepsilon, 1+\varepsilon\right)\hat{A}_i \right] $$

with the sequence-level importance ratio defined as the length-normalized geometric mean of per-token ratios [1, Eq. 7]:

$$ s_i(\theta) = \left(\frac{\pi_\theta(y_i|x)}{\pi_{\theta_{old}}(y_i|x)}\right)^{\!1/|y_i|} = \exp\!\left(\frac{1}{|y_i|}\sum_{t=1}^{|y_i|} \log\frac{\pi_\theta(y_{i,t}|x,y_{i,<t})}{\pi_{\theta_{old}}(y_{i,t}|x,y_{i,<t})}\right) $$

Unlike GRPO's objective, which sums a per-token clipped term over every token of every response (restated by the GSPO paper as its own Eq. 2) [1], GSPO's sum runs only over the G responses: the whole response is clipped as one unit, weighted by one scalar $s_i(\theta)$, so every token in a response contributes equally to its gradient [1]. The paper notes the clipping ranges "in previous algorithms (e.g., GRPO) typically differ in order of magnitude" from GSPO's, due to the two ratios' distinct definitions [1] — its own MoE experiments used $\varepsilon_{low}=3\times10^{-4}$, $\varepsilon_{high}=4\times10^{-4}$ for GSPO against a tuned $0.2/0.27$ for the GRPO baseline in the same comparison [1].

**The advantage** is identical to GRPO's outcome-supervision rule: for a group of rewards $\{r(x,y_i)\}_{i=1}^G$,

$$ \hat{A}_i = \frac{r(x,y_i) - \operatorname{mean}\{r(x,y_i)\}_{i=1}^G}{\operatorname{std}\{r(x,y_i)\}_{i=1}^G} $$

this is the same normalized-reward advantage GRPO uses [1]; the only difference from GRPO is that GSPO applies this single scalar through $s_i(\theta)$, one ratio for the whole response, rather than broadcasting it through a per-token ratio [1].

**Gradient**: the paper derives that GSPO's gradient weights every token in a response by the same sequence-level ratio $s_i(\theta)$ (Eq. 8-10), whereas GRPO's gradient weights each token by its own token-level ratio $w_{i,t}(\theta)$, which the paper shows can range unboundedly outside $[1-\varepsilon, 1+\varepsilon]$ for tokens whose advantage sign disagrees with the clip direction (Eq. 11-12) — this unequal per-token weighting is the instability source GSPO removes [1].

**GSPO-token**: a token-level variant that keeps GSPO's sequence-level ratio for clipping but multiplies it by a stop-gradient-adjusted per-token log-probability term; the paper states that GSPO-token and GSPO are "numerically identical in the optimization objective, clipping condition, and theoretical gradient" once every token in a response is set to the same advantage, while GSPO-token still allows per-token advantage customization for cases like multi-turn RL [1, Eq. 13-14]. Neither framework ships GSPO-token as a first-class trainer; trl exposes it only as an experimental class [9], and this card does not verify a verl equivalent.

## Cost

**Theory, from the method's own math:**

- Time and memory relative to GRPO are essentially unchanged: GSPO samples the same G responses per prompt and runs the same forward/backward passes over the policy, with no value network in the objective, matching GRPO's removal of PPO's critic [1][2]. A KL term is absent from the paper's own formulas [1]; enabling one in either framework adds a reference-model forward pass, as in GRPO.
- The only structural change from GRPO is arithmetic, not model count: computing $s_i(\theta)$ requires the same per-token log-probabilities GRPO already computes, just aggregated once per sequence instead of clipped per token — this does not add a pass over the model, only a reduction over an already-computed tensor [1].
- A naive reading might expect sequence-level clipping to need fewer stored per-token values than GRPO; it does not — both methods need every token's log-probability under $\pi_\theta$ and $\pi_{\theta_{old}}$ to build the ratio, GSPO just reduces them before clipping instead of after [1][8].

**In practice, per framework:**

- trl `GRPOTrainer` [8]: setting `importance_sampling_level="sequence"` changes only how `log_importance_weights` is aggregated in `_compute_loss` — from the raw per-token log-ratio tensor to `(log_ratio * mask).sum(-1) / mask.sum(-1)`, a reduction over an already-computed tensor, before clipping and multiplying by the advantage [8]. No extra forward pass or extra model is introduced; memory and compute follow the same `generation_batch_size` / per-device batch and gradient-accumulation knobs as GRPO.
- verl [10][7]: `compute_policy_loss_gspo` reuses the same `old_log_prob` and `log_prob` tensors GRPO's `vanilla` loss consumes, reduces them to one ratio per sequence with `torch.sum(... , dim=-1) / seq_lengths`, then always aggregates the loss with `loss_agg_mode="seq-mean-token-mean"` regardless of the actor's global `loss_agg_mode` setting [10]. Peak memory is governed by the same `ppo_micro_batch_size_per_gpu` / `ppo_mini_batch_size` knobs as any other verl policy-loss mode [7], not by the GSPO ratio computation itself.

## How to use it

- Prompts and rewards: identical requirements to GRPO — one prompt per group, a scalar reward per response, either a rule-based verifier or a reward model [1][2].
- trl's own documented recipe for reproducing the paper's setting is: `importance_sampling_level="sequence"`, `loss_type="grpo"` (not the trl default `"dapo"` — using a per-token-normalizing loss with a sequence-level ratio "sums per-token contributions, which effectively weights each sequence by its completion length instead of optimizing the per-sequence objective" [8]), `beta=0.0`, `epsilon=3e-4`, `epsilon_high=4e-4`, `gradient_accumulation_steps=1`, `steps_per_generation=4` — trl's docs note `steps_per_generation` "must be 4 times `gradient_accumulation_steps`" to match the paper's four mini-batches per rollout batch [4].
- Key knobs, with each source's own value ("not stated" = the source was checked and does not give the value):

| knob | trl default [8] | trl GSPO recipe [4] | verl default [7] | paper [1] |
| --- | --- | --- | --- | --- |
| importance_sampling_level / loss_mode | `"token"` | `"sequence"` | `"vanilla"` (token-level) | sequence-level (defining feature) |
| loss_type / loss_agg_mode | `"dapo"` | `"grpo"` | `token-mean` (forced to `seq-mean-token-mean` inside the gspo function) | not stated |
| clip range $\varepsilon$ (low / high)$^\dagger$ | `epsilon` 0.2$^\dagger$ / defaults to `epsilon` if `epsilon_high` unset | `3e-4`$^\ddagger$ / `4e-4`$^\ddagger$ | `clip_ratio_low` 0.2$^\dagger$ / `clip_ratio_high` 0.2$^\dagger$ | `3e-4`$^\ddagger$ / `4e-4`$^\ddagger$ (GSPO); `0.2`$^\dagger$ / `0.27`$^\dagger$ (paper's own tuned GRPO baseline) |
| KL coefficient $\beta$ | `beta` 0.0 | `0.0` | `use_kl_loss` False (`kl_loss_coef` 0.001 if enabled) | omitted from the formulas [1] |
| group size G | `num_generations` 8 | not stated in the recipe | `rollout.n` defaults to 1 via `actor.rollout_n` | not stated |
| mini-batches per rollout batch | `steps_per_generation` not stated | 4 | not checked | 4 |

  $^\dagger$ clips a per-token importance ratio (GRPO/PPO-style); $^\ddagger$ clips GSPO's length-normalized, sequence-level ratio $s_i(\theta)$ — the two ratios are differently scaled, so cells marked $\dagger$ and $\ddagger$ in this row are not the same quantity and must not be compared directly [1].

- Trade-off carried over unchanged from GRPO: larger G gives a steadier group baseline at more rollout cost per prompt. Neither the GSPO paper's own text (read in full for this card) nor the trl/verl documentation pages already cited in this card's knobs table gives GSPO-specific guidance on choosing G beyond GRPO's own recommendation [1].
- Install, launch, and the rest of the framework surface belong to the trl and verl framework cards; this card stops at the knobs that define the method.

## While it runs

- Signals: the paper's own live diagnostic is the fraction of clipped tokens, tracked per algorithm — it reports GSPO clips a far larger fraction of tokens than GRPO (roughly two orders of magnitude, read from Figure 2) yet still trains more efficiently, which the paper reads as evidence that GRPO's smaller clip fraction was hiding noisy, not clean, gradients [1]. trl logs a `clip_ratio` metric from its fused Liger GRPO loss when `use_liger_kernel=True` [8]; whether that metric is computed per-token or per-sequence under `importance_sampling_level="sequence"` is not verified here.
- Published reference runs: the paper's Figure 1 shows training-reward, AIME'24, LiveCodeBench, and CodeForces curves for GSPO against "GRPO (w/ Routing Replay)" on a Qwen3-30B-A3B-Base cold start, with GSPO ahead throughout, but the paper gives no tabulated endpoint scores — only the curves themselves [1].
- Degeneracies and defaults: a group of one gives GRPO's usual 0/0 advantage, and the same applies to GSPO's group-relative advantage since it reuses GRPO's formula unchanged [1][2]; verl's `rollout.n` (hence `actor.rollout_n`) defaults to 1 and must be raised [7]. trl's default `loss_type="dapo"` combined with `importance_sampling_level="sequence"` silently departs from the paper's setup — trl's own trainer emits a warning for exactly this combination, naming `loss_type="grpo"` as the fix [8].
- MoE-specific degeneracy the paper documents directly: in the paper's own 48-layer Qwen3-30B-A3B-Base runs, roughly 10% of activated experts differ between $\pi_\theta$ and $\pi_{\theta_{old}}$ after a single gradient update, which the paper says invalidates GRPO's token-level ratio and previously required a "Routing Replay" workaround (caching and replaying $\pi_{\theta_{old}}$'s expert routing) that GSPO's paper reports is no longer needed [1].
- Named successors: GSPO-token, defined in the same paper as a token-level variant for finer-grained advantage customization (see How it works); the GSPO paper's own reference list and text (read in full for this card) name no further successor paper that fixes a documented GSPO bias [1].
- Known failure modes: the paper's own limitations are narrow — it states GRPO's, not GSPO's, per-token ratio "fails to perform the intended distribution-correction role" and can cause irreversible collapse that resuming from a checkpoint does not fix [1]; the paper does not describe a parallel failure mode for GSPO itself. A GitHub issue-search API query for "GSPO" against `huggingface/trl` returned 57 matching issues [11]; one, opened as a follow-up splitting out a caveat a maintainer (`@albertvillanova`) raised in review of an earlier PR, reports that trl's KL bias-correction term is applied as a per-token correction when `importance_sampling_level="token"`, but under `importance_sampling_level="sequence"` (the GSPO configuration) the same correction broadcasts one sequence-level ratio across every token's KL term, so the resulting KL gradient is neither the intended per-token correction nor an unbiased reverse-KL gradient in that configuration — open and unresolved, with unverified maintainer status for the issue's opener, at the time of reading [11]. The same query against `verl-project/verl` (formerly `volcengine/verl`) returned 76 matching issues [12]; a spot-check of one open, unresolved report describes garbled rollout output when training a Qwen3-Next-80B model with GSPO settings on verl 0.7.0, but the issue thread does not reach a maintainer-confirmed root cause, so this card does not treat it as a settled failure mode [12].
- What the gain is - and is not: the paper's claims are about training stability and efficiency relative to GRPO under the same compute (Figure 1) and about removing the need for Routing Replay in MoE training (Section 5.3), plus reduced sensitivity to inference/training engine precision mismatches because only sequence-level, not token-level, likelihoods are used (Section 5.4) [1]. The paper does not claim GSPO changes what capability RL training can add to a base model — it makes no Maj@K/Pass@K-style capability-ceiling analysis of its own.
