# Tree-GRPO

GRPO for multi-turn tool-using agents, but the group of rollouts per prompt is grown as a tree of shared-prefix thought-action-observation steps instead of independent chains, so branch points give free step-level preference signal on top of the usual outcome reward.

**Tree-GRPO** (Tree-based Group Relative Policy Optimization) is an online-RL method for training LLM agents with multi-turn tool use, introduced in "Tree Search for LLM Agent Reinforcement Learning" (https://arxiv.org/abs/2509.21240), accepted at ICLR 2026 [1]. Its parent is GRPO, defined in the DeepSeekMath paper as a variant of PPO [2] that replaces the value network with a group-relative reward baseline [3]. Tree-GRPO keeps GRPO's group-relative advantage but changes how the group is sampled: instead of independently sampling G full chains per prompt, it first rolls out M independent chains to initialize M trees, then repeats L times a step of randomly picking N non-leaf nodes across the trees and continuing generation from each, producing a new branch; every node is one complete Thought-Action-Observation step rather than a token or sentence [1]. The paper gives two reasons for this design: agent rollouts are expensive in both tokens and tool calls, and sharing prefixes lets tree search reach more rollouts than chain-based sampling under the same budget [1]; and because only a single outcome reward is available per trajectory, chain-based GRPO assigns every step in a multi-turn trajectory the same credit, which the authors identify as a cause of training instability on long-horizon tasks [1] - the tree's branch points let the method back-propagate outcome rewards into step-level preference signal without any extra supervision [1].

The method is new (submitted 2025-09-25) and its own repository, not a general framework release, is its only adoption so far; it reports its own gains rather than being cited as adopted by a landmark system. On the paper's own multi-hop QA benchmark with Qwen2.5-3b, Tree-GRPO scored an average of 36.8 versus chain-based GRPO's 31.8 (a 16% relative gain) at matched rollout budget, and versus GSPO's 33.5 (Table 1) [1]; at a token/tool-call budget of 2 rollouts per prompt it reached 31.6 versus chain-based GRPO's 14.9, a 112% relative gain (Table 3) [1]. Lineage: PPO (2017 [2]) -> GRPO (DeepSeekMath, 2024 [3]) -> Tree-GRPO (2025 [1]), built on top of the Search-R1 agent-RL codebase [4] and veRL [1][5]. Among three name-colliding candidates all called "Tree-GRPO" or "tree-based GRPO" (this LLM tool-agent paper, a diffusion-model post-training paper, and an embodied-agent fine-tuning paper), this one was confirmed as the correct match by citation count, the highest of the three on a live lookup: 53 citations against 22 and 16 for the other two [6]; this card covers only the method defined by [1].

**When to pick it**: multi-turn LLM agent RL with tool calls (e.g., search) under a limited token/tool-call rollout budget, where the only reward available is a single outcome score per trajectory [1]. Prefer plain GRPO [3] - the parent - when rollouts are cheap or the task is single-turn, since Table 1 shows the tree-based gain shrinking as tasks require fewer interaction turns (e.g., single-hop QA) [1]. The paper's nearest online neighbor it benchmarks against is GSPO, a GRPO variant that replaces token-level importance ratios with trajectory-level reweighting for training stability but does not change how rollouts are sampled or credited [1][7]; on Table 1's Multi-Hop QA average, GSPO scored lower than Tree-GRPO in all 5 model settings tested; on the Single-Hop QA average GSPO scored lower in 4 of 5, beating Tree-GRPO only at Qwen2.5-7b (52.5 vs. 52.2) [1]. The paper's own Proposition 3.1 shows the nearest offline alternative - constructing explicit step-level DPO pairs from positive/negative trajectory continuations [8] - is gradient-equivalent to Tree-GRPO's intra-tree advantage term, but Tree-GRPO gets that signal online from a single rollout tree instead of building a separate preference dataset [1].

**Variant of**: GRPO [3].

**Data it needs**: prompts only (questions), no pre-collected chosen/rejected pairs or per-answer scores; the reward is a rule-based outcome score - Exact Match for single-/multi-hop QA, F1 for web-agent QA [1]. On-policy: every rollout, including tree expansions, is generated fresh from the current policy $\pi_\theta$ each training step [1]. Training scale in the paper: 79,168 examples for single-hop QA and 90,447 for multi-hop QA, each run for 180 steps; 2,200 examples for web-agent QA run for 34 steps (2 epochs) [1].

**Extra models**: no value network, inherited from GRPO [1][3]. The objective's KL term needs a reference model $\pi_{ref}$, but per the paper's Algorithm 1 this reference is reset to the current policy $\pi_\theta$ at the start of every training step, not held fixed at an SFT checkpoint [1]. No separate reward model in the paper's experiments - reward is computed by a rule (EM/F1 match), not a learned scorer [1]. No trained judge. Cost details below.

**Shipped by**: only the authors' own research repository, AMAP-ML/Tree-GRPO on GitHub (Apache-2.0, 393 stars as of this reading), which is a fork/extension of veRL and Search-R1, not a merge into either project's mainline [5][9]. Entry point is a shell script, `bash train_multihopqa_tree_search.sh`, not a Python trainer class [5]. The README marks the codebase "work in progress" as of its Sep 25, 2025 release note [5]. Neither trl nor verl's own documentation lists a Tree-GRPO trainer; building it on top of either would mean writing a custom rollout loop that samples nodes for expansion from an in-memory tree structure and computes two group-relative advantage terms per node (see How it works), not just adding a loss on an existing trainer.

## How it works

The loop in one line: build M chain-rooted trees, expand N random non-leaf nodes per tree for L rounds, then update the policy on a GRPO-style clipped objective whose advantage combines a within-tree and an across-tree group-relative baseline.

**Tree-search sampling** [1, Algorithm 1]. For each prompt $x_i$: (1) Initialization - generate $M$ independent chain rollouts as the roots of $M$ trees. (2) Sampling - randomly select $N$ non-leaf nodes per tree ($M \times N$ total). (3) Expansion - for each selected node, take the context from the tree root to that node plus the prompt, and continue generation to a new leaf; insert the new branch into its source tree. Steps 2-3 repeat for $L$ rounds, giving a final group size $G = M \times (L \times N + 1)$ rollouts per prompt [1]. Each node is one Thought-Action-Observation step, not a token or sentence [1]. The paper derives the expected token/tool-call budget of this scheme as

$$ \mathbb{E}[B_{tree}] = M \cdot B + L \cdot N \cdot B/2 $$

where $B$ is the expected budget of one complete chain and $B/2$ is used because a randomly selected expansion node sits, in expectation, at half the maximum tree depth [1, Eq. 4].

**Objective** [1, Eq. 8]:

$$ J_{Tree\text{-}GRPO}(\theta) = \mathbb{E}_{x\sim D,\, H\sim\pi_{old}}\Bigg[\frac{1}{G}\sum_{i=1}^{G}\frac{1}{|H_i|}\sum_{t=1}^{|H_i|}\Big\{\min\big[r_{i,t}(\theta)\hat A_{tree}(H_i),\, \operatorname{clip}(r_{i,t}(\theta),1-\epsilon,1+\epsilon)\hat A_{tree}(H_i)\big] - \beta D_{KL}\big[\pi_\theta(H|x)\,\|\,\pi_{ref}(H|x)\big]\Big\}\Bigg] $$

$r_{i,t}(\theta)$ is the token-level importance ratio between the current and previous policy; $\epsilon$ is PPO's clip range, inherited from PPO's clipped surrogate objective [2]; $\beta$ scales a per-token KL penalty against $\pi_{ref}$ - the same structural form as GRPO's objective, with the group-relative advantage $\hat A$ replaced by a tree-based one [1].

**Tree-based advantage** [1, Eqs. 6-7]. For a trajectory $H_i$, both terms use the same normalized-reward form,

$$ \hat A_{Intra/Inter\text{-}tree}(H_i) = \big(R(H_i) - \operatorname{mean}(\{R(H_j)\}_{j\in G_{Intra/Inter}(T_i)})\big)\,/\,\operatorname{std}(\{R(H_j)\}_{j\in G_{Intra/Inter}(T_i)}) $$

with the group defined either as the rollouts sharing $H_i$'s own tree (intra-tree) or as all rollouts across all $M$ trees for the prompt (inter-tree). The final advantage sums both: $\hat A_{tree}(H_i) = \hat A_{Intra\text{-}tree}(H_i) + \hat A_{Inter\text{-}tree}(H_i)$ [1, Eq. 7]. At every branching point, sibling subtrees that share a prefix but diverge afterward get different back-propagated outcome rewards, which the intra-tree term turns into an implicit preference signal between the two branches - the paper's Proposition 3.1 shows this term's gradient has the same form as a step-level DPO gradient, differing only in the weighting term [1].

Worked example matching the paper's default multi-hop config ($M=2, N=2, L=1$, so $G = 2\times(2\times1+1)=6$) [1]: suppose tree 1 has rewards $\{1,0,0\}$ and tree 2 has rewards $\{1,1,0\}$ (rewards are 0/1 exact-match). Intra-tree mean/std are computed within each 3-rollout tree; inter-tree mean/std are computed across all 6 rollouts. A rollout in tree 1 with reward 1 therefore gets a large positive intra-tree term (it beats its 2 siblings) added to a smaller inter-tree term (it is average among all 6); the two terms only coincide when $M=1$, i.e., a single tree.

Table 4's ablation is the paper's own evidence that both terms are needed: at $M=2,N=2,L=1$, using $\hat A_{Intra\text{-}tree}$ alone caused training collapse on all four multi-hop datasets, $\hat A_{Inter\text{-}tree}$ alone reached 33.8 average (a +6.3% relative gain over chain-based GRPO's 31.8), and the sum of both reached 36.8 (+16%) [1, Table 4]. The paper attributes the intra-tree-alone collapse to too few branches per tree giving a high-variance baseline when the tree is small [1].

## Cost

**Theory, from the method's own math**: Eq. 4 says the tree-search budget is $M\cdot B + L\cdot N\cdot B/2$ against a chain-based budget of $M\cdot(L\cdot N+1)\cdot B$ for the same number of rollouts $G$ - the tree amortizes the shared-prefix cost of $L\cdot N$ of the $G$ rollouts down to half a chain's cost each [1, Eq. 4]. This is a token/tool-call generation-cost argument, not a claim about wall-clock; the paper does not give a wall-clock cost model. On memory: the objective needs a reference model for the KL term, exactly as GRPO does with $\beta>0$ [1]; no value network is added, same as GRPO relative to its own parent, PPO [2]. A naive reading of the advantage sum ($\hat A_{Intra}+\hat A_{Inter}$) might suggest two independent normalization passes double the compute of a single group-relative pass; in practice both terms are computed from the same set of $G$ reward scalars already held for the prompt (one intra-tree mean/std per tree, one inter-tree mean/std over all trees), so the added cost is bookkeeping over scalars, not a second rollout or forward pass.

**In practice**: the only shipped implementation is the authors' own veRL-based repository [5]. Its README states the codebase is built on Search-R1 and veRL, and that installation requires vLLM 0.8.5.post1 for rollout generation, a separate retriever/search-API server process, and PPO-style config keys inherited from veRL (training batch size, PPO mini-batch size) [5]. Because this is a research fork rather than a maintained trainer class, this card cannot cite an independent framework doc for its complexity claims beyond the paper's own Table 5 config (below); no comparison to a second implementation is possible.

## How to use it

- Prompts: question-only inputs from the target agent task; the paper used Wikipedia-based multi-hop/single-hop QA (NQ, TriviaQA, PopQA, HotpotQA, 2WikiMultiHopQA, Musique, Bamboogle) via a local E5 retrieval server, and real web-search QA (SimpleQA, GAIA, WebWalkerQA, BrowseComp) via a live search API [1].
- Reward convention: the paper adds a format penalty to the raw score, $r(y) = \operatorname{score}(y) - \lambda_f$ if the output fails a format check (e.g., malformed tags) else $r(y) = \operatorname{score}(y)$, with $\lambda_f = 0.2$ in every experiment, following the convention of a separate Jin et al. paper on RL for reasoning-search agents, not Search-R1 itself [1][10].
- Knobs, from the paper's own hyperparameter table (there is only one source - no second framework to compare against) [1, Table 5]:

| knob | single-/multi-hop QA | web-agent QA |
| --- | --- | --- |
| learning rate | 1e-6 | 1e-6 |
| LR warmup ratio | 0.285 / 0.5 | 0 |
| KL type | K3 | K3 |
| KL coefficient $\beta$ | 0.001 | 0.001 |
| training batch size | 512 | 128 |
| PPO mini-batch size | 64 | 64 |
| max response length | 4096 tokens | 8000 tokens |
| max observation length | 500 tokens | 1000 tokens |
| max tool-calls | 3 | 5 |
| default chain-based group size | 4 | 4 |
| default tree config (M, N, L) | (2, 2, 1) | (2, 2, 1) |

- Tree-shape trade-off: at a fixed rollout budget, decreasing the tree count $M$ while raising expansion count $N$ or rounds $L$ increases the total number of rollouts $G$ but narrows exploration, since more rollouts then share the same prefix [1]. Table 3 shows this is not free: at budget $\approx 16$/prompt, $(M{=}8,N{=}2,L{=}1)$, $(M{=}6,N{=}3,L{=}1)$, and $(M{=}4,N{=}5,L{=}1)$ scored 36.1, 36.5, and 37.3 average on multi-hop QA respectively - more branching per tree (lower $M$) gave a small additional gain at that budget, but the single-hop average was flat to slightly down across the same three settings (51.7, 51.7, 51.2) [1, Table 3].
- The learning-rate warmup ratio is flagged by the paper as an unusually sensitive hyperparameter for models under 3B, with Tree-GRPO outperforming chain-based GRPO across every warmup setting tested [1].

## While it runs

- Signals and their healthy shapes: the paper reports, on its own multi-hop QA runs comparing Qwen2.5-3b and Llama3.2-3b-it, that beyond the reward curve, tree-based training also increases the average number of tool calls per trajectory from about 2.4 to about 3.0 (an aggregate figure over both models' comparison plots, not broken out per model in the paper's text) - i.e., the agent learns to use more turns rather than collapsing to short interaction paths, which the authors describe as a documented failure mode of chain-based training under sparse outcome reward [1]. No config or metric name for logging this is given beyond the paper's own figures; the shipped repo tracks training logs through SwanLab but the README does not document individual metric names [5].
- Published reference runs: the paper's own Table 1 numbers are the reference curve to compare against - e.g., Qwen2.5-3b Tree-GRPO reaches 50.0 average EM on single-hop QA and 36.8 on multi-hop QA at the default (M=2,N=2,L=1) config [1]; the repository links a public SwanLab dashboard of its training logs (swanlab.cn/@yux1ang/Tree-GRPO/overview), but this card did not fetch that dashboard's contents [5].
- Degeneracies and defaults: at small trees (e.g., $M=2,N=2,L=1$), using the intra-tree advantage alone causes training collapse on all four multi-hop datasets tested, because too few sibling rollouts per branch point give a high-variance baseline; the paper's fix is to always sum the intra-tree term with the inter-tree term, which acts as a fallback baseline [1, Table 4]. This is a method-defined default, not a framework config default - there is no separate "framework" reading to diverge from it. The KL coefficient default (0.001) is shared with the paper's chain-based GRPO baseline in the same table, and the paper reports an ablation (Figure 6) showing Tree-GRPO stays more stable than chain-based GRPO across different KL coefficient settings, without giving specific numeric curves in the extracted text [1].
- Named successors: none found - checked this paper's own citation/related-work text (Section 5) and its GitHub repository's README (fetched 2026-08-10) for a stated successor or fork building on Tree-GRPO; neither mentions one.
- Known failure modes: the paper's own ablation (Appendix B.3) reports that replacing agent-step nodes with token/sentence-level tree nodes underperforms even chain-based GRPO on the same tasks - e.g., 22.2 average on multi-hop QA for token/sentence-level tree search versus 36.8 for agent-step-level and 31.8 for chain-based GRPO on Qwen2.5-3b - which the authors attribute to token-level branch points lacking clear purpose and to token-level credit undermining the integrity of an agent step [1, Table 6]. No maintainer-reported issues were checked, since the GitHub repository's issue tracker was not fetched for this card.
- What the gain is - and is not: the paper's own analysis attributes Tree-GRPO's gains to (1) more rollouts per fixed token/tool-call budget from prefix sharing, and (2) finer step-level process credit derived purely from the existing outcome reward, without any additional reward model or human step labels [1]; the paper does not claim the method adds new capability beyond what chain-based GRPO's outcome-reward RL can reach - it claims better credit assignment and sample efficiency under a fixed rollout budget, most notably on models below 7B and under tight budgets, with diminishing relative gains reported on the 14B model (RL "offers limited benefits" there per the paper's own text) [1].
