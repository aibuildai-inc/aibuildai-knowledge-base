# VeRA

Item: https://arxiv.org/abs/2310.11454

LoRA with the low-rank matrices frozen and shared across every layer: keep one random pair $A$, $B$ for the whole model and train only two small per-layer scaling vectors that rescale them.

**VeRA** (Vector-based Random Matrix Adaptation) is a parameter-efficient fine-tuning method for adapting a pretrained model to a new task, introduced by Kopiczko, Blankevoort, and Asano [1]. The paper's abstract describes LoRA as reducing trainable parameters but still facing storage challenges at scale, and presents VeRA as a method that cuts the trainable-parameter count further while keeping LoRA's task performance, by sharing one pair of low-rank matrices across all layers and learning only small scaling vectors per layer [1]. Its parent is LoRA, which finetunes a pretrained weight matrix $W_0$ by adding a trainable low-rank update $BA$ on top of it [2]. VeRA instead freezes a single, randomly initialized pair of low-rank matrices $A$ and $B$ and shares them across all adapted layers; each layer only learns two scaling vectors that rescale rows and columns of the shared matrices, and these scaling vectors, together with the frozen matrices, can be merged into the original weights so there is no added inference latency [1]. The paper gives three reasons for the design: LoRA's per-task checkpoints still add up to a large storage bill at scale (rank-16 LoRA on GPT-3's query/value layers needs at least 288MB per adapter, which becomes 275TB for a million per-user adapters) [1]; prior work found the intrinsic dimensionality needed to fine-tune a model is much lower than the parameter count LoRA actually uses, for example a $d_{90}$ of 896 for RoBERTa-base versus LoRA's reported 0.3M trainable parameters [1]; and a line of work on random weights and random projections showed that freezing most parameters and training only a small structured subset can still reach strong performance [1].

The clearest evidence of adoption is implementation-level: Hugging Face's `peft` library ships VeRA as a first-party, top-level-exported tuner (`VeraConfig`, `VeraModel`) [3][4]. A follow-on paper, PVeRA, builds a probabilistic version directly on top of VeRA and reports it outperforms VeRA on the VTAB-1k image-adaptation benchmark, 71.4% average accuracy versus VeRA's 69.9% [5]. In the originating paper's own results, VeRA matches LoRA on the GLUE benchmark with an order of magnitude fewer trainable parameters (Table 2), instruction-tunes Llama and Llama 2 7B/13B on the cleaned Alpaca dataset within roughly a point of LoRA's MT-Bench score using about 100x fewer trainable parameters (Table 4: e.g. Llama 2 13B, LoRA 5.77 with 250.3M parameters vs VeRA 5.93 with 2.4M parameters), and beats LoRA at matched parameter counts on RTE by 4 accuracy points (Figure 2) [1]. Lineage in one line: LoRA (2021 [2]) -> VeRA (ICLR 2024 [1]) -> PVeRA (2025 [5]).

**When to pick it**: pick VeRA over its parent LoRA [2] when many task- or user-specific adapters must coexist in memory or be stored cheaply, since only the small scaling vectors (plus one shared seed) differ per adapter [1]; do not pick it when adapted layers have widely different input/output shapes, because the single shared matrix pair must be sized for the largest layer and smaller layers waste that capacity [3]. Against AdaLoRA, a LoRA variant that dynamically reallocates a fixed rank budget across layers by importance instead of sharing matrices [6], VeRA's efficiency comes from parameter sharing, not adaptive allocation, and the two ideas are not evaluated against each other in the VeRA paper. Against BitFit, which trains only the model's existing bias terms [1], VeRA is not more accurate on RoBERTa-base GLUE (BitFit scored 85.4 average versus VeRA's 85.2, at trainable-parameter counts of 0.1M vs 0.043M, in the paper's own Table 2) [1] but needs the extra frozen random matrices and per-layer vectors that BitFit does not.

**Variant of**: LoRA [2].

**Data it needs**: whatever supervised data the underlying fine-tuning task needs — VeRA is not a preference- or reward-based method. The paper trains it on GLUE (labeled sentence-pair/single-sentence tasks), the E2E benchmark (structured input to natural-language output pairs), the cleaned Alpaca dataset for instruction tuning (51K instruction/demonstration pairs, one epoch), and image-classification datasets (10 labeled images per class) [1]. Training is offline: it consumes a fixed, pre-collected dataset rather than fresh on-policy samples from the model being trained.

**Extra models**: none. VeRA trains a single base model plus lightweight adapters; it needs no value network, reference model, reward model, or judge. The frozen shared matrices $A$, $B$ are not a second model — they are parameter buffers that can be regenerated from a stored RNG seed instead of saved to disk [1][3]. Cost details below.

**Shipped by**: `peft` (Hugging Face) exports `VeraConfig` and `VeraModel` from its top-level package [4]; the docs carry no experimental or maintenance-mode marker for it [3]. No other implementing library was checked.

## How it works

Per training step: run the frozen base layer plus the shared low-rank path, backprop only into the two per-layer scaling vectors, repeat over the fine-tuning dataset like ordinary supervised fine-tuning.

**LoRA's update** (the parent, Eq. 3) [2]:

$$ h = W_0 x + \Delta W x = W_0 x + BAx $$

$W_0 \in \mathbb{R}^{d\times k}$ is frozen; $B \in \mathbb{R}^{d\times r}$ and $A \in \mathbb{R}^{r\times k}$ are trained per layer, with $r \ll \min(d,k)$ [2].

**VeRA's update** (Eq. 2) [1]:

$$ h = W_0 x + \Delta W x = W_0 x + \Lambda_b B \Lambda_d A x $$

Here $A \in \mathbb{R}^{r\times n}$ and $B \in \mathbb{R}^{m\times r}$ are frozen, randomly initialized (Kaiming init), and shared across every adapted layer; $\Lambda_b$ and $\Lambda_d$ are diagonal matrices built from trainable vectors $b \in \mathbb{R}^{m}$ and $d \in \mathbb{R}^{r}$, so $d$ rescales the rows of $A$ and $b$ rescales the rows of the resulting $B\Lambda_dA$ product [1]. $B$ and $A$ do not need to be low-rank in a memory sense since they are never stored per task — only the RNG seed, plus $b$ and $d$, are task-specific [1]. In the reference implementation $b$ is initialized to all ones and $d$ to i.i.d. random values before being overwritten: $b$ is set to zero and $d$ is set to a single non-zero constant (`d_initial`, 0.1 by default) so the adapter is the identity on the first forward pass, matching the paper's own initialization strategy [1][7].

**Parameter count** [1]: with $L_{tuned}$ adapted layers and hidden size $d_{model}$, VeRA's trainable-parameter count is $|\Theta| = L_{tuned}\times(d_{model}+r)$, against LoRA's $|\Theta| = 2\times L_{tuned}\times d_{model}\times r$ — VeRA grows by $L_{tuned}$ per unit of rank instead of by $2\,L_{tuned}\,d_{model}$. Worked example from the paper's own Table 1, RoBERTa-base, query and key layers: at rank 1, LoRA needs 36.8K trainable parameters (144KB) versus VeRA's 18.4K (72KB); at rank 16, LoRA needs 589.8K (2MB) versus VeRA's 18.8K (74KB); at rank 256, LoRA needs 9,437.1K (36MB) versus VeRA's 24.5K (96KB) [1] — VeRA's footprint barely moves as rank grows because only $d\in\mathbb{R}^{1\times r}$ grows with rank, while the shared $A,B$ do not need to be stored at all [1].

## Cost

**Theory, from the method's own math:**

- Time: the forward pass adds the same shape of low-rank matrix multiplications as LoRA ($x \to A \to B \to h$), so per-step compute through the adapter path scales with rank $r$ just as LoRA's does — VeRA's parameter savings do not by themselves imply cheaper compute, because the paper's own experiments use ranks an order of magnitude larger than typical LoRA ranks (e.g. rank 1024 on RoBERTa-base GLUE, versus LoRA's typical single- to double-digit ranks) [1]. At inference, the scaling vectors and shared matrices merge into $W_0$ exactly as in LoRA, so there is no extra inference latency once merged [1].
- Memory: no second trained model is added (no value network, no reference model) — the trained state is just two vectors per adapted layer. The frozen shared $A,B$ matrices need to be materialized in memory during training/inference (unless regenerated on the fly from the seed), but they are shared once across the whole model rather than duplicated per layer, and per-task storage only needs the vectors plus a seed, not a copy of $A,B$ [1].
- A naive reading of "VeRA uses far fewer trainable parameters" as "VeRA is cheaper to run" needs correction from the practice layer below: choosing a large rank to make VeRA competitive with LoRA's accuracy, combined with `peft`'s constraint that shared matrices are sized for the largest adapted layer, can erase some of the compute and memory advantage in models with uneven layer shapes.

**In practice, per framework:**

- `peft` [3][4]: the `VeraConfig.r` default is 256, and its own docstring recommends choosing higher rank values than typical LoRA ranks precisely because VeRA uses far fewer parameters per unit of rank [4]. `save_projection` (default `True`) stores the shared $A,B$ matrices in the checkpoint for guaranteed reproducibility; setting it `False` instead regenerates them from `projection_prng_key` at load time, shrinking the checkpoint but not guaranteeing bit-identical restoration across PyTorch versions/hardware [4]. Because the shared matrices are sized to the largest adapted layer's shape, models whose adapted linear layers vary a lot in size (e.g. transformer up/down projections) over-provision the shared matrices and lose some of VeRA's parameter-efficiency advantage [3]. At the pinned commit, `peft`'s VeRA model code resolves bitsandbytes 8-bit and 4-bit quantized linear layers to its own `Linear` tuner class via a shared `resolve_quantization_backend` helper, so bitsandbytes-quantized `nn.Linear` layers are supported [4]; this was added after an earlier version lacked it, per a 2024 bug report describing shape mismatches under quantization [8] and a follow-up feature-request issue proposing the fix, which a maintainer closed as completed [9]. VeRA's trainable vectors are cast to float32 during training by default, even when the base model is loaded in float16/bfloat16, to avoid training instability; an earlier bug that skipped this upcasting for the shared matrices themselves was reported and fixed in a merged pull request [10].

## How to use it

- Data preparation: any task-specific supervised dataset that LoRA would use for the same task — labeled classification/regression pairs for GLUE-style tasks, input/output text pairs for generation, or instruction/response pairs for instruction tuning [1]. The paper applies VeRA to the query and value projection matrices for GLUE and to all linear layers except the final one for instruction tuning, training the task head or output layer separately in the usual way [1].
- Target modules: `peft`'s `VeraConfig.target_modules` selects which layers are adapted. The docs' when-not-to-use section and the `target_modules` field docstring both say only linear layers are supported [3], but at the pinned commit the source itself supports two layer classes, `torch.nn.Linear` and `transformers.pytorch_utils.Conv1D` — `_create_new_module` raises a `TypeError` for anything else, with the message "only `torch.nn.Linear` (optionally quantized) and `transformers.pytorch_utils.Conv1D` are supported," and sets `is_target_conv_1d_layer`/`fan_in_fan_out` when a `Conv1D` (e.g. GPT-2's) is targeted [4]. The docs' own `fan_in_fan_out` field docstring corroborates the `Conv1D` case, so the "only linear layers" line elsewhere in the same docs page is an internal inconsistency, not confirmed elsewhere [3].
- Key knobs, with each source's own value ("not stated" = the source was checked and does not give the value):

| knob | `peft` default [4] | paper — GLUE, RoBERTa-base [1] | paper — instruction tuning [1] |
| --- | --- | --- | --- |
| rank $r$ | 256 | 1024 | 1024 (VeRA) vs LoRA's 64 |
| $d$ init value | `d_initial` 0.1 | 0.1 | not stated |
| $b$ init value | 0 (hard-coded) | 0 | not stated |
| shared-matrix init | Kaiming (uniform, via PyTorch default) | Kaiming Uniform | not checked |
| learning rate (adapter) | not stated | 4E-3 (varies by task, Table 8) | 4E-3 |
| dropout | `vera_dropout` 0.0 | not stated | not stated |

  Two readings of this table: the paper's own ablation found $d_{init}$ values of $10^{-1}$ and $10^{-7}$ clearly outperform $1.0$ on MRPC/RTE, and `peft`'s default of 0.1 sits inside that better-performing range [1][4]; and the paper's own rank choice for GLUE and instruction tuning (1024) is far above `peft`'s conservative default of 256, consistent with the paper's advice to use much higher ranks than LoRA would.
- Trade-off specific to VeRA: because raising rank only adds $L_{tuned}$ parameters instead of $2L_{tuned}d_{model}$ per unit of rank, there is comparatively little parameter-count cost to using a large rank — the paper's own scaling-rank experiment on RTE shows VeRA outperforming LoRA by 4 accuracy points once VeRA is given a rank high enough to match LoRA's parameter count [1]. The compute cost of that larger rank, however, is not eliminated (see Cost).

## While it runs

- Signals and their healthy shapes: no framework-published, VeRA-specific live monitoring metric was found — a check of the `peft` VeRA documentation page turned up only the standard training loss and the constructor/config arguments, with no logged quantity analogous to trl's GRPO clip-fraction or entropy metrics [3]. The paper's own post-hoc diagnostic, not a live-run signal, is the magnitude of the trained $d$ vector per layer after finetuning finishes: on RTE with RoBERTa-large, adaptation magnitude is larger for query matrices than value matrices, and larger in later transformer layers than earlier ones [1].
- Published reference runs: no separate raw-log repository was found; the paper's own result tables (Table 2 for GLUE, Table 3 for E2E, Table 4 for instruction-tuning MT-Bench scores, Table 5 for image classification) are the reference numbers to compare a new run against [1].
- Degeneracies and defaults: the paper's own ablation shows that training only one of the two scaling vectors badly hurts performance — dropping $d$ ("only b") drops RTE accuracy from 85.8 to 64.3, and dropping $b$ ("only d") drops it to 67.0, both far below the full method [1]; using uniform-range initialization ($[0,0.1]$) for the frozen shared matrices instead of Kaiming initialization collapses RTE accuracy from 85.8 to 53.1 (and MRPC from 90.5 to 68.9) [1]; separately, in the $d$-init ablation, setting the initial value of $d$ to 1.0 instead of $10^{-1}$ or $10^{-7}$ drops RTE from 85.8 to 60.3 [1]. `peft`'s `save_projection=False` option is a config state to watch: it trades checkpoint size for a reproducibility guarantee across PyTorch versions and hardware that the library does not make when this is disabled [4].
- Named successors: PVeRA replaces VeRA's deterministic scaling vectors with a probabilistic latent-space formulation and reports higher VTAB-1k average accuracy than VeRA (71.4% vs 69.9%) plus the ability to do Monte Carlo uncertainty quantification, which VeRA cannot [5].
- Known failure modes: from the paper's own conclusion, applicability of VeRA beyond Transformer language and vision models is untested and left to future work, and the authors suggest the method could still benefit from dynamic parameter-budget allocation or different initialization/regularization schemes, implying the fixed rank and static shared matrices are not necessarily optimal as shipped [1]. From `peft`'s closed GitHub issues (`huggingface/peft`, searched for issues mentioning VeRA): quantized base models originally raised shape-mismatch errors because bitsandbytes packs quantized weights into flat tensors that VeRA's shared-matrix mechanism could not handle, before quantization support was added (see Cost) [8]; and an earlier version of `peft` failed to upcast the shared $A,B$ matrices to float32 when the base model was loaded in float16/bfloat16, which a maintainer confirmed was a bug and merged a fix for [10].
- What the gain is - and is not: the paper's own contribution is parameter and storage efficiency at matched or better task performance versus LoRA, not a new capability — its GLUE, E2E, instruction-tuning, and image-classification results are all framed as matching or slightly exceeding LoRA's accuracy with far fewer trainable parameters, not as exceeding full fine-tuning or unlocking behavior LoRA-style adaptation cannot reach [1].
