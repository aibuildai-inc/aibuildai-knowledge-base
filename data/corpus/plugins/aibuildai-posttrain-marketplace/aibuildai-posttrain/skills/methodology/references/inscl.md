# InsCL

A replay-buffer sizing rule for continual instruction tuning: when a new task arrives, measure how different each old task is from it (Wasserstein distance between instruction sets), replay more from the more-different old tasks, and within each replay pool oversample the instructions with the most distinct, complex intent tags.

**InsCL** (Instruction-based Continual Learning) is a data-efficient continual-learning paradigm for fine-tuning LLMs on a sequence of instruction-tuning tasks, introduced to make replay-based continual learning use the instructions themselves rather than treating replay data as generic text [1]. Its parent setting is Continual-T0, which first fine-tuned LLMs on a task stream and showed that randomly replaying a fixed number of previous examples per task limits forgetting [2]; InsCL keeps that same random-replay skeleton but replaces the fixed replay count with two instruction-driven rules [1]. First, a dynamic-replay rule sizes the replay quota per previous task in proportion to that task's Wasserstein distance from the current task's instruction distribution, so a more dissimilar old task gets replayed more [1]. Second, an Instruction Information Metric (InsInfo), an IDF-style score over GPT-4-assigned intent tags, biases sampling within each task's replay pool toward instructions with more numerous and rarer tags [1]. The paper is at https://arxiv.org/abs/2403.11435 [1]. It gives three reasons for existing: replay-based CL is the cheapest CL family for LLMs (no extra parameters or per-task heads, unlike regularization- or architecture-based CL) but plain random replay ignores the instructions that make instruction-tuning data distinctive [1]; instructions are treated as high-quality, low-cost task descriptions that make a distributional similarity measure between tasks tractable [1]; and prior instruction-tuning work found that harder, more diverse instructions improve LLM performance, motivating a quality-aware sampler over a purely random one [1].

InsCL was accepted at NAACL 2024 [3]; this card did not find external adoption by named production systems in the search performed for it (arXiv full-text scan and a GitHub repository-name search, both 2026-08-09). In the paper's own 16-task, LLaMA-7B benchmark, InsCL's Section 5.1 text reports that once all 16 tasks have been trained, InsCL's progressive Relative Gain (Figure 3) is 3.0 points above Random Replay (the Continual-T0-style baseline) and 27.96 points above No Replay [1]; the paper's separate Table 2, which averages Relative Gain over all 16 stages instead of reading only the final stage, shows InsCL's per-order AVG beating Random Replay by 2.54 / 1.53 / 1.02 points (Reverse / Random / Curriculum) and No Replay by 16.67 / 13.36 / 8.57 points [1]. Lineage in one line: Continual-T0 / random replay (Scialom et al., 2022 [2]) -> InsCL (2024 [1]), with Diverse Instruction (Yin et al.'s Dynosaur, 2023 [4]) as a sibling instruction-based replay strategy InsCL benchmarks against, not a descendant. The paper name match was confirmed as the single highest-relevance hit under an exact-title arXiv search, with no other candidate paper sharing the title.

**When to pick it**: pick InsCL over plain random replay [2] when you are continually instruction-tuning one LLM on a stream of tasks, can hold a replay buffer of raw examples from every previous task, and want the replay budget itself to track task drift instead of being split evenly; in the paper's own Table 2, averaged over all 16 stages, InsCL beat random replay by 1.0-2.5 Relative Gain points depending on training order (Reverse/Random/Curriculum) and brought the standard deviation of Relative Gain down to about 3-9 (×10⁻⁴), against Random Replay's own 5-19 (×10⁻⁴) across the three orders [1]. Prefer a consolidation-based method such as EWC [5] when storing raw past-task data is not allowed (EWC instead penalizes changes to parameters that were important for old tasks, using no replay buffer at all) [5]. Prefer Diverse Instruction (Yin et al.'s Dynosaur CL variant, which replays the instructions most dissimilar to the current task's instructions) [4] only as a simpler ablation: InsCL's own Table 2 shows Diverse Instruction underperforming both Random Replay and InsCL on all three training orders [1].

**Variant of**: Continual-T0 / random replay for continual instruction tuning [2].

**Data it needs**: a stream of instruction-tuning tasks, each example an {instruction, input, output} triple (Table 1 of the paper shows this template) [1]; the paper's own scale is 765 English SuperNI tasks regrouped into 16 categories, LLaMA-7B as the base model, 2 epochs per task at batch size 64 [1]. This is not an RL method: each stage is standard supervised fine-tuning (language-modeling loss) on the current task's data unioned with a sampled replay set from the raw stored data of every prior task; the replay set is drawn from a static buffer of previously seen examples, not from fresh model rollouts [1].

**Extra models**: none held for training in the sense of a second trained network - GPT-4 is used offline, once per instruction, to produce intent tags for the InsInfo metric, needing no gradients [1]. The instruction embeddings that feed the Wasserstein-distance calculation are computed with LLaMA-7B itself, the same base model InsCL fine-tunes, run in a forward-only, no-gradient pass to produce sentence embeddings [1]. No value network, reference model, or reward model is used because InsCL is a data-selection method layered on ordinary SFT, not a preference- or reward-based method.

**Shipped by**: no post-training library in this survey packages InsCL as an importable trainer. The paper's own authors released a reference implementation at github.com/OPPO-Mente-Lab/InsCL (author affiliation OPPO AI Center matches the repo owner) [6], but it is a set of standalone scripts, not an installable package: `replay/InsCL_sampling.py` builds the replay set offline (using the POT library for Wasserstein distance) and `train_CL.py` / `run_train.sh` then run ordinary sequential SFT over the resulting per-stage datasets [6]. Building InsCL support into a trainer would mean adding a data-preparation stage before an existing SFT loop (compute per-task instruction embeddings, Wasserstein distances, and InsInfo tags, then materialize each stage's augmented dataset) rather than writing a new loss or a new sampling loop inside training itself.

## How it works

Per continual-learning stage: when task $i$ arrives, for every earlier task $j<i$ compute a replay quota, sample that many examples from $j$ biased toward high-InsInfo instructions, and train ordinary SFT on task $i$'s data unioned with all the sampled replay sets [1].

**Training objective**, standard causal language modeling over instruction+input as the prompt [1]:

$$ \mathcal{L} = -\frac{1}{|y|}\sum_{t=1}^{|y|} \log p_\theta\!\left(y_t \mid x, y_{<t}\right) $$

where $x$ is the instruction concatenated with the input and $y$ is the target output [1]. InsCL changes nothing about this loss; it only changes which examples from which tasks are unioned into the training set at stage $i$ [1]:

$$ D_i^{\alpha} = D_i \cup \sum_{j=1}^{i-1} R_j^{\alpha} $$

$D_i$ is the current task's own data, $R_j^{\alpha}$ is the replay set sampled from task $j$, and $\alpha$ is a replay hyperparameter controlling total sampling quantity (the paper sets $\alpha=200$ per previous task under uniform replay) [1].

**Dynamic replay - sizing $R_j$ by task similarity.** InsCL measures instruction-set similarity between tasks $A$ and $B$ with the Wasserstein distance, using cosine distance as the ground cost $d$ between instruction embeddings and treating each task's instructions as a probability distribution over that embedding space [1]:

$$ W(\mu_A,\mu_B) = \inf_{\pi \in \Pi(\mu_A,\mu_B)} \int_{\mathbb{R}} d(x_A,x_B)\, d\pi(x_A,x_B) $$

The per-task replay quota for stage $i$ is then this distance normalized across all earlier tasks and scaled by the total replay budget $\alpha$ [1]:

$$ \alpha_j^{*} = \frac{W_{j,i}}{\sum_{k=1}^{i-1} W_{k,i}} \times \alpha,\qquad j \in [1,i-1] $$

Worked example, three prior tasks with $\alpha=200$ and raw distances $W_{1,4}=1$, $W_{2,4}=2$, $W_{3,4}=1$ (sum $=4$): task 1 gets $\alpha_1^{*}=1/4\times200=50$, task 2 gets $\alpha_2^{*}=2/4\times200=100$, task 3 gets $\alpha_3^{*}=50$ - the task whose instructions differ most from the current task (task 2) is replayed twice as heavily as the other two.

**InsInfo - biasing which examples fill the quota.** GPT-4 tags each instruction with fine-grained intent entities [1]. For an instruction with $T$ tags drawn from a pool of $N$ previously-seen instructions, where $f_t$ is how often tag $t$ occurs in that pool [1]:

$$ \mathrm{InsInfo} = \sum_{t=1}^{T} \log \frac{N}{f_t} $$

This is IDF summed over an instruction's own tags [1]: an instruction with more tags, or with rarer tags, scores higher, and InsCL's replay sampling is guided to prefer higher-InsInfo instructions within each task's quota $\alpha_j^{*}$ [1]. Worked example, pool size $N=100$: a two-tag instruction whose tags occur 50 and 10 times scores $\log(100/50)+\log(100/10) = \log 2 + \log 10 \approx 0.69+2.30=2.99$ (natural log); a one-tag instruction whose tag occurs 90 times scores $\log(100/90)\approx0.11$ - the rarer, more multiply-tagged instruction is far more likely to be sampled into replay. Combining the two rules - dynamic replay for $\textit{how many}$ per task, InsInfo for $\textit{which}$ examples - is what the paper calls InsCL; the ablation in While it runs quantifies each rule's separate contribution [1].

## Cost

**Theory, from the method's own math:** InsCL adds no extra model and no extra forward/backward pass to standard SFT - the union $D_i^{\alpha}=D_i\cup\sum R_j^{\alpha}$ only changes dataset size, so training cost scales with $|D_i|+\sum_j |R_j^{\alpha}|$ tokens through the same single trained model, same objective [1]. The one-off, non-training cost is a preprocessing stage before stage 1: a GPT-4 call per instruction (offline, no gradients) for InsInfo tags, an embedding pass per instruction for Wasserstein distance, and an optimal-transport solve per task pair at each stage boundary (the paper does not state its complexity), all independent of the LLM being fine-tuned [1]. A naive reading of the objective would suggest replay only adds an SFT-token cost that grows with $\alpha$; it does, but does not add anything on the memory side, since no additional model is held.

**In practice, per framework:** the authors' own repository is the only implementation found; the theory-level cost above is what it runs. `replay/InsCL_sampling.py` computes distances with the POT library (pinned `POT==0.9.3` in `requirements.txt`) and writes a replay set to `replay/replay_data/`, and `merge_data.sh` unions it into each stage's training file before `run_train.sh` starts ordinary SFT [6]. No batching, parallelism, or GPU-memory guidance for the sampling step is given in the README beyond "install the pip file" [6]; the training script (`train_CL.py`) is described only as calling the training function "in a sequential loop... to simulate incremental learning of staged fine-tuning" [6], so per-stage SFT cost is whatever the underlying `train_CL.py`/`train` setup costs, not a quantity this card verified from the script body.

## How to use it

- Data preparation: split every task's data into train/held-out (the paper holds out 20% of each task for evaluation) [1]; run the tagger once over the full instruction pool to get InsInfo scores, and compute per-task instruction embeddings for Wasserstein distance, both before the sequential training loop starts [1].
- Label/reward convention: none beyond the {instruction, input, output} SFT triple; InsCL adds no reward or preference signal [1].
- Key knobs, with the paper's own values as the only anchor found (no framework ships defaults):

| knob | paper value [1] |
| --- | --- |
| total replay budget $\alpha$ per previous task (uniform baseline) | 200 |
| base model | LLaMA-7B |
| epochs per task | 2 |
| batch size | 64 |
| optimizer / learning rate | Adam, 2e-5 |
| number of tasks in the stream | 16 (from 765 SuperNI tasks) |
| held-out fraction per task | 20% |

- Trade-offs a run designer faces: raising the total replay budget $\alpha$ reduces forgetting but grows every later stage's training set, since $D_i^\alpha$ accumulates a share of every prior task; the dynamic-replay rule only changes how that fixed $\alpha$ is split across prior tasks, so it does not by itself bound total replay cost as the task stream lengthens (the union in $D_i^\alpha$ keeps adding terms for every $j<i$) [1]. The InsInfo tagger requires calling an external LLM (GPT-4 in the paper) once per instruction before any training stage runs, so its accuracy and cost gate the whole pipeline [1].

## While it runs

- Signals and their healthy shapes: the paper's own metric is Relative Gain at each stage $i$, the average, over all previously trained tasks $j<i$, of that task's current Rouge-L score divided by its single-task upper-bound Rouge-L, expressed as a percent [1]. A healthy run stays close to 100 (no forgetting) and does not fall sharply as more tasks are added; the paper reports InsCL sustaining Relative Gain above 90% through all 16 stages, while No Replay drops below 80% after the 8th task and below 65% by the last [1]. The paper also defines a per-task forgetting rate $FG_i = (R_i^{*}-R_i^{-1})/R_i^{*}\times100\%$, comparing a task's Rouge-L right after it was trained ($R_i^{*}$) to its Rouge-L at the end of the whole stream ($R_i^{-1}$) [1]; under InsCL almost all 16 tasks stay below 20% forgetting rate, versus much larger drops for tasks like Program Execution and Code under No Replay [1].
- Published reference run: Table 2 in the paper reports InsCL at 90.50 / 94.43 / 96.20 average Relative Gain (Reverse / Random / Curriculum training order) with standard deviations of 9.32 / 7.62 / 2.81 (×10⁻⁴), against Random Replay at 87.96 / 92.90 / 95.18 (STD 18.85 / 10.84 / 4.80) and No Replay at 73.83 / 81.07 / 87.63 (STD 182.87 / 121.9 / 51.30) [1]. The paper's ablation (Table 3, averaged over the three orders) isolates each rule's contribution: Random Replay 92.01 (STD 11.50) -> +Dynamic replay with real distribution 93.25 (STD 8.57) -> +InsInfo-guided sampling alone 93.52 (STD 17.90) -> full InsCL 93.71 (STD 6.58); the paper states dynamic replay mainly cuts variance while InsInfo mainly raises the average, and combining both gives the best score and the lowest variance of any row [1].
- Degeneracies and defaults: the Wasserstein-distance calculation needs a real distribution of instructions per task; when that is unavailable the paper falls back to a uniform-distribution assumption, and the paper's own ablation shows this uniform variant scores lower and less stable (93.14 avg / 8.67 STD) than using the real distribution (93.25 avg / 8.57 STD) [1]. No degeneracy specific to group size or reward variance applies here since InsCL has neither groups nor rewards; the closest analogue is a stage with only one prior task, where the dynamic-replay normalization $W_{j,i}/\sum_k W_{k,i}$ reduces to giving that one task the full budget $\alpha$, which this card did not see tested separately in the paper.
- Named successors: not established by this card. The only searches run were a read of InsCL's own related-work and bibliography (2403.11435, fetched 2026-08-09), which by construction lists only work InsCL cites and cannot contain a later paper, and a GitHub repository-name search for the string "InsCL" (49 repositories matched, e.g. justforforfor/insclr, kevzlou7979/insclix.ui.gwt - none is a paper or a fork extending this method) [6]. Neither search could surface a forward-citing successor paper, so this card does not claim one exists or does not.
- Known failure modes: the paper's own Limitations section states that InsCL's performance depends on high-quality instructions, and that fuzzy instructions can corrupt both the task-similarity calculation and the InsInfo-guided sampling, misleading the method; it recommends applying InsCL only after collecting high-quality instruction data [1]. The GitHub repository (OPPO-Mente-Lab/InsCL, checked 2026-08-09) lists two open issues, "Data tags" and a question asking whether a prior task can itself be an embedding task; neither has any comment or maintainer reply, so no maintainer-confirmed failure mode or numerical trap is available from this source [6].
- What the gain is - and is not: the paper's forgetting-category analysis (Section 5.4, curriculum order) finds that when tasks are trained with No Replay, the forgotten instances in tasks like Program Execution, Code, and Comprehension are mostly "Instruction-Unrelated" - the model's output stops matching the instruction's intent at all, not just declining in quality - and attributes this to a loss of instruction-following ability on complex-reasoning tasks specifically, rather than a uniform, task-independent decline [1]. InsCL is a replay-scheduling method: it decides how much and which past data to re-show the model, and does not itself add any new instruction-following or reasoning capability beyond what the SFT stages already train.
