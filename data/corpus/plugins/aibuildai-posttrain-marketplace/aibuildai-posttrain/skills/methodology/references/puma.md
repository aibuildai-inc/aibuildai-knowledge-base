# PUMA

Fine-tune an LLM web agent on heuristic pseudo-labels, then run DPO over sampled function-call parameters, conditioning both stages on a task-filtered slice of the user's historical web-behavior memory.

**PUMA** (Personalized User Memory-enhanced Alignment), from https://arxiv.org/abs/2410.17236v2, is a framework for adapting an LLM into a personalized web agent, introduced in "Large Language Models Empowered Personalized Web Agents" [1]. The paper's own abstract describes it as a system that "utilizes a memory bank with a task-specific retrieval strategy to filter relevant historical Web behaviors" and, based on those behaviors, "aligns LLMs for personalized action execution through fine-tuning and direct preference optimization" [1]. Its alignment stage is a direct application of DPO, whose own paper defines the method and its loss [2]; PUMA does not modify the DPO loss, it changes what preference data feeds it. The mechanism has two steps: (1) a long-term memory bank of a user's past purchases and reviews is filtered by cosine similarity to the current instruction and then further pruned to the fields relevant to the identified web function (product attributes for search, titles/categories/IDs for recommendation, ratings/comments for review); (2) the LLM is first supervised fine-tuned (SFT) on heuristically constructed pseudo-label parameters for that function, then refined with DPO on preference pairs built by sampling diverse candidate parameters and scoring them with the benchmark's own result-accuracy metric [1]. The paper's introduction and framework sections give two reasons for this design: prior LLM-based web agents overlook personalized data such as user profiles and historical web behaviors when understanding instructions and executing actions [1]; and the parameter space for a web function call is too large for the model to learn reliable outputs from instructions alone, motivating the heuristic-SFT-then-DPO pipeline [1]. Separately, as an experimental result rather than a stated design motivation, the paper's efficiency analysis reports that PUMA (LLaMA-2-7B) completes single-turn tasks in an average of 2.8 seconds versus 6.5-6.9 seconds for the GPT-4o-based baselines, attributing the gap to PUMA's smaller model and compact memory structure (Sec. 6.2.1, Fig. 7) [1].

The defining paper is also the introduction of the benchmark PUMA is evaluated on (PersonalWAB), so there are no external "landmark adopters" in the sense of other training systems reusing PUMA as a component; a citation search on Semantic Scholar for arXiv:2410.17236 returned 77 citing papers as of 2026-08-09, the highest-cited being survey papers on web agents and LLM personalization that reference PUMA as an example system, not systems built on it [3]. On the paper's own PersonalWAB benchmark, PUMA with a fine-tuned LLaMA-2-7B backbone reaches 0.994 overall function accuracy and 0.406 overall result accuracy in the single-turn track, beating all six GPT-4o-based prompting baselines, whose overall scores range 0.684-0.815 function accuracy and 0.350-0.359 result accuracy - the no-memory baseline scores 0.684/0.355 and the cosine-similarity-relevant-memory baseline scores 0.800/0.356 (Table 3) [1]. Lineage in one line: DPO (2023 [2]) -> PUMA (WWW 2025 [1]), with no named successors found by the citation search above [3].

**When to pick it**: a task where an LLM agent must call structured web functions (search, recommend, generate a review) personalized to one user's purchase-and-review history, and where a small self-hosted model is preferred over prompting a frontier model with the full history in context [1]. The paper's own ablation gives the internal contrast: removing DPO and keeping only memory + SFT loses very little (overall result accuracy 0.399 vs 0.406 with DPO), while removing SFT collapses result accuracy to 0.054 and removing the memory step alone drops it to 0.373 (Table 5) [1] - so memory retrieval and SFT do most of the work and DPO is the smallest of the three components. As a plain DPO run, PUMA's DPO stage is offline: the paper builds the preference set once, by sampling parameter candidates and scoring them, before training, rather than resampling from the live policy during training [1][2]. No online-RL alternative is tested by the paper itself.

**Variant of**: DPO [2], specialized by prepending a memory-retrieval and heuristic-SFT pipeline that generates the preference data DPO consumes.

**Data it needs**: an instruction-function training set (to fine-tune web function selection), per-user historical behavior records (purchased-product metadata and review text, stored in a memory bank), and, for the DPO stage, pairs of best/worst function-parameter candidates per instruction with the associated instruction+memory+function context; the benchmark used is PersonalWAB, built from 1,000 Amazon-Review users, 40,000+ web behaviors and 9,000+ synthetic instructions, split 80% historical / 10% train / 10% test by timestamp [1][4]. Offline: DPO trains on a preference set constructed once from sampled candidates scored by the benchmark's rank-based accuracy metric, not from fresh rollouts each training step [1].

**Extra models**: one frozen reference model $\pi_{ref}$, the SFT checkpoint, required by the DPO loss itself [1][2]. No value network. No separate learned reward model: preference labels come from the benchmark's own deterministic result-accuracy score (rank of the target item, or embedding similarity for reviews), not a trained scorer [1]. The authors' own DPO script loads the SFT model as both the trainable and (via a merged copy) reference model and trains with `trl.DPOTrainer` [5].

**Shipped by**: no general-purpose RL/alignment library ships PUMA as a named trainer - it is a task-specific pipeline (memory retrieval + heuristic-SFT + DPO), not a single reusable algorithm. The only public implementation is the paper authors' own repository (`HongruCai/PersonalWAB`, commit `23ff65c`), which fine-tunes LLaMA-2-7B with LoRA via a custom SFT script and then runs the DPO stage with trl's `DPOTrainer` (`from trl import DPOConfig, DPOTrainer`) [4][5]. Building PUMA in a new stack would mean two different jobs: reusing an existing DPO trainer (e.g. trl's) for the alignment step, and writing the memory-retrieval and heuristic-pseudo-labeling logic from scratch, since no framework ships that as a generic component [4][5].

## How it works

The loop, once per training run: fine-tune function selection -> for each instruction retrieve and filter memory -> SFT on heuristic parameter pseudo-labels -> sample diverse parameter candidates and score them -> DPO on the resulting best/worst pairs [1].

**Memory retrieval.** The long-term memory for user $u$ is $M=\{m_i \mid i=1,\dots,n\}$, one entry per purchased product plus its review [1]. Given instruction $i$ and identified function $f$, the task-specific memory is:

$$ M_i = \operatorname{Extract}\left(\operatorname{TopK}\left(M, \operatorname{sim}(i, m_j), K\right), f\right) $$

where $\operatorname{sim}(i, m_j)$ is cosine similarity between the instruction and a memory entry, and $\operatorname{Extract}(\cdot, f)$ keeps only the fields relevant to $f$ (product title/category/price/store for search, title/category/parent ASIN for recommendation, ratings/comments for review) [1]. The paper does not report a specific $K$; instead it sweeps the resulting memory-context token budget over 256, 512 and 768 tokens, finding 768 gives the best overall result accuracy (0.406) against 0.391 at 256 and 0.395 at 512, with recommendation accuracy the most sensitive to the budget (Table 6) [1].

**Heuristic SFT.** The model is trained on (instruction, task-specific memory, function) -> parameter pairs, with pseudo-labels built per function: for search, ChatGPT-generated textual queries; for recommendation, the most recent same-category product IDs found in $M_i$; for review, the dataset's real review text [1].

**DPO stage.** After SFT, diverse parameter candidates are generated with temperature 1.5 sampling and beam search of beam size 10, then each candidate is scored by the benchmark's own result-accuracy metric - for search/recommendation, a function of the target item's rank $r$ in the returned list:

$$ \text{Res Acc} = \begin{cases} 1 - \dfrac{r-1}{10}, & r \le 10 \\ 0, & r > 10 \end{cases} \qquad r \in \mathbb{N}^{+} $$

and for review, cosine similarity between the generated and actual review under a sentence-transformer embedding [1]. The best- and worst-scoring candidates per instruction, $p_i^{b}$ and $p_i^{w}$, form the preference set $\mathcal{D}_{DPO} = \{(p_i^{b}, p_i^{w}, x_i)\}$, where $x_i$ packs the instruction, task-specific memory and function [1]. The DPO loss is the method's own, unmodified [1][2]:

$$ \mathcal{L}_{DPO} = -\mathbb{E}\left[\log \sigma\left(\beta \log\frac{\pi_\theta(p^b\mid x)}{\pi_{ref}(p^b\mid x)} - \beta \log\frac{\pi_\theta(p^w\mid x)}{\pi_{ref}(p^w\mid x)}\right)\right] $$

with $\pi_{ref}$ the SFT checkpoint and $\beta$ a temperature-like coefficient on the log-ratio difference [1][2]. Worked example: suppose the target item sits at rank $r=3$ in the top candidate's returned list and does not appear in a bottom candidate's list at all ($r>10$). The top candidate scores $1-\frac{3-1}{10}=0.8$ and the bottom candidate scores $0$; these become $p_i^b$ and $p_i^w$ for that instruction, and the DPO loss pushes $\pi_\theta$ to prefer the rank-3 output over the miss, relative to how much the SFT reference already preferred it [1].

## Cost

**Theory, from the method's own math**: the DPO stage needs one frozen reference-model forward pass alongside the trainable policy's forward/backward, for both $p^b$ and $p^w$ per example - twice the sequences of a single-response SFT step, no value network [1][2]. Before DPO can run, the pipeline must first generate diverse candidates per instruction (beam size 10, temperature 1.5) and score every one with the benchmark's evaluator, an offline generation-and-scoring cost paid once before training starts, not repeated every DPO step [1].

**In practice, per implementation (the authors' own repo, commit `23ff65c`)**: SFT and DPO both fine-tune LLaMA-2-7B with LoRA (rank 16, alpha 32, dropout 0, target modules covering all attention and MLP projections) on 4x24GB NVIDIA A5000 GPUs, batch size 1 per GPU with gradient accumulation 16, under DeepSpeed [1][5]. The DPO stage caps sequence length at `source_length=1024` and prompt length at `prompt_length=768`, runs `train_epoch=5` at `learning_rate=5e-5`, and passes `beta=0.1` to `trl.DPOTrainer` [5], the coefficient that appears as $\beta$ in the DPO loss above [1][2]. The SFT stage's launch script sets `learning_rate=3e-4` over `train_epoch=10` [5]; this does not match the paper's own text, which states the SFT learning rate as 4e-3 [1] - the two sources disagree by roughly an order of magnitude, and this card does not resolve which was actually used to produce the paper's reported numbers.

## How to use it

- Prepare per-user memory as the paper does: one record per purchased product plus its review, with function-specific fields extracted at retrieval time (search: title/category/price/store; recommendation: title/category/parent ASIN; review: rating/comment) [1].
- SFT labels are heuristic, not human-written: search-query labels come from prompting ChatGPT with the instruction and memory; recommendation labels are the most recent same-category product IDs already in the retrieved memory; review labels are the dataset's real review text [1].
- DPO labels are the benchmark's own scorer applied to sampled candidates, not a separate reward model - reuse of this recipe elsewhere requires an equivalent scriptable evaluator for the target task [1].
- Key knobs, with the paper's own values as the only published anchor and the authors' repo defaults alongside (no independent framework ships PUMA, so there is only one "framework" column here):

| knob | paper [1] | authors' repo default (commit `23ff65c`) [5] |
| --- | --- | --- |
| SFT learning rate | 4e-3 | 3e-4 |
| DPO learning rate | 5e-5 | 5e-5 |
| DPO beta | not stated as a swept value; used in Eq. 4 | 0.1 |
| LoRA rank / alpha | not stated | 16 / 32 |
| memory context budget | 768 tokens (best of 256/512/768 swept) | `prompt_length=768` in DPO script |
| candidate sampling | temperature 1.5, beam size 10 | same (paper describes the script's own settings) |

- Trade-off the ablation exposes directly: memory retrieval and SFT deliver almost all of the accuracy gain over a no-memory baseline; DPO adds a comparatively small further gain (0.399 -> 0.406 overall result accuracy) at the cost of the extra candidate-generation, scoring and reference-model-forward-pass stage described in Cost [1]. A team tight on training budget could stop after SFT and lose relatively little on this benchmark.

## While it runs

- Signals: the paper reports final metrics only (function accuracy and result accuracy per task, per Table 3), not training-time curves such as reward margin or loss trajectories; no first-hand guidance on live monitoring signals was found in the paper or in the authors' repository's documentation, checked via the arXiv HTML full text and the GitHub README at commit `23ff65c` [1][4].
- Published reference runs: Table 3 (single-turn) and Table 4 (multi-turn) give PUMA's final scores against six baselines, and Table 5 gives the ablation numbers above - the only "known-good" numbers available are these end-of-training tables, not intermediate curves [1].
- Degeneracies and defaults: the memory-length sweep shows recommendation accuracy is the most sensitive to a too-short context budget, dropping from 0.054 to 0.019 between 768 and 256 tokens even though overall function accuracy barely moves (0.994 to 0.994) (Table 6) [1] - a memory budget picked too small silently damages mainly the recommendation task. A related but separate ablation shows the same recommendation-accuracy metric drops further, to 0.008, when task-specific memory retrieval is removed entirely rather than merely shortened (Table 5) [1]. The SFT-learning-rate mismatch between the paper's text and the authors' own script (above) is a live discrepancy: which value the reported numbers actually used is not stated by either source.
- Named successors: none found by the citation search described above (Semantic Scholar, arXiv:2410.17236, 77 citing papers as of 2026-08-09, top hits are surveys) [3].
- Known failure modes: the paper's own analysis of the ablation states that removing SFT causes the model to struggle to generate function parameters that align with user needs (result accuracy collapses to 0.054 from 0.406) [1]. Searching the repository's GitHub issue tracker (all 2 issues, both closed, as of 2026-08-09) found one relevant maintainer reply: the author states the DPO stage is sensitive to data quality and training hyperparameters because both its preference labels and the SFT pseudo-labels are GPT-generated and can drift if a different GPT model version is used to regenerate them, and separately that recommendation-task result accuracy cannot approach 1 even with a perfectly correct behavior history, because the recommendation module itself has limited capability - reproducing near-1 scores there is not expected [6].
- What the gain is - and is not: the paper's own ablation attributes almost all of PUMA's accuracy gain to task-specific memory retrieval and heuristic SFT, with DPO's own contribution being the smallest of the three components (0.399 -> 0.406) [1]; the method does not claim to add capability beyond what the retrieved memory and heuristic labels can already teach the base LLaMA-2-7B model.
