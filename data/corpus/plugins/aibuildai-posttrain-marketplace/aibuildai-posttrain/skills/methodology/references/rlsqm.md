# RLSQM

PPO fine-tuning where the reward model is trained not on human preferences but on scores from a deterministic static-analysis tool, so a code-generation policy learns to satisfy code-quality properties (has an assertion, calls the focal method, avoids test smells) with no human labels at all.

**RLSQM** (Reinforcement Learning from Static Quality Metrics) is a reinforcement-learning fine-tuning method for LLM-based unit-test generation, introduced by Steenhoek, Tufano, Sundaresan, and Svyatkovskiy as an approach that trains a reward model on the outputs of a static analysis tool and then optimizes an LLM against that reward with PPO [1]. Its parent is PPO [2], and RLSQM follows the RLHF recipe of Ouyang et al. [3] almost exactly - initialize the policy from an SFT checkpoint, initialize the value function from the reward model's weights, and penalize the policy for drifting from its initial weights with a KL term - substituting a static-analysis-derived scalar for the human-labeled reward [1]. The paper gives three reasons for building it this way: LLMs trained on open-source code reproduce that code's test smells, and up to 37% of the base model's generated tests were missing calls to the method under test [1]; supervised fine-tuning on a filtered "golden" dataset improves quality but cannot penalize negative examples, since it only ever sees good tests [1]; and the reward model is more general than calling the static analyzer directly - it can combine multiple metrics into one score and still return a score when the analyzer itself fails on malformed code [1]. The paper is at https://arxiv.org/abs/2310.02368 [1]. It was confirmed as the defining source over a second arXiv entry, 2412.14308, which carries the identical title and the same four authors; that entry's own withdrawal notice states it was intended as a replacement of arXiv:2310.02368 and that any subsequent updates will appear there, so this card treats 2310.02368 as the live paper [7].

RLSQM has no landmark-system adopter identified in the sources read for this card. A Semantic Scholar citations query for this paper returned 51 citing records, checked 2026-08-10 [8]; among the fetched candidates, one 2026 diffusion-code-generation paper places RLSQM in a related-work comparison table of RL-for-code reward designs, describing it as using syntax and static-checking reward signals over an LLM policy, with no hinting strategy, but does not build on it or report using its trained models [9]. No source read for this card describes RLSQM deployed in a production system. In the paper's own results, the best configuration (Combined Reward optimizing "calls the focal method" and "no conditional/exception handling") raised syntactic correctness to 99.6% (versus 90% for the strongest GPT-4 baseline) and improved quality metrics over the base Codex model by up to 23.2 percentage points, over an SFT baseline by up to 11.6 points, and over GPT-4 by up to 15.3 points (Fig. 4, RQ2) [1]. Lineage in one line: RLHF/PPO (Christiano et al. 2017 [4]; Schulman et al. 2017 [2]; Ouyang et al. 2022 [3]) -> RLSQM (2023 [1]) -> no paper naming itself a bias-fixing successor was found among the 51 citing records checked [8].

**When to pick it**: pick RLSQM's recipe - PPO against a reward model trained on a deterministic, automatable checker - when the target quality signal can be computed by a static tool (syntax, structural properties, style rules) rather than requiring human judgment or program execution; the paper's own ablations show it clearly beats filtering-based SFT [1], its offline alternative, on the same base model and data (Fig. 4) [1]. Its parent, PPO [2], is the underlying optimizer RLSQM reuses unmodified; the nearest online neighbor is standard RLHF with a human-trained reward model, as in Ouyang et al. [3], which RLSQM's whole training loop (SFT init, value-function init from the reward model, KL-to-initial-policy penalty) is copied from, substituting the reward source [1].

**Variant of**: PPO [2], via the InstructGPT-style RLHF recipe [3].

**Data it needs**: prompts built from a focal method plus adaptive focal-class context (entire focal file, shrunk in stages if it exceeds context length) and a filepath "hint" that primes the test's method signature - no target/label column, since the reward comes from a static analyzer, not from stored answers [1]. The reward model is trained on 10,000 sampled prompt/completion pairs generated by the SFT model and scored offline by the analyzer (an MSE regression target, Eq. 1); the reward model is then held fixed while PPO trains the policy on-policy, sampling 1,000 prompts and generating fresh completions from the current policy at every step [1]. Reported training scale: the C# focal-method corpus was split into three equal, per-repository partitions for SFT / reward-model / policy-model training, with a further 5% of focal methods held out for test and 10% for validation within each split [1].

**Extra models**: three, all standard to the InstructGPT-style PPO recipe RLSQM copies [3]: a value network (initialized from the reward model's weights, per Ouyang et al. [3]) [1]; a reward model (a regression head trained to imitate the static analyzer's scalar score, Eq. 1) [1]; and an implicit reference policy - the paper's KL term is written against $\pi_{\theta_0}$, the policy's own initial (SFT) weights, not against a separately-loaded frozen copy the paper describes managing at inference time [1]. No library ships this method under the RLSQM name (see Shipped by), so there is no framework default to compare it against; this is the method's own definition, not a configurable default.

**Shipped by**: no library implements RLSQM. Building it would mean writing a reward-model training loop that regresses against a project-specific static analyzer's scalar output (an MSE loss on top of a standard sequence-classification head), then pointing an existing PPO trainer (e.g. trl's `PPOTrainer`) at that reward model instead of a human-preference reward model - the PPO loop itself needs no new code, but the analyzer and reward-model training pipeline are bespoke to whatever quality metric is being optimized.

## How it works

Each PPO step: the current policy generates a unit test token-by-token as an episodic RL rollout (prompt + tokens generated so far as the observation, one token per action, episode ends on a stop token or the max-length cap), a static Quality Analyzer scores the finished test on the target quality propert(ies), the reward model reproduces that score, and the policy is updated on the KL-penalized, clipped PPO objective [1].

**Total reward** (Eq. 2) [1]:

$$ R(x,y) = \hat{R}(x,y) - \beta D_{KL}(\pi_{\theta_0}, \pi_\theta) $$

$\hat{R}(x,y)$ is the reward model's predicted score for prompt $x$ and generated test $y$; $\pi_{\theta_0}$ is the policy's initial (SFT) weights and $\pi_\theta$ its current weights; $\beta$ scales the penalty for drifting from the initial policy [1].

**Clipped surrogate objective** (Eq. 3) [1]:

$$ L^{CLIP}(\theta) = \mathbb{E}\left[\min\left(r_t(\theta) A^{old}, \; \operatorname{clip}_{1\pm\epsilon}(r_t(\theta))\, A^{old}\right)\right], \qquad r_t(\theta) = \frac{\pi_\theta(a_t \mid s_t)}{\pi_{\theta_{old}}(a_t \mid s_t)} $$

$r_t(\theta)$ is the probability ratio between the current and pre-update policy for action $a_t$ in state $s_t$; $A^{old}$ is the advantage estimate on $(s_t, a_t)$ computed from $R$ under the old policy; $\epsilon$ is the PPO clip range confining how far one update can move the ratio [1]. The paper states this objective is not tied to PPO specifically and names A2C and NLPO as alternative RL algorithms an implementation could substitute [1].

**Individual Reward** (Table II, left) [1]: for a single property $P$, reward is $-1$ if the test is syntactically incorrect (regardless of $P$), $0$ if syntactically correct but $P$ is false, and $1$ if syntactically correct and $P$ is true.

**Combined Reward** (Eq. 4, over $k$ properties) [1]:

$$ R_{Comb}(x_i, y_i) = \begin{cases} \sum_{j=1}^{k} R_{P_j}(x_i, y_i) & \text{if } y_i \text{ has correct syntax} \\ -1 & \text{otherwise} \end{cases} $$

Worked example with $k=2$ properties (Assertion, Focal call), from Table II's right-hand example [1]: a syntactically incorrect test scores $-1$ regardless of either property; a syntactically correct test with neither property scores $0$; correct syntax plus exactly one of the two properties scores $1$; correct syntax plus both properties scores $2$.

**Sequential Reward** [1]: train an Individual-Reward policy on one property to convergence (the "1st stage" model), then continue PPO fine-tuning that checkpoint against a second property's reward model (the "2nd stage" model) - a two-phase curriculum rather than a single combined score.

Reward-model training minimizes MSE against the analyzer's score (Eq. 1) [1]:

$$ \text{MSE} = \frac{1}{n}\sum_{i=1}^{n}\left(R(x_i, y_i) - \hat{R}(x_i, y_i)\right)^2 $$

## Cost

**Theory, from the method's own math**: relative to plain SFT, RLSQM adds a full PPO loop - the same trained-model count as any InstructGPT-style RLHF run, with the reward source swapped [1][3]. Generation happens inside the loop (on-policy sampling from the current policy every step), so wall-clock scales with how many fresh completions PPO needs per update; the paper does not give a per-step sample count, only a total training-prompt budget (1,000 prompts for PM training) [1]. Memory-wise, PPO trains a policy network and a value network end-to-end (gradients + optimizer state for both) while holding a reward model and an initial-policy snapshot for scoring and the KL term - the value network's weights are initialized from, but train independently of, the reward model, so after initialization it is a fourth full-sized set of trainable weights, not a shared one [1].

**In practice, per framework**: no framework ships RLSQM, so there is no framework-measured cost figure to report; the only concrete cost numbers available are the paper's own, from its specific Azure ML setup (8x NVIDIA A100 40GB GPUs, 96 vCPUs, 1,924GB RAM per VM): supervised fine-tuning took about 16 hours, reward-model training took about 2.5 hours, and policy-model (PPO) training took about 4 hours per run [1]. These are wall-clock numbers for this paper's Codex-Cushman-scale model (code-cushman-001, described as a GPT-style, causal-LM-pretrained model) and specific hardware, not a general per-framework claim [1].

## How to use it

- Prompt construction: adaptive focal context - try the entire focal file first, then progressively abbreviate (drop non-focal method bodies to signatures, then strip fields/comments, then keep only the focal class signature and focal method) until the prompt fits the context window, plus a filepath "hint" appended to condition the model toward the focal method [1].
- Reward/label convention: the target is not a stored label but a live call to the Quality Analyzer, a tree-sitter-based AST tool (inspired by tsDetect for Java) that checks syntactic correctness and structural test-quality properties; the reward model is trained to imitate this tool's scalar output on a 10k-example sample, then that reward model - not the analyzer - is queried during PPO [1].
- Sampling settings the paper reports for generation: temperature 0.7, top_p 1.0, frequency_penalty 0.5, and completions capped at 512 tokens with the remaining ~1,536 tokens of the 2,048-token window given to context [1]. No PPO-specific hyperparameter values (learning rate, clip $\epsilon$, KL coefficient $\beta$) are given as numbers anywhere in the paper's main text or appendices; the paper states only that these were manually tuned on the Individual Reward setting and that results depend on that tuning, without publishing the chosen values [1]. Because no other implementation of this exact method exists, there is no framework-default column to place beside the paper's (largely unpublished) values.
- Individual vs. Sequential vs. Combined reward is itself the main run-design choice, not a fixed default: Individual Reward training reliably improved the targeted property (e.g. Assertion frequency rose to 92.8%, Focal-call frequency to 90.9% in the best individual-reward run) [1]; Sequential Reward (train on one property, then a second) improved the 2nd-stage property in 5 of 6 tested Assertion/Duplicate-Assertion pairings, but on the full 12-pairing sweep only 6 of 12 second-stage metrics improved or stayed flat while 6 regressed [1]; Combined Reward summing two properties' scores gave mixed results too - 6 of 12 optimized properties improved and 6 regressed at 2-property scale, and optimizing all four properties in one reward model underperformed several smaller 2- or 3-property combinations, which the authors attribute to the reward range widening (-1 to 4) and the policy settling into a locally-good-enough optimum [1].
- Training-data resampling: because the reward model's training data (derived from the base model's own generations) had a skewed distribution of quality-property labels, the authors undersampled the majority label and the syntax-error negatives to balance it, which they report was necessary for stable PPO convergence [1].

## While it runs

- **Signals and their healthy shapes**: the paper monitors two failure signatures directly during policy-model training and treats them as validation checkpoints to guard against, not passive log lines: mode collapse, where the model converges to a narrow output band such as literally empty test bodies, and catastrophic forgetting, where the model optimizes only the one property being trained on and drops all others [1]. Reward-model training is checked by requiring near-0 MSE loss (Eq. 1) on held-out validation data; policy-model training is checked by requiring the reward-model-predicted score to keep increasing on validation prompts, and the reported best checkpoint is chosen by overall validation quality rather than the single optimized metric alone [1].
- **Published reference runs**: no published live training curves (loss-vs-step or reward-vs-step plots) are included in the source read; the paper reports only converged endpoint metrics per configuration (Table III - base-model property frequencies; Table V - Sequential Reward outcomes; Table VI - Combined Reward outcomes; Fig. 4 - best-configuration comparison against baselines) [1].
- **Degeneracies and defaults**: the paper reports RLSQM was unstable when applied directly to the un-fine-tuned base model - generating repetitive assertions or comments, or empty tests - and had to be initialized from an SFT checkpoint to avoid this [1]. A held-out validation split (10% by repository) was reported as critical to avoiding both mode collapse and catastrophic forgetting during PPO; the paper gives no numeric default for validation fraction beyond that 10% [1].
- **Named successors**: a Semantic Scholar citations query for RLSQM's paper (51 citing records, checked 2026-08-10) was searched, and no citing paper found in that set frames itself as fixing a documented RLSQM bias [8]; a 2026 diffusion-code-generation paper cites RLSQM in a reward-design comparison table but presents itself as a broader empirical study of reward choices, not a fix to RLSQM specifically [9].
- **Known failure modes**: from the paper's own limitations discussion - Combined Reward training over more properties tends to get stuck in a "relatively high reward" local optimum as the reward range widens (from a two-outcome {-1,1} range to a five-outcome {-1,...,4} range at four properties), which the authors attribute to an exploration/exploitation imbalance the PPO setup does not resolve on its own [1]; documentation-related properties (comments, descriptive names) regressed under RLSQM relative to the base model, which the authors attribute to the SFT initialization stage itself having already regressed on those properties before PPO started [1]; and properties that are correlated in the reward-model's training data can transfer unintentionally - a policy trained to reward focal-method calls also increased assertion frequency, which the authors trace to 34% of focal calls in the training corpus appearing as arguments inside assertion statements [1]. No maintainer-issue-tracker source exists for this claim, since no library ships the method (see Shipped by).
- **What the gain is - and is not**: the paper's own comparison shows RLSQM improves structural/best-practice properties (assertions, focal-method calls) and suppresses specific test smells (duplicate assertions, conditional/exception logic) far more reliably than it improves documentation properties (comments, descriptive names), where GPT-4 remained ahead (23% descriptive names, 78% comments, versus RLSQM's SFT-inherited regression on both) [1]. The method's own ablations (Table VI) show that optimizing more properties jointly does not monotonically improve outcomes - RLSQM raises the specific structural/smell properties its reward model targets, not general test-writing quality across every dimension the authors measured [1].
